### TODO-035: 同步/异步路径缺失 PreToolUse/PostToolUse Hook 调用

**文件**: `agent-kernel/.../core/ToolCallingLoop.java:100-221`

**问题**: Reactive 路径（`executeReactiveLoop`）已正确实现 `firePreToolUse()` 和 `firePostToolUse()`，但：
- **同步路径** `executeWithTools()` (L100-148): 无任何 hook 调用
- **异步路径** `executeWithToolsAsync()` (L161-221): 同样无 hook 调用

| 特性 | Sync Path | Async Path | Reactive Path |
|---|---|---|---|
| Tool execution hooks | ❌ 缺失 | ❌ 缺失 | ✅ |
| CancellationToken | ✅ (L106) | ❌ 缺失 | ✅ |
| Tracing/Spans | ❌ | ❌ | ✅ |
| CostTracker check | ❌ | ❌ | ✅ (L252) |

**影响**: 通过 sync/async 路径执行的工具调用完全绕过安全审计和成本追踪。AgentLoop.run() 就使用 sync 路径。

**Reference**: Claude Code 所有执行路径（同步/流式/子agent）共享同一套 hook pipeline，不存在路径差异。

**Action**:
- [ ] 在 `executeWithTools()` 的工具执行前后加入 `firePreToolUse()`/`firePostToolUse()`
- [ ] 在 `executeWithToolsAsync()` 同上
- [ ] 或者：统一 sync/async 路径也走 reactive（sync = reactive.blockLast()）
- **Priority**: P0 — 安全审计漏洞

### TODO-036: CostTracker.record() 从未被调用 — Token 预算完全失效

**文件**: 
- `ToolCallingLoop.java:252` — 检查 `costTracker.isOverBudget()` ✅
- `ToolCallingLoop.java` — **全文件无 `costTracker.record()` 调用** ❌
- `AgentLoop.java` — **全文件无 `costTracker.record()` 调用** ❌

**grep 验证**:
```
grep -rn "costTracker.record" runner --include="*.java"
# 结果：仅有 CostTracker.java 自身的 record() 方法定义
```

**问题**: CostTracker 形成了一个"检查但从不记录"的空壳：
- `isOverBudget()` 永远返回 false（因为 consumed 永远是 0）
- `remainingTokens()` 永远返回 maxBudgetTokens
- 即使 ClaudeProvider 已正确解析 `usage.input_tokens`/`output_tokens`（L385-402），这些数据也没有传递到 CostTracker

**Reference**: Claude Code 在每次 LLM 响应后立即从 `usage` 字段提取并记录，这是 token 预算管理的基础链路。

**Action**:
- [ ] 在 `executeReactiveLoop()` 中，LLM_COMPLETE 事件后从 `response.getUsage()` 提取并调用 `costTracker.record()`
- [ ] 在 `executeWithTools()` 同步路径的每次 `provider.complete()` 后也调用 `record()`
- [ ] 确保 AgentLoop Builder 将 CostTracker 传递到 ToolCallingLoop Builder
- **Priority**: P0 — 当前 token budget 功能完全失效，与上一轮 TODO-010 重复确认

### TODO-037: AgentLoop.runStream() 绕过 ToolCallingLoop + 无 Compaction

**文件**: `agent-kernel/.../agent/AgentLoop.java:158-198`

**问题**: `runStream()` 直接调用 `llmProvider.completeStream()`，完全绕过：

- [ ] 添加 `@Deprecated(forRemoval=true)` 注解
- **Priority**: P1 — 使用此路径的场景存在功能缺失

### TODO-038: InterruptibleRun.interrupt() 存在竞态窗口

**文件**: `agent-kernel/.../orchestrator/InterruptibleRun.java:86-124`

**问题**: `interrupt()` 的逻辑序列：
1. 检查 `phase == RUNNING` (L87)
2. 设置 `phase = INTERRUPTED` (L120)

在步骤 1 和 2 之间，另一个线程可能：
- 流正常完成 → `phase = COMPLETED`
- 此时 interrupt() 仍会取消 token、保存部分文本到 memory → **状态不一致**

同时 `messages` 使用 `Collections.synchronizedList()`，但迭代时（通过 `Collections.unmodifiableList()` 快照）不是原子的，高并发下可能拿到不完整视图。

**Reference**: OpenClaw 使用 `synchronized` 状态机转换保证原子性；Claude Code 使用 `Mutex` 保护 agent state transitions。

**Action**:
- [ ] `interrupt()` 方法加 `synchronized` 并使用 CAS 状态转换
- [ ] `messages` 改为 `CopyOnWriteArrayList` 确保迭代安全
- [ ] 考虑 ReentrantLock + Condition 替代 volatile + synchronized 混用
- **Priority**: P1 — 并发场景下的状态一致性问题

### TODO-039: ClaudeProvider 缺少 native completeStreamReactive() 实现

**文件**: `agent-kernel/.../llm/claude/ClaudeProvider.java` — 未 override `completeStreamReactive()`

**问题**: ClaudeProvider 依赖 `LLMProvider` 接口的 default bridge 实现（LLMProvider.java:72-98），该实现：
1. 在 `Flux.create(sink -> ...)` 内部调用 `completeStream()`
2. `completeStream()` 返回 `CompletableFuture<LLMResponse>`
3. callback 桥接模式丢失 Reactor backpressure
4. 每个 streaming 请求占用一个 `boundedElastic` 线程直到 Future 完成

**影响**: 
- Reactive 流的 backpressure 机制失效
- 高并发下 `boundedElastic` 线程池可能耗尽（默认 CPU*10）
- tool call 的 `input_json_delta` 增量 JSON 在 bridge 过程中丢失

**Reference**: Vercel AI SDK 5 只要求实现一个原生 `doStream()` 方法；LangChain 只需 `_stream()`。Bridge 模式是退化方案。

**Action**:
- [ ] ClaudeProvider override `completeStreamReactive()` 直接返回原生 Flux
- [ ] 复用 `completeStream()` 的 SSE 解析逻辑，但直接 emit 到 Flux.create sink
- [ ] 添加 `TOOL_CALL_DELTA` 事件类型，传递增量 tool 参数 JSON
- **Priority**: P1 — 性能 + 信息完整性

### TODO-040: 服务端工具执行无超时保护

**文件**: `agent-kernel/.../core/ToolExecutor.java:139-179`

**问题**: 客户端工具有超时机制（通过 `CompletableFuture.get(timeout)`），但服务端工具执行（`tool.execute(args)`）是直接阻塞调用，无超时限制。如果工具实现 hang（如 HTTP 请求无响应、文件锁死），整个 ToolCallingLoop 线程永久阻塞。

**Reference**: 
- Claude Code 对每个工具调用有独立超时（BashTool 120s, 文件读取 30s, HTTP 30s）
- OpenClaw 使用 Docker 容器级超时 + 进程级 kill

**Action**:
- [ ] 为 `ToolExecutor.executeToolCall()` 增加可配置超时
- [ ] 使用 `CompletableFuture.supplyAsync(() -> tool.execute(args)).get(timeout, MILLISECONDS)`
- [ ] 超时后返回 `ToolResult.error(id, "Tool execution timed out after Ns")`
- [ ] 在 `Tool` 接口或 `ToolMetadata` 中添加 `timeoutMs` 属性
- **Priority**: P1 — 防止单个工具 hang 导致整个 agent loop 死锁

### TODO-041: ResilientLLMProvider.isRetryable() 默认重试过于宽松

**文件**: `agent-kernel/.../llm/ResilientLLMProvider.java:198-221`

**问题**: `isRetryable()` 的最后一行是 `return true;`（L220），意味着**所有未被明确匹配的异常都会被重试**，包括：
- 工具参数错误 → 重试无意义
- JSON 解析失败 → 重试无意义
- 业务逻辑异常 → 重试无意义
- `NullPointerException` → 重试无意义

且 HTTP 状态码判断仍基于字符串匹配（`msg.contains(": 400")`），已在 05-05 分析中提出但未修复。

**Reference**: Claude Code 和 OpenAI SDK 使用结构化异常（`LLMProviderException.httpStatusCode`）判断重试策略。

**Action**:
- [ ] `isRetryable()` 默认值改为 `return false;`
- [ ] 为 `LLMProviderException` 添加 `int httpStatusCode` 字段
- [ ] ClaudeProvider/OpenRouterProvider 抛异常时设置正确的 status code
- [ ] `isRetryable()` 基于 status code 数字判断：429/5xx → 重试，4xx → 不重试
- **Priority**: P1 — 防止不可恢复错误被无意义重试

### TODO-043: Memory Flush Before Compaction — 防止信息丢失

**文件**: `agent-kernel/.../context/SnipCompactor.java`

**问题**: SnipCompactor 删除 N 轮之前的 TOOL 消息，这些消息可能包含关键工具执行结果（如代码分析结论、搜索结果摘要）。删除后这些信息永久丢失。

**Reference**: 
- OpenClaw v2026.5.18: 在 compaction 前，将对话中的重要事实 flush 到 `MEMORY.md`
- Claude Code: 5 层 compaction pipeline 的第 4 层是 LLM 生成摘要，保留关键决策
- 成本排序原则：**最便宜的方法先执行**（free truncation → paid summarization）

**Action**:
- [ ] 在 CompactionChain 执行前，扫描将被 Snip 的消息
- [ ] 提取关键信息（tool result 的前 N 字符或 LLM 生成摘要）
- [ ] 写入 `MemoryProvider.writeEphemeral()` 或 `writeDurable()`
- [ ] 或在 SnipCompactor 中添加 `PreSnipHook` 回调
- **Priority**: P2

### TODO-045: Compact-and-Retry on Context Overflow — 自愈恢复

**Reference**: OpenClaw v2026.5 的 auto-compaction 在 context overflow 错误后自动触发 compact + retry（而非仅在预防性阈值检查时触发）。

**问题**: 当前 CompactionChain 仅在 `AgentLoop.buildMessages()` 后主动执行。如果 compaction 后仍超 context limit（compaction 估算不准确），LLM 直接返回 400 错误，整个请求失败。

**Action**:
- [ ] 在 ToolCallingLoop 的 LLM 调用处捕获 context overflow 错误（400 + "context_length_exceeded"）
- [ ] 触发 emergency compaction（更激进的 Snip + Micro 参数）
- [ ] 用 compacted messages 重试 LLM 调用
- [ ] 最多重试 2 次，仍失败则向上传播错误
- **Priority**: P2

## Execution Path Consistency Matrix (New Finding)

**本轮最关键的发现之一**: AgentLoop 的三条执行路径在功能覆盖上严重不一致。

| 特性 | `run()` (sync) | `runStream()` (callback) | `runReactive()` (Flux) |
|---|---|---|---|
| ToolCallingLoop | ✅ | ❌ **绕过** | ✅ |
| Context Compaction | ✅ | ❌ **缺失** | ✅ |
| CancellationToken | ❌ (Builder 未传) | ❌ | ✅ |
| PreToolUse Hook | ❌ | N/A (无工具) | ✅ |
| PostToolUse Hook | ❌ | N/A | ✅ |
| CostTracker check | ❌ | ❌ | ✅ (但 record 未接入) |
| CostTracker record | ❌ | ❌ | ❌ |
| Observer callbacks | ✅ partial | ❌ | ✅ |
| Memory save | ✅ | ✅ | ✅ |
| Tracing spans | ❌ | ❌ | ✅ |

**结论**: 只有 `runReactive()` 路径是功能完整的。`run()` 缺少安全 hooks 和成本追踪。`runStream()` 缺少工具能力和 compaction，应当废弃。
