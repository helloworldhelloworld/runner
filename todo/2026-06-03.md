### TODO-054: Graduated Permission Model — 从二级 allow/deny 升级为多级信任谱

**Reference**: Claude Code 泄露源码揭示 **6 级权限模式**（graduated trust spectrum）：

| Mode | Behavior |
|---|---|
| `default` | 首次使用每个工具时请求权限 |
| `acceptEdits` | 自动批准文件编辑和常见文件系统命令 |
| `plan` | 只读模式，创建计划但不执行 |
| `auto` | **ML 分类器**评估每个工具调用（7 模式） |
| `dontAsk` | 除非预批准规则，否则自动拒绝 |
| `bypassPermissions` | 跳过所有提示；`rm -rf /` 和 `rm -rf ~` 仍需确认 |

**规则评估顺序**: `deny > ask > allow` — 第一条匹配规则生效，deny 始终优先。

**Bash 特殊处理**:
- 复合命令感知（`&&`, `||`, `;`, `|`）— 每个子命令独立检查
- 进程包装器剥离（`timeout`, `time`, `nice`, `nohup`, `stdbuf`）
- 内置只读命令白名单（`ls`, `cat`, `echo`, `pwd` 等）

**OpenClaw 对照**: Profile-based allowlist/denylist + sandbox mode additional gate + exec approvals（管道段逐一校验）

**OpenAI Agents SDK 对照**: Guardrails 作为一等公民原语，附加在 agent 上，每次循环迭代验证 input/output

**Runner 现状**:
- `ScopedToolRegistry` 实现 deny > allow 二级过滤，仅在 Orchestrator 路径生效
- 无 plan-only 模式
- 无 ML 分类器
- 无 Bash 复合命令解析
- 无 "危险操作终极保护"（Claude Code 即使 bypassPermissions 仍拦截 `rm -rf /`）

**Action**:
- [ ] 引入 `PermissionMode` 枚举：`DEFAULT`, `ACCEPT_EDITS`, `PLAN_ONLY`, `DENY_UNLESS_APPROVED`, `BYPASS`
- [ ] `ToolExecutor` 在执行前查询 `PermissionGate.evaluate(tool, args, mode)` 返回 `ALLOW/DENY/ASK`
- [ ] CLI 工具增加复合命令解析器：拆分 `&&`, `||`, `;`, `|` 后逐段检查
- [ ] 硬编码危险命令终极保护列表（`rm -rf /`, `rm -rf ~`, `mkfs`, `dd if=/dev/zero`）
- [ ] 后续考虑 ML 分类器（Claude Code `auto` 模式）
- **Priority**: P1
- **Effort**: 3d（基础实现）+ 5d（ML 分类器 — 后续）
- **Relates to**: TODO-050 (Sandbox), TODO-047 (Hook System)

### TODO-055: Lane Queue Pattern — 每 Session 串行队列防并发冲突

**Reference**: OpenClaw 架构的核心并发模型 — **Lane Queue**:
- 每个 session 拥有独立的串行队列
- 队列内任务严格按序执行，一个完成后才启动下一个
- 防止多 channel 交互导致的并发 bug（如同时从 WhatsApp 和 Slack 发消息到同一 session）

**Claude Code 对照**: 单 session 单 agent loop，通过 `InterruptibleRun` 处理中断

**Runner 现状**:
- `Gateway` → `Orchestrator` → `AgentLoop` 路径无显式串行化
- `InterruptibleRun` 有 interrupt/resume 能力，但 **并发请求不排队**
- 如果同一 session 同时收到两个请求（WebSocket + REST），可能产生竞态：两个 `AgentLoop.runReactive()` 并行操作同一 session 的 memory 和 context
- `MemoryProvider.addMessage()` 没有 session 级锁

**Action**:
- [ ] `SessionManager` 为每个 sessionKey 维护一个 `Semaphore(1)` 或 `SerialQueue`
- [ ] 请求进入 `Orchestrator.chatStreamReactive()` 前 acquire，完成后 release
- [ ] 排队中的请求通过 `Flux` 的 `delaySubscription` 等待前序完成
- [ ] 超时保护：排队超过 N 秒自动拒绝（返回 "session busy" 错误）
- **Priority**: P1 — 多 transport（WebSocket + REST + SSE）场景下的正确性保障
- **Effort**: 2d
- **Relates to**: TODO-038 (InterruptibleRun 竞态)

### TODO-056: 5 种输入类型统一 — 超越 chat message 的 agent 触发

**Reference**: OpenClaw 定义 **5 种 agent loop 输入类型**:

| 输入类型 | 描述 | 触发方式 |
|---|---|---|
| **Messages** | 用户聊天消息 | WebSocket/REST/SSE |
| **Heartbeats** | 定时器，每 30 分钟触发一次 | 内部调度器 |
| **Crons** | 定时任务（如 "每天 9 点总结邮件"） | Cron 表达式 |
| **Hooks** | 内部事件（启动/关闭） | 生命周期回调 |
| **Webhooks** | 外部系统事件（GitHub PR、Jira ticket） | HTTP callback |

**Claude Code 对照**: 
- `SessionStart` hook = Hooks 类型
- `CronCreate/CronDelete/CronList` tools = Crons 类型
- `RemoteTrigger` tool = Webhooks 类型
- `ScheduleWakeup` tool = Heartbeats 类型

**Runner 现状**:
- 仅支持 Messages 类型（用户主动发送的聊天消息）
- 无 Heartbeat/Cron/Webhook 触发机制
- Agent 是完全被动的 — 只能响应，不能主动行动

**Action**:
- [ ] 定义 `AgentTrigger` 接口：`TriggerType` 枚举（MESSAGE, HEARTBEAT, CRON, HOOK, WEBHOOK）
- [ ] `Gateway` 接受 `AgentTrigger` 而非仅 `GatewayRequest`
- [ ] 实现 `CronScheduler`：Quartz 或 ScheduledExecutorService，到期时生成 `CronTrigger` 送入 agent loop
- [ ] 实现 `WebhookEndpoint`：REST endpoint 接收外部 HTTP 回调，转化为 `WebhookTrigger`
- [ ] 实现 `HeartbeatScheduler`：可配置间隔，触发 agent 自省（检查待办、整理 memory）
- **Priority**: P2 — 从"被动聊天助手"升级为"主动 agent"的关键能力
- **Effort**: 5d
- **Depends on**: TODO-055 (Lane Queue) — 各类触发需要排队串行化

### TODO-057: Lazy Tool Loading + ToolSearchTool — 按需工具发现

**Reference**: Claude Code 泄露源码的关键模式 — **Lazy Tool Loading**:
- 默认上下文中仅加载 <20 个常用工具
- 其他工具通过 `ToolSearch` 元工具按需发现和加载
- 工具定义占用大量 context（每个工具约 200-500 tokens），40 个工具 = 8000-20000 tokens
- Lazy loading 将工具 context 开销从 O(N) 降至 O(k)，k = 实际使用的工具数

**Anthropic Agent SDK 对照**: 四级 context 成本递增模型：
```
Hooks (cheapest) → Skills → Plugins → MCP (most expensive)
```

**OpenClaw 对照**: 
- MCP tools 通过 `bundle-mcp` plugin ID 注册
- 如果配置链导致无可用工具，**立即停止**而非继续无工具对话

**Runner 现状**:
- `ToolRegistry.getToolDefinitions()` 一次性返回所有工具定义
- 全部注入 `LLMOptions.toolDefinitions` → 每次 LLM 调用都携带完整工具列表
- 已有 `ToolRegistry.search(keyword)` 方法，但从未被 LLM 作为工具使用

**Action**:
- [ ] 实现 `ToolSearchTool`：接受自然语言查询，返回匹配工具的名称和描述
- [ ] `ToolRegistry` 增加 `getCoreToolDefinitions()` — 仅返回标记为 `@CoreTool` 的工具（<20 个）
- [ ] `AgentLoop` 默认使用 `getCoreToolDefinitions()`，LLM 通过 `ToolSearchTool` 激活更多工具
- [ ] 被激活的工具在当前 session 内保持可用（session-scoped activation）
- [ ] 工具定义变更会破坏 prompt cache — lazy loading 同时优化 cache 命中率（TODO-048 协同）
- **Priority**: P1 — 工具数量增长后 context 成本和 cache 命中率的关键优化
- **Effort**: 3d
- **Synergy**: TODO-048 (Prompt Caching) — 更少的工具定义 = 更稳定的 cache prefix

### TODO-058: Read-Before-Edit Guard — 编辑前强制读取保护

**Reference**: Claude Code 的 `Edit` 工具内置硬约束：
- Edit 要求**当前对话中已经 Read 过目标文件**
- 且文件自上次 Read 以来**磁盘内容未变更**
- 违反任一条件，Edit 拒绝执行并返回错误

**设计意图**: 防止 LLM 基于"记忆"中的过时文件内容进行编辑（LLM 可能在之前的对话中见过文件，但文件可能已被修改）

**OpenClaw 对照**: 无此机制，但 compaction 前的 silent pre-compaction memory flush 部分缓解了此问题

**Runner 现状**:
- 工具系统无跨工具状态追踪
- 如果 LLM 调用文件编辑工具，无法验证它是否先读取了文件
- 在 context compaction 后尤其危险 — 文件内容可能已被 snip 但 LLM 仍"记得"旧内容

**Action**:
- [ ] `ToolCallingLoop` 维护 `sessionReadFileTracker: Map<String, String>` — 记录文件路径 → 读取时的内容哈希
- [ ] 文件读取工具执行后注册 `(filePath, contentHash)`
- [ ] 文件编辑工具执行前检查：(1) 文件是否已被 Read；(2) 磁盘当前哈希是否匹配
- [ ] 不匹配时返回 `ToolResult.error("File changed since last read. Please re-read before editing.")`
- **Priority**: P2 — 防止 compaction 后的幽灵编辑
- **Effort**: 1d
- **Relates to**: TODO-051 (Context Compaction — compaction 后文件内容丢失使此保护更关键)

### TODO-059: Effort Levels — 推理深度可调

**Reference**: Claude Code 实现 **5 级推理深度**：

| Level | 用途 | Token 消耗 |
|---|---|---|
| `low` | 文件查找、目录列出 | 最少 |
| `medium` | 平衡 | 中等 |
| `high` | 重构、调试 | 较多 |
| `xhigh` | 深度推理（推荐 Opus） | 多 |
| `max` | 多步深度分析 | 最多 |

**实现机制**: 通过 `max_tokens` 和 `thinking.budget_tokens` 参数调节 LLM 输出深度

**LangGraph 对照**: Retry middleware 可配置 exponential backoff，间接实现 "再想想"

**Runner 现状**:
- `LLMOptions` 有 `maxTokens` 但无 thinking budget 概念
- 所有请求使用相同推理深度
- 无法根据任务复杂度自动调整

**Action**:
- [ ] `LLMOptions` 增加 `effortLevel` 枚举：`LOW`, `MEDIUM`, `HIGH`, `XHIGH`, `MAX`
- [ ] 每个 level 映射到 `maxTokens` + `thinkingBudgetTokens` 组合
- [ ] `AgentProfile` 可配置默认 effort level
- [ ] 工具可以建议升级 effort level（如调试工具发现复杂错误时建议 `HIGH`）
- [ ] 后续：基于 `CostTracker` 剩余 budget 自动降级 effort level
- **Priority**: P2
- **Effort**: 2d
- **Depends on**: TODO-036 (CostTracker) — 需要准确的 token 消耗数据来实现自动调整

### TODO-060: Model Fallback Chain + Quality-Based Circuit Breaker

**Reference**: 2026 行业最佳实践的共识模式：

**Claude Code**: 
- 内部模型代号：Capybara (Claude 4.6 variant), Fennec (Opus 4.6), Numbat (unreleased)
- 44 个 feature flags 控制模型切换
- Exponential backoff with jitter 处理 429 rate limit

**OpenClaw**:
- Model fallback system: 主模型失败/冷却/不可用时自动切换备选模型
- Provider plugins 通过 `registerProvider(...)` 注册

**LangGraph v1.1**: Model retry middleware with configurable exponential backoff

**行业共识 — 3 级 Graceful Degradation**:
```
1. Try primary model (e.g., Opus)
2. Fall back to smaller model (e.g., Sonnet)
3. Return cached results or escalate to human
```

**Quality-Based Circuit Breaker**（2026 新兴实践）:
- 不仅追踪 HTTP 状态，还追踪**输出质量**
- Schema 不合规、空响应、幻觉检测 → 质量失败
- 3 次连续质量失败 → 开路 → 切换备选模型
- 定期探针检测恢复

**Runner 现状**:
- `ResilientLLMProvider` 有重试逻辑，但 `isRetryable()` 默认 `return true`（TODO-041）
- 无 fallback chain
- 无输出质量追踪
- 无 circuit breaker（TODO-005）

**Action**:
- [ ] 实现 `FallbackChainLLMProvider`：按优先级尝试多个 provider（如 Claude → OpenRouter → 本地模型）
- [ ] 修复 `isRetryable()` (TODO-041)：基于 HTTP status + 异常类型判断
- [ ] 实现 `CircuitBreaker`：3 状态（Closed → Open → Half-Open），tracking failure rate + quality score
- [ ] 质量评估点：schema 合规性（tool_use 格式正确？）、非空响应、stop_reason 合理
- [ ] `CostTracker` 记录 fallback 频率作为可观测指标
- **Priority**: P1
- **Effort**: 3d (FallbackChain + CircuitBreaker) + 1d (quality scoring)
- **Merges**: TODO-005 (Circuit Breaker), TODO-041 (isRetryable)

### TODO-062: Checkpointed State — 节点级状态快照用于回放/恢复

**Reference**: LangGraph 的核心创新 — **Checkpointed State**:
- 每个 graph node 执行后自动 checkpoint 状态
- 启用 human-in-the-loop 审批（暂停在某节点等待人工确认）
- 时间旅行调试（回退到任意节点重新执行）
- 故障恢复（从最后成功的 checkpoint 恢复）

**Claude Code 对照**:
- 全部状态存储为 messages — 完整状态可从 history 重建
- Session 持久化（save/resume）
- Context Collapse 有专用持久化类型（`ContextCollapseCommitEntry`, `ContextCollapseSnapshotEntry`）

**OpenClaw 对照**:
- Task Brain 基于 SQLite 的统一任务管理
- Session 状态持久化到数据库

**Runner 现状**:
- `SubagentRuntime` 使用 `ConcurrentHashMap` — 完全内存，重启即丢失
- 无 session 状态持久化（TODO-046）
- 无故障恢复机制

**Action**:
- [ ] 定义 `Checkpoint` record：sessionKey, turnIndex, messages snapshot, tool state, timestamp
- [ ] `ToolCallingLoop` 每轮完成后写入 `CheckpointStore`
- [ ] `CheckpointStore` 接口 + `SQLiteCheckpointStore` 实现
- [ ] `AgentLoop` 支持 `resumeFrom(checkpointId)` — 从指定 checkpoint 恢复执行
- [ ] 后续：human-in-the-loop 审批模式（暂停于 PreToolUse hook 等待用户确认后继续）
- **Priority**: P3 — 长期架构演进
- **Effort**: 5d
- **Relates to**: TODO-046 (Task Brain), TODO-055 (Lane Queue)

## 关键洞察总结

### 1. Runner 与 Claude Code 的本质差距不在模型，在 harness

Claude Code 512K 行源码中 98.4% 是运维基础设施。Runner 的核心抽象（Tool, LLMProvider, StreamEvent, AgentLoop）设计合理，但基础设施层（权限、hook、compaction、cost tracking、fault tolerance）远未达到生产级别。**填补 harness 差距比优化模型调用更有价值。**

### 2. "统一执行路径"是一切优化的前提

三路径不一致（run/runStream/runReactive）导致的问题链：hooks 缺失 → 权限检查无法统一 → cost tracking 失效 → compaction 不触发 → 安全保护缺位。TODO-049 是最高杠杆点——解决它，3 个 TODO 自动消失，6 个 TODO 获得实施基础。

### 3. OpenClaw 的 Lane Queue 模式是被忽视的关键需求

多 transport (WebSocket + REST + SSE) 场景下，同一 session 的并发请求未排队是潜在的数据腐败风险。这不是功能需求，是正确性需求。

### 4. Lazy Tool Loading 是 Prompt Caching 的协同乘数

单独实施 Prompt Caching 可节省 ~80% input cost。加上 Lazy Tool Loading（工具定义从 40 个降至 <20 个），cache prefix 更短更稳定，cache 命中率更高，两者协同效果大于各自之和。

### 5. 社区已收敛——不追需要创新，追需要对齐

ReAct loop、hub-and-spoke orchestration、deny > allow 权限、prompt caching、circuit breaker、OTel tracing —— 这些已是 2026 的行业标配。Runner 不需要在这些领域创新，只需要**对齐行业基线**。真正的差异化应放在领域特定能力（soul-modules, memory 个性化）上。
