## New Deep Analysis Findings

### TODO-054: Context-Pressure Preflight（OpenClaw v2026.6 Pattern）

**Reference**: OpenClaw v2026.6 将 context pressure 从"事后 compaction"前移到"事前 preflight"——tool-heavy session 执行前预检 context budget，如果预计 tool output 会导致 overflow，提前触发 compact 或降级策略。

**Runner 现状**:
- `ContextCompactor.compact()` 仅在 `AgentLoop.buildMessages()` 后执行——此时 messages 已经组装完毕
- 如果单个 tool result 特别大（如全文件内容），组装后才发现超限，浪费已执行的工具计算
- 无"预检"机制：不检查即将执行的工具是否可能产生大量输出

**Action**:
- [ ] 在 `ToolCallingLoop` 的每轮工具执行前，估算当前 context 使用率
- [ ] 如果使用率 > 80%，触发 preemptive compact（Snip 更多轮次）
- [ ] 如果使用率 > 95%，跳过非必要工具调用，直接返回已有结果
- [ ] 参考 Context Engineering 最佳实践：预留 10-15% buffer
- **Priority**: P1 — 长会话稳定性
- **Effort**: 2d
- **Depends on**: TODO-030 (TokenCounter) 实现后预估才准确

### TODO-055: Outcomes — Rubric-Based Self-Grading Loop（Anthropic Managed Agents Pattern）

**Reference**: Anthropic 在 Code with Claude 2026 发布会推出 Outcomes：
- 开发者写 rubric 定义成功标准
- 独立 grader（可以是同模型或不同模型）评估 agent 输出
- 不达标时自动触发修订循环
- 内部测试：task success +10pp, docx +8.4%, pptx +10.1%

**Runner 适用场景**:
- 代码生成后自动检查是否编译通过
- 回答质量评估（是否完整、是否有幻觉）
- 多轮任务的阶段性质量关卡

**Action**:
- [ ] 设计 `OutcomeRubric` 接口：`grade(AgentResponse) → GradeResult{pass/fail, feedback}`
- [ ] `OutcomeLoop`: 如果 grade fail，将 feedback 注入 conversation → 重新执行 → 最多 N 轮
- [ ] 内置 rubric 实现：`CompilationRubric`（代码编译检查）、`SchemaRubric`（输出 schema 校验）
- [ ] 可配置 grader model（允许用小模型做 grading 降低成本）
- **Priority**: P2 — 质量提升机制
- **Effort**: 3d
- **New dimension**: 之前 TODO 未覆盖

### TODO-058: Guardrails 三层防护（Input / Output / Tool）

**Reference**: 
- OpenAI Agents SDK: Input guardrails（验证用户输入）+ Output guardrails（验证 agent 输出）+ Tool guardrails（验证工具调用参数）— tripwire 机制立即停止执行
- Microsoft Agent Governance Toolkit: 7 包系统覆盖 OWASP Agentic AI 全部 10 项
- Anthropic Managed Agents: Outcomes 作为 output guardrail 的一种实现

**Runner 现状**:
- ❌ 无 Input guardrails（用户输入无校验）
- ❌ 无 Output guardrails（agent 输出无校验，如检测幻觉或敏感信息泄露）
- ❌ 无 Tool guardrails（工具参数无校验——TODO-002 Input Validation 的超集）
- AgentObserver 的 void callback 无法阻止执行

**Action**:
- [ ] 设计 `Guardrail<T>` 接口：`evaluate(T input) → GuardrailResult{PASS / TRIPWIRE(reason)}`
- [ ] `InputGuardrail`: 在 AgentLoop.run* 入口处校验用户输入
- [ ] `OutputGuardrail`: 在 LLM_COMPLETE 后、返回用户前校验 agent 输出
- [ ] `ToolGuardrail`: 在 firePreToolUse 后、tool.execute 前校验工具参数
- [ ] Tripwire 行为：立即抛 `GuardrailTripwireException`，中止当前 agent loop
- [ ] 内置实现：`ContentPolicyGuardrail`（敏感内容检测）, `SchemaGuardrail`（参数 schema 校验）
- **Priority**: P1 — 安全性 + TODO-002 的完整方案
- **Effort**: 3d
- **Merges**: TODO-002 (Input Validation), 部分 TODO-044 (Untrusted outputs)

### TODO-059: Append-Only Session Storage（Claude Code Pattern）

**Reference**: Claude Code 使用 append-only session storage——消息只追加不修改，compaction 产出新的"摘要消息"而不是修改/删除旧消息。这确保了完全的可审计性和"时间旅行"调试能力。

**Runner 现状**:
- `MemoryProvider.getHistory()` 返回可变 `List<Message>`
- `SnipCompactor` 直接从 list 中删除消息——物理删除，不可恢复
- 无审计日志（谁在何时删了什么消息）
- `MessageSnapshot` ADR 在 2026-04-08 TODO 中提出但未实现

**Action**:
- [ ] MemoryProvider 切换为 append-only 模型：新增 `appendMessage()`，废弃直接 list mutation
- [ ] Compaction 产出 `SummaryMessage` 追加到 storage，旧消息标记为 "compacted"（不物理删除）
- [ ] `buildMessages()` 过滤 compacted 消息，只返回活跃消息 + 摘要
- [ ] 审计日志：记录每次 compaction 的时间、被压缩的消息 ID 范围、压缩比
- **Priority**: P2 — 可审计性和调试能力
- **Effort**: 3d
- **Relates to**: architecture-todos/2026-04-08 T-01 (MessageSnapshot)

### TODO-060: Per-Agent Model + Cost Policy（Context Engineering Best Practice）

**Reference**: Context Engineering 2026 最佳实践——context budget 应按组件分配：System 10-15%, Tools 15-20%, Knowledge 30-40%, History 20-30%, Buffer 10-15%。

**Runner 现状**:
- ContextCompactor 基于消息数量（Snip）和字符数（Micro），不基于 token 比例
- 无"budget 分配"概念——system prompt 可以无限膨胀占满 context
- 无 per-component 的 token 计量

**Action**:
- [ ] 设计 `ContextBudget`：按组件分配 token 上限
- [ ] `PromptEngine` 组装 system prompt 时检查 System budget（截断过长的 skill prompt）
- [ ] `ToolCallingLoop` 累计 tool result tokens，超过 Tool budget 时触发 truncation
- [ ] History budget 驱动 SnipCompactor 的保留轮数（而非硬编码 N 轮）
- [ ] 暴露 budget usage metrics（for TODO-008 OTel integration）
- **Priority**: P2 — 长会话稳定性 + 成本控制
- **Effort**: 3d
- **Depends on**: TODO-030 (TokenCounter)

## Key Observations & Strategic Notes

### 1. P0 连续 6 轮未动是系统性问题

不是单个 TODO 的问题，而是 **开发节奏问题**：
- 近 3 周工作聚焦 MCP 可靠性和测试覆盖（有价值但非 P0）
- P0 架构债务持续累积 23 天
- **建议**：freeze 新功能开发 2 周，集中清理 Phase 1 + Phase 2

### 2. Anthropic 官方验证了 runner 的架构方向

Managed Agents 的 Dreaming = TODO-053, Outcomes = TODO-055, Multiagent = SubagentRuntime 已有基础。
说明 runner 的架构规划方向正确，但**执行速度需要追赶**。

### 3. "统一执行路径"仍是最高杠杆改动

TODO-049 解决后：
- TODO-035/037 自动解决（-2 个 TODO）
- TODO-036 只需在一处接入（简化实现）
- Hook/Guardrails 只需在一处插入（简化设计）
- 从 3 条不一致路径变为 1 条可检查路径（对齐 Claude Code 设计哲学）

### 4. Prompt Caching 的 ROI 被持续低估

5min TTL 对交互 session 命中率 > 90%（每轮 < 5min 间隔）。
以 Claude Opus 4.6 ($15/M input) 计算：
- 每 session 平均 20 轮，system prompt + tools ~6000 tokens
- 无缓存：20 × 6000 × $15/M = $1.80/session
- 有缓存：首轮 1.25× + 19轮 0.1× = $0.28/session → **节省 $1.52/session (84%)**

### 5. OpenClaw "Context Pressure Preflight" 是下一代 compaction 的关键演进

从"reactive compaction"（超限后压缩）到"proactive preflight"（执行前预检）。
这解决了一个实际痛点：工具执行完后才发现 context 不够，浪费了计算资源。
