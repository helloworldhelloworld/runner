### TODO-054: Structured Concurrency 替代 ThreadPoolExecutor（Agent 生命周期）

**Reference**: Java 21 Structured Concurrency (JEP 462) + WishTree Tech 2026 分析

**问题本质**:
- `SubagentRuntime` 使用 `ThreadPoolExecutor` 管理子 agent 生命周期
- ThreadPoolExecutor 的问题：orphaned threads（父 agent 取消后子线程继续运行）、难以实现 cascade-stop 语义、shutdown hook 依赖 @PreDestroy 而非结构化取消
- `InterruptibleRun` 的 CancellationToken 是手动传播模式 — 如果任何中间层忘记检查 token，取消信号就丢失

**Claude Code 对照**:
- Claude Code 使用 AbortController + AbortSignal 链式传播（JS 原生结构化取消）
- 子 agent 自动继承父 agent 的 signal，取消自动级联
- 无需手动 check token — signal abort 触发 Promise rejection

**Java 21 Structured Concurrency 方案**:
```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var subagent1 = scope.fork(() -> runSubagent(profile1, input));
    var subagent2 = scope.fork(() -> runSubagent(profile2, input));
    scope.join();           // blocks until all complete or one fails
    scope.throwIfFailed();  // cascade-cancel on failure
    return merge(subagent1.get(), subagent2.get());
}
// scope close = automatic cleanup of ALL forked tasks
```

**优势**:
- 父 agent 取消 → 所有 forked 子 agent 自动取消（无需手动 CancellationToken 传播）
- scope close 保证无 orphaned threads（比 @PreDestroy + shutdown hook 更可靠）
- 异常自动传播（ShutdownOnFailure / ShutdownOnSuccess 策略）
- ScopedValue 可替代 ThreadLocal 做 session context 传播

**Action**:
- [ ] `SubagentRuntime` 从 ThreadPoolExecutor 迁移到 StructuredTaskScope
- [ ] `CancellationToken` 考虑用 ScopedValue<Boolean> 替代手动传递
- [ ] 子 agent spawn 使用 scope.fork()，cascade-stop 变为 scope 自动行为
- [ ] AgentLoop 的 reactive 路径需要 bridge：Flux → Virtual Thread scope（Reactor 的 Schedulers.boundedElastic() + VT）
- **Priority**: P2 — 架构现代化，但不阻塞当前功能
- **Effort**: 5d（含 SubagentRuntime 重写 + 回归测试）
- **Risk**: Reactor Flux 和 Structured Concurrency 的交互需要仔细设计（Flux 是 push-based，SC 是 pull-based）

### TODO-055: Agentic Backpressure — 流式管道端到端压力传导

**Reference**: Vercel AI SDK 5.x Backpressure Advanced Guide + BoundaryML Agentic Backpressure Deep Dive

**问题本质**:
Runner 的流式管道：
```
LLMProvider → Flux<StreamEvent> → ToolCallingLoop → AgentLoop → Gateway → WebSocket/SSE → Client
```

**当前缺失**:
1. **无 client-to-server backpressure**: WebSocket/SSE 推送无速率控制，慢客户端导致服务端内存堆积
2. **LLM provider 无 backpressure**: ClaudeProvider 的 SSE 读取是纯推模式，Flux.create() 而非 Flux.push()
3. **Tool output 无 backpressure**: 长输出工具（如大文件读取）一次性注入全部内容
4. **缺少 overflow strategy**: 无 BufferOverflowStrategy 配置，理论上可以 OOM

**Claude Code 对照**:
- 使用 Node.js Streams 的 highWaterMark 机制实现自然 backpressure
- Tool output 有 `maxSingleResultChars` 截断（L1 Budget Reduction）
- 客户端 ACK 机制：客户端处理不及时时暂停推送

**Vercel AI SDK 5.x 对照**:
- `pipeDataStreamToResponse()` 内建 drain/pause 机制
- `transformStream` 支持 backpressure-aware transformation
- Consumer-driven pull model：客户端 ReadableStream 拉取速率决定生产速率

**Action**:
- [ ] Gateway WebSocket 输出添加 bounded buffer（`Flux.onBackpressureBuffer(256, DROP_OLDEST)`）
- [ ] ClaudeProvider SSE 读取从 `Flux.create(BUFFER)` 改为 `Flux.create(ERROR)` + 显式 buffer strategy
- [ ] 工具输出添加 maxChars 截断（与 TODO-051 L1 Budget Reduction 协同）
- [ ] SSE transport 添加 client ACK / flow-control（或降级为 drop-oldest 策略）
- [ ] 监控：添加 buffer usage metrics（水位线告警）
- **Priority**: P1 — 生产环境稳定性保障
- **Effort**: 3d
- **Depends on**: 无

### TODO-056: 4-Layer Memory Hierarchy（对齐 Claude Code + OpenClaw）

**Reference**: 
- Claude Code 4 层 memory: Session Memory (ephemeral) → Project Memory (CLAUDE.md) → User Memory (~/.claude/memory.md) → Global Memory (autoDream consolidated)
- OpenClaw SOUL.md hierarchy: SOUL.md (identity) → AGENTS.md (operating rules) → MEMORY.md (curated long-term) → Daily Logs (raw)

**Runner 现状**:
- `MemoryProvider` 接口仅支持 `getHistory()` + `addMessage()` — 单层 session memory
- `kernel-memory` 模块有 BM25 + vector search，但仅用于 retrieval，无写入时的分层逻辑
- 无 project-level memory（类似 CLAUDE.md 的 per-project instructions）
- 无 user-level memory（跨 project 的用户偏好和知识）
- 无 durable memory consolidation（session 结束后全部丢失）

**Claude Code 关键设计细节（泄露源码）**:
- Project Memory: `CLAUDE.md` files，hierarchical（root > workspace > dir），200 行 compact index always in context
- User Memory: `~/.claude/memory.md`，全局性，跨 project 持久化
- autoDream 整理时使用 forked subagent（隔离推理状态）+ 15s blocking budget per phase
- Memory 文件格式: 结构化 Markdown sections (## Preferences, ## Decisions, ## Patterns)

**OpenClaw 关键设计细节**:
- SOUL.md 每次 session 完整注入（personality consistency > token efficiency）
- MEMORY.md 由 agent 主动写入（`memory_write` tool）
- Pre-compaction flush: 压缩前 silent turn 提醒 agent 存储重要事实
- 无 RAG — 全量注入 memory files（哲学选择：一致性优先于效率）

**统一设计方案**:
```
Layer 0: Session Memory    — MemoryProvider.getHistory() (已有)
Layer 1: Project Memory    — per-project .agent/instructions.md (新增)
Layer 2: User Memory       — ~/.lightweight-ai/memory.md (新增)
Layer 3: Durable Memory    — MemoryConsolidationTask output (TODO-053)
```

**Action**:
- [ ] 设计 `ProjectMemoryProvider`：读取项目根目录 `.agent/instructions.md`（类似 CLAUDE.md）
- [ ] 设计 `UserMemoryProvider`：读取 `~/.lightweight-ai/memory.md`（跨 project）
- [ ] PromptEngine 在 system prompt 构建时注入 Project Memory + User Memory
- [ ] 添加 `memory_write` tool：agent 可主动写入 User Memory
- [ ] 添加 `project_memory_read` tool：agent 可查询 project memory
- [ ] Project Memory 支持 hierarchical 读取（root > module > submodule）
- **Priority**: P2 — 用户体验的持续性提升
- **Effort**: 5d（基础实现）+ 3d（hierarchical + write tools）
- **Depends on**: TODO-053 (Memory Consolidation) 提供 Layer 3

### TODO-057: AG-UI Protocol 对齐 — Agent-User Interaction 标准化

**Reference**: AG-UI (Agent-User Interaction Protocol) — Codecademy 2026 Guide

**问题本质**:
MCP 解决了 Agent↔Tool 交互标准化，但 Agent↔User 交互仍是各框架自定义。AG-UI 是 2026 年新兴标准，旨在标准化：
- 流式文本输出协议（TEXT_DELTA + content block IDs）
- 工具调用中间状态可视化
- 用户确认/修改工具参数的交互
- Agent 内部状态变更的实时通知

**Runner 现状**:
- StreamEvent 18 种 EventType 是自定义协议
- WebSocket 输出格式是 StreamEventSerializer 自定义序列化
- 无标准化的客户端 SDK（每个前端需要自己解析事件）
- 缺少 content block ID（多个并行 TEXT_DELTA 流无法关联）

**AG-UI 核心设计**:
- 每个 event 有 `eventId` + `parentId`（构成 event tree）
- TEXT_DELTA 绑定到 content block（`blockId`），支持并行输出
- TOOL_CALL event 包含 `confirmationRequired` flag
- 状态变更使用 `STATE_DELTA` event（类似 CRDT patch）
- 支持 Server-Sent Events 和 WebSocket 两种 transport

**Action**:
- [ ] StreamEvent 添加 `eventId` 字段（UUID，唯一标识每个事件）
- [ ] StreamEvent 添加 `parentId` 字段（建立 event 父子关系）
- [ ] TEXT_DELTA 添加 `blockId`（支持并行文本流区分）
- [ ] TOOL_CALL_START 添加 `confirmationRequired` flag（对接 Hook System TODO-047）
- [ ] 设计 `AgUiEventAdapter`：将内部 StreamEvent 转换为 AG-UI 标准格式输出
- [ ] 考虑 STATE_DELTA event 用于暴露 agent 内部状态变更
- **Priority**: P3 — 长期标准化方向
- **Effort**: 3d（eventId/parentId/blockId）+ 2d（AG-UI adapter）
- **Note**: 不需要立即迁移，可以渐进式添加字段保持向下兼容

### TODO-058: LangGraph-style Checkpointing — Agent 状态持久化与恢复

**Reference**: LangGraph 0.4 PostgresSaver + Temporal durable execution patterns

**问题本质**:
- `InterruptibleRun` 支持 interrupt/resume，但状态仅存内存
- 进程重启 = 所有 interrupted runs 丢失
- 无法实现跨进程的 agent 恢复（如 pod 迁移、rolling update）
- SubagentRuntime 的 SubagentRun 状态也仅存内存

**Claude Code 对照**:
- Session transcripts 持久化到 disk（`.claude/sessions/`）
- KAIROS sessions 可跨重启恢复
- autoDream 的 memory consolidation 保证重要状态不丢失

**LangGraph 对照**:
- `Checkpointer` 接口：每个 graph node 执行后自动持久化状态
- `PostgresSaver` / `SQLiteSaver`：状态存到数据库
- Time Travel：可以回退到任意 checkpoint 重新执行
- Human-in-the-loop：pause at node → persist → user responds → resume from checkpoint

**Action**:
- [ ] 设计 `AgentCheckpointer` 接口：`save(runId, phase, state)` + `restore(runId)`
- [ ] `InterruptibleRun` 状态变更时自动 checkpoint（RUNNING → INTERRUPTED → RESUMED）
- [ ] 实现 `FileSystemCheckpointer`（开发用）和 `JdbcCheckpointer`（生产用）
- [ ] SubagentRun 的 lifecycle state 也通过 checkpointer 持久化
- [ ] 进程启动时扫描 INTERRUPTED 状态的 runs，支持恢复
- [ ] 可选：Time Travel — checkpoint 快照支持回退到任意点重新执行
- **Priority**: P2 — 生产级可靠性
- **Effort**: 5d（基础实现）+ 3d（JDBC + recovery）
- **Note**: 短期可用 FileSystem 实现，长期需要数据库支持

- [ ] `PatternPermissionPolicy`：基于 glob/regex 匹配 tool name + args
- [ ] `SessionPermissionCache`：缓存 ASK_ONCE_SESSION 的用户决策
- [ ] 预留 `ClassifierPermissionPolicy` 接口（未来接入 ML 分类器）
- [ ] Hook System (TODO-047) 的 HookDecision 与 Permission System 统一（避免两套拦截机制）

### TODO-060: Lazy Tool Loading — 降低 context 占用

**Reference**: Claude Code Pattern #4 — 默认 <20 tools in context，按需激活

**问题本质**:
- LLM 的 tool definitions 占 context window 约 1000-5000 tokens
- 工具越多，LLM 选择准确率越低（"choice overload"）
- Claude Code 默认只加载 ~20 核心工具，其余通过 "tool discovery" 按需激活
- Runner 目前将 `ToolRegistry.getToolDefinitions()` 全量注入 LLMOptions

**Claude Code 具体实现**:
- 核心工具（read_file, write_file, bash, etc.）始终可用
- MCP tools 按 capability 分组，首次使用后才进入 active set
- Tool discovery prompt: "If you need a capability not in your current tools, describe what you need and I'll provide it"
- 动态 tool_choice 参数控制

**OpenClaw 具体实现**:
- Skills 以 "compact skills list (names + descriptions only)" 形式注入 system prompt
- 完整 skill content 仅在被激活时加载
- ClawHub 5700+ skills 不可能全部注入 — 按需搜索 + 激活

**Action**:
- [ ] `ToolRegistry` 分层：`coreTools`（始终注入）+ `discoverableTools`（按需激活）
- [ ] `LLMOptions.toolDefinitions` 默认只包含 coreTools
- [ ] 添加 `activate_tool` meta-tool：LLM 可以请求激活某个 discoverable tool
- [ ] System prompt 注入 discoverable tools 的 compact list（name + one-line description）
- [ ] MCP tools 默认为 discoverable（除非配置为 core）
- [ ] 可配置阈值：当 total tools < N 时全量注入，> N 时切换到 lazy 模式
- **Priority**: P2 — 性能优化，对长 MCP tools 列表尤其重要
- **Effort**: 3d
- **Note**: 需要配合 Prompt Caching (TODO-048) — lazy loading 改变 tool definitions 会打断 cache

### TODO-061: OpenClaw-style Pre-Compaction Memory Flush

**Reference**: OpenClaw v2026.6 — silent pre-compaction turn + Claude Code KAIROS autoDream

**问题本质**:
Context compaction（Snip/Micro）删除旧消息时，其中的重要事实可能永久丢失。信息仅存在于 conversation history 中，没有被提取到 durable memory。

**OpenClaw 方案**:
- Compaction 触发前，先插入一个 **silent system turn**:
  ```
  "Before your conversation history is compressed, please save any important 
  facts, decisions, or context to your MEMORY.md file using the memory_write tool."
  ```
- Agent 响应这个 turn 时会主动调用 `memory_write` 保存重要信息
- 然后再执行 compaction
- 这个 turn 本身在 compaction 后被删除（不占用压缩后的空间）

**Claude Code 方案**:
- autoDream 的 Gather 阶段本质上做同样的事，但是在 idle time 异步执行
- 非紧急场景（token budget 不紧张）时走 autoDream
- 紧急场景（即将 overflow）时走 inline flush

**Action**:
- [ ] `CompactionChain` 执行前，检查是否有 `memory_write` tool 可用
- [ ] 如果有，插入 silent pre-compaction turn 让 agent 保存重要信息
- [ ] 设置 pre-compaction turn 的 token budget（最多消耗 N tokens）
- [ ] 超时/超 budget 后强制进入 compaction
- [ ] 与 TODO-056 (Memory Hierarchy) 配合：flush 目标为 User Memory / Project Memory
- **Priority**: P2 — 合并进 TODO-051 (4-Layer Compaction) 作为 L0 阶段
- **Effort**: 2d
- **Depends on**: TODO-056 (Memory Hierarchy) 提供 write 目标

## Key Insights (2026-06-07)

1. **统一执行路径 remains 最高杠杆**: 5 轮分析始终排 #1。阻塞原因不明 — 建议作为唯一 sprint goal。
2. **Backpressure 是新发现的生产风险**: 之前未被识别。慢客户端 + 大 tool output = OOM。Runner 的纯推模式在生产环境下不可接受。
3. **Memory Hierarchy 是下一个差异化方向**: Claude Code 和 OpenClaw 都投入重兵于 4 层 memory。Runner 仅有 1 层。这是用户体验连续性的核心。
4. **Structured Concurrency 是 Java 21 的天然优势**: Runner 基于 Java 21 却未利用 SC — 这是相对于 Node.js (Claude Code) 和 Python (OpenClaw) 框架的独特机会。
5. **Permission System 和 Hook System 需要统一设计**: 避免两套拦截机制（PermissionPolicy vs HookDecision）互相冲突。建议 TODO-047 和 TODO-059 合并设计。
6. **OpenClaw CVE-2026-25253 的教训**: 135K 暴露实例，50K 直接可攻击。Sandbox 不是 P2 优化 — 是 P0 安全底线。
7. **Claude Code 的 QueryEngine (46K lines) 启示**: 将 agent interaction lifecycle 集中管理比分散在多个类更好维护。Runner 的 AgentLoop + ToolCallingLoop + Gateway 分散模式增加了一致性维护成本。
