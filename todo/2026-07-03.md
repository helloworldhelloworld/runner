### TODO-054: External Harness Attachment 模式（OpenClaw v2026.7.1-beta.1）

**Reference**: OpenClaw 新增 `openclaw attach` 命令，允许外部 harness 附着到已有 Gateway session 进行交互式 Codex 风格工作流。

**核心价值**:
- Gateway session 不再是封闭的单 harness 入口，外部工具/IDE/测试 harness 可中途接入
- 支持双向事件流：外部 harness 订阅 StreamEvent + 注入 GatewayRequest
- 典型场景：debugging 时附着 trace harness、IDE 插件附着到已有 session、自动化测试接入生产 session

**Runner 现状**:
- Gateway 绑定单一 ChatHandler，无外部附着点
- WebSocket handler 与 session 1:1 绑定，无多 consumer 能力
- `SessionStreamRegistry` 支持多 observer 但仅限 agent-web 内部

**Action**:
- [ ] Gateway 支持 `attach(sessionId)` → 返回 `Flux<StreamEvent>` 只读订阅
- [ ] Gateway 支持 `attachWithControl(sessionId)` → 双向：订阅 + 注入请求
- [ ] WebSocket handler 支持 `attach` 帧（复用已有 session）
- [ ] 访问控制：attach 需要 session owner 或显式授权 token
- **Priority**: P2 — 开发者体验 + IDE 集成价值高，但非安全/稳定性瓶颈
- **Effort**: 3d
- **Prerequisite**: 无

**Reference**: OpenClaw 所有 bundled channels（WebSocket/REST/SSE/Telegram 等）改为统一的 setup/secret contract 机制。非破坏性但要求自定义 channel 初始化脚本对齐。

- **Priority**: P2 — 架构清洁度，降低新 transport 接入成本

### TODO-057: Automatic Prompt Caching（Anthropic 2026 新特性）

**Reference**: Anthropic 2026 新增 **automatic caching**——只需在 request body 顶层加一个 `cache_control` 字段，无需逐 block 标记。

**关键更新（对比 2026-05-22 分析）**:
- Workspace-level cache isolation（新：替代旧 org-level）
- 支持 automatic caching（新：简化实现，一行代码）
- Cache write: $3.75/M（25% premium）, Cache read: $0.30/M（**90% 折扣**）
- 所有 active Claude models 均支持

**自动缓存 vs 显式缓存**:
```
自动缓存（新，推荐）:
  request body 顶层: "cache_control": {"type": "ephemeral"}
  → SDK 自动为 system + tools 中最长的可缓存前缀添加断点

显式缓存（旧，精细控制）:
  system 数组最后一个 block: "cache_control": {"type": "ephemeral"}
  tools 数组最后一个 tool: "cache_control": {"type": "ephemeral"}
```

**Action** (supersedes TODO-048):
- [ ] ClaudeProvider request body 添加顶层 `"cache_control": {"type": "ephemeral"}`（1 行代码）
- [ ] 记录 `cache_creation_input_tokens` / `cache_read_input_tokens` 到 CostTracker（需 TODO-036 先修）
- [ ] CompactionChain 加 cache-aware 逻辑（不打断 system prompt + tools 前缀）
- [ ] 可选：对高频 session 启用 1h TTL（write 价格 2x 但跨 5min 窗口仍合算）
- **Priority**: P0 — 1 行代码，每 session 节省 ~90% input token 成本
- **Effort**: 0.5d（基础）+ 1d（cache-aware compaction）
- **Supersedes**: TODO-048, TODO-024
- **Depends on**: TODO-036（CostTracker.record）修复后可追踪效果

### TODO-058: Controller-Agent-Runtime 三层分离（OpenHands Pattern）

**Reference**: OpenHands 9-Component SDK 的核心架构洞见——将 agent 执行分为三个独立关注点：
1. **Controller** — 执行管理器（操作约束、生命周期、超时、budget）
2. **Agent** — 决策者（选择工具、规划步骤）
3. **Runtime** — 隔离执行环境（sandbox、文件系统、网络）

**Runner 现状**:
- `AgentLoop` 混合了 Controller + Agent 职责（既管理执行生命周期，又构建 context、调度 LLM）
- `ToolCallingLoop` 混合了 Controller + Runtime（既检查 budget/cancellation，又直接执行工具）
- `ToolExecutor` 是纯 Runtime，但无隔离层
- 缺失：Runtime 层无法替换（无法从"直接执行"切换到"Docker 沙箱执行"）

**Action**:
- [ ] 抽取 `AgentController` 接口：管理 budget、timeout、cancellation、hook dispatch、observer notification
- [ ] `AgentLoop` 精简为纯 Agent 角色：context 构建 + LLM 调度 + memory 管理
- [ ] `ToolExecutor` 升级为 `ToolRuntime` 接口：`DirectRuntime`（现状）/ `SandboxRuntime`（Docker）/ `IsolateRuntime`（V8/Wasm）
- [ ] Controller 持有 Agent + Runtime 引用，编排执行流
- **Priority**: P2 — 架构改进，为 sandbox (TODO-001/050) 铺路
- **Effort**: 5d
- **Enables**: TODO-001 (Sandboxing), TODO-050 (OWASP)

### TODO-059: Plan & Act 双模式（Cline Pattern）

**Reference**: Cline 的核心架构创新——将 agent 执行分为两个显式阶段：
1. **Plan Phase**: 只读操作（读文件、搜索、分析），产出执行计划
2. **Act Phase**: 写操作（编辑文件、运行命令），每步需确认

**为什么有效**:
- Plan phase 只使用 SAFE 级别工具，不改变世界状态
- 用户在 Act phase 前可审查计划、修改方向
- LLM 先"思考"再"行动"，减少无谓的 tool call
- 对长 session（23min 平均）尤其重要——避免前 10 分钟执行的操作后来要回滚

**Runner 适用**:
- `ToolPolicy.byRiskLevel()` 已提供 SAFE/WRITE/SYSTEM 分级
- Plan phase = `ToolPolicy.byRiskLevel(SAFE)` 的 agent run
- Act phase = 正常 run（按 agent profile 的 toolPolicy）
- 用户确认可通过 Elicitation hook 实现

**Action**:
- [ ] `AgentProfile` 新增 `planActMode: boolean`（默认 false）
- [ ] 启用时：首轮 ToolCallingLoop 用 `byRiskLevel(SAFE)` 覆盖 toolPolicy → 产出计划
- [ ] 计划发送给用户（通过新 `PLAN_READY` StreamEvent 或 Elicitation）
- [ ] 用户 approve 后进入 Act phase，恢复正常 toolPolicy
- **Priority**: P3 — 用户体验优化，长 session 场景价值高
- **Effort**: 3d
- **Depends on**: TODO-056 Phase 3（Elicitation event）

### TODO-060: LM-Centric Tool Interface 优化（SWE-agent ACI Pattern）

**Reference**: SWE-agent 的核心洞见——LLM 是一种**新型终端用户**，需要为 LLM 认知优化的工具接口（Agent-Computer Interface），而非复用人类 UX。

**关键设计原则**:
- 工具输出应 token-efficient（不要返回冗余信息）
- 错误信息应 LM-understandable（结构化、可操作）
- 工具发现应上下文相关（不要一次列出 50 个工具）

**Runner 现状**:
- `Tool.getDescription()` 为人类编写，未针对 LLM 认知优化
- `ToolResult` 返回原始字符串，可能包含大量冗余
- `ToolRegistry.getToolDefinitions()` 返回所有已注册工具，无按上下文过滤
- `MicroCompactor` 截断 tool output 但截断方式（首尾各 200 chars）不一定保留 LLM 最需要的信息

**Action**:
- [ ] `ToolResult` 添加 `summary` 字段：工具可提供 LLM-optimized 摘要（默认 null，降级用 text）
- [ ] `ToolRegistry` 支持 `getContextualTools(userMessage)` → 基于消息内容返回 top-K 相关工具（lazy loading）
- [ ] `MicroCompactor` 升级：对结构化 output（JSON/XML）优先保留 schema + 关键字段而非首尾
- [ ] 工具 description 优化指南：添加到 docs/guides/，规范 LLM-friendly description 写法
- **Priority**: P2 — 减少 token 浪费、提升 tool selection 准确率
- **Effort**: 3d
- **Related**: TODO-051 (Compaction), 参考 Claude Code 的 lazy tool loading pattern

### TODO-061: Supervisor vs Swarm 双编排模式（LangGraph Pattern）

**Reference**: LangGraph 证明的两种主流多 agent 编排模式：
1. **Supervisor**: 中央路由器分派子任务 → 收集结果 → 综合响应（精确但高延迟）
2. **Swarm**: 去中心化，agents 直接通信/handoff（低延迟但路由不精确）

**Runner 现状**:
- Orchestrator = Supervisor 模式（`AgentRouter` → 单 agent 处理）
- SubagentRuntime = 异步 spawn（不是真正的 Swarm——spawn 后由 parent 等待，无 peer-to-peer）
- 无 Scatter-Gather 模式（并行扇出同一问题到多 agent，汇总最佳答案）

**Action** (extends TODO-052):
- [ ] SubagentRuntime 支持 `SWARM` mode：subagent 可直接 handoff 到 peer（无需回到 parent）
- [ ] 新增 `ScatterGatherTool`：并行扇出同一输入到 N 个 agent → 收集 → 选择/合并最佳结果
- [ ] `AgentProfile` 新增 `orchestrationMode: SUPERVISOR | SWARM | SCATTER_GATHER`
- **Priority**: P3 — 进阶编排，当前 Supervisor 已能满足多数场景
- **Effort**: 5d
- **Extends**: TODO-052 (Agent Handoff 双模式)

### TODO-062: MCP Session-Isolated Tool State

**Reference**: MCP 2026 best practices 明确要求 **session-isolated tool state**——工具跨调用的缓存和状态必须按 session 隔离，不允许全局变量。

**Runner 现状**:
- `McpToolClient` 维护全局 tool list（`discoverMcpTools` 写入共享 map）
- `McpRequestMetaContext` 是 `ThreadLocal`，线程安全但不是 session 级
- MCP tool call 结果不缓存（每次重新调用远程 server）

**Action**:
- [ ] `McpToolClient` 的 tool call 结果按 sessionId 缓存（LRU）
- [ ] `McpRequestMetaContext` 改为 session-scoped（从 `GatewayRequest` 传入）
- [ ] MCP server 端支持 session headers（透传 sessionId 到远程 tool server）
- **Priority**: P2 — 多用户场景的正确性保障
- **Effort**: 2d

## 七、Deep Research 补充发现（本轮新增）

本轮深度研究覆盖了 15+ 个开源项目和学术论文，以下摘录对 runner 最具参考价值的发现：

### A. Claude Code 实际架构（泄露源码 v2.1.88 确认）

- **master agent loop** = `query.ts` 1,729 行 `while(true)` async generator（内部代号 "nO"）
- **98.4%** 代码是确定性基础设施（权限、上下文管理、工具路由、恢复）；仅 1.6% 是 AI 决策逻辑
- **5 层 compaction** 确认：L1 Budget Reduction → L2 Snip → L3 MicroCompact → L4 Context Collapse → L5 AutoCompact（~13K tokens 余量时触发，生成 ≤20K summary）
- **anti-thrashing**: 若 compaction 后上下文立刻重新填满，3 次后停止 auto-compact
- **tool search / deferred loading**: MCP tool schema 默认延迟加载，仅 tool names 进 context；超过 10% context window 时才 auto-load
- **7 种 permission mode**: Plan → Default → acceptEdits → Auto(ML classifier) → dontAsk → bypassPermissions → Bubble(subagent)
- **Auto mode**: 双阶段 ML classifier，运行在 Sonnet 4.6，stage-1 快速 yes/no → stage-2 chain-of-thought
- **KAIROS**: 未发布的自治 daemon 模式，引用 150+ 次，持久后台 agent + append-only 日志
- **memory 4 层**: CLAUDE.md(用户指令) + Auto Memory(MEMORY.md ≤200行/25KB) + Session Memory(JSONL) + Auto Dream(4-phase consolidation)

**对 runner 的启示**:
- runner 的 2 层 compaction vs Claude Code 的 5 层差距明显，TODO-051 优先级应升高
- runner 无 tool schema deferred loading，当 MCP tools 增多时 context 开销线性增长 → 新增 TODO-060 lazy loading
- runner 的 ToolPolicy 二级(deny>allow) vs Claude Code 7-mode 渐进式 → 考虑渐进式信任模型

### B. Aider Repo Map（tree-sitter + PageRank）

- tree-sitter 解析 → 符号定义/引用图 → Personalized PageRank → token-budget-aware 渲染
- 效果：同等任务 Aider 使用 4.2x 少于 Claude Code 的 tokens
- **Architect/Editor 双模型模式**：expensive planner + cheap editor，对标 runner 的 Orchestrator + SubagentRuntime

**对 runner 的启示**:
- runner 的 `ToolRegistry.search(keyword)` 是基础 keyword search；可升级为 tree-sitter + PageRank 的 context-aware tool/file selection
- TODO-060 (LM-Centric Tool Interface) 应包含 repo-map 概念

### C. MCP 安全发现（2025-2026）

- **43%** 早期 MCP servers 存在命令注入漏洞（Invariant Labs 2025）
- **40%** MCP servers 无认证，79% 明文处理凭据（2026 audit）
- CVE-2025-6514: mcp-remote 通过恶意 authorization_endpoint 实现 RCE
- **OAuth 2.1 + PKCE** 成为 2025.11 spec 强制要求
- HTTP+SSE transport **已废弃**（spec 2025-03-26），改为 streamable HTTP
- 2026.7 release candidate 引入 **stateless operation**

**对 runner 的启示**:
- runner 的 `McpToolClient` 无 OAuth/认证机制 → 生产部署前必须补充
- runner 的 `McpToolWrapper` 无 input validation → tool args 应 validate against JSON Schema（TODO-002 范围）
- MCP transport 应优先 streamable HTTP 而非 SSE（ADR-008 已正确选型）

### D. 行业数据点

- **65%** 企业 AI agent 失败源于 **context drift**，而非模型能力（Google Cloud 2025 报告）
- **同模型 + 不同 harness = 7 分差距**（Terminal-Bench: GPT-5.5 + Codex 83.4% vs + Terminus 76.4%）→ agent loop 设计比模型重要
- **mini-swe-agent**: 100 行 Python，>74% SWE-bench Verified → scaffold 复杂度应随模型进步而降低
- **AI coding session** 平均时长 4min(Q1 2025) → 23min(Q1 2026) → context management 成为关键
- **LLMSummarizingCondenser**（OpenHands）: 将旧消息 LLM 摘要替换 → 成本降低 2x 无性能退化

### E. OpenHands Event Sourcing Pattern

- 所有交互 = immutable events，append-only log
- State = 从 event log 派生（deterministic replay）
- Condenser 也是 stateless——状态全在 event log 中的 `CondensationEvent`
- 9 种 pluggable condenser 策略

**对 runner 的启示**:
- runner 的 `StreamEvent` 已在这条路上，但 event log 不是 single source of truth
- 长期可考虑 event-sourcing 架构升级（P3，与 TODO-046 Task Brain 关联）

### F. Cline SDK Layered Architecture

- 4 层分包：shared → llms → agents → core
- **agents** 层 browser-compatible、stateless → 可嵌入 serverless/浏览器
- **Plugin system**: 注册工具、observe lifecycle events、注入 rules/commands、shape agent context
- **gRPC-over-postMessage**: webview ↔ extension 类型安全通信

**对 runner 的启示**:
- runner 的 agent-kernel 是 monolith（158 source files），可参考 Cline 分层
- agent-sdk 目前大量 placeholder → 可参考 Cline 的 4 层分包设计重新定位
