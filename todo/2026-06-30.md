# Architecture Optimization TODO — 2026-06-30

> 基于 OpenClaw、Claude Code（泄露源码分析）、CrewAI、AutoGen/AG2、Mastra、Vercel AI SDK 等开源社区最佳实践，对 runner (lightweight-ai-kernel) 现有架构的分析与优化建议。

---

## 一、Context Management（上下文管理）

### 现状
runner 目前有 2 层 Context Compaction：
- **SnipCompactor** — 删除超过 N 轮的 TOOL 消息
- **MicroCompactor** — 截断过大的 tool result（保留首尾各 200 字符）

### 对标分析

| 框架 | Context 管理层数 | 关键特性 |
|---|---|---|
| **Claude Code** | **5 层** lazy-degradation pipeline | MicroCompact(缓存优化) → SnipCompact(LRU归档) → Context Collapse(可逆摘要) → AutoCompact(子agent摘要) → Reactive(413应急) |
| **Mastra** | 3 种记忆类型 | Working memory + Semantic recall + Observational memory（后台agent维护压缩观察日志替代原始历史） |
| **Vercel AI SDK 7** | 5 层记忆分类 | Session / Semantic / Procedural / Episodic / Scratchpad |
| **AG2 Beta** | 4 阶段生命周期 | Assembly policies + Compaction + MemoryTool + Middleware |

### TODO

- [ ] **P0: 增加 Context Collapse 层（可逆摘要）** — 在 SnipCompactor 之后、溢出之前，用 LLM 生成摘要替换旧消息，但保留原始消息在独立 store 中（可回溯）。参考 Claude Code Layer 3 的设计，在 ~90% context 利用率时触发。
- [ ] **P0: 增加 AutoCompact 层（子agent摘要）** — 当对话接近 context window 上限时，fork 一个轻量 agent 生成结构化摘要（≤20K tokens）。参考 Claude Code Layer 4，在 ~83.5% 时触发。
- [ ] **P1: 增加 Reactive 应急层** — 捕获 LLM API 返回的 413/context overflow 错误，紧急保留最后 N 条消息。参考 Claude Code Layer 5。
- [ ] **P1: MicroCompactor 升级为 cache-aware** — 将 volatile 内容推到消息末尾，stable prefix 保持不变以提高 LLM cache 命中率。参考 Claude Code MicroCompact 的 cache 优化策略。
- [ ] **P2: 引入 Observational Memory** — 后台 agent 维护压缩观察日志替代原始会话历史，保持 context window 紧凑。参考 Mastra 的 observational memory 模式。

## 二、Resilience & Error Handling（韧性与错误处理）

### 现状
runner 目前没有可见的 retry/backoff/circuit breaker 机制，CostTracker 仅做 token 预算检查，LLMProvider 调用失败直接传播。

### 对标分析

| 框架 | 韧性机制 |
|---|---|
| **Claude Code** | ML 分类器门控 tool 调用 + prompt injection 探测 + 7 模式权限 |
| **AG2 Beta** | Middleware stack (BaseMiddleware) — on_turn/on_llm_call hooks 支持 retry/logging/token limit |
| **CrewAI** | max_iter 防无限循环 + Task Guardrails 验证输出 + guardrail_max_retries |
| **Vercel AI SDK** | experimental_repairToolCall 修复畸形 tool 输入 + WorkflowAgent 持久执行(崩溃恢复) |

### TODO

- [ ] **P0: LLMProvider 增加 Retry + Exponential Backoff** — 对 429/503/timeout 等瞬态错误自动重试（指数退避 + jitter），最多 3 次。可实现为 `ResilientLLMProvider` 装饰器包装任意 LLMProvider。
- [ ] **P0: 增加 Fallback Chain** — 主模型失败时自动降级到备选模型（如 Claude → OpenRouter），至少两级。
- [ ] **P1: ToolCallingLoop 增加 Tool Result Guardrail** — tool 执行结果在送回 LLM 之前进行验证/转换，失败时反馈给 agent 重试。参考 CrewAI Task Guardrails。
- [ ] **P1: 引入 Middleware/Interceptor 机制** — 在 AgentLoop 的关键节点（LLM 调用前后、tool 执行前后）支持可插拔的 middleware chain，用于日志、metrics、token 限制、retry 等横切关注点。参考 AG2 Beta 的 BaseMiddleware。
- [ ] **P2: Tool 输入修复机制** — 当 tool schema 验证失败时，自动尝试修复（如用更强模型重新生成参数），而非直接报错。参考 Vercel AI SDK 的 repairToolCall。
- [ ] **P2: Circuit Breaker 模式** — 对频繁失败的 LLMProvider 或 MCP tool server 实施熔断，快速失败而非持续超时。

## 三、Multi-Agent Orchestration（多智能体编排）

### 现状
runner 有 4 层 Orchestrator 架构（AgentProfile → AgentRegistry → Orchestrator → SubagentRuntime），支持 spawn/wait/list/cascade-stop。路由方式为按 agentId 静态路由。

### 对标分析

| 框架 | 多 agent 编排模式 |
|---|---|
| **Claude Code** | Orchestrator-workers + worktree 隔离 + Workflow 确定性编排（控制流是代码） |
| **OpenClaw** | Channel-Brain-Body 三层 + 多 agent workspace 隔离 + Heartbeat 定时巡检 |
| **CrewAI** | Sequential / Hierarchical / Consensual process + Flows(事件驱动编排) |
| **AutoGen 0.4** | Actor model + typed message routing + Teams(RoundRobin/Selector/Swarm) |
| **AG2 v0.9** | 统一 GroupChat + Pattern classes + OnCondition/Handoff + ContextVariables |
| **Mastra** | Supervisor / Handoff / Hierarchical + graph-based workflow engine |

### TODO

- [ ] **P0: 增加 Workflow 确定性编排引擎** — 支持用代码（而非 LLM）定义多 agent 协作的控制流（顺序、并行、条件分支、循环）。每个步骤委派给独立 agent。参考 Claude Code 的 Workflow 和 Mastra 的 graph-based workflow。
- [ ] **P1: 增加 Agent Handoff 模式** — agent 之间的控制权转移，无需中央协调器。基于条件触发（如 OnCondition），适合流水线式处理。参考 AG2 v0.9 Swarm 和 Mastra Handoff。
- [ ] **P1: 增加 Supervisor 模式** — 一个主管 agent 动态委派任务给专家 agent，跟踪进度、评估完成度。参考 CrewAI Hierarchical 和 Mastra Supervisor。
- [ ] **P1: AgentRouter 增加 LLM-based 动态路由** — 除了静态 agentId 路由外，支持 LLM 根据请求内容自动选择最佳 agent。参考 AutoGen 0.4 SelectorGroupChat。
- [ ] **P2: 增加 ContextVariables 跨 agent 共享状态** — SubagentRuntime 中引入结构化共享上下文，agent 之间可传递状态而非仅传递消息。参考 AG2 v0.9 ContextVariables。
- [ ] **P2: 增加 Heartbeat 定时巡检** — 支持 agent 定时执行后台任务（如收件箱检查、状态轮询）。参考 OpenClaw 的 Heartbeat（每 30 分钟主会话 turn）。

## 四、Tool System（工具系统）

### 现状
runner 有 5 种 Tool 供给机制（SPI/Manual/DynamicPlugin/MCP/CLI），ToolPolicy 提供 ALLOW/DENY/ABSTAIN 三值决策链，RiskLevel 三级。但缺少工具沙箱、权限门控的精细度不如 Claude Code。

### 对标分析

| 框架 | Tool 系统特色 |
|---|---|
| **Claude Code** | ~40 tools 独立沙箱 + 7 模式权限 + ML 分类器门控 + deny-first 规则管线 |
| **OpenClaw** | 100+ skills + ClawHub 公共注册表 + 按 agent 角色过滤 + 周边级访问控制 |
| **Mastra** | Zod schema 校验 + 双向 MCP（既消费又暴露） |
| **Vercel AI SDK 7** | Tool approval policies（auto-approve/auto-deny/user-approve/typed function） |

### TODO

- [ ] **P0: MCP Server 能力（双向 MCP）** — runner 目前只作为 MCP Client 消费外部工具。增加 MCP Server 模式，将 runner 自身的 Tool/Skill 暴露为 MCP 服务供外部系统调用。参考 Mastra 的 MCPServer 和 Spring AI 的 MCP server support。
- [ ] **P1: Tool Approval Policy 增强** — 在现有 ToolPolicy 之上增加运行时审批机制：auto-approve（安全 tool 自动通过）、user-approve（需用户确认）、typed function（自定义审批逻辑）。参考 Vercel AI SDK 7 和 Claude Code 的 3-tier 权限。
- [ ] **P1: Tool 执行沙箱** — 高风险 tool（RiskLevel.SYSTEM）在隔离环境中执行（Docker 容器 / seccomp sandbox），防止意外副作用。参考 AutoGen 的 DockerCommandLineCodeExecutor。
- [ ] **P2: Tool Registry Hub（公共注册表）** — 类似 OpenClaw ClawHub，提供社区工具发现和分发机制。
- [ ] **P2: activeTools 动态裁剪** — 每轮 LLM 调用时根据上下文动态选择活跃工具子集，减少 token 消耗。参考 Vercel AI SDK 的 activeTools。

## 五、Memory System（记忆系统）

### 现状
runner 有 3 层记忆（Session/Ephemeral/Durable），kernel-memory 模块支持 BM25 + Vector 混合搜索，MemoryProvider 按 sessionKey 隔离。

### 对标分析

| 框架 | 记忆系统 |
|---|---|
| **Vercel AI SDK 7** | 5 类记忆：Session / Semantic / Procedural / Episodic / Scratchpad |
| **Mastra** | Working memory(结构化) + Semantic recall(向量) + Observational memory(后台压缩) |
| **AG2 Beta** | Assembly policies + MemoryTool(显式读写) + Mem0 集成(多DB混合) |
| **Claude Code (KAIROS)** | 每日追加日志 + 4 阶段 "dream" 整合（Orient→Gather→Consolidate→Prune） |

### TODO

- [ ] **P1: 增加 Procedural Memory** — 存储 agent 学会的操作步骤和技能模式，跨会话复用。与现有 SkillGeneratorObserver（self-improving）结合，将 Trajectory → Skill 的产物持久化为 procedural memory。
- [ ] **P1: 增加 MemoryTool（显式记忆读写）** — 让 LLM 主动决定何时读写记忆，而非仅依赖自动注入。参考 AG2 Beta MemoryTool。
- [ ] **P1: Memory Assembly Policy** — 每次 LLM 调用前，通过策略组合决定注入哪些记忆（而非全量注入 durable memory），按相关性和 token 预算裁剪。参考 AG2 Beta Assembly Policies。
- [ ] **P2: Dream Cycle 记忆整合** — 定期（如每日）运行后台 agent 对 ephemeral memory 进行 4 阶段整合：定向→收集→浓缩→修剪。参考 Claude Code KAIROS 的 dream cycle。
- [ ] **P2: Graph Memory** — 引入知识图谱存储实体关系，支持结构化推理。参考 AG2 的 Neo4j/FalkorDB Graph RAG。

## 六、Streaming & Event System（流式与事件系统）

### 现状
runner 使用 Reactor Flux<StreamEvent> 统一流式抽象，StreamEvent 是 closed enum（ADR-005），有 TRACE/POST_PROCESS_DATA 开放扩展槽。

### 对标分析

| 框架 | 流式特色 |
|---|---|
| **Claude Code** | 自定义双缓冲渲染器 + cell 级 diff + 帧合并（200 token/s 下 1 paint/帧间隔） |
| **Vercel AI SDK** | Data Stream Protocol（单字符事件码） + SSE 传输 + React hooks 客户端 |
| **OpenClaw** | Gateway WebSocket/HTTP 多路复用单端口 |

### TODO

- [ ] **P1: 标准化 Stream Protocol** — 定义类似 Vercel AI SDK Data Stream Protocol 的有线协议（带事件码），使客户端可以增量解析而非依赖完整 JSON 反序列化。当前 StreamEventSerializer 是完整 JSON，对高频 TEXT_DELTA 不够高效。
- [ ] **P1: 帧合并（Frame Coalescing）** — 当 StreamEvent 产生速率超过客户端消费能力时，合并同类事件（如连续 TEXT_DELTA）为单次发送。减少 WebSocket 帧数和客户端渲染压力。
- [ ] **P2: System Reminders 机制** — 参考 Claude Code 在 messages.create() 时注入 50 种 system reminder（放在对话消息中而非 system prompt，因 system prompt 会被缓存），作为 agent 的 "神经系统" 持续提供上下文感知。

## 七、Permission & Safety（权限与安全）

### 现状
runner 有 ToolPolicy（ALLOW/DENY/ABSTAIN 链式决策）+ RiskLevel（SAFE/WRITE/SYSTEM），MCP 边界的 RiskLevel 推断（ADR-007）。

### 对标分析

| 框架 | 安全模型 |
|---|---|
| **Claude Code** | 7 模式 deny-first + ML 分类器 + prompt injection 探测 + 3-tier 权限 |
| **OpenClaw** | 周边级访问控制 + 按 agent 角色能力范围 |
| **CrewAI** | allow_delegation 控制 + 防无限委派循环 |

### TODO

- [ ] **P1: Prompt Injection 检测** — 对 tool result 内容进行 prompt injection 探测，标记可疑内容。参考 Claude Code 的 prompt-injection probe。
- [ ] **P1: 增加 delegation 防环机制** — SubagentRuntime 中增加委派深度和循环检测，防止 agent 之间无限相互委派。参考 CrewAI 的 allow_delegation=False 和 maxSpawnDepth 的增强。
- [ ] **P2: 细粒度权限模式** — 从当前的 ToolPolicy 升级为多模式权限系统（如 Claude Code 的 7 种模式），不同场景使用不同权限策略（开发模式宽松、生产模式严格）。

### 现状分析

基于 CLAUDE.md 和架构探索发现的结构性问题：

### TODO

- [ ] **P0: ScopedToolRegistry 从继承改为组合** — 当前 ScopedToolRegistry extends ToolRegistry，存在 CLAUDE.md 记录的 `isEnabled()` 未覆盖 bug 历史。改为组合模式（持有 delegate ToolRegistry + ToolPolicy filter），消除 override 遗漏风险。

- [ ] **P2: 模块边界加强** — agent-kernel 承载过多职责（agent loop + orchestrator + gateway + llm + memory + context + trace + speech + learn），考虑拆分：

### 现状
runner 有 Tracer/SpanContext/SpanExporter 基础追踪设施，但缺少结构化的可观测性管线。

### TODO
