## New Findings: Deep Architecture Analysis

### 1. ToolCallingLoop 构造器膨胀 (Telescoping Constructor Anti-pattern)

**文件**: `agent-kernel/.../core/ToolCallingLoop.java:49-91`

ToolCallingLoop 有 **7 个构造器** 形成望远镜反模式：
```java
ToolCallingLoop(provider, toolExecutor, maxIterations)
ToolCallingLoop(provider, toolExecutor, maxIterations, executionContext)
ToolCallingLoop(provider, toolExecutor, maxIterations, executionContext, tracer)
ToolCallingLoop(provider, toolExecutor, maxIterations, executionContext, tracer, cancellationToken)
ToolCallingLoop(provider, toolExecutor, maxIterations, executionContext, tracer, cancellationToken, costTracker)
```

已有 Builder，但外部代码（AgentLoop.run 同步路径 L119-124）仍直接用旧构造器，跳过了 cancellationToken 和 costTracker 注入。

**影响**: 同步路径的 AgentLoop.run() 完全绕过 CancellationToken 和 CostTracker，这意味着：
- 同步 AgentLoop.run() 无法被打断（InterruptibleRun 无效）
- 同步路径没有 token 预算控制
- observers 在同步路径也不会触发（L119 未传 observers）

**Action**:
- [ ] 统一 AgentLoop 的同步和 reactive 路径，都走 Builder
- [ ] 删除望远镜构造器，仅保留 `Builder` + 测试用的最小构造器
- **Priority**: P1

### 2. AgentLoop.runStream() 不走 ToolCallingLoop

**文件**: `agent-kernel/.../agent/AgentLoop.java:158-198`

`runStream()` 方法直接调用 `llmProvider.completeStream()`，完全绕过了 ToolCallingLoop。这意味着：
- 流式回调路径 **没有工具调用能力**
- 没有 context compaction
- 没有 observer hooks
- 没有 memory context 注入后的 compaction

**Reference**: Claude Code 的所有执行路径都经过统一的 agent loop，无论是 sync/async/stream 模式。

**Action**:
- [ ] 废弃 `runStream()`，统一到 `runReactive()` 
- [ ] 或者改造 `runStream()` 也走 ToolCallingLoop（callback → reactive bridge）
- **Priority**: P1

### 3. ClaudeProvider 不处理 tool_result 消息格式

**文件**: `agent-kernel/.../llm/claude/ClaudeProvider.java:314-333`

`buildMessagesArray()` 将 TOOL 角色消息直接映射为 `role: "user"` + 纯文本 content。但 Claude API 期望：
```json
{
  "role": "user",
  "content": [{"type": "tool_result", "tool_use_id": "...", "content": "..."}]
}
```

当前实现丢失了 `tool_use_id` 和 structured content block，导致：
- 多工具并行调用时 Claude 无法关联哪个 result 对应哪个 tool_use
- 可能导致 400 错误或 Claude 混淆工具结果

**Reference**: Claude API Messages spec 要求 tool_result 必须包含 tool_use_id。

**Action**:
- [ ] `buildMessagesArray()` 识别 TOOL 角色，生成 `content: [{type: "tool_result", tool_use_id: ..., content: ...}]`
- [ ] 从 ConversationMessage.metadata("tool_use_id") 提取 ID
- [ ] 为 assistant 消息也生成 `content: [{type: "text", ...}, {type: "tool_use", id: ..., name: ..., input: ...}]` 结构
- **Priority**: P0 — 影响核心功能正确性

### 6. SubagentRuntime 用 synchronized(activeRuns) 且 activeRuns 本身是 ConcurrentHashMap

**文件**: `agent-kernel/.../orchestrator/SubagentRuntime.java:84`

```java
private final Map<String, SubagentRun> activeRuns = new ConcurrentHashMap<>();
...
synchronized (activeRuns) {  // 83-89: 已经是 ConcurrentHashMap，synchronized 有意义吗?
    if (activeRuns.size() >= maxConcurrent) { throw ... }
    activeRuns.put(runId, run);
}
```

这里 synchronized 是为了原子性地做 check-then-put，但其他方法（stop, stopAll, getActiveRuns）没加 synchronized，形成 **竞态窗口**：
- `stop()` 在 `synchronized` 外部调 `activeRuns.remove()`
- `spawn()` 的 size 检查和 put 是原子的，但 `stop()` 可能在 size 检查后、put 前删除一个 entry，导致浪费一个并发槽

**Reference**: Claude Code 的 subagent 管理使用 `Semaphore` 控制并发。

**Action**:
- [ ] 用 `Semaphore(maxConcurrent)` 替代 size check + synchronized
- [ ] 或将所有 activeRuns 的 mutation 统一到 synchronized block
- **Priority**: P2

### 7. completedRuns 缓存清理算法 O(n)

**文件**: `agent-kernel/.../orchestrator/SubagentRuntime.java:223-231`

```java
if (completedRuns.size() > MAX_COMPLETED_CACHE) {
    completedRuns.entrySet().stream()
        .min(Comparator.comparingLong(e -> e.getValue().getStartTime()))
        .ifPresent(oldest -> completedRuns.remove(oldest.getKey()));
}
```

每次 cache put 时全量扫描找最旧 entry。MAX_COMPLETED_CACHE=200 时影响小，但如果调大会成为瓶颈。

**Action**:
- [ ] 替换为 `LinkedHashMap(accessOrder=true)` 或 Caffeine/Guava Cache
- **Priority**: P3 (低优先级，当前数量级下无性能问题)

### 8. LLMProvider 接口 4 种执行模式 — 实现负担重

**文件**: `agent-kernel/.../llm/LLMProvider.java`

LLMProvider 接口要求实现 4 个方法：`complete()`, `completeAsync()`, `completeStream()`, `completeStreamReactive()`。但：
- `completeStreamReactive()` 已有 default 实现（bridge from callback）
- `completeAsync()` 在所有实现中都是 `CompletableFuture.supplyAsync(() -> complete(...))`
- 真正需要 provider 实现的只有 `complete()` + `completeStream()`

**Reference**: 
- Vercel AI SDK 只要求实现一个 `doStream()` 方法
- LangChain 只要求 `_generate()` + `_stream()`

**Action**:
- [ ] 将 `completeAsync()` 提供 default 实现
- [ ] 考虑简化为只需实现 `complete()` + `completeStream()`（或只 `completeStreamReactive()`）
- [ ] 减少新增 LLM Provider 的实现负担
- **Priority**: P2

### 9. MemoryProvider.search() 是阻塞调用在 Reactive 链路中

**文件**: `agent-kernel/.../agent/AgentLoop.java:229`

`runReactive()` 中 `memoryProvider.search(input)` 是阻塞调用。虽然外层有 `subscribeOn(Schedulers.boundedElastic())`，但：
- `boundedElastic` 线程池大小有限（默认 CPU*10），高并发下可能耗尽
- memory search 涉及 BM25 + Vector 计算，可能耗时较长
- `addMessage()` 也是阻塞写

**Reference**: Claude Code 的 memory 操作全部异步化，不阻塞 agent loop。

**Action**:
- [ ] 为 MemoryProvider 增加 `Mono<List<MemorySearchResult>> searchAsync(query)` 接口
- [ ] AgentLoop.runReactive() 内部改用 flatMap + async memory 调用
- [ ] 或者至少用 `Mono.fromCallable(search).subscribeOn(elastic)` 显式标注阻塞点
- **Priority**: P2

### 10. Token 计数缺失 — CostTracker 无数据来源

**文件**: 
- `CostTracker.java` — 提供 `record(inputTokens, outputTokens)` 接口
- `ToolCallingLoop.java` — 检查 `costTracker.isOverBudget()` 但**从未调用 `record()`**
- `AgentLoop.java` — 构建 CostTracker 但不传递给 ToolCallingLoop（同步路径完全跳过）

**问题**: CostTracker 是个空壳 — 预算检查永远返回 false（因为 consumed 永远是 0）。

**Reference**: Claude Code 在每次 LLM 响应后从 `usage` 字段提取 token count 并立即记录。

**Action**:
- [ ] 在 ToolCallingLoop.executeReactiveLoop() 中，LLM_COMPLETE 事件后调用 `costTracker.record(response.getUsage())`
- [ ] 在 AgentLoop 构造时将 CostTracker 传递给 ToolCallingLoop Builder
- [ ] 在 ResilientLLMProvider 的 response 中确保 usage 信息被传递
- **Priority**: P1 — 当前 token budget 功能完全失效

### 11. Orchestrator 无法获取 AgentLoop 的 MemoryProvider

**文件**: `agent-kernel/.../orchestrator/Orchestrator.java:196-200`

```java
private MemoryProvider getMemoryProvider(AgentLoop agent) {
    // AgentLoop 当前没有暴露 memoryProvider getter
    // 暂时通过 AgentFactory 的共享引用获取
    return agentFactory.getSharedMemory();
}
```

AgentLoop 的 memoryProvider 是 private final 且无 getter。Orchestrator 只能通过 AgentFactory 的共享引用获取，这导致：
- 如果不同 Agent 用不同 MemoryProvider，InterruptibleRun 拿到的可能是错误的实例
- 架构上的 implicit coupling

**Action**:
- [ ] 给 AgentLoop 添加 `public MemoryProvider getMemoryProvider()` getter
- [ ] 或者让 InterruptibleRun 不直接依赖 MemoryProvider，改为通过 AgentLoop 保存断点
- **Priority**: P2

## New Research Insights (External Frameworks Deep Dive)

### OpenClaw 2026.5 Architecture Highlights

OpenClaw (347K+ stars) 的最新架构揭示了 runner 可借鉴的几个关键模式：

**1. Session Lane Queue Serialization**
- OpenClaw 实现了 **两级队列序列化**：session lane + global lane
- Session lane 防止同一会话内的工具/LLM 竞态
- Global lane 限制并发 LLM 调用，避免超出 API rate limit
- **Runner 对比**: ToolCallingLoop 内部是串行的，但 SubagentRuntime 的并发控制仅靠 synchronized + ConcurrentHashMap，无全局 LLM 调用限制

**2. `steer` 模式 — 中断注入**
- 当用户在 agent 运行中发送新消息，OpenClaw 的 `steer` 模式将新消息注入到每个 tool call 之后
- 剩余的 pending tool calls 被跳过，新消息在下一次 response 前注入
- **Runner 对比**: InterruptibleRun 的 interrupt() 是全量取消，没有"在 tool 间隙注入"的精细控制

**3. SOUL.md / TOOLS.md 分离**
- SOUL.md = 角色人格（每次注入 context）
- TOOLS.md = 工具元数据（token-efficient：只列名称，按需读取 schema）
- **Runner 对比**: AgentProfile 的 systemPrompt 和 toolAllowList 在代码中，不支持文件配置和热更新
- **Already in TODO-013** (Workspace-as-Config)，但 OpenClaw 的具体实现模式值得参考

**4. Memory Flush Before Compaction**
- OpenClaw 在执行 context compaction 前，先将对话中的重要事实 flush 到文件
- 防止 compaction 丢失关键信息
- **Runner 对比**: CompactionChain(Snip, Micro) 直接压缩，无预保存步骤 → 可能丢失 Snip 掉的 tool result 中的重要信息
- **New Action**: 在 SnipCompactor 执行前，提取被删除消息中的关键信息写入 MemoryProvider.writeDurable()

### Claude Code 泄露源码深度分析

基于 VILA-Lab 学术分析 (arXiv:2604.14228) 和多篇逆向工程报告：

**1. 核心比例：1.6% AI 逻辑 + 98.4% 基础设施**
- 512,000 行 TypeScript，只有 1.6% 是 AI 决策逻辑
- 大量代码在：context management, tool routing, recovery, permission gating
- **启示**: runner 的 agent-kernel ~13K 行已经是精简的，但需要更多投入在基础设施（observability, resilience, permission）

**2. StreamingToolExecutor + RWLock**
- 工具在模型 **还在流式输出时** 就开始执行（不等完成）
- 使用 RWLock: 读操作并行，写操作独占
- **Runner 对比**: ToolCallingLoop 在 LLM 流完成后才开始工具执行（`concatWith(Flux.defer(...))`）
- **New TODO**: 评估能否在 TEXT_DELTA 阶段检测到完整 tool_use 块后立即开始执行

**3. 14 Cache-Break Vectors 监控**
- Claude Code 主动监控 14 种可能使 prompt cache 失效的条件
- 优化 cache hit rate 以降低成本
- **Runner 对比**: 完全未实现 prompt caching（TODO-024 已记录）

**4. 108+ Feature Flags, 44 编译时 flags**
- KAIROS（自主 daemon）, autoDream（记忆整合）, BUDDY（伴侣模式）等 20+ 已构建但未发布的功能
- **启示**: 长期功能用 feature flags 隔离，可以大胆实验而不影响主线

**5. 23 条 Bash 安全检查**
- `bashSecurity.ts` 2,592 行，18 个被阻止的 Zsh 内建命令
- Unicode 零宽字符注入检测，IFS null-byte 注入防御
- **Runner 对比**: CliTool 没有安全检查（TODO-001 已记录，但严重性需提升）
