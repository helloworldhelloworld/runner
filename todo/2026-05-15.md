## New Findings: Code Audit (2026-05-05 → 2026-05-15)

### Finding-A: AgentLoop.run() 同步路径 Builder 漏传关键字段

**文件**: `agent-kernel/.../agent/AgentLoop.java:119-123`

```java
ToolCallingLoop loop = ToolCallingLoop.builder()
    .provider(llmProvider)
    .toolExecutor(toolExecutor)
    .maxIterations(maxToolIterations)
    .build();  // ← 漏了 cancellationToken, costTracker, tracer, observers
```

上次 TODO 标记了"统一同步/reactive 路径都走 Builder"。现在同步路径确实改用了 Builder，但 **只设了 3 个字段**，漏掉了：
- `cancellationToken` → 同步 run() 仍无法被打断
- `costTracker` → token 预算控制在同步路径完全失效
- `tracer` → 同步路径无 trace
- `observers` → 同步路径不触发 onPreToolUse/onPostToolUse

**对比**: `runReactive()` 路径（L255 附近）应该也通过 Builder 构建，需检查是否同样缺失。

**Action**:
- [ ] AgentLoop.run() 的 Builder 追加 `.cancellationToken(this.cancellationToken)` `.costTracker(this.costTracker)` `.tracer(this.tracer)` `.observers(this.observers)`
- [ ] 确认 runReactive() / runStream() 也完整传递
- [ ] 添加 UT: 验证同步路径构建的 ToolCallingLoop 包含 cancellationToken 和 costTracker
- **Priority**: P1 — 从"部分修复"升级为"必须彻底完成"

### Finding-B: CostTracker.record() 仍从未被调用 — 功能完全空壳

**全局搜索结果**: `grep -rn "costTracker.record" --include="*.java" | grep -v target` → **0 结果**

整条链路：
1. `ClaudeProvider.parseResponse()` 解析 `usage` 字段 → 构建 `LLMResponse.usage` ✅
2. `ToolCallingLoop.executeReactiveLoop()` 检查 `costTracker.isOverBudget()` ✅

- [ ] 添加 UT: mock provider 返回带 usage 的 response，验证 costTracker.consumed 递增
- **Priority**: P0 升级 — 这是完全失效的功能，不是缺失功能

### Finding-C: ClaudeProvider.buildMessagesArray() 仍丢失 tool_result 结构

**文件**: `agent-kernel/.../llm/claude/ClaudeProvider.java:314-333`

```java
private ArrayNode buildMessagesArray(List<ConversationMessage> messages) {
    for (ConversationMessage msg : messages) {
        if (msg.getRole() == MessageRole.SYSTEM) continue;
        ObjectNode messageNode = objectMapper.createObjectNode();
        messageNode.put("role", convertRole(msg.getRole()));
        messageNode.put("content", msg.getTextContent());  // ← TOOL 消息变成纯文本
        array.add(messageNode);
    }
}
```

`ToolResult.toApiFormat()` 方法已存在并通过测试（`ToolResultTest.java:106-112`），但 `buildMessagesArray()` **从未调用它**。

Claude API 期望：
```json
{"role": "user", "content": [{"type": "tool_result", "tool_use_id": "toolu_xxx", "content": "..."}]}
```

当前发送：
```json
{"role": "user", "content": "tool result plain text"}
```

同理，ASSISTANT 消息中的 tool_use blocks 也被丢弃（只保留 text content），导致 Claude 看不到自己之前调用了什么工具。

**注意**: `ToolResult.toApiFormat()` 和测试已经写好了 → 修复成本极低，只需在 buildMessagesArray 中调用。

**Action**:
- [ ] TOOL 角色: 使用 `content: [msg.getMetadata("tool_use_id") → toApiFormat()]` 结构
- [ ] ASSISTANT 角色: 如果包含 tool_use metadata，生成 `content: [{type: "text"}, {type: "tool_use", id, name, input}]`
- [ ] 添加集成测试: 验证多轮 tool call 的完整消息格式
- **Priority**: P0 — 多工具并行调用时 Claude 无法关联 tool_result → tool_use

### Finding-D: ResilientLLMProvider.isRetryable() 字符串匹配 — 仍未修复

**文件**: `agent-kernel/.../llm/ResilientLLMProvider.java:198-221`

```java
private boolean isRetryable(Throwable e) {
    String msg = e.getMessage();
    if (msg.contains(": 400") || msg.contains(": 401") ...  // 脆弱
```

具体风险场景：
- 如果 Claude 返回的 error body 包含 `"Your request had status: 400 but was retried"` → 误判为不可重试

**Action**:
- [ ] 创建 `LLMProviderException extends RuntimeException` with `int httpStatusCode` 字段
- [ ] ClaudeProvider / OpenRouterProvider 抛异常时设置正确 status code
- [ ] `isRetryable()` 改为 `exception.getHttpStatusCode() >= 500 || exception.getHttpStatusCode() == 429`
- **Priority**: P1 — 影响生产环境重试策略的正确性

### Finding-F: ClientToolAliasRegistry 全局 static volatile — 测试隔离风险

**文件**: `agent-kernel/.../agent/directive/ClientToolAliasRegistry.java`

`ClientToolAliasRegistry` 使用 `static volatile ClientToolAliasSource source` 全局状态。`reset()` 方法存在但需要手动调用。

**风险**: 
- 并行测试如果设置不同的 `ClientToolAliasSource`，可能互相污染
- `defaultSource()` 的 `synchronized` 与 `setSource()` 的非 synchronized 写入之间有微妙的竞态：如果 `setSource(custom)` 在 `defaultSource()` 的 `source == null` check 之后、`source = new PropertiesClientToolAliasSource()` 之前执行，custom 会被覆盖

**Action**:
- [ ] 将 `setSource()` 也放入 `synchronized` block，或将 defaultSource 初始化改为 `static final` + `AtomicReference`
- [ ] 测试中使用 `@AfterEach reset()` 确保隔离（`ClientToolAliasRegistryTest` 已做到）
- [ ] 长期: 考虑改为实例注入（Spring Bean），避免 static mutable state
- **Priority**: P3 — 当前测试已做 reset，但设计不够健壮

## Cross-cutting Architecture Issues (Upgraded from Research)

### Issue-1: Prompt Caching 仍为零实现 — 成本影响持续放大

**背景更新**: Claude API Prompt Caching 已 GA（不再需要 beta header）。定价已标准化：
- cache_creation: 1.25x base price
- cache_read: 0.1x base price（节省 90%）
- TTL: 5 分钟

**Runner 现状**: `grep -rn "cache_control" --include="*.java" | grep -v target` → **0 结果**

对于 runner 的典型 agent loop（system prompt ~2000 tokens + tool definitions ~3000 tokens），每轮 tool loop 迭代重新发送完整 prompt，浪费 ~90% 的 input token 成本。

**Action** (更新自 TODO-024):
- [ ] ClaudeProvider.buildRequestBody() 中，为 system message 和 tools array 添加 `cache_control: {type: "ephemeral"}`
- [ ] 不再需要 beta header（已 GA）
- [ ] CostTracker 区分 cache_creation / cache_read / regular input tokens
- [ ] 添加 cache hit rate 监控指标
- **Priority**: P0 升级 — 直接影响运营成本，且修复成本极低（几行代码）

### Issue-3: 依赖可见性 — agent-kernel 内部类暴露过多

**发现**: agent-kernel 有 169 个 Java 文件，但模块边界控制粗粒度（全部 public class）。以下类不应被外部模块直接引用：
- `ToolCallingLoop` — 应由 `AgentLoop` 封装
- `ToolExecutor` — 内部调度器
- `SpanContext`, `Tracer` 内部实现类

**Reference**: Java 9+ module system 或至少 package-private 封装。Claude Code 的 1.6% AI 逻辑 vs 98.4% 基础设施比例表明：暴露面越小越好。

**Action**:
- [ ] 评估引入 `module-info.java` 的可行性（Java 9+ module system）
- [ ] 或至少将 ToolCallingLoop, ToolExecutor 改为 package-private，通过 AgentLoop facade 暴露
- [ ] 为 agent-kernel 的 public API 建立 Javadoc 表面审计
- **Priority**: P3

## New Code Review: ClientTool Alias System

### 架构评价: ★★★★☆

**优点**:
- 清晰的关注点分离: `DirectiveDescriptor` 合并注解 + 外部配置，对工具实现透明
- 可插拔: `ClientToolAliasSource` 是 SAM 接口，支持 Spring/Nacos/Apollo 热切换
- 去重: `normalizeAliases()` 正确处理空白、重复、与主名冲突
- ToolRegistry 自动展开: 注册一个 ClientTool 自动创建 N 个 alias proxy
- 测试覆盖: `ClientToolAliasRegistryTest` 覆盖了主路径和边界

**关注点**:
1. **全局可变 static 状态** — `ClientToolAliasRegistry.source` 是 static volatile，不利于测试隔离和 Spring 容器管理
2. **ToolRegistry.registerClientToolAliasesIfPresent()** 隐式行为 — 注册 1 个工具可能创建 N+1 个条目，调用方无明确提示
3. **竞态窗口** — `setSource()` 非 synchronized 与 `defaultSource()` synchronized 之间有微妙 race（见 Finding-F）

### 与 OpenClaw TOOLS.md 模式对比

OpenClaw 的做法: 工具元数据完全外部化为 TOOLS.md 文件，支持热更新、版本控制、per-workspace 差异化。

Runner 的 ClientTool Alias 系统走了一条**混合路径**: 
- 基础定义在注解中（编译时）
- 别名通过外部配置扩展（运行时）
- 这比纯注解灵活，但不如纯文件配置可控

**建议**: 当前混合方案是务实的增量改进。未来可考虑将完整 tool metadata（不只是别名）外部化到 YAML/JSON 配置，对齐 TODO-013 (Workspace-as-Config)。

## Deep Research Findings (2026-05-15 Latest)

### OpenClaw Architecture Deep Dive (310K+ stars, MIT License)

原名 "Clawdbot"，由奥地利开发者 Peter Steinberger 创建（2025.11），2026.1.30 更名为 OpenClaw。

**Gateway-centric hub-and-spoke 架构**:
- `openclaw gateway` 启动单 Node.js 进程，监听 `ws://127.0.0.1:18789`
- Channel Adapter 只做协议转换（WhatsApp/Telegram/Slack/Discord/Signal/iMessage），不包含智能
- Agent Loop: intake → context assembly → model inference → tool execution → streaming → persistence
- Session 内串行执行，并行必须显式 opt-in

**关键设计模式**:
1. **Workspace-First Philosophy** — 身份在纯文本文件中，不在数据库：
   - SOUL.md（人格/价值观/语调/行为边界，每次注入 context）
   - TOOLS.md（工具使用说明）
   - AGENTS.md（操作手册，每次注入 system prompt）
   - MEMORY.md（持久记忆：模式/偏好/事实）
   - HEARTBEAT.md（定时任务配置）
2. **Heartbeat Pattern** — 每 30 分钟读取 HEARTBEAT.md，定时任务到期时无需用户输入自动执行
3. **Per-Session Serial + Model Resolver** — 自动 provider fallback when rate-limited
4. **Multi-Agent** — 同一 gateway 内多 agent，各自 workspace/memory/channel，通过 webhook 互通

**Runner 对比**:
- Agent Loop 结构高度一致 ✅
- 缺少 Workspace-as-Config（TODO-013）
- 缺少 Heartbeat/Proactive（TODO-014）
- 缺少 Channel Adapter 抽象（runner 直接绑定 WebSocket/REST）
- 缺少 per-session 串行保证（SubagentRuntime 并发控制不完整）

### Claude Code 泄露源码完整分析 (v2.1.88, 512K TS)

**泄露经过**: 2026.3.31，安全研究员 Chaofan Shou 发现 npm 包 `@anthropic-ai/claude-code` v2.1.88 附带 59.8MB source map 文件，指向完整源码（~1900 文件）。

**技术栈**: Bun (非 Node.js) + React + Ink (终端 UI) + Zod v4 (schema 校验)

**核心架构**:

1. **QueryEngine (46K 行)** — 所有 LLM API 调用、streaming、caching、orchestration 的核心。相当于 runner 的 ToolCallingLoop + LLMProvider + CostTracker 的合体。集中化的好处：retry/rate limit/context budget/streaming error 统一推理。

2. **40+ Tools** — 每个独立模块，各自权限门控。base tool 定义 29K 行 TS，覆盖 schema validation + permission enforcement + error handling。Tool 被拒绝时返回 error ToolResult 而非 crash → LLM 自适应选择替代策略。

3. **三层权限**: allowed_tools (自动批准) → disallowed_tools (阻止，优先级最高) → permission_mode (其余)。

4. **三层 Memory**:
   - Layer 1: MEMORY.md — 轻量级索引（~150 字符/条目），始终在 context 中。存储 **位置** 而非数据。
   - Layer 2: Topic Files — 实际知识，按需获取，永不全量加载
   - Layer 3: Raw Transcripts — 从不全量重读，只 grep 特定标识符
   - **Self-Healing**: agent 主动修正自己的 memory。更新仅在文件写入成功后允许。

5. **5 层 Context Compaction**:
   - MicroCompact — 本地编辑，无 API 成本；基于时间清除旧 tool results
   - Context Collapse — 对话段落摘要
   - Session Memory — 提取关键上下文到文件
   - Full Compact (AutoCompact) — 完整对话压缩 + 选择性文件重注入，接近限制时触发，保留 token buffer
   - PTL Truncation — 丢弃最旧消息组
   - 连续 3 次 compaction 失败后停止尝试 (`MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3`)

6. **KAIROS (未发布，源码中引用 150+ 次)** — 将 Claude Code 从请求-响应变为持久后台进程。维护 append-only 日志，周期性 `<tick>` 提示决定是否主动行动，15 秒阻塞预算。

7. **autoDream** — 空闲时 fork 子 agent 做记忆整合：合并跨 session 观察、消除矛盾、将暂定笔记转为确认事实。

8. **Multi-Agent Swarm** — 协调者 spawn 子 agent，各自工具权限 + context 边界。**共享 memory space**（区别于朴素多 agent 各自独立设计）。

9. **Rust Rewrite 进行中** — 6 模块：runtime, api, tools, commands, compat-harness, rusty-claude-cli

**Runner 对比新发现**:
- runner MemoryProvider 是扁平的 3 层（session/ephemeral/durable），缺少"位置索引"模式（Memory 只存位置指针，内容按需获取）→ **New TODO-035**
- runner 无 Self-Healing Memory（agent 不能修正自己的 memory）→ **New TODO-036**
- runner compaction 只有 2 层（Snip + Micro），缺少 Session Memory 提取和 Full Compact → 已在 TODO-006
- runner 无 compaction 失败计数和退出机制 → **补充到 TODO-006**
- Tool 被拒绝时 runner 的行为未定义（ToolExecutor 可能抛异常）→ **补充到 TODO-011**

- Checkpointing at every super-step boundary → human-in-the-loop, time-travel debugging, fault tolerance

## Supplementary TODOs from Latest Research

### TODO-035: Memory 位置索引模式 (Claude Code MEMORY.md Pattern)
- **Reference**: Claude Code 的 MEMORY.md 只存 ~150 字符的位置指针，实际内容在 Topic Files 中按需获取。runner 的 durable memory 全量注入 system prompt。
- **Gap**: 当 durable memory 增长到数百条目时，全量注入会消耗大量 context token
- **Action**:
  - [ ] 设计 MemoryIndex 轻量层: 每条 durable memory 缩减为标题 + 摘要（≤150 字符）
  - [ ] 全量注入 MemoryIndex 到 system prompt（低成本）
  - [ ] 实际内容按需通过 `recall_memory` tool 获取
  - [ ] 减少 system prompt token 消耗，同时保留信息可达性
- **Priority**: P2

### TODO-036: Self-Healing Memory
- **Reference**: Claude Code 的 agent 主动修正 memory 文件。更新仅在文件写入成功后允许，防止失败尝试污染 memory。
- **Gap**: runner 的 MemoryProvider 只有 addMessage/search/write，agent 无法修正已有 memory 条目
- **Action**:
  - [ ] 为 MemoryProvider 添加 `updateDurable(key, newValue)` 和 `deleteDurable(key)` 方法
  - [ ] 添加 `update_memory` tool 供 LLM 主动修正过时信息
  - [ ] 添加写入确认机制: 只有 `writeDurable` 成功后才允许更新索引
- **Priority**: P2

### TODO-037: Compaction 失败计数与退出 (补充 TODO-006)
- **Reference**: Claude Code `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3`，连续失败后停止尝试
- **Gap**: CompactionChain 无失败追踪，如果 compaction 持续失败会无限重试
- **Action**:
  - [ ] 在 CompactionChain 中添加连续失败计数
  - [ ] 超过阈值后禁用自动 compaction，emit WARNING StreamEvent
  - [ ] 添加 recovery 机制: 下一次成功后重置计数
- **Priority**: P2

### TODO-038: Tool 拒绝时的优雅降级
- **Reference**: Claude Code tool 被拒绝时返回 error ToolResult（而非 crash），LLM 看到错误后自适应选择替代策略
- **Gap**: ToolExecutor/ScopedToolRegistry 拒绝时行为未定义，可能抛异常导致整个 agent loop 中断
- **Action**:
  - [ ] ScopedToolRegistry.get() 返回 null 时，ToolExecutor 生成 ToolResult.error("Tool 'xxx' is not available for this agent")
  - [ ] 将此 error result 返回给 LLM，让它选择替代方案
  - [ ] 添加 UT: 验证被拒绝的 tool 不会中断 agent loop
- **Priority**: P1
