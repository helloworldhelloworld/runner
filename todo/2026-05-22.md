### TODO-047: Hook System 需对齐 3-Tier Handler 模型（Claude Code Pattern）

**Reference**: Claude Code Harness 的 hook 系统分三层 handler：
1. **Command hooks** — shell 命令，处理确定性检查（如文件保护、格式校验）
2. **Prompt hooks** — LLM prompt，处理语义评估（如代码质量、安全意图判断）
3. **Agent hooks** — 完整 agent 执行，处理需要工具访问的深度分析

**Runner 现状**:
- `AgentObserver` 仅支持 callback 接口（`onPreToolUse(toolName, args)`），等价于 Claude Code 的 Command hook 一层
- 无 Prompt hook：不能在 hook 中询问 LLM "这个操作是否安全？"
- 无 Agent hook：不能在 hook 中执行工具（如读取文件确认上下文后再判断）
- hook 返回类型是 void，**无法 block/modify/defer 工具调用**

**Claude Code 关键设计**:
- PreToolUse hook 可以返回 `allow`、`deny`、`ask`（需用户确认）、`defer`（交给下游判断）
- hook 可以 **修改 tool_input**（参数注入/消毒）并 **追加上下文**
- Exit code 2 = 硬拦截工具执行

**OpenClaw v2026.5 关键设计**:
- typed-hook policy gate：非 bundled 插件的 conversation hooks（`before_model_resolve`, `llm_input`, `llm_output` 等）默认被静默丢弃，除非显式 `hooks.allowConversationAccess: true`
- before-tool authorization hooks 用于 inline skill dispatch

**Action**:
- [ ] `AgentObserver.onPreToolUse()` 返回类型从 `void` 改为 `HookDecision`（ALLOW/DENY/ASK/MODIFY）
- [ ] 引入 `HookHandler` 接口，支持 Command（同步函数）、Prompt（LLM 调用）、Agent（完整 agent 执行）三种模式
- [ ] ToolCallingLoop 在 `firePreToolUse()` 后根据 HookDecision 分支处理
- [ ] 考虑 hook 白名单策略（OpenClaw 的 typed-hook policy gate 模式）
- **Priority**: P1 — 这是 TODO-010 的实质性设计方案
- **Effort**: 3-5d（含 acceptance test）
- **Blocks**: TODO-001 (BashTool Sandboxing) 和 TODO-044 (Untrusted outputs) 都依赖 hook 系统的拦截能力

### TODO-048: Prompt Caching — 2026 TTL 变更后的紧迫性升级

**Reference**: Anthropic 2026 年初将 prompt cache TTL 从 60 分钟下调至 5 分钟。

**关键数据**:
- Cache write: 基础 input 价格的 1.25x（5min cache）或 2x（1h cache）
- Cache read: 基础 input 价格的 **0.1x**
- Claude Opus 4.7: 最低 4096 tokens 才能缓存
- Claude Sonnet 4.6: 最低 2048 tokens
- 如果 prefix 小于阈值，请求成功但 **静默按全价收费**

**Runner 影响分析**:
- System prompt + tool definitions 在同一 session 内每轮完全重传
- 典型 system prompt（base + skills + memory）约 2000-8000 tokens
- Tool definitions（含 MCP tools）约 1000-5000 tokens
- 每轮重传成本：约 3000-13000 tokens input（大部分重复内容）
- 启用 prompt caching 后：首轮 1.25x，后续 **0.1x** → 每 session 节省 ~80% input 成本

**Claude Code 实践**:
- 14 个 cache-break vectors — system prompt、tool definitions、images、extended thinking 设置变更都会打断缓存
- Cache-aware compaction — compaction 时保护 prompt cache block 边界不被打断
- `cache_control` 标记放在 system prompt 末尾和 tool definitions 末尾

**Action**:
- [ ] ClaudeProvider 在 request body 的 `system` 数组最后一个 block 添加 `"cache_control": {"type": "ephemeral"}`
- [ ] `tools` 数组最后一个 tool 添加 `"cache_control": {"type": "ephemeral"}`
- [ ] 添加 `CacheMetrics`：跟踪 cache_creation_input_tokens / cache_read_input_tokens 比率
- [ ] 在 CostTracker 中记录缓存命中率（需 TODO-036 先修复）
- [ ] CompactionChain 需要 cache-aware 逻辑：不打断 system prompt 边界
- **Priority**: P1 → **升级为 P0** — 5 分钟 TTL 意味着交互式 session 几乎每轮都能命中缓存，ROI 极高
- **Effort**: 2d（基础实现）+ 1d（cache-aware compaction）
- **Depends on**: TODO-036 (CostTracker.record) 修复后才能追踪缓存效果

### TODO-049: 统一执行路径 — 消除三路径不一致（架构级重构）

**本轮代码审查再次确认**：执行路径不一致是 runner 最大的架构隐患。

**当前 Execution Path Coverage Matrix（5-22 确认版）**:

| Feature | `run()` sync | `runStream()` callback | `runReactive()` Flux |
|---|---|---|---|
| ToolCallingLoop | ✅ | ❌ **绕过** | ✅ |
| Context Compaction | ✅ | ❌ **缺失** | ✅ |
| CancellationToken | ❌ (Builder 未传) | ❌ | ✅ |
| PreToolUse Hook | ❌ | N/A (无工具) | ✅ |
| PostToolUse Hook | ❌ | N/A | ✅ |
| CostTracker record | ❌ | ❌ | ❌ (所有路径) |
| CostTracker check | ❌ | ❌ | ✅ (但 record 未接入) |
| Observer callbacks | ✅ partial | ❌ | ✅ |
| Tracing spans | ❌ | ❌ | ✅ |

**Claude Code 对照**: 所有执行路径（同步/流式/子 agent）共享 **同一套核心 pipeline**，不存在路径差异。

**OpenClaw 对照**: 单一 agent loop entry point，不同 transport 层（WebSocket/REST/CLI）只影响输出格式，不影响核心逻辑。

**Vercel AI SDK 对照**: 只要求 provider 实现一个 `doStream()` 方法，sync 是 stream 的 blocking wrapper。

**提议方案**:
```
Before:  run()  →  ToolCallingLoop(sync)     → provider.complete()
         runStream()  →  provider.completeStream()  (NO ToolCallingLoop)
         runReactive()  →  ToolCallingLoop(reactive)  → provider.completeStreamReactive()

After:   run()  =  runReactive().blockLast()       ← sync 是 reactive 的 blocking wrapper
         runStream()  =  @Deprecated → delegate to runReactive()
         runReactive()  →  ToolCallingLoop(reactive)  → provider.completeStreamReactive()
```

**Action**:
- [ ] `run()` 实现改为 `runReactive().blockLast()`
- [ ] `runStream()` 加 `@Deprecated(forRemoval=true)` 并 delegate 到 `runReactive()` + callback bridge
- [ ] 删除 ToolCallingLoop 的 `executeWithTools()` 和 `executeWithToolsAsync()`
- [ ] 仅保留 `executeReactiveLoop()` 作为唯一执行路径
- [ ] 删除望远镜构造器（7 个），仅保留 Builder
- [ ] 写 acceptance test：sync 路径也能触发 PreToolUse hook + CostTracker record
- **Priority**: P0 — 统一后，TODO-035/036/037 自动解决
- **Effort**: 3d（含大量回归测试）
- **Resolves**: TODO-035, TODO-036 (部分), TODO-037

### TODO-051: Context Compaction 升级至 4 层 Pipeline

**Reference**: Claude Code 5 层 compaction pipeline（成本排序原则：最便宜先执行）:

```
L1: Budget Reduction — 截断超大单条 tool output（free）
L2: Snip — 按时间深度删除旧 TOOL 消息（free）
L3: MicroCompact — 无 API 调用的本地压缩（free）
       ↓ 以上全部 free，以下需要 API 调用
L4: Context Collapse — LLM 对选定片段生成摘要（paid, 按需）
L5: AutoCompact — LLM 对整个会话历史生成摘要（paid, last resort）
```

**Runner 现状**: 2 层（Snip + Micro），均为 free 操作。缺少 L1（Budget Reduction）和 L4/L5（LLM 摘要）。

**OpenClaw 补充**: 
- 在 compaction 前触发 **silent pre-compaction memory flush** — 提示 LLM 将重要事实写入 MEMORY.md
- 自动 compact-and-retry：context overflow 后自动 compact + retry
- **Circuit breaker**: 连续 3 次 compaction 失败后停止重试（Claude Code 数据：1279 个 session 累计浪费 250K API calls/day）

**Action**:
- [ ] L1: `BudgetReductionCompactor` — 单条 tool output 超过 `maxSingleResultChars`（默认 50000）时截断
- [ ] L4: `SummarizationCompactor` — 当 L1-L3 仍不够时，对最旧的 N 轮对话调用 LLM 生成摘要
- [ ] 在 L4 执行前，触发 memory flush（TODO-043 的 PreSnipHook）
- [ ] Circuit breaker: 连续 N 次 LLM 摘要失败后跳过 L4，直接 Snip 更多轮次
- [ ] Compact-and-retry: ToolCallingLoop 捕获 `context_length_exceeded` → emergency compact → retry
- **Priority**: P1 — 长会话场景的稳定性保障
- **Effort**: 3d（L1 + L4 基础实现）+ 2d（circuit breaker + compact-and-retry）
- **Merges**: TODO-006, TODO-043, TODO-045

### TODO-052: Agent Handoff 双模式（Spawn + Delegate-in-place）

**Reference**: 
- OpenAI Agents SDK 1.0 GA: **Handoff**（转交控制权，原 agent 退出）+ **Agent-as-Tool**（内联调用，原 agent 保持控制）双模式
- OpenClaw ACP: **sessions_spawn**（异步 spawn 到独立 session）+ **sessions_send**（直接消息通信）
- Claude Code: 3 种 subagent 执行模型，含 forked subagent（autoDream 内存整理在隔离 fork 中运行，不干扰主 agent 推理状态）
- CrewAI: Sequential / Hierarchical / **Consensual** 三种编排模式

**Runner 现状**:
- 仅支持 Spawn 模式（SpawnSubagentTool → 异步 spawn + WaitSubagentTool → 阻塞等待）
- 无 Handoff 模式（转交控制权后原 agent 退出循环）
- 无 Agent-as-Tool 模式（同步内联调用 subagent，结果直接作为 tool result）
- 无 Consensual 模式（多 agent 投票/讨论后达成共识）

**Action**:
- [ ] 新增 `DelegateSubagentTool`：同步调用 subagent，结果直接返回为 tool result（Agent-as-Tool 模式）
- [ ] 新增 `HandoffSubagentTool`：转交控制权，原 agent ToolCallingLoop 退出，新 agent 接管 session
- [ ] SubagentRuntime 支持 `SpawnMode` 枚举: `ASYNC_SPAWN`, `SYNC_DELEGATE`, `HANDOFF`
- [ ] 考虑后续支持 Consensual 模式（多 agent 投票）
- **Priority**: P2 — 这是 TODO-007 的实质性设计方案
- **Effort**: 3d（Delegate + Handoff）+ 2d（acceptance tests）
- **Merges**: TODO-007

### TODO-053: KAIROS-inspired 后台 Memory Consolidation

**Reference**: Claude Code KAIROS 的 autoDream 四阶段 memory consolidation:
1. **Orient** — 扫描近期 session logs
2. **Gather** — 提取相关模式和决策
3. **Consolidate** — 压缩为持久化 memory（≤25KB）
4. **Prune** — 去噪

**关键架构特性**:
- 在 **forked subagent** 中执行，隔离于主 agent 推理状态
- 每阶段 **15 秒 blocking budget**，超时自动 background
- 触发条件：24 小时 + 至少 5 个 session
- Append-only logging 用于审计

**Runner 适用场景**:
- 长期 session 累积的 ephemeral memory 需要定期整理
- 跨 session 的用户偏好和项目知识需要提炼为 durable memory
- 当前 MemoryProvider 仅做 getHistory/addMessage，无主动整理机制

**Action**:
- [ ] 设计 `MemoryConsolidationTask`：定期扫描 ephemeral memory → LLM 摘要 → 写入 durable memory
- [ ] 通过 SubagentRuntime spawn forked subagent 执行，不干扰主 session
- [ ] 添加 blocking budget（默认 30s per phase）
- [ ] 触发条件可配置（session 数、时间间隔）
- [ ] 可选：将 consolidation 结果写入 MEMORY.md 式的结构化文件
- **Priority**: P3 — 长期用户体验优化
- **Effort**: 5d
