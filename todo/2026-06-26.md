## 本轮新增分析维度

### A. Claude Code "98.4% 基础设施" 范式对照

VILA-Lab 论文（arXiv:2604.14228）揭示：Claude Code 512K 行代码中仅 1.6% 是 AI 决策逻辑，98.4% 是确定性基础设施——权限门、上下文管理、工具路由、恢复逻辑。核心 agent loop 是一个简单的 while-loop，真正的工程复杂性在环绕它的系统中。

**每一轮 agent turn 的 9 步 pipeline**：
1. Settings resolution
2. State initialization
3. Context assembly（运行时从 ~28 个小段条件组装系统提示）
4. 5 层 pre-model shapers（compaction pipeline）
5. Model call
6. Tool dispatch
7. Permission gate
8. Tool execution
9. Stop condition evaluation

**Runner 对照**：runner 的 AgentLoop/ToolCallingLoop 覆盖了步骤 3-6/8-9，但在以下方面有显著差距：
- 步骤 1/2（Settings resolution / State init）：无等价物，配置散落在 Builder 参数和 Spring Config 中
- 步骤 4（5 层 compaction）：仅 2 层（Snip + Micro）
- 步骤 7（Permission gate）：ToolPolicy.evaluate() 存在但 hook 无法拦截/修改
- 无运行时组装系统提示（28 段条件缓存拼装）
- 无 append-only session storage

### B. OpenClaw "Workspace-First" 范式对照

OpenClaw 的核心设计哲学：配置文件是 agent 身份和行为的唯一真相源。

| 文件 | 职责 | Runner 等价 |
|---|---|---|
| `SOUL.md` | Agent 身份 + 决策边界 + 沟通默认值 | `AgentProfile.systemPrompt` (硬编码) |
| `HEARTBEAT.md` | 自治循环调度（自然语言，非 cron） | `TriggerSource` SPI (未落地) |
| `MEMORY.md` | 动态累积上下文（指针索引 ≤200行） | `MemoryProvider.writeDurable` (无 index 层) |
| `IDENTITY.md` | 个性化 | 无 |
| `TOOLS.md` | 工具能力声明 | `ToolRegistry` (代码注册) |
| `AGENTS.md` | 多 agent 定义 | `AgentRegistry` (代码注册) |

**关键洞察**：OpenClaw 的 workspace-first 模式让 agent 配置可以版本控制、可移植、可复制，而 runner 的 agent 配置全部硬编码在 Java 代码或 Spring yml 中，修改 agent 行为需要重新编译。

### C. MCP 2026 Roadmap 关键演进

| 变化 | 影响 |
|---|---|
| **无状态会话** | server 可水平扩展，restart/scale-out 对 client 透明 |
| **会话迁移** | client 可无缝重连到另一个 server 实例 |
| **Auth 网关标准化** | SSO 集成、审计日志、网关行为 |
| **配置可移植性** | MCP server 配置可以跨环境迁移 |

**Runner 影响**：`agent-mcp` 当前假设有状态连接（`McpToolClient` 维护 session state），需要适配无状态模式。

### TODO-054: 运行时组装系统提示（Claude Code Pattern: Conditional Prompt Sections）

**Reference**: Claude Code 的系统提示不是一个大字符串，而是从 ~28 个小段（individually-cached, conditionally-included）运行时组装：
- 按 app 分叉（CLI vs Desktop）
- 按 surface 分叉（interactive vs SDK vs background vs Cowork）
- 按 model 分叉（更强的模型得到更短的 prompt）

- `PromptEngine.build()` 已有 `registerSkill`/`registerSection` 机制

- [ ] `PromptSection` 添加 `Predicate<PromptContext> condition` 字段，支持条件包含

- [ ] system prompt 分段编排：base + model-specific + skills + memory，每段可独立缓存
- [ ] 可选：添加 remote injection slot（通过配置文件或 API 动态注入 prompt 段）
- **Priority**: P2 — prompt caching（TODO-048）实现后，分段缓存才有实质意义
- **Effort**: 2d

### TODO-055: Append-Only Session Storage（Claude Code Pattern: Durable State）

**Reference**: Claude Code 使用 append-only JSONL 文件存储 session transcript：
- 每个 project 独立 session 文件（`~/.claude/projects/`）
- 记录 messages、tool results、compaction markers、events
- 代码修改前 snapshot 受影响文件用于 revert
- Session 可 resume（重新加载 JSONL）
- 为 KAIROS autoDream 提供审计素材

**Runner 现状**：
- `MemoryProvider` 仅提供 in-memory history + ephemeral/durable 文件写入
- 无 session transcript persistence（重启后丢失）
- 无 file snapshot/revert 机制
- 无 session resume 能力

**Action**:
- [ ] 设计 `SessionTranscript` 接口：append(event), replay() → `List<StreamEvent>`
- [ ] 实现 `JsonlSessionTranscript`：每个 session 一个 `.jsonl` 文件，追加写入
- [ ] ToolCallingLoop 在每次 tool execution 前/后 append event
- [ ] AgentLoop 在每次 LLM response 后 append message
- [ ] session resume：从 JSONL 恢复 conversation history
- [ ] 可选：代码修改工具（write_file 等）执行前 snapshot 原文件
- **Priority**: P2 — 长 session 恢复和审计的基础
- **Effort**: 3d

### TODO-056: Lazy Tool Loading（Claude Code Pattern: Deferred Tool Definitions）

**Reference**: Claude Code 默认只向 LLM 注入 <20 个核心工具的 schema，其余工具仅注入名称列表。当 LLM 需要某个工具时，通过 `tool_search` 工具按需加载完整 schema。这大幅减少了 context window 中 tool definitions 的 token 消耗。

**Runner 现状**：
- `ToolRegistry.getToolDefinitions()` 返回**所有**已注册工具的完整 JSON Schema
- 随着 MCP tools 增长，tool definitions 可能占用 3000-10000+ tokens
- `ToolRegistry.search(query)` 方法已存在但未被利用

**Action**:
- [ ] 引入 `ToolLoadingStrategy` 枚举: `EAGER`（当前行为）、`LAZY`（仅注入名称+描述，按需加载 schema）
- [ ] 新增 `search_tools` 内置工具：LLM 通过此工具按名称/描述搜索并加载完整 schema
- [ ] `LLMOptions.toolDefinitions` 支持 compact 模式（name + description only）
- [ ] 当注册工具数 > 20 时自动切换到 LAZY 模式
- [ ] ClaudeProvider/OpenRouterProvider 构建请求体时区分 full schema vs compact reference
- **Priority**: P2 — MCP 工具数量增长后变为 P1
- **Effort**: 3d
- **Synergy**: 与 TODO-048 (Prompt Caching) 协同——减少 tool definition tokens 使 prompt 更易缓存

### TODO-059: 自愈式 Memory 与 Memory Index（Claude Code + OpenClaw Pattern）

**Reference**:
- **Claude Code 3 层 memory**: in-context → MEMORY.md（≤200 行指针索引）→ 磁盘全量 transcript
- **Self-healing memory**: agent 发现之前的假设错误时，主动重写相关 memory 文件（不只是在对话中纠正）
- **Strict Write Discipline**: 仅在成功操作后写入 memory，降低存储错误信息的风险
- **OpenClaw**: `MEMORY.md` 是动态累积的上下文，agent 自主管理

**Runner 现状**：
- `MemoryProvider` 有 `writeEphemeral`/`writeDurable` 但无 index 层
- 无 self-healing 机制（写入后不会自动更新/纠正）
- 无 write discipline（任何时候都可以写入）
- `kernel-memory` 有 BM25+vector search 但无 pointer index 优化

**Action**:
- [ ] 引入 `MemoryIndex`：≤200 行的 compact 索引文件，always-in-context
- [ ] Index 包含 topic → file 的映射，LLM 按需检索具体文件
- [ ] 自愈机制：agent 在 tool result 包含与已有 memory 矛盾的信息时，自动更新相关 memory
- [ ] Write discipline：仅在 tool execution 成功后允许写入 durable memory
- [ ] Memory GC：超过大小阈值时自动归档旧条目
- **Priority**: P2 — 长期用户体验
- **Effort**: 5d
- **Merges**: 部分覆盖 TODO-053 (Memory Consolidation)

### TODO-063: Durable Sessions — 可恢复流式连接（Emerging Pattern）

**Reference**: "Durable Sessions" 是 2025-2026 涌现的基础设施类别（ElectricSQL 提出）：
- **Resumable streaming**：client 在 last-acknowledged offset 重连，无重复 token，无重启
- **Cross-device continuity**：在一个设备开始，另一个设备恢复
- **Async completion**：agent 在用户断连后完成，结果在重连时可用
- Ably、Upstash、Durable Streams 等已有生产实现

**Runner 现状**：
- WebSocket 连接断开 = session 丢失
- 无 offset-based 重连
- 无 cross-device session 恢复

**Action**:
- [ ] `StreamEvent` 添加 `sequenceId` 字段（单调递增）
- [ ] `SessionManager` 支持 session persistence + 重连时从 last sequenceId 恢复
- [ ] WebSocket handler 支持 `resume` 参数（提供 lastSequenceId）
- [ ] 与 TODO-055 (Session Storage) 协同：JSONL transcript 提供 replay 源
- **Priority**: P3 — 长 session 场景的可靠性保障
- **Effort**: 3d
- **Depends on**: TODO-055 (Session Storage)

### TODO-064: Guardrails 作为一等公民（OpenAI Agents SDK Pattern）

**Reference**: OpenAI Agents SDK 将 Guardrails 提升为框架级概念：
- **Input Guardrails**：在 agent 处理前验证用户输入（prompt injection 检测、PII 脱敏、schema 验证）
- **Output Guardrails**：在响应返回用户前验证（schema 强制、有毒语言检测、事实性检查）
- **Tool Guardrails**：包裹工具调用（权限边界、速率限制、高风险操作审批）
- Guardrails **与 agent 执行并行运行**，实现 fail-fast
- **Tripwire 机制**：guardrail 触发时立即停止 agent 执行

**Runner 现状**：
- ToolPolicy.evaluate() 是纯规则引擎，仅覆盖 tool guardrails 的子集
- 无 input guardrails（用户输入未经验证直接进入 LLM）
- 无 output guardrails（LLM 输出未经验证直接返回用户）
- soul-safety 模块有 crisis detection 但未集成到 agent loop

**Action**:
- [ ] 设计 `Guardrail<T>` 接口：`evaluate(context, input/output) → GuardrailResult`
- [ ] `GuardrailResult` 包含 `tripwire: boolean`（立即停止执行）和 `message: String`
- [ ] `AgentLoop` 在 LLM 调用前运行 input guardrails，在返回前运行 output guardrails
- [ ] `ToolCallingLoop` 在工具调用前/后运行 tool guardrails（与 TODO-047 Hook System 协同）
- [ ] 将 `soul-safety` CrisisDetector 包装为 InputGuardrail
- [ ] Guardrails 与 agent 执行并行运行（`Flux.merge` + 首个 tripwire 取消 agent）
- **Priority**: P1 — 生产安全的基础
- **Effort**: 3d
- **Synergy**: TODO-047 (Hook System) 提供执行点，TODO-064 提供评估框架

## 本轮关键洞见

1. **"Dumb loop, smart harness"是行业共识** — Claude Code 98.4% 代码是基础设施而非 AI 逻辑。runner 当前的 ToolCallingLoop 是好的，但周围的基础设施（compaction、permissions、hooks、session storage）严重不足。
2. **P0 项目 5 轮未动已成系统性风险** — 建议 Minion runner 侧基本完成后立即转入 P0 债务清理。
3. **Prompt Caching + Lazy Tool Loading 是低投入高回报组合** — 分别降低 ~80% input 成本和减少 3000-10000 tokens context 占用。
4. **Workspace-First 配置是 DX 升级方向** — OpenClaw 247K stars 验证了这一模式的市场认可，runner 应逐步外部化 agent 配置。
5. **MCP 2026 无状态演进需要提前准备** — 当前有状态假设会成为 MCP 生态兼容性障碍。
6. **安全类 TODO 形成 dependency chain** — Hook System (047) → Sandbox (050) → Untrusted (044) → ML Classifier (058)，必须按序推进。
7. **Session 持久化是多个高级特性的前提** — Self-healing memory、memory consolidation、session resume 都依赖 append-only storage。
