### TODO-054: ToolSearchTool — 延迟工具加载（Claude Code 核心模式）

**Reference**: Claude Code 管理 **184 个工具**，但从不一次性全部注入 context。其 **ToolSearchTool** 是一个"寻找工具的工具"：
- 默认仅注入 <20 个核心工具 + ToolSearchTool 本身
- 当 LLM 需要某能力时，调用 ToolSearchTool 发现并加载对应工具定义
- 支持 regex 和 BM25 搜索（搜索工具名、描述、参数名、参数描述）
- 发现的工具通过 `tool_reference` 内联展开
- **典型效果：减少 85%+ 的工具定义 token 消耗**
- **关键约束：已加载工具的 prefix 不变，prompt cache 不失效**

**OpenClaw 对照**: `src/tools/planner.ts` 实现了 ToolPlan，选择性注入与当前 turn 相关的工具集合。

**Runner 现状**:
- `ToolRegistry.getToolDefinitions()` 返回所有已注册工具的完整定义，全量注入每次 LLM 请求
- `ToolRegistry.search(query)` 方法已存在，但仅用于 debug/查询，未集成到 LLM 请求流程
- 随着 MCP tools + CLI tools + 内建工具增长，工具定义可能消耗 3000-8000 tokens
- 无 deferred loading 机制、无 tool_reference 展开协议

**Impact Analysis**:
- 当前 10-15 个工具，token 开销尚可接受
- 但接入更多 MCP servers 后（每 server 平均 5-10 tools），工具定义可达 20,000+ tokens
- 与 TODO-048（Prompt Caching）强关联：工具定义变更是 14 个 cache-break vectors 之一

**Action**:
- [ ] 引入 `DeferredToolDefinition`：仅保留 name + 简短描述（~50 tokens/tool），不含完整 schema
- [ ] 实现 `ToolSearchTool`（Tool 接口）：接收 query → `ToolRegistry.search(query)` → 返回匹配工具的完整定义
- [ ] `LLMOptions.toolDefinitions` 支持两种模式：`FULL`（当前行为）、`DEFERRED`（仅核心工具 + ToolSearchTool）
- [ ] 工具定义分层：`coreTools`（always loaded, <20）+ `deferredTools`（on-demand）
- [ ] 确保 deferred tool 加载不破坏 prompt cache（新工具定义追加在 messages 中而非修改 tools 数组）
- **Priority**: P2 — 当前工具数量尚可，但 MCP 生态扩展后将变为 P0
- **Effort**: 3d
- **Depends on**: TODO-048（Prompt Caching）先实现后，才能验证 cache 兼容性

### TODO-055: Speculative Tool Execution — 工具与 LLM 生成并行

**Reference**: Claude Code 实现了**投机执行**：
- 当 LLM 输出包含 tool_use block 时，不等待整个 response 完成即开始执行工具
- 每个工具有 `isConcurrencySafe` 标志：Read/Grep/Glob 标记为 safe，Edit/Write/Bash 标记为 unsafe
- 安全的只读工具可以在 LLM 仍在生成时并行执行
- **效果：减少 turn 级延迟，尤其是多工具调用场景**

**Runner 现状**:
- `ToolCallingLoop.executeReactiveLoop()` 严格顺序：先收集完整 LLM response → 然后提取 tool calls → 然后执行工具
- L273-279: `provider.completeStreamReactive()` 的所有事件先 accumulate 到 `List<StreamEvent>`
- L285: `concatWith(Flux.defer(...))` 确保工具执行在 LLM 流完成后才开始
- 多个工具之间已有并行执行（L324 `Flux.merge`），但与 LLM 生成没有并行

**Action**:
- [ ] Tool 接口添加 `default boolean isConcurrencySafe() { return false; }` 方法
- [ ] 只读工具（MathTools, TimeTools, MemorySearch 等）标记 `isConcurrencySafe = true`
- [ ] ToolCallingLoop 在 LLM 流中检测到 tool_use block 时，立即开始执行 concurrency-safe 工具
- [ ] 非 safe 工具仍等待 LLM 完成后顺序执行
- [ ] 添加 feature flag 控制开关（初期默认关闭）
- **Priority**: P3 — 性能优化，非功能性阻塞
- **Effort**: 5d（需大幅重构 ToolCallingLoop 的事件收集逻辑）
- **Risk**: 投机执行的工具结果可能被后续 LLM 输出推翻（如 LLM 最终未产生该 tool call）

### TODO-058: Active Memory — 阻塞预加载替代惰性检索（OpenClaw 模式）

**Reference**: OpenClaw 的 **Active Memory** 是一个阻塞子 agent：
- 在主 agent loop 开始前运行
- 执行 BM25 + vector 混合搜索，找到与当前 query 相关的历史记忆
- 将检索到的 "beliefs" 注入 system prompt
- 解决传统 reactive memory 的延迟问题：主 agent 不需要等待 memory search tool 返回

**Claude Code 对照**: 三层 memory — in-context (message array) + external file (MEMORY.md pointer index) + project config (CLAUDE.md)。MEMORY.md 是 **<200 行的紧凑索引**，始终在 context 中。

**Runner 现状**:
- `AgentLoop.runReactive()` L228: `memoryProvider.search(input)` 同步阻塞调用
- 搜索结果通过 `formatMemoryContext()` 格式化后追加到 system prompt
- 但 search 仅搜索 ephemeral memory 的 keyword 匹配，无 vector 搜索（`kernel-memory` 的 `MemoryIndex` 有 BM25 + vector 但未完全集成到 AgentLoop 路径）
- 无 "belief" 概念、无紧凑索引、无按需加载详细记忆

**Action**:
- [ ] 将 `MemoryIndex`（BM25 + vector hybrid search）从 `kernel-memory` 桥接到 `AgentLoop` 的 memory search 路径
- [ ] 引入 `MemoryIndex.md` 紧凑索引文件（每个 fact ≤150 chars），始终注入 system prompt
- [ ] search 结果按 relevance score 排序，取 top-N 注入（默认 N=5）
- [ ] 考虑 `ActiveMemoryAgent`：在主 agent 前运行的微型 agent，专门做 memory retrieval + injection
- **Priority**: P2 — 当 memory 量增长后体验显著改善
- **Effort**: 3d

## 架构原则差距分析（Claude Code 98.4% 确定性基础设施原则）

arXiv:2604.14228 指出 Claude Code 的**核心洞察**：一个生产级 agent 中，**98.4% 的代码是确定性基础设施**（权限门控、context 管理 pipeline、工具路由、recovery 机制），仅 1.6% 是 AI 决策逻辑。

**Runner 与此原则的对照**:

| 确定性基础设施层 | Claude Code | Runner | Gap |
|---|---|---|---|
| **权限门控** | 7 种模式 + ML 分类器 + deny > ask > allow 规则链 | ScopedToolRegistry deny > allow 二级 | 缺 ask/defer/modify 语义 |
| **Context 管理** | 5 层 cascade + cache-aware + circuit breaker | 2 层 (Snip + Micro) | 缺 BudgetReduction, LLM 摘要, circuit breaker |
| **工具路由** | 184 tools + ToolSearchTool 延迟加载 + 投机执行 | 全量注入 + 顺序执行 | 缺延迟加载 + 投机执行 |
| **Recovery** | 10 次重试 + Retry-After + circuit breaker + compact-and-retry | ResilientLLMProvider 3 次重试 + isRetryable 默认 true | 缺 compact-and-retry, circuit breaker |
| **成本控制** | CostTracker + prompt cache + cache-aware compaction | CostTracker 存在但 record() 未调用 | 功能完全失效 |
| **Hook/Lifecycle** | 12 lifecycle events + 3-tier handler + PreToolUse block/modify | AgentObserver void callbacks | 无拦截能力 |
| **Memory** | 3 层 (in-context + MEMORY.md index + CLAUDE.md) + autoDream | getHistory() + search() | 无紧凑索引、无后台整理 |
| **Token 计数** | estimateTokens 全栈集成 | TokenCounter 接口存在但返回 null | 完全未实现 |
| **Structured Output** | tool_use JSON + text response | 仅 text | 缺结构化输出 |
| **Guardrails** | 7 permission modes + ML + hooks | 无 | 完全缺失 |

**结论**: Runner 的 AI 决策逻辑（AgentLoop, ToolCallingLoop）设计合理，但确定性基础设施层远未达到生产级水平。98.4% 原则表明，**大部分开发精力应投入基础设施而非 agent 逻辑**。

## Supplementary: 2026 跨框架最佳实践要点（第三维度研究）

### 关键行业共识（影响 runner 的决策）

1. **"Start single-agent, escalate deliberately"** — 大多数团队过早采用多 agent 架构。runner 当前的单 agent + orchestrator 设计是正确的起点，不应在基础设施完善前增加 multi-agent 复杂性。

2. **Parallel Tool Execution 4x speedup** — 2026.2 论文证明宽度扩展（每步 3 个并行工具调用）比顺序执行快 4x，成本降 40-70%。runner 的 `Flux.merge` 已支持工具间并行，但缺少与 LLM 生成的并行（TODO-055）。

3. **Circuit Breaker 是生产必需** — agent retry loops 可进入无限循环，产生数千次相同的失败调用并持续计费。三态模型：Closed (正常) → Open (持续失败，停止调用) → Half-Open (试探恢复)。runner 完全缺失此模式。

4. **Hierarchical Summarization > Sliding Window** — proactive 背景压缩一致优于 reactive 截断。runner 的 SnipCompactor 是 reactive 模式，缺少 proactive background summarization。

5. **Guardrails 已成为框架标配** — OpenAI SDK (3 types)、LangGraph (graph nodes)、CrewAI (limited)、Strands (policy) 均有内建。runner 是唯一完全缺失 guardrails 的框架级项目。

6. **MCP + A2A 双协议栈** — MCP 用于工具访问，A2A (Agent-to-Agent, Linux Foundation 治理, 150+ 组织) 用于 agent 间通信。runner 仅支持 MCP，未来需考虑 A2A 兼容性。

7. **LangGraph Checkpointing 模式** — 每个 graph node 执行后保存完整状态到持久存储（PostgreSQL/Redis），支持进程重启后恢复。runner 的 InterruptibleRun 类似但不持久化。

8. **Google ADK 1.0 GA** — 2026 年 Google 发布跨语言 Agent SDK (Python/Go/Java/TypeScript)，支持 A2A 协议。Java 实现可作为 runner 的参考。
