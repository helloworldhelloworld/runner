## Part I: External Research Updates (2026-05-18)

### 1. OpenClaw v2026.5.16-beta — 关键架构演进

#### 1.1 Task Brain（v2026.3.31 引入，v2026.5 稳定）
- **统一任务生命周期管理器**: SQLite 后端，将 ACP 任务、subagent spawn、cron 作业、CLI 后台进程统一到一个 ledger
- **状态机**: run → attempt → subscribe，可审计
- **Runner 差距**: SubagentRuntime 和 Orchestrator 各自维护独立状态（activeRuns + completedRuns + InterruptibleRun），无统一 ledger
- **Action**: 考虑引入 `TaskLedger`，统一跟踪所有异步执行单元的生命周期

#### 1.2 Session Lane Queue Serialization（正式稳定）
- **两级队列**: Global Lane（maxConcurrent=4）+ Session Lane（严格串行 concurrency=1）
- **4 种队列模式**: `collect`（合并排队消息）、`steer`（注入当前 run，取消 pending tool calls）、`followup`（等当前完成）、`steer-backlog`（steer + 保留 followup）
- **v2026.5 默认 steer 模式**: `/queue steer` 成为默认
- **Runner 差距**: InterruptibleRun 只有二元中断（cancel all），无 steer 式"在 tool 间隙注入新消息"
- **Action**: TODO-035（新增）

#### 1.3 Per-Agent Bootstrap Profile Overrides
- `contextInjection`、`bootstrapMaxChars` 可按 agent 覆盖
- Subagent 任务现在显示为可见的 `[Subagent Task]` 消息（不再隐藏在 system prompt 中）
- **Runner 差距**: AgentProfile 已有 systemPrompt 和 tool list，但没有 context injection 策略和 bootstrap 字符限制
- **Action**: AgentProfile 添加 `contextInjectionMode` 和 `maxBootstrapChars` 字段

#### 1.4 Memory Flush Before Compaction（确认模式）
- OpenClaw 在 compaction 前执行 **silent internal turn**：agent 写重要事实到 MEMORY.md
- 外部 memory provider（如 Mem0）在 turn 级别捕获
- **Runner 差距**: CompactionChain(Snip, Micro) 直接丢弃旧消息，无预保存步骤
- **Status**: TODO-031 已记录，本轮提升为 P1

### 2. Claude Code 源码深度分析 — 新发现

#### 2.1 queryLoop State 机制（新发现）
- `queryLoop()` 的 `State` 对象跟踪 `transition` 字段，记录 **上一轮为什么继续**
- 这使得 recovery 逻辑能区分"tool 失败后重试" vs "正常 tool 循环" vs "用户中断后恢复"
- **Runner 差距**: ToolCallingLoop 只有 iteration count，无状态转移原因跟踪
- **Action**: TODO-036（新增）

#### 2.2 Compaction 的 Prompt Cache 感知优化（新发现）
- **关键创新**: 当 prompt cache 命中时，compaction 不修改本地消息数组
- 改为在 API 请求中附加 `cache_edits` 块，按 `tool_use_id` 删除特定 tool_result
- 摘要调用复用相同的 system prompt + tools + model + message prefix，确保 cache key 不变
- **3,960 行 pipeline across 5 files**: cheapest first, heaviest last
- **Runner 差距**: 完全无 prompt caching（TODO-024），更谈不上 cache-aware compaction
- **Action**: prompt caching 实现后，CompactionChain 需要感知 cache state

#### 2.3 StreamingToolExecutor 投机执行（确认细节）
- 工具调用按 `isConcurrencySafe()` 分区：相邻 safe tools 合并为并行 batch，unsafe tool 开新串行 batch
- 并行上限 `getMaxToolUseConcurrency()` = 10
- `all` generator 按完成顺序 yield 结果（不是输入顺序）
- context modifiers 在 safe batch 中排队，serial batch 中立即应用
- **Runner 差距**: ToolCallingLoop 等待 LLM 完成后串行执行 → 效率低（TODO-032 已记录）

#### 2.4 Bash Security 全貌
- **4,437 行 across 23 files**: 手写递归下降 AST parser
- Fail-closed allowlist 策略，18 个 blocked Zsh builtins
- 零宽字符注入检测，IFS null-byte 注入防御
- **Runner 差距**: CliTool 零安全检查（TODO-001 已记录，但严重性严重不足）

#### 2.5 ULTRAPLAN
- 未发布功能：cloud container running Opus model 30 分钟执行复杂规划
- 与 KAIROS（always-on daemon）互补
- **启示**: runner 的 SubagentRuntime 应考虑"长时间运行 agent"场景（当前无超时管理）

#### 2.6 autoDream 记忆整合
- 利用用户空闲期执行：合并跨会话观察、消除矛盾、将试探性观察升级为确认事实
- 架构灵感来自生物学的睡眠记忆巩固
- **Runner 差距**: TODO-021 已记录（P3），建议维持 P3 但设计时预留接口

#### 3.2 新兴行业共识（2026 Q2）

1. **"Harness > Model" 共识**: VILA-Lab 论文 (arXiv:2604.14228) 核心结论——foundation model 推理能力趋同后，确定性工程治具成为关键差异化因素。1.6% AI 逻辑 vs 98.4% 基础设施的比例广泛被引用。
2. **MCP 成为事实标准**: Linux Foundation AAIF 下 MCP (tools) + A2A (agent-to-agent) + AG-UI (frontend) 三协议并行，MCP 采纳率最高。
3. **Prompt Caching 是必选项**: Claude API prompt caching 可节省 80% input token 成本；不使用 = 烧钱。
4. **Feature Flags for AI**: Claude Code 44 flags 的模式被多个框架采纳——gated development 允许大胆实验。
5. **"Optimistic Execution" 模式**: OpenAI Agents SDK 的 guardrails 与工具执行并行运行，不是串行校验→执行。
6. **Model-driven over Framework-driven**: AWS Strands 和 Anthropic Agent SDK 都押注让 LLM 自主决定工具使用，而非硬编码的编排图。
7. **OTel 成为通用 Observability 标准**: Google ADK、Vercel AI SDK 6、Semantic Kernel、AWS Strands 全部原生 OTel。Runner 仅有 trace 骨架。
8. **Checkpointing for Durability**: LangGraph、Google ADK、CrewAI Flows 都收敛到持久状态快照支持 interrupt/resume。
9. **Microsoft 统一**: AutoGen + Semantic Kernel 合并为 Microsoft Agent Framework（RC1 2026-02）。
10. **Progressive Disclosure (Google ADK)**: SkillToolset 模式——90% context 缩减，按需加载 schema（类似 TODO-012）。

## Part II: New Architectural Issues Found

### 源码审查发现的新问题（未在之前 TODO 中记录）

### TODO-035: Steer Mode — 中断注入精细控制 [NEW]
- **Reference**: OpenClaw v2026.5 的 steer 模式——在 tool 间隙注入新消息，不全量取消
- **Gap**: InterruptibleRun.interrupt() 是二元操作（全量取消 + 保存断点），无法在 tool 间隙插入新指令
- **现状代码**: `InterruptibleRun.java` — interrupt() 设置 CancellationToken.cancel()，ToolCallingLoop 在下一轮检测到后退出
- **改进方案**:
  - [ ] CancellationToken 扩展为 `InterruptionToken`，支持 `cancel()` 和 `steer(newMessage)`
  - [ ] ToolCallingLoop 每轮检查时区分：cancel → 退出 vs steer → 注入消息继续执行
  - [ ] 实现 `collect` 模式（合并排队消息）和 `steer` 模式（注入 + 跳过 pending tools）
- **Priority**: P2 — 当前 interrupt/resume 可用，steer 是增强

### TODO-036: ToolCallingLoop State Transition Tracking [NEW]
- **Reference**: Claude Code 的 `queryLoop` 维护 `State.transition` 字段，记录上一轮为什么继续
- **Gap**: ToolCallingLoop 只有 iteration counter，无法区分"正常 tool 循环" vs "tool 失败重试" vs "中断恢复"
- **改进方案**:
  - [ ] 添加 `LoopState` enum: `INITIAL`, `TOOL_RESPONSE`, `TOOL_ERROR_RETRY`, `STEER_INJECTION`, `BUDGET_WARNING`
  - [ ] 每轮记录 transition reason，传递给 LLM options 或在 StreamEvent 中暴露
  - [ ] 用于 error recovery 决策（如 tool 连续失败 3 次 → 自动降级）
- **Priority**: P2

### TODO-037: Unified Task Ledger (OpenClaw Task Brain Pattern) [NEW]
- **Reference**: OpenClaw 的 Task Brain——SQLite 后端统一管理 ACP 任务、subagent、cron、后台进程
- **Gap**: Runner 有 3 个独立的状态管理：
  - `SubagentRuntime.activeRuns` (ConcurrentHashMap)
  - `SubagentRuntime.completedRuns` (ConcurrentHashMap)
  - `Orchestrator.runs` (InterruptibleRun map)
- **问题**: 无法统一查询"当前系统中所有执行中的任务"，无法跨组件追踪
- **改进方案**:
  - [ ] 设计 `TaskLedger` 接口 with SQLite/InMemory 实现
  - [ ] 统一 SubagentRun + InterruptibleRun 的生命周期跟踪
  - [ ] 添加 list/query API，支持按 status、agent、session 过滤
  - [ ] 为未来的 cron/heartbeat 任务预留
- **Priority**: P2

### TODO-038: GatewayController Unbounded Thread Pool Leak [NEW]
- **File**: `agent-web/.../gateway/GatewayController.java`
- **Issue**: `Executors.newCachedThreadPool()` 无上限线程增长，无 `@PreDestroy` shutdown
- **Impact**: 高并发下线程泄漏，最终 OOM
- **改进方案**:
  - [ ] 替换为 `Executors.newFixedThreadPool(N)` 或使用 Spring 管理的 `TaskExecutor`
  - [ ] 添加 `@PreDestroy` shutdown 方法
- **Priority**: P1 — 生产环境必修

### TODO-039: Silent Exception Swallowing Pattern [NEW]
- **Files**: 多处 `catch (Exception ignored) {}`:
  - `Tracer.java:55` — exporter 异常静默吞掉
  - `DynamicPluginProvider.java:167` — IOException 静默吞掉
  - `CliTool.java:96, 109` — IOException 静默吞掉
  - `AgentLoop.java:282` — 记忆保存失败静默吞掉
- **问题**: 生产环境无法诊断工具加载失败、记忆丢失、trace 中断等问题
- **改进方案**:
  - [ ] 统一使用 `logger.warn("...", e)` 替代 `// ignored`
  - [ ] 对关键路径（记忆保存、tool 注册）使用 `logger.error()` + metric counter
- **Priority**: P1

### TODO-040: Hardcoded Configuration Values [NEW]
- **Files**: 多处魔法数字应提取为可配置项:
  - `SubagentRuntime.java:220`: `MAX_COMPLETED_CACHE = 200`
  - `ResilientLLMProvider.java:49-50`: `maxRetries=2, initialBackoffMs=1000`
  - `CliTool.java:38`: `timeoutSeconds = 30`
  - `Orchestrator.java:45-46`: `RUN_TTL_MS = 3600000, CLEANUP_INTERVAL_MS = 300000`
  - `ClientToolWrapper.java:58`: `DEFAULT_TIMEOUT_MS = 60_000`

  - [ ] 所有魔法数字通过构造器注入
  - [ ] 提供合理默认值 + 环境变量覆盖
- **Priority**: P2

### TODO-043: Optimistic Guardrail Execution (OpenAI SDK Pattern) [NEW]
- **Reference**: OpenAI Agents SDK 的 guardrails 与工具执行 **并行运行**——不是"先校验再执行"的串行模式
- **Gap**: Runner 的 AgentObserver.onPreToolUse() 是同步拦截，阻塞工具执行
- **改进方案**:
  - [ ] 添加 `OptimisticGuardrail` 接口：并行执行 guardrail 校验和工具调用
  - [ ] 如果 guardrail 在工具完成前触发拒绝，取消工具执行
  - [ ] 如果工具先完成且 guardrail 通过，直接返回结果（零额外延迟）
- **Priority**: P3 — 性能优化，当前串行模式功能正确

### TODO-044: Deferred Tool Schema Loading (Google ADK SkillToolset Pattern) [NEW]
- **Reference**: Google ADK 的 SkillToolset 实现 90% context 缩减——只加载工具名和一句描述，完整 schema 按需获取
- **Gap**: 与 TODO-012 (Deferred MCP Schema) 相似，但 SkillToolset 模式更激进——连内部工具也延迟加载
- **改进方案**:
  - [ ] ToolRegistry 支持"轻量模式"：`getToolDefinitionsLite()` 只返回 name + description
  - [ ] LLM 首次调用时只发送 lite definitions
  - [ ] 当 LLM 返回 tool_use 时，如果 args 不完整，附加完整 schema 后 re-prompt
  - [ ] 大幅减少每次 LLM 调用的 input token 消耗
- **Priority**: P2 — 与 prompt caching 互补的 token 节省策略

### TODO-045: Durable Agent State with Dormancy Gates (Google ADK Pattern) [NEW]
- **Reference**: Google ADK 的 dormancy gates——长时间运行的 agent 可以暂停到持久存储，外部事件唤醒
- **Gap**: Runner 的 agent 生命周期与 WebSocket 会话绑定，断开即丢失
- **改进方案**:
  - [ ] 设计 `AgentCheckpoint`：序列化 AgentLoop 状态（context + memory index + tool state）
  - [ ] 添加 `suspend()` / `resume(checkpointId)` API
  - [ ] 检查点持久化到 SQLite（复用 Task Ledger 基础设施）
  - [ ] 支持 webhook 触发唤醒
- **Priority**: P3 — 长期演进，为 heartbeat/cron 场景铺路

## Part V: Key Design Principles Extracted from Research

### 来自 Claude Code 的架构原则

> "As foundation models converge in reasoning, the deterministic engineering harness becomes the critical differentiator."
> — VILA-Lab, arXiv:2604.14228

1. **Cheapest First, Heaviest Last** — compaction cascade 按成本排序
2. **Cache-Aware Everything** — 任何修改 context 的操作都要考虑 prompt cache 命中率影响
3. **Fail-Closed Security** — allowlist 而非 denylist
4. **Transition-Aware Loop** — 记录"为什么继续"而非只记录"执行了几轮"
5. **Speculative Execution** — 安全的工具可以在 LLM 还在输出时提前执行

### 来自 OpenClaw 的架构原则

1. **File = Config** — 文件即配置（SOUL.md, TOOLS.md, IDENTITY.md, HEARTBEAT.md）
2. **Flush Before Forget** — compaction 前 flush 关键信息到持久存储
3. **Queue Mode Spectrum** — 中断不是二元的，提供多种模式
4. **Coordinator Minimal Privilege** — coordinator agent 只有协调工具，无执行权限
5. **Visible Subagent Tasks** — subagent 任务在对话中可见，不隐藏在 system prompt
