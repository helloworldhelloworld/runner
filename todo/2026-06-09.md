# Architecture Optimization TODO — 2026-06-09

## 研究来源

- **OpenClaw 2026.4**: 五层架构（Input Sources → Integration Gateway → Agent Core → Output/Action → External Systems），runner ADR-004 已参照对齐。[github.com/openclaw/openclaw](https://github.com/openclaw/openclaw)（15K+ stars, MIT）— Node.js 实现，配置优先（SOUL.md 定义 agent），多通道 gateway
- **Claude Code 泄露源码分析**: 学术论文 [arXiv 2604.14228](https://arxiv.org/abs/2604.14228)（Dive into Claude Code）+ [VILA-Lab 分析仓库](https://github.com/VILA-Lab/Dive-into-Claude-Code)。核心发现：
  - Agent loop 仅占 1.6% 代码量，98.4% 是确定性基础设施（权限、上下文管理、工具路由、恢复）
  - 权限系统：7 种模式 + ML 分类器
  - 上下文管理：3 层压缩 — MicroCompact（局部）→ AutoCompact（接近 ceiling 自动触发，13K buffer，最大 20K summary）→ Full Compact（全对话）
  - 工具系统：每个 tool 自定义 input schema + permission level + execution logic
  - 可扩展性：MCP + plugins + skills + hooks 四种机制
  - Subagent 委派 + worktree 隔离
- **开源社区最佳实践**: LangGraph (graph-based agent)、AutoGen (multi-agent conversation)、CrewAI (role-based orchestration)、Spring AI (Java生态)、Semantic Kernel (plugin/planner)
- **Spring AI 2025-2026**: `@Tool` 注解声明式工具定义、`@ToolParam` 参数描述、Tool Argument Augmenter 动态增强输入 schema。[官方文档](https://docs.spring.io/spring-ai/reference/api/tools.html) | [Augmenter 博客](https://spring.io/blog/2025/12/23/spring-ai-tool-argument-augmenter-tzolov/)

### 关键验证结论

runner 的核心架构（Agent Loop + ToolRegistry + Reactive Streaming + ContextCompactor）与 Claude Code 实际架构高度对齐，这是编码 Agent 领域的 proven pattern。主要差距在于：权限分级精细度、上下文压缩的自动触发机制（AutoCompact）、以及 Tool Argument Augmenter 模式

## 一、Critical — 线程安全与数据完整性

### TODO-001: InterruptibleRun StringBuilder 线程安全
- **文件**: `agent-kernel/.../orchestrator/InterruptibleRun.java`
- **问题**: `accumulatedText` 是 `StringBuilder`（非线程安全），在 reactive 流中被多线程 append，与 interrupt() 并发访问存在数据竞争
- **对标**: Claude Code 使用 immutable event accumulator 模式，每个 event 产生新的 snapshot
- **修复方案**: 
  1. 替换为 `StringBuffer` (最小改动) 
  2. 或使用 `AtomicReference<String>` + CAS append
  3. 推荐: 采用不可变累积模式，`accumulatedText` 改为 `AtomicReference<StringBuilder>` 并在 interrupt() 中使用 `getAndSet(new StringBuilder())`
- **优先级**: P0

### TODO-002: ToolCallingLoop 错误静默吞没
- **文件**: `agent-kernel/.../core/ToolCallingLoop.java`
- **问题**: `doOnError(e -> tracer.endSpanWithError(llmSpan, e))` 只 trace 不传播，客户端收不到 ERROR event；Observer 异常被 `catch (Exception ignored) {}` 吞掉
- **对标**: LangGraph 每个 node 失败后 emit 显式 error event 并支持 fallback edge；Claude Code 有 error recovery + user-visible error message 机制
- **修复方案**:
  1. 在 `doOnError` 中 emit `StreamEvent.error(e)` 再 propagate
  2. Observer 异常至少 log.warn()
  3. 添加 `onErrorResume` 策略：可配置 retry / fallback / propagate
- **优先级**: P0

## 二、High — 性能与韧性

### TODO-003: ToolExecutor 缺少 per-tool 超时
- **文件**: `agent-kernel/.../core/ToolExecutor.java`
- **问题**: server-side 并行工具执行使用 `CompletableFuture.allOf()` 无超时，一个 tool hang 住阻塞整个 batch。client-side 有 `clientToolTimeoutMs` 但 server-side 无对等机制
- **对标**: 
  - Claude Code: 每个 tool 有独立超时（bash 120s, read/write 30s, web 60s），超时后 kill + 返回 timeout error
  - Spring AI: `ToolCallback` 支持 `@Tool(timeout=...)` 注解
  - AutoGen: tool executor 有 per-tool timeout + cancellation
- **修复方案**:
  1. Tool 接口增加 `default Duration getTimeout()` 方法（默认 60s）
  2. ToolExecutor 使用 `CompletableFuture.orTimeout(tool.getTimeout())` 
  3. 超时时 emit `TOOL_ERROR` event 并继续其他 tool
  4. application.yml 增加全局 `tool.default-timeout` 配置
- **优先级**: P1

### TODO-004: ClaudeProvider 同步阻塞 HTTP 调用
- **文件**: `agent-kernel/.../llm/claude/ClaudeProvider.java`
- **问题**: `complete()` 用 OkHttp `execute()` 同步阻塞；`completeStream()` 用 `BufferedReader.readLine()` 阻塞。虽然 `supplyAsync()` 移到单独线程池，但使用的是 `ForkJoinPool.commonPool()` 而非 bounded I/O 线程池
- **对标**: OpenRouterProvider 使用 `Schedulers.boundedElastic()`；Spring AI 的 ChatClient 全异步
- **修复方案**:
  1. 使用 OkHttp 的 `enqueue(Callback)` 异步 API
  2. 或统一使用 `Schedulers.boundedElastic()` 替代 `ForkJoinPool.commonPool()`
  3. streaming 改用 Reactor `Flux.push()` + OkHttp async callback
- **优先级**: P1

### TODO-005: SubagentRuntime 拒绝策略缺失
- **文件**: `agent-kernel/.../orchestrator/SubagentRuntime.java`
- **问题**: `executor.submit()` 无 `RejectedExecutionHandler`，虽然有 `synchronized` 计数保护，但 shutdown 期间的 submit 仍可能抛 `RejectedExecutionException`
- **对标**: Claude Code subagent 有明确的 capacity error 返回给 LLM，LLM 会调整策略（减少并发 spawn）
- **修复方案**:
  1. 添加 `CallerRunsPolicy` 或自定义 rejection handler
  2. Rejection 时 emit `SUBAGENT_ERROR` event（reason: capacity_exceeded）
  3. 返回有意义的错误信息给 LLM，引导其减少并发
- **优先级**: P1

## 三、Medium — 架构改进

### TODO-006: 引入 Tool Input Validation 层
- **问题**: ToolExecutor 不校验 LLM 传来的 args 是否符合 ToolSchema，可能传入 null/错误类型
- **对标**:
  - Claude Code: tool args 经过 JSON Schema 校验，不合法时返回 validation error 让 LLM 重试
  - Semantic Kernel: `KernelFunction` 有参数类型推断 + 自动转换
  - LangChain: Pydantic model 做参数校验
- **修复方案**:
  1. 添加 `ToolInputValidator` 在 ToolExecutor.execute 前校验 args vs ToolSchema
  2. 校验失败时返回 `ToolResult.error("Invalid input: ...")` 让 LLM 修正
  3. 使用 `everit-org/json-schema` 或 `networknt/json-schema-validator`
- **优先级**: P2

### TODO-007: CostTracker 超预算优雅终止
- **问题**: 超预算时 ToolCallingLoop 直接 exit 返回 `[cancelled]`，LLM 丢失上下文，用户看不到原因
- **对标**:
  - Claude Code: 接近限额时插入 system message 提示 LLM 总结并收尾
  - LangGraph: budget exhaustion 是一个 graph edge，可以路由到 summarization node
- **修复方案**:
  1. 新增 `EventType.BUDGET_WARNING` 和 `BUDGET_EXCEEDED`
  2. 接近 80% 预算时 inject system hint: "Token budget nearly exhausted, please summarize"
  3. 超预算时 emit `BUDGET_EXCEEDED` event 而非静默退出
  4. 前端展示预算消耗进度
- **优先级**: P2

### TODO-008: ContextCompactor 与 Memory Search 时序问题
- **问题**: AgentLoop 中 Memory search 在 compaction 之前执行，compactor 可能删除 memory search 赖以判断 relevance 的上下文
- **对标**:
  - Claude Code: context window management 是分层的 — 先 compact 历史，再用 compacted context 做 retrieval
  - LangGraph: retrieval node 接收的是已经 pruned 的 state
- **修复方案**:
  1. 调整执行顺序: compact first → memory search with compacted context
  2. 或: memory search 使用独立的 relevance scoring（不依赖 full context）
  3. 评估影响后决定方案
- **优先级**: P2

### TODO-009: 分布式追踪 (OpenTelemetry) 集成
- **问题**: `TraceContext` 是自研的，不支持标准 OpenTelemetry。Subagent 创建新 UUID 但无 parent-child span 关系
- **对标**:
  - Spring AI: 原生 Micrometer + OpenTelemetry 集成
  - LangSmith / LangFuse: LangChain 生态的标准追踪方案
  - Claude Code: 内部使用结构化 trace，每个 tool call 有 parent span
- **修复方案**:
  1. 引入 `opentelemetry-api` + `opentelemetry-sdk`
  2. Tracer 适配 OpenTelemetry `Span` API
  3. LLM call、tool execution、subagent spawn 自动创建 span
  4. 支持 Jaeger / Zipkin exporter
- **优先级**: P2

### TODO-010: MCP Progress 事件丢失
- **问题**: `ProgressRouter` 返回的 Flux 在 client disconnect 时 dispose，progress 更新丢失。长时间运行的 MCP tool 用户看不到进度
- **对标**: Claude Code MCP 集成有独立的 progress tracking，不依赖 client 连接存活
- **修复方案**:
  1. ProgressRouter 解耦 progress 聚合与 Flux 生命周期
  2. 添加 `ProgressStore` 持久化进度状态
  3. 客户端重连后可查询历史 progress
- **优先级**: P2

## 四、Low — 代码质量与可维护性

### TODO-011: MicroCompactor 负数边界
- **文件**: `agent-kernel/.../context/MicroCompactor.java`
- **问题**: 当 `text.length() < keepChars * 2` 时 `snippedCount` 可能为负数
- **修复方案**: 添加 `if (text.length() <= keepChars * 2) return text;` 前置检查
- **优先级**: P3

### TODO-012: ScopedToolRegistry 缺少方法覆盖审计
- **问题**: `registerAll()`, `clear()`, `disable()/enable()` 未覆盖，可能绕过权限检查
- **修复方案**: 
  1. 审计 ToolRegistry 所有 public 方法
  2. ScopedToolRegistry 覆盖所有涉及 tool 可见性的方法
  3. 添加测试: 通过 parent 修改 tool，验证 scoped view 正确过滤
- **优先级**: P3

### TODO-013: 废弃包清理
- **问题**: `.instruction`, `.skill` (旧版), `.plugin` 包标记 @Deprecated 但仍有引用
- **修复方案**: 
  1. 梳理所有引用点，迁移到新 API（PromptEngine、Tool）
  2. 添加 `@Deprecated(forRemoval = true)` 注解
  3. 制定 deprecation timeline（2个版本后移除）
- **优先级**: P3

## 五、新能力 — 参考社区最佳实践

### TODO-014: 引入 Structured Output / Response Format
- **背景**: Claude API 支持 `response_format` (JSON mode) 和 tool_use 结构化输出
- **对标**:
  - Spring AI: `ChatClient.prompt().call().entity(MyClass.class)` 自动解析
  - LangChain: `with_structured_output()` 方法
  - Semantic Kernel: `KernelFunction` 自动 serialize/deserialize
- **方案**: LLMOptions 增加 `responseFormat` 字段，LLMProvider 传递到 API 请求

### TODO-015: Graph-based Agent Orchestration (长期)
- **背景**: 当前 Orchestrator 是 Router + AgentLoop 线性链路，复杂工作流（条件分支、并行-汇聚、循环）需要手写 SubagentRuntime 编排
- **对标**:
  - LangGraph: 有向图 (nodes = agents/tools, edges = conditions)，支持 checkpoint + resume
  - AutoGen: GroupChat + sequential/round-robin/custom speaker selection
  - CrewAI: Process types (sequential, hierarchical)
- **方案**: 
  1. 短期: AgentProfile 增加 `workflow` 字段定义简单 DAG
  2. 长期: 引入 `WorkflowEngine`，支持 node/edge 定义 + conditional routing + parallel fork-join
- **注意**: 这是大型改造，需要独立 ADR 讨论

### TODO-016: Agent Memory 增强 — Persistent Memory + RAG
- **背景**: 当前 memory 三层（session/ephemeral/durable）但 durable memory 是全量注入 system prompt，随知识增长会溢出
- **对标**:
  - Claude Code: CLAUDE.md + project knowledge 是 selective injection
  - LangChain: VectorStoreRetriever + ConversationalRetrievalChain
  - AutoGen: Teachable agent with persistent memory
  - MemGPT/Letta: 分层 memory 管理（core/archival/recall）
- **方案**:
  1. Durable memory 从全量注入改为 top-K retrieval
  2. 引入 embedding-based similarity search（kernel-memory 已有 vector 支持）
  3. 添加 memory tool: `save_memory`, `search_memory`（让 agent 自主管理记忆）

### TODO-017: Permission / Confirmation Model
- **背景**: 当前 tool 只有 `isAutoExecute()` 开关，缺少分级权限
- **对标**:
  - Claude Code: 三级权限 — auto-allow, ask-user, deny。按 tool 类型、参数模式、目录范围精细控制
  - Semantic Kernel: `FunctionInvocationFilter` 拦截链
- **方案**:
  1. Tool 增加 `PermissionLevel` enum: AUTO, CONFIRM, DENY
  2. AgentObserver.onPreToolUse 支持返回 ALLOW/DENY/ASK_USER
  3. 前端实现确认弹窗，WebSocket 双向通信

### TODO-018: Retry / Resilience 模式标准化
- **问题**: 各 LLMProvider 的 retry 逻辑不统一，有的有 ResilientLLMProvider wrapper，有的没有
- **对标**:
  - Spring AI: 统一 `RetryTemplate` 配置
  - LangChain: `RetryOutputParser` + `RunnableRetry`
  - 通用: Resilience4j circuit breaker + retry + rate limiter
- **方案**:
  1. 引入 Resilience4j 替代自研 retry
  2. 统一配置: `llm.retry.max-attempts`, `llm.retry.backoff`, `llm.circuit-breaker.threshold`
  3. 暴露 metrics 到 Micrometer

### TODO-019: 5 层 Context Compaction Pipeline（对标 Claude Code）
- **背景**: runner 目前只有 2 层压缩（Snip + Micro），Claude Code 泄露源码揭示了 5 层流水线，按成本从低到高依次执行：
  1. **Budget Reduction** — 基础截断
  2. **Snip** — 截断缓存的 tool 输出（runner 已有）
  3. **Microcompact** — 轻量压缩（runner 已有）
  4. **Context Collapse** — 结构化压缩（合并相邻同角色消息、折叠重复 tool 调用模式）
  5. **Auto-Compact** — 接近 context ceiling 时自动生成 ≤20K token 的结构化摘要，附带最近访问的文件（每个 ≤5K token）、活跃计划、相关 skills
- **关键差距**: runner 缺少 Context Collapse 和 Auto-Compact 层，在长对话场景下 context 利用率低
- **方案**:
  1. CompactionChain 新增 `ContextCollapseCompactor`：合并连续同 role 消息、折叠重复 tool 模式
  2. 新增 `AutoCompactor`：监控 token 使用量，接近阈值（如 80%）时调用 LLM 生成摘要替换历史
  3. 配置化：`context.compaction.auto-compact-threshold=0.8`, `context.compaction.summary-max-tokens=20000`
  4. Auto-Compact 摘要后附加 recently accessed files 和 active plans（参考 Claude Code 设计）
- **优先级**: P1（长对话场景的核心能力）

### TODO-020: Session 序列化防竞态（对标 OpenClaw）
- **背景**: OpenClaw 使用 "session lane" 模式——每个 session key 的 run 是序列化的，写锁在 streaming 前获取，transcript 重写/压缩/截断共用同一锁，从根源上防止 session 内竞态
- **当前问题**: runner 的 InterruptibleRun 依赖 `synchronized` 细粒度锁 + `volatile` 字段，但 interrupt() 与 streaming 之间的 happens-before 关系不够强
- **方案**:
  1. 引入 per-session `ReentrantReadWriteLock`：streaming 持读锁，interrupt/compact 持写锁
  2. 或采用 single-writer 模式：每个 session 的所有状态变更通过单线程 `SerialExecutor` 串行化
  3. 评估 OpenClaw session lane 模式在 Java Reactor 环境下的可行性
- **优先级**: P1（与 TODO-001 关联，可一并解决）

### TODO-021: A2A (Agent-to-Agent) 协议支持
- **背景**: Google 2025 年发布 A2A 协议，已有 150+ 组织支持。MCP 解决 agent-to-tool，A2A 解决 agent-to-agent 跨运行时通信。Microsoft Agent Framework 1.0、Spring AI、CrewAI 均已集成
- **当前状况**: runner 的 SubagentRuntime 是进程内 spawn，无法跨运行时调用外部 agent
- **方案**:
  1. 短期: 了解 A2A 协议规范，评估与 SubagentRuntime 的集成点
  2. 中期: 实现 `A2AAgentClient`，支持 discover + invoke 外部 agent
  3. 长期: runner 自身暴露为 A2A server，让其他框架的 agent 调用 runner agent
- **优先级**: P3（长期方向，MCP 优先级更高）

### TODO-022: KAIROS 式后台记忆巩固
- **背景**: Claude Code 的 KAIROS 是一个 always-on 后台守护进程，执行 `autoDream` 流程：合并观察、消除矛盾、将 insight 转化为可操作事实。MEMORY.md 是轻量索引（~150 chars/行），topic files 存储实际数据
- **当前状况**: runner 的 memory 三层（session/ephemeral/durable）是被动的，ephemeral 日志不会自动整合到 durable knowledge
- **方案**:
  1. 新增 `MemoryConsolidator` 后台任务（ScheduledExecutorService）
  2. 定期扫描 ephemeral memory，使用 LLM 提取 key insights
  3. 自动更新 durable memory index（类似 MEMORY.md 的 pointer 结构）
  4. 去重 + 矛盾检测：新 insight 与已有 durable memory 对比
- **优先级**: P3（前沿能力，需要 TODO-016 RAG 增强先完成）

### TODO-023: Spring AI Advisors 模式借鉴
- **背景**: Spring AI 的 Advisors API 是 middleware chain 模式（类似 Servlet Filter），composable building blocks 用于 Memory、RAG、tool calling 拦截。当前 runner 的 AgentObserver 是 callback 模式（onPre/onPost），不支持链式组合和短路
- **对标**:
  - Spring AI: `RequestResponseAdvisor` chain with `order()` priority
  - LangChain: `RunnableMiddleware` 可组合管道
  - Semantic Kernel: `FunctionInvocationFilter` 拦截链
- **方案**:
  1. 新增 `AgentAdvisor` 接口：`before(context) → context | abort`, `after(context, result) → result`
  2. AgentLoop 支持注入 advisor chain，按 `@Order` 排序执行
  3. 内置 advisor: `MemoryAdvisor`, `RagAdvisor`, `CostLimitAdvisor`, `PermissionAdvisor`
  4. AgentObserver 保留兼容但标记 `@Deprecated`
- **优先级**: P2（架构演进，提升可组合性）
