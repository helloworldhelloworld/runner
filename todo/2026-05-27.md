### TODO-054: WebSocket Transport — HttpClient 连接泄漏 + 竞态 + 重连缺陷（6 个子问题）

**文件**: `agent-mcp/.../transport/WebSocketMcpClientTransport.java`

**问题 1 — HttpClient 连接泄漏** (L90-92):
`connect()` 每次调用都创建新的 `HttpClient.newBuilder().build()`，包括重连时（L236）。JDK HttpClient 内部维护连接池和选择器线程。重连 10 次 = 10 个 HttpClient 实例泄漏，旧 WebSocket 也未关闭。

**问题 2 — connected/webSocket 赋值竞态** (L98 vs L148):
`InboundListener.onOpen()` 设置 `connected = true`（L148），但 `this.webSocket = ws` 在 `thenAccept`（L98）中赋值。`onOpen` 先于 `thenAccept` 触发，存在窗口期 `connected == true` 但 `webSocket == null`。`sendMessage()` 虽有 `|| ws == null` 保护（L105），但会返回误导性错误 "not connected"。

**问题 3 — 重连前未关闭旧 WebSocket** (L234-236):
`scheduleReconnect()` 调用 `connect(this.handler)` 但从未关闭旧 WebSocket。server 侧看到两个 open 连接，可能导致重复消息。

**问题 4 — reconnect subscribe() 无错误处理** (L235):
`connect(this.handler).subscribe()` 无 error handler，连接失败时异常被静默丢弃（`Operators.onErrorDropped`），transport 进入死状态。

**问题 5 — sendMessage 连接检查在 assembly time** (L103-106):
连接检查在 `Mono.defer` 外部执行（eager），而非 subscription time（lazy）。如果 caller 先构造 Mono、再连接、再 subscribe，仍会得到错误。

**问题 6 — closeGracefully 不等待 close 握手** (L126):
`ws.sendClose()` 返回的 `CompletionStage` 被丢弃，close frame 可能未实际发送。

**问题 7 — 重连后无 MCP session 重新 initialize**:
代码注释已说明此限制。但 MCP WebSocket Transport SEP-1287 要求 `mcpSessionId` 实现 session 持久化。

**Action**:
- [ ] `HttpClient` 提升为实例变量，connect() 复用
- [ ] `webSocket` 赋值移到 `onOpen` 中，或 `connected` 移到 `thenAccept` 中
- [ ] reconnect 前关闭旧 WebSocket：`old.sendClose(NORMAL_CLOSURE, "reconnecting")`
- [ ] reconnect 添加 error handler：`subscribe(null, ex -> { logger.warn(...); scheduleReconnect(); })`
- [ ] sendMessage 整体包裹在 `Mono.defer` 内
- [ ] closeGracefully 返回 `Mono.fromFuture(ws.sendClose(...))`
- [ ] 添加 `reconnectCallback: Runnable` 参数（由 McpToolClient 传入 re-initialize 逻辑）
- **Priority**: P1 — 连接泄漏 + 竞态 + session 不一致
- **Effort**: 2d

### TODO-055: WebSocket InboundListener.buffer 线程安全问题

**文件**: `agent-mcp/.../transport/WebSocketMcpClientTransport.java:144-174`

**问题**: `InboundListener` 内部用 `StringBuilder buffer` 拼接分片消息。JDK WebSocket.Listener 的 `onText()` 文档说明回调在单线程执行（前一个 CompletionStage 完成前不会调下一个），但：
1. `onClose()` 和 `onError()` 可能与 `onText()` 并发——此时 buffer 可能处于不完整状态
2. 重连后旧 Listener 的 buffer 可能还有残留数据（connect() 创建新 InboundListener，但旧 listener 的 onClose 可能先触发）
3. `StringBuilder` 不是线程安全的——如果 JDK 实现在边界条件下从不同线程回调，会导致内存损坏

**问题 2 — 无消息大小限制**:
`buffer.append(data)` 无限追加。如果恶意 MCP server 发送超大分片消息（如 100MB），会导致 OOM。

**Action**:
- [ ] 在 `onText()` 中添加 buffer 大小检查（如 maxMessageSize = 10MB）
- [ ] 超过限制时清空 buffer + 断开连接 + 记录错误
- [ ] 在 `onClose()`/`onError()` 中清空 buffer 防止残留
- [ ] 考虑在 connect() 时清理旧 listener 引用
- **Priority**: P1 — 安全（OOM 攻击向量）
- **Effort**: 0.5d

### TODO-056: McpToolClient.discoveredTools 可见性 + ToolClient.mcpClients 可变性问题

**文件**: 
- `agent-mcp/.../McpToolClient.java:47` — `private List<McpToolWrapper> discoveredTools;`
- `agent-mcp/.../ToolClient.java:53` — `private final List<McpToolClient> mcpClients;`

**问题 1 — discoveredTools 非 volatile**:
`discoveredTools` 在 `discoverMcpTools()` 中赋值（L109），在 `currentToolNames()`、`getDiscoveredTools()`、`applyToolListChange()` 中读取。赋值线程（initialize 线程）可能与读取线程（toolsChangeConsumer 回调线程、refreshScheduler 线程）不同。无 volatile 标记 = 读线程可能看到 null 或旧值。

**问题 2 — ToolClient.mcpClients Builder 共享**:
`Builder` 直接传递 `builder.mcpClients`（ArrayList 引用）给 `ToolClient`（L58），而非拷贝。如果 Builder 在 build() 后被复用或持有引用，外部可以修改 ToolClient 的 mcpClients 列表。

**问题 3 — applyToolListChange 非原子**:
`applyToolListChange()` 先赋值 `this.discoveredTools = wrappers`（L371），再注册/注销 registry（L375-382）。如果 refreshTools() 同时在另一个线程运行，两个线程可能交叉注册/注销，导致 registry 状态不一致。

**Action**:
- [ ] `discoveredTools` 标记为 `volatile`，或改用 `AtomicReference<List<McpToolWrapper>>`
- [ ] ToolClient 构造器拷贝 mcpClients：`this.mcpClients = new ArrayList<>(builder.mcpClients)`
- [ ] `applyToolListChange` 和 `refreshTools` 加 `synchronized(this)` 或使用 lock
- **Priority**: P2 — 并发正确性
- **Effort**: 0.5d

### TODO-057: WebSocket Transport 缺少 TLS 证书验证配置 + URI Scheme 校验

**文件**: `agent-mcp/.../transport/WebSocketMcpClientTransport.java:69-71`

**问题 1 — 无 TLS 配置接口**:
Builder 不支持自定义 SSLContext / TrustManager。生产环境中 MCP server 可能使用自签证书或内部 CA——没有 TLS 配置意味着要么无法连接，要么开发者会绕过证书验证（更危险）。

**Reference**: MCP Security Best Practices 2026 明确要求 "Clients must validate certificate chains and not ignore certificate errors"。

**问题 2 — URI Scheme 未校验**:
构造器接受任意 URL（L70: `this.uri = URI.create(builder.url)`），不检查是否为 `ws://` 或 `wss://` scheme。如果传入 `http://` URL，会在 buildAsync 时抛出非直觉错误。

**问题 3 — ToolClient.createTransport URL 替换不完整**:
`ToolClient.Builder.createTransport()` 中：
```java
String wsUrl = config.getUrl()
    .replaceFirst("^http://", "ws://")
    .replaceFirst("^https://", "wss://");
```
如果 URL 已经是 `ws://` 或 `wss://`，不做替换（正确）。但如果是 `ftp://` 或无 scheme，会原样传递导致运行时失败。

**Action**:
- [ ] Builder 添加 `sslContext(SSLContext)` 配置方法
- [ ] URI 构造时校验 scheme 必须是 `ws` 或 `wss`
- [ ] ToolClient.createTransport 添加 scheme 校验和友好错误信息
- **Priority**: P2 — 安全 + 可用性
- **Effort**: 1d

### TODO-058: ToolClient.addMcpServer 不继承全局 headerProvider

**文件**: `agent-mcp/.../ToolClient.java:94-106`

**问题**: `ToolClient.addMcpServer(name, transport, timeout)` 运行时动态添加 MCP server 时，直接使用传入的 transport，不应用 `headerProvider`。但 Builder 阶段通过 `fromConfig()` 创建的 transport 会应用 headerProvider（三层 header 合并）。

这导致：
- Builder 阶段创建的 MCP client = 有 auth header
- 运行时动态添加的 MCP client = 无 auth header
- 如果 MCP server 需要认证，运行时添加的 client 会 401

**对比**: Builder 内部的 `addMcpServer()` 也不继承 headerProvider（L360-370），但至少调用方可以自己构造带 header 的 transport。运行时的 `addMcpServer()` 应该提供 header 注入点。

**Action**:
- [ ] 在 ToolClient 中保存 headerProvider 引用
- [ ] addMcpServer 提供 overload：`addMcpServer(name, config)` 使用 Builder.createTransport 自动构造
- [ ] 或者在 ToolClient 级别提供 `withHeaders()` wrapper 用于动态添加场景
- **Priority**: P2 — API 一致性
- **Effort**: 0.5d

### TODO-060: Memory Providence Labels — 可信度标记

**Reference**: OpenClaw 2026.4+ Memory 模型引入 providence labels：
- `observed`: 从外部来源直接获取（如 tool result）
- `confirmed`: 用户明确确认的信息
- `inferred`: 模型推断的信息（可信度较低）
- `imported`: 从 transcript 或历史会话导入

**关键洞见**: "The providence labels aren't bureaucracy — they're what makes the memory trustworthy when the brain changes." — 当 LLM 模型升级或提示词变更时，inferred 类型的记忆可能需要重新验证。

**Runner 现状**:
- MemoryProvider 的 3 层记忆（Session/Ephemeral/Durable）不区分信息来源
- 所有 memory 条目同等对待——tool result、用户确认、LLM 推断混在一起
- 当 ContextCompactor 需要裁剪时，无法优先保留高可信度信息
- Durable memory 可能包含 LLM 推断的错误信息，永久污染上下文

**Action**:
- [ ] `Memory` 或 `MemoryEntry` 添加 `ProvenanceLabel` 枚举：OBSERVED, CONFIRMED, INFERRED, IMPORTED
- [ ] `MemoryProvider.addMessage()` 接受 provenance 参数
- [ ] SnipCompactor 裁剪时优先删除 INFERRED > IMPORTED > OBSERVED > CONFIRMED
- [ ] Durable memory 写入时标记来源，定期审计 INFERRED 条目
- **Priority**: P3 — 长期记忆质量
- **Effort**: 2d

### TODO-061: Streaming Tool Execution — 模型还在输出时开始执行已完成的 tool_use

**Reference**: Claude Code 的 `StreamingToolExecutor` 在模型还在流式输出时就开始执行已完成的 tool_use blocks（RWLock 并发控制）。这是显著的延迟优化——不需要等待整个 LLM 响应完成。

**OpenClaw 对照**: `steer` 模式将新用户消息注入到 tool 间隙，跳过未完成的 tool calls。

**Runner 现状**:
- `ToolCallingLoop.executeReactiveLoop()` 使用 `concatWith(Flux.defer(...))` 模式——等 LLM 流完全结束后才开始工具执行
- 如果 LLM 一次返回 5 个 tool_use，第 1 个 tool_use 在流的前 10% 就已完成，但要等到 100% 流完成后才开始执行
- 对于长输出 + 多工具的场景，这浪费了大量并行执行时间

**Action**:
- [ ] 在 Flux pipeline 中监听 `content_block_stop` (tool_use) 事件，立即触发该工具的执行
- [ ] 使用 ReadWriteLock：读操作（查询）并行，写操作（文件修改）独占
- [ ] 工具结果缓存，等 LLM 流完成后统一收集并构造下一轮 messages
- [ ] 需评估对 CancellationToken 和 CostTracker 的影响
- **Priority**: P2 — 性能优化
- **Effort**: 3d
- **Note**: 需在 TODO-049（统一执行路径）之后实施

### Claude Code 12 Hook Events 完整模型（2026.5 最新文档）

| Event | When | Can Block? | Key Capability |
|---|---|---|---|
| **PreToolUse** | Before ANY permission check | ✅ deny/allow/ask | Modify tool input, append context |
| **PostToolUse** | After tool success | ❌ | Reactive: format, test, log |
| **Notification** | Status, progress | ❌ | UI updates |
| **Stop** | Agent exits | ❌ | Cleanup |
| **SubagentStop** | Subagent exits | ❌ | Cascade cleanup |
| **SessionStart** | New session | ❌ | Setup hooks |
| **SessionEnd** | Session close | ❌ | Teardown |
| **PermissionRequest** | At approval boundary | ✅ | Override permission mode |
| **Error** | Any error | ❌ | Recovery hooks |
| **CompactionStart** | Before compaction | ❌ | Pre-flush memory |
| **CompactionEnd** | After compaction | ❌ | Post-compaction actions |
| **ModelSwitch** | Provider/model change | ❌ | Cache invalidation |

**关键设计差异**:
1. **PreToolUse fires BEFORE permission check** — 这意味着 hook 可以在 permission 系统之前就 deny 一个操作。即使在 `--dangerously-skip-permissions` 模式下，hook deny 仍然生效。
2. **4 种 handler 类型**: Command (shell), Prompt (LLM), Agent (subagent), HTTP (webhook)
3. **4 种 decision**: allow, deny, ask (需用户确认), defer (交下游)
4. **Input modification**: PreToolUse 可以修改 tool_input 参数（参数消毒/注入）

**Runner TODO-047 需升级**: 不仅是返回 HookDecision，还需要支持 input modification 和 fires-before-permission 语义。
