## Deep Research Findings: 2026-05-17

### I. Claude Code 泄露源码深度分析 (v2.1.88, 512K行 TypeScript)

**来源**: npm package `@anthropic-ai/claude-code` 源码泄露 (2026.3.31)，VILA-Lab 学术分析 (arXiv:2604.14228)，多篇逆向工程报告。

#### 1. 核心架构：AsyncGenerator Agent Loop ("nO")

Claude Code 的核心是一个 `async function*` (AsyncGenerator) 实现的 while 循环：

```
assemble context → call model → dispatch tools → check permissions → execute → repeat
```

**关键设计选择**：
- 循环在 LLM 返回无 tool_use 时终止（与 Runner 的 ToolCallingLoop 相同模式）
- 一个 "turn" = 一次往返：LLM 输出 → 工具执行 → 结果回送
- **只有 1.6% 是 AI 决策逻辑，98.4% 是基础设施代码**
- 5 种核心事件类型：SystemMessage, AssistantMessage, UserMessage, RequestStartEvent, TombstoneMessage

**Runner 对比**: Runner 的 ToolCallingLoop.executeReactiveLoop() 已实现相同模式，结构合理。但 AgentLoop 的同步路径 (run()) 和流式路径 (runStream()) 没有统一到 reactive 路径，造成功能差异。

#### 2. 五级 Context Compaction Pipeline

Claude Code 实现了渐进式压缩：

| Level | 名称 | 触发条件 | 策略 |
|-------|------|---------|------|
| 1 | Budget Reduction | 始终 | 截断超大 tool output |
| 2 | Snip | 对话历史过长 | 删除旧消息 |
| 3 | Microcompact | cache 开销过大 | 轻量压缩 |
| 4 | Context Collapse | 历史极长 | 折叠整段对话 |
| 5 | Auto-compact | 最后手段 | LLM 自我总结（可配置） |

**设计原则**: **Lazy degradation** — 先用最轻量的策略，不够再升级。

**Runner 对比**: 仅有 Level 1-2 (MicroCompactor ≈ Budget Reduction, SnipCompactor ≈ Snip)。缺少 Level 4-5 的高级压缩策略。且 Runner 没有基于 token 计数的触发阈值（因为 TokenCounter 未实现 —— TODO-030）。

#### 3. 三层记忆架构

| Layer | Claude Code | Runner |
|-------|------------|--------|
| L1: In-Context | 活跃对话窗口 | Session Memory (MemoryProvider.getHistory) |
| L2: External File | `memory.md` 指针索引 → 主题文件 | Ephemeral Memory (日志文件) |
| L3: Static Config | `CLAUDE.md` (项目配置) | Durable Memory (长期知识) |

**关键差异**: Claude Code 的 L2 是一个**指针索引文件**，指向多个主题记忆文件。Runner 的 Ephemeral Memory 是日期分割的日志，缺少主题化组织。

#### 4. 权限模型：五种模式 + ML 分类器

| Mode | 行为 |
|------|------|
| Default | 危险操作需用户确认 |
| acceptEdits | 文件编辑自动通过 |
| dontAsk | 全部阻止 |
| bypassPermissions (YOLO) | 全部通过 |
| Auto | ML 分类器决定 |

**Auto Mode 的 yoloClassifier** (1,495 行):
- **Stage 1 (Fast Path)**: Sonnet 4.6, max_tokens=64, 低延迟
- **Stage 2 (Thinking Path)**: 如果 Stage 1 不确定，用 CoT 推理
- 评估三类风险：Scope Escalation, Untrusted Infrastructure, Prompt Injection
- **Fail-closed**: 分类器不可用时拒绝操作
- **Denial tracking**: 3 次连续或 20 次总拒绝 → 升级到人工审核

**Runner 对比**: ScopedToolRegistry 仅有 deny > allow 二元控制。无风险分级，无 ML 分类器。

#### 5. Bash 安全：4,437 行，23 个文件

- 使用 **tree-sitter-bash** WASM 构建完整 AST
- **手写递归下降解析器** (不依赖外部 shell parser)
- 25+ 验证器链（regex + shell-quote + AST 分析）
- 已知漏洞：CR 注入（`shell-quote` 的 `\s` 将 CR 视为分词符，但 bash 的 IFS 不包含 CR）

**Runner 对比**: CliTool 完全无安全检查。差距巨大。

#### 6. Hooks 系统：4 种处理器类型

| Type | 能力 |
|------|------|
| Command | Shell 脚本 |
| HTTP | Webhook POST |
| Prompt | 单轮 Claude yes/no 评估 |
| Agent | 启动 subagent |

- **PreToolUse**: 唯一可阻止操作的 hook (exit code 2)
- **PostToolUse**: 操作后检查/格式化
- **Stop**: Claude 完成任务时触发 (exit code 2 可强制继续)
- **Notification**: 消息/里程碑通知

**Hooks guarantee execution** — 与 prompt 指令不同，hooks 保证执行。

**Runner 对比**: AgentObserver 是开发者级别的 Java 接口 (onPreToolUse/onPostToolUse)。缺少：用户可配置 hooks、Shell/HTTP/Agent handler、阻止能力。

#### 7. 多 Agent 架构：双路径

| Path | 机制 | 隔离 |
|------|------|------|
| Lightweight (In-Process) | 同一 Node.js 进程，AsyncLocalStorage 隔离 | 内存级 |
| Pane-Based (Cross-Process) | **文件邮箱** (~/.claude/work/ipc/) | 进程级 |

**文件邮箱**: Leader 每 500ms 轮询 inbox 文件。优势：跨进程工作、断连存活、有审计轨迹、无守护进程。

**Runner 对比**: SubagentRuntime 是线程池 + ConcurrentHashMap（In-Process 隔离）。缺少跨进程/跨机器 agent 通信能力。

#### 8. autoDream 记忆整合（4 阶段）

1. **Scan** — 扫描现有记忆文件
2. **Extract** — 提取高价值数据（纠正、决策、重复模式）
3. **Merge** — 合并重复条目、删除矛盾事实
4. **Optimize** — 保持 MEMORY.md 索引在大小限制内

**Runner 对比**: 无记忆整合机制。TODO-021 已记录但未实现。

#### 9. KAIROS 守护模式

- 后台常驻 agent，5 分钟心跳周期
- 主动执行任务（收件箱整理、状态监控）
- 写入日期戳日志文件 (`logs/YYYY/MM/YYYY-MM-DD.md`) — Write-Ahead Log 模式

**Runner 对比**: TODO-014 (Heartbeat/Proactive Agent) 已记录但未实现。

### II. OpenClaw 最新架构 (350K+ stars, 2026.5)

**来源**: 官方文档、GitHub 仓库分析、社区深度分析文章。

#### 1. Hub-and-Spoke 架构

- **Gateway** (控制平面): Node.js 进程，WebSocket 服务 (port 18789)，事件总线
- **Agent Runtime** (执行引擎): 独立进程，拥有自己的 workspace、bootstrap 文件、session store

**Runner 对比**: Runner 的 Gateway + Orchestrator 模式类似，但都在同一进程内。OpenClaw 的进程级隔离更适合生产环境。

#### 2. Bootstrap 文件系统 (Workspace-as-Config)

| 文件 | 用途 |
|------|------|
| SOUL.md | 人格/语气定义 |
| AGENTS.md | Agent 规则 |
| USER.md | 用户信息 |
| IDENTITY.md | Agent 身份 |
| TOOLS.md | 环境说明 |
| MEMORY.md | 学习到的模式 |
| HEARTBEAT.md | 定时任务配置 |

每个文件有字符限制，防止 context 溢出。

**Runner 对比**: AgentProfile 是 Java 代码定义。TODO-013 (Workspace-as-Config) 已记录但未实现。

#### 3. Pre-compaction Memory Flush（独立验证）

OpenClaw 在 context compaction 前执行一个**静默内部 turn**：
- 提醒 agent 将重要上下文写入磁盘 (MEMORY.md)
- 然后才清除原始对话历史
- 如果未写入磁盘的信息，compaction 后就丢失

**Runner 对比**: SnipCompactor 直接删除旧 TOOL 消息，无预保存步骤。TODO-031 已记录。**两个独立系统（Claude Code + OpenClaw）都实现了此模式，说明这不是可选优化，而是必要的架构组件。**

#### 4. Lane Queue 会话序列化

- 每个 session 有独立的 **Lane Queue**，请求串行执行
- 防止同一会话内的跨 context 数据泄漏
- Session 级别隔离，不同 session 可并行

**Runner 对比**: AgentLoop 内部是串行的（ToolCallingLoop 是递归 Flux），但 Orchestrator 层面没有 per-session 请求排队。如果同一 session 快速发两个请求，InterruptibleRun 会打断第一个，这是设计意图。但如果需要排队模式（不打断），则缺少此能力。

#### 5. DMScope 会话分区

```
SessionKey = workspace:channel:userId
DMScope 级别：
- main: 所有 DM 共享一个 session
- per-peer: 每个对话者独立 session
- per-channel-peer: 每个频道+对话者独立
- per-account-channel-peer: 最大隔离
```

**Runner 对比**: Runner 的 sessionKey 是 `agent:<agentId>:main:<sessionId>`。固定两级 (agent + session)，不支持灵活的分区策略。

#### 6. 插件生命周期钩子（14 个注入点）

```
before_agent_start, agent_end,
before_compaction, after_compaction,
before_tool_call, after_tool_call, tool_result_persist,
message_received, message_sending, message_sent,
session_start, session_end,
gateway_start, gateway_stop
```

**Runner 对比**: AgentObserver 有 7 个钩子 (onAgentStart, onLLMRequest, onLLMResponse, onAgentComplete, onError, onPreToolUse, onPostToolUse)。缺少: compaction 钩子、session 生命周期钩子、gateway 生命周期钩子。

#### 7. Provider Manifest — 运行时热切换

OpenClaw 2026.4 引入 **provider manifest**：运行中的工作流可以切换 LLM 模型，无需重构。

**Runner 对比**: LLMProvider 在构造时固定，不支持运行时切换。ResilientLLMProvider 有 health tracking 但只用于重试判断，不用于 provider 切换。

### ISSUE-B: CostTracker.record() 无生产调用方（功能完全失效）

**文件链路**:
- `CostTracker.java` — 有 `record(inputTokens, outputTokens)` 方法
- `ToolCallingLoop.java:252` — 检查 `costTracker.isOverBudget()` 但**从未调用 `record()`**

- [ ] 同步路径 `run()` 也需要在 `loop.executeWithTools()` 后记录 token
- **Priority**: P1 — 5-10 行代码修复一个完全失效的功能

### ISSUE-C: ClaudeProvider 消息格式不符合 Claude API 规范

**文件**: `agent-kernel/.../llm/claude/ClaudeProvider.java:314-333`

**当前实现** (`buildMessagesArray()`):
```java
for (ConversationMessage msg : messages) {
    ObjectNode messageNode = objectMapper.createObjectNode();
    messageNode.put("role", convertRole(msg.getRole())); // TOOL → "user"
    messageNode.put("content", msg.getTextContent());     // 纯文本！
    array.add(messageNode);
}
```

**Claude API 期望**:
```json
// Assistant 消息（包含 tool_use）
{"role": "assistant", "content": [
    {"type": "text", "text": "Let me search..."},
    {"type": "tool_use", "id": "toolu_xxx", "name": "search", "input": {...}}
]}

// User 消息（包含 tool_result）
{"role": "user", "content": [
    {"type": "tool_result", "tool_use_id": "toolu_xxx", "content": "Results..."}
]}
```

**当前问题**:
1. TOOL 角色消息被转为 `role: "user"` + 纯文本 `content`，丢失 `tool_use_id` 和 `tool_result` 结构
2. Assistant 消息不包含 `tool_use` content blocks，只有纯文本
3. **多工具并行调用时 Claude 无法关联 tool_result ↔ tool_use**
4. **可能导致 Claude API 400 错误**

**ToolCallingLoop 已正确设置 metadata**:
```java
// L401-408: createToolResultMessage() 正确保存了 tool_use_id 到 metadata
return ConversationMessage.builder()
    .role(MessageRole.TOOL)
    .textContent(toolResult.getContent())
    .metadata(Map.of("tool_use_id", toolResult.getToolUseId(), "is_error", toolResult.isError()))
    .build();
```

但 `ClaudeProvider.buildMessagesArray()` 完全忽略了 metadata。

**Action**:
- [ ] `buildMessagesArray()` 识别 TOOL 角色，生成 `content: [{type: "tool_result", tool_use_id: metadata.get("tool_use_id"), content: textContent}]`
- [ ] 识别 ASSISTANT 消息中的 `tool_calls` metadata，生成 `content: [{type: "text"}, {type: "tool_use", ...}]`
- [ ] 单元测试覆盖：多工具并行场景下的消息序列化
- **Priority**: P0 — 影响核心功能正确性

## New TODOs from Latest Research

### TODO-035: Pre-compaction Memory Flush (升级优先级)

**双重验证**: Claude Code (L2 memory flush) 和 OpenClaw (pre-compaction silent turn) 都独立实现了此模式。

**当前问题**: SnipCompactor 直接删除超过 keepRecentRounds 的 TOOL 消息。这些消息可能包含关键的工具执行结果（如搜索结果、计算结果），删除后 LLM 完全丢失这些信息。

**实现方案**:

## Latest Community Best Practices (2026.5 研究补充)

### "Agent = Model + Harness" 共识

2026 年行业共识: **2025 年关注构建 agents, 2026 年关注让 agents 生产可靠**。最高 ROI 来自 harness engineering — checkpointing, error recovery, context management, observability, security enforcement。

最成功的实现使用**简单可组合的模式**，而非复杂框架。Anthropic 推荐：从最简架构开始（环境 + 工具集 + system prompt + 循环调用模型），复杂度会杀死迭代速度。

### 关键行业模式与 Runner 对标

#### 1. Context Engineering (Anthropic 2026 术语)

"Context engineering" 是 "prompt engineering" 的自然演进。核心原则：**找到最小的高信号 token 集合来最大化期望结果的概率**。

- **Compaction API**: Anthropic 发布了生产级 compaction API (`compact-2026-01-12`)
- **ACON (Failure-Driven Optimization)**: 分析完整 context 成功但压缩 context 失败的案例，修订压缩 prompt。结果：26-54% peak token 降低
- **Context Rot**: token 数增加时，模型准确召回信息的能力下降

**Runner Action**: 考虑集成 Anthropic compaction API 作为 Level 5 compaction 策略

#### 2. Error Classification (LangGraph 模式)

LangGraph 区分 4 种错误类型:
| 类型 | 处理策略 |
|------|---------|
| Transient | 指数退避重试 |
| LLM-recoverable | 将错误作为 ToolMessage 返回，让模型自行调整 |
| User-fixable | 中断等待人工输入 |
| Unexpected | 冒泡到调试层 |

**Runner Action**: ResilientLLMProvider 当前只区分 retryable/non-retryable。应扩展为 4 类错误处理策略。

#### 3. MCP 生态爆发 (9,400+ registry entries)

MCP 现在是 AAIF (Agentic AI Foundation) 下的厂商中立标准，407% 增长 (2025.9 → 2026.4)。

**关键最佳实践**:
- 每个 MCP server 应有一个明确单一的职责（不做大一统）
- Tool descriptions 是关键：研究发现 89.8% 存在 "未声明限制"，89.3% 缺少 "使用指南"，84.3% 参数不透明
- **MCP Gateway Pattern**: Agent 与单一 gateway 通信，gateway 处理认证、连接管理、下游工具路由
- 使用 Resource Indicators (RFC 8707) 做 scoped permissions

**Runner Action**: agent-mcp 模块的 McpToolSourceProvider 应验证 tool descriptions 质量

#### 4. Multi-Agent 生产模式收敛

**~70% 生产部署使用 Orchestrator-Worker 模式**。2026 年 5 家主要厂商独立收敛到此模式:
- Cognition ("Devin can Manage Devins")
- Anthropic (brain/hands, role-scoped subagents)
- OpenAI (nested handoffs in Agents SDK)
- Microsoft (Agent Framework 1.0)
- LangChain (supervisor-as-tool)

**Runner 已对齐**: Orchestrator + SubagentRuntime ≈ Orchestrator-Worker 模式 ✅

#### 5. Memory 架构演进

**Dual-Store** (Vector DB + Knowledge Graph) 成为 2026 生产标准:
- Vector DB: 相似性搜索
- Knowledge Graph: 结构化实体关系遍历
- 记忆类型: Semantic (事实) + Preference (偏好) + Summarization (摘要) + Institutional (领域知识)
- Token 效率: 2026 每次检索 ~6,956 tokens (vs 2025 ~26,000 tokens)
- **Staleness 问题**: 外部世界变化但系统记忆不变 — 最常见的生产问题

**Runner Action**: kernel-memory 的 BM25+Vector 混合搜索是正确方向。缺少 Knowledge Graph 层和 staleness detection。

#### 6. Security: Lethal Trifecta + Progressive Enforcement

**致命三角**: 当三个条件同时满足时风险急剧上升:
1. 访问敏感系统
2. 处理不可信输入
3. 能够改变外部状态

**沙箱分层**:
- MicroVM (Firecracker): 最强隔离, 独立内核, 150ms 冷启动
- gVisor: 用户态内核, 系统调用拦截
- Hardened containers: 仅用于受信代码

**渐进式执行** (4 阶段): Discovery → Observation → Selective Enforcement → Full Least Privilege

**Runner Action**: CliTool 同时满足致命三角的全部三个条件（访问文件系统、处理 LLM 输出、执行系统命令）。安全加固优先级应为 **P0 CRITICAL**。

#### 7. Long-Running Agent Harness (Anthropic 模式)

Anthropic 的长运行 agent 使用结构化暂存文件 (`claude-progress.txt`) + git 历史:
- 记录已完成步骤、当前阻塞、架构决策、下一步动作
- Initializer agent 在首次运行时设置环境
- Coding agent 每次 session 做增量进展，留下清晰 artifacts

**Runner Action**: 可在 Heartbeat/KAIROS 模式 (TODO-014) 中借鉴此模式
