## I. New Findings from External Research (2026-05-16)

### 1. OpenClaw 2026.5 (v2026.5.3 ~ v2026.5.5) 架构演进

OpenClaw 在 5 月连续发布三个版本，引入多项架构级变化：

#### 1.1 Canvas Lazy Loading — 按需加载子系统
- **变化**: Canvas（HTTP host, hosted media resolver, CLI, tool runtime）改为懒加载，Gateway 启动时不加载，首次使用时才初始化
- **影响**: 启动时间和峰值内存显著降低
- **Runner 对比**: agent-web 的 `@Configuration` 在启动时一次性装配所有 bean（ToolRegistry, LLMProvider, MemoryProvider, Orchestrator），无懒加载机制
- **启示**: 对于 MCP 工具、DynamicPluginProvider 等重量级组件，应支持延迟初始化

#### 1.2 Codex App-Server Runtime 模式
- **变化**: OpenAI agent turns 默认通过 Codex app-server 路径执行，带有 isolated per-agent state、subscription-backed auth、长运行 turn 支持
- **影响**: 每种 LLM provider 可以有专属的 runtime 模式
- **Runner 对比**: 所有 LLM provider（Claude, OpenRouter）共用同一个 ToolCallingLoop 和 AgentLoop 执行路径，没有 per-provider runtime 定制能力

#### 1.3 文件传输工具系统 (file_fetch, dir_list, dir_fetch, file_write)
- **变化**: 新增 file-transfer plugin，支持 16MB/round-trip 的二进制文件操作
- **Runner 对比**: agent-tools 的文件操作能力有限，CliTool 的 ProcessBuilder stdout 流不适合大文件传输
- **启示**: 未来可能需要 BinaryStreamingTool 支持大文件场景

#### 1.4 Queue Mode 架构详解 (steer-backlog 新模式)
- **变化**: 新增 `steer-backlog` 模式 = steer 当前 turn + 保留消息用于 followup
- **4 种 queue mode**: collect（默认，合并消息）、steer（中断注入）、followup（等待后新 turn）、steer-backlog（混合）
- **Runner 对比**: InterruptibleRun 只有 interrupt()（全量取消）和 resume()（新 turn），没有 steer（tool 间隙注入）和 collect（合并等待消息）
- **Gap 细化**:
  - 缺少 `steer` 模式：用户消息应在下一个 tool call 边界注入，而不是取消整个 turn
  - 缺少 `collect` 模式：多条快速消息应合并为一条，而不是每条都触发 interrupt

### 2. Claude Code 2026.5 新特性对比

#### 2.1 Hook System 增强
- **PostToolUse hooks 可替换工具输出**: `hookSpecificOutput.updatedToolOutput` 允许 hook 修改任何工具（之前仅 MCP 工具）的输出结果
- **duration_ms 字段**: PostToolUse/PostToolUseFailure 输入中新增工具执行时长
- **terminalSequence 字段**: Hook 可输出桌面通知、窗口标题等终端控制序列
- **Runner 对比**: AgentObserver 的 `onPostToolUse(toolName, args, result)` 是只读回调，无法修改 result；没有 duration 追踪；没有终端控制能力
- **Action**: 升级 AgentObserver.onPostToolUse 为可修改返回值（`ToolResult onPostToolUse(...) → modified result`）

#### 2.2 Permission Context 丰富化
- **新增字段**: `decision_reason`, `blocked_path`, `title`, `display_name`, `description` 在 ToolPermissionContext 中
- **permission_mode 参数**: ClaudeAgentOptions 支持 "acceptEdits" 等预设权限模式
- **Runner 对比**: ScopedToolRegistry 的 deny > allow 是二元判断，没有 reason、context、mode 等丰富语义
- **Action**: 权限拒绝时应返回 structured rejection（含 reason），而非简单的 false

#### 2.3 Agent SDK 架构
- **Agent Loop 一致性**: Agent SDK 与 Claude Code 共用同一个 agent loop、tool routing、context management
- **Runner 对比**: agent-sdk 的 `DefaultAgent` 和 agent-kernel 的 `AgentLoop` 是独立实现，SDK 路径未经过 Orchestrator

### 3. 跨框架 2026.5 最新共识

#### 3.1 Microsoft Azure AI Agent Design Patterns（2026 新发布）
- **6 种编排模式**: Centralized（单控制器）、Decentralized（P2P）、Hierarchical（上下级）、Sequential（流水线）、Parallel（扇出扇入）、Hybrid
- **核心建议**: 生产系统从 Centralized 开始，遇到瓶颈再 Decentralize
- **模型分层**: 路由/分类用便宜模型（Haiku），复杂推理用贵模型（Opus），降低 40-60% 成本
- **Runner 对比**: Orchestrator 是 Centralized + Sequential 模式；SubagentRuntime 提供 Parallel（spawn/wait）；缺少 Hierarchical（上下级链）和 Decentralized（P2P handoff）
- **Action**: 评估 AgentRouter 是否应支持模型分层路由

#### 3.2 MCP 2026 Roadmap — Streamable HTTP
- **Streamable HTTP Transport**: 替代 SSE 成为首选远程传输，兼容标准 load balancer/proxy/CDN
- **Persistent Session Handles**: 服务端可发送增量通知（roots, tools, resources 变更），而非全量拉取
- **OAuth 2.1 + PKCE**: 远程 MCP 必须强制认证
- **Runner 对比**: agent-mcp 使用 stdio 和 SSE transport，未支持 Streamable HTTP；无 MCP session 概念；无认证
- **Action**: 跟踪 MCP SDK 升级，准备 Streamable HTTP 迁移

#### 3.3 多框架一致结论：57% 企业已部署 Multi-Agent
- Gartner 预测 2026 年底 40% 企业应用包含 AI Agent
- **关键挑战**: context 在 agent 间传递时的窗口限制
- **Runner 对比**: SubagentRuntime 的 spawn 创建完全隔离的 context，没有 context transfer/inheritance 机制

## II. New Architecture Issues Identified

### TODO-035: SubagentRuntime Cascade Stop 存在 ConcurrentModificationException

**文件**: `agent-kernel/.../orchestrator/SubagentRuntime.java:150-159`

`stop()` 方法在 ConcurrentHashMap 的 stream 迭代中调用 `activeRuns.remove()`，可能导致 `ConcurrentModificationException`：

```java
activeRuns.values().stream()
    .filter(r -> r.getSessionKey().startsWith(prefix) && !r.getRunId().equals(runId))
    .forEach(child -> {
        child.cancel("Cascade stop from parent " + runId);
        announcer.accept(StreamEvent.subagentCancelled(child.getRunId(), ...));
        activeRuns.remove(child.getRunId());  // ← 在迭代中修改 map！
    });
```

**影响**: 当多个 subagent 级联停止时，可能抛出异常导致部分 subagent 未被正确清理（线程泄漏）。

**Action**:
- [ ] 先 collect 到 List，再遍历 remove：
  ```java
  List<SubagentRun> children = activeRuns.values().stream()
      .filter(r -> ...).toList();
  for (SubagentRun child : children) {
      child.cancel(...);
      activeRuns.remove(child.getRunId());
  }
  ```
- **Priority**: P1 — 并发 bug，可能导致线程/资源泄漏

### TODO-036: ResilientLLMProvider 默认重试未知异常

**文件**: `agent-kernel/.../llm/ResilientLLMProvider.java:198-220`

`isRetryable()` 方法对未知异常默认返回 `true`：
```java
private boolean isRetryable(Throwable e) {
    String msg = e.getMessage();
    if (msg == null) return true;  // ← 未知异常默认重试
    // ... specific checks ...
    return true;  // ← 兜底也是 true
}
```

**影响**: `NullPointerException`、`IllegalArgumentException` 等编程错误也会被重试 3 次，掩盖 bug 并浪费 API 调用。

**Reference**: Claude Code 和 OpenAI SDK 只重试已知的 transient failure（429, 500, 502, 503, 504, connection reset, timeout），其余默认不重试。

**Action**:
- [ ] 默认返回 `false`，只对已知 transient failure 返回 `true`
- [ ] 与 TODO from 2026-05-05 (LLMProviderException 结构化 status code) 协同修复
- **Priority**: P1 — 掩盖生产环境 bug

### TODO-037: ToolCallingLoop Async Path 不检查 CostTracker

**文件**: `agent-kernel/.../core/ToolCallingLoop.java:161-221`

三种执行路径的 budget 检查不一致：
- **Sync path** (L106-115): 检查 CancellationToken，不检查 CostTracker
- **Reactive path** (L245-256): 检查 CancellationToken + CostTracker ✅
- **Async path** (L161-221): 两者都不检查 ❌

**影响**: 通过 `executeWithToolsAsync()` 路径执行的 agent 无法被 token 预算控制或取消。

**Action**:
- [ ] Async path 添加 cancellationToken 和 costTracker 检查
- [ ] 或废弃 async path，统一到 reactive path（与 TODO from 2026-05-05 AgentLoop.runStream 统一建议一致）
- **Priority**: P1 — 执行路径不一致

### TODO-038: ClientToolAliasRegistry 使用 Static Mutable Singleton

**文件**: `agent-kernel/.../directive/ClientToolAliasRegistry.java:21`

```java
private static volatile ClientToolAliasSource source;
```

`ClientToolAliasRegistry` 使用 static mutable singleton 模式：
- `setSource()` 全局修改静态引用，影响所有 ClientTool 实例
- `defaultSource()` 的 synchronized + volatile 双检锁存在微妙竞态：`setSource(custom)` 后立即调 `aliasesFor()` 可能仍拿到旧的 `PropertiesClientToolAliasSource`（发生在 `defaultSource()` 的 synchronized 块内 source 已被初始化但 `s` 局部变量读到了 null 之后的路径）
- 测试隔离困难：需要 `reset()` 清理全局状态

**Reference**: Spring 生态中类似配置应通过 `@Bean` 注入，而非 static 全局变量

**Action**:
- [ ] 将 `ClientToolAliasSource` 作为构造器参数注入 `DirectiveDescriptor.from()` 或 `ClientTool` 构造器
- [ ] 或改为 Spring `@Bean` + `@Primary` 机制，保持 DI 容器管理
- [ ] 至少为测试提供 scope-isolated 的 source 注入方式
- **Priority**: P2 — 不影响功能，但违反 DI 原则且测试不友好

### TODO-040: ToolRegistry.registerClientToolAliases 不走 ScopedToolRegistry 校验

**文件**: `agent-kernel/.../agent/ToolRegistry.java:434-448`

别名工具通过 `tools.compute()` 直接注册到全局 registry，绕过了 `registerToolInternal()` 的校验逻辑。如果 ScopedToolRegistry 的 deny list 包含别名工具名，别名仍会被注册到全局 registry（ScopedToolRegistry 在查询时会过滤，但 ToolDefinitions 可能泄漏）。

- **Priority**: P2

### TODO-042: InterruptibleRun 缺少 Steer 模式

**文件**: `agent-kernel/.../orchestrator/InterruptibleRun.java`, `Orchestrator.java`

当前只有两种中断策略：
1. `interrupt()` — 全量取消当前 turn，CancellationToken.cancel()
2. `resume()` — 开始全新 turn

缺少 OpenClaw 的 `steer` 模式：在当前 tool call 结束后（tool 边界），将用户新消息注入到 context 中，跳过剩余 pending tool calls，让 LLM 在下一轮迭代时看到新消息。

**场景**: 用户在 agent 执行多步工具调用时发送修正指令（"不，改用另一个文件"），当前实现只能取消整个 turn 重来，而 steer 模式可以在当前工具执行完毕后优雅地注入修正。

**Action**:
- [ ] 在 InterruptibleRun 添加 `steer(String message)` 方法
- [ ] ToolCallingLoop 在每次 tool execution 后检查是否有 steer message
- [ ] 如有，跳过剩余 pending tool calls，将 steer message 追加到 messages 后继续 LLM 调用
- [ ] 添加 AGENT_STEER 事件类型
- **Priority**: P2 — UX 改进，非功能性问题

### TODO-043: 无全局 LLM 调用并发控制

**文件**: `agent-kernel/.../llm/ResilientLLMProvider.java`, `SubagentRuntime.java`

SubagentRuntime 有 `maxConcurrent` 限制 subagent 线程数，但没有限制实际 LLM API 调用并发数。在以下场景下会突破 API rate limit：
1. 多个 subagent 同时发起 LLM 调用
2. 主 agent + 多个 subagent 并发
3. ToolCallingLoop 的并行 tool execution 触发嵌套 LLM 调用

**Reference**: 
- OpenClaw 的 Global Lane 限制全局 LLM 并发
- Claude API 有 per-organization rate limit，突破会导致 429 错误

**Action**:
- [ ] 在 ResilientLLMProvider 或新的 ThrottlingLLMProvider 装饰器中添加 Semaphore
- [ ] 配置 `maxConcurrentLLMCalls`（默认值 = API tier 对应的并发限制）
- [ ] 超过限制时排队等待，而非直接发请求后被 429
- [ ] 与 TODO-004 (Rate Limiting) 协同：Semaphore 控制并发，RateLimiter 控制频率
- **Priority**: P1 — 生产环境 burst 场景必需

### TODO-047: 模型分层路由 (Model Tiering)

**Reference**: 
- Microsoft Azure: 路由/分类用便宜模型，复杂推理用贵模型，降 40-60% 成本
- OpenClaw: per-agent model selection
- Claude Code: 不同子任务用不同 model tier

**Gap**: AgentProfile 有 `modelOverride` 但没有 per-task model selection。所有 AgentLoop 中的 LLM 调用用同一个 model。

**场景**:
- 路由决策 → Haiku（快且便宜）
- 工具参数生成 → Sonnet（中等成本）
- 复杂推理/生成 → Opus（最贵但最强）

**Action**:
- [ ] AgentProfile 添加 `routingModel` 字段（用于 AgentRouter 决策）
- [ ] ToolCallingLoop 可配置不同 LLMProvider 用于不同阶段
- [ ] 或在 LLMOptions 中添加 `modelTier` hint，让 Provider 选择对应模型
- **Priority**: P2 — 成本优化

### TODO-048: Compaction 前 Memory Flush 实现细化

**Reference**: 前次 TODO-031 已记录概念。OpenClaw 2026.5 进一步明确了 flush 策略：
- 被 Snip 删除的消息中如果包含"决策"、"用户偏好"、"关键事实"，应提取到 Durable Memory
- 使用轻量 LLM 调用（Haiku 级别）判断是否需要保留

**Runner 现状**: SnipCompactor 直接删除 keepRecentRounds 之前的 TOOL 消息，无预保存。MicroCompactor 截断大 result 为首尾 200 chars，中间信息永久丢失。

**具体场景**:
1. Agent 在第 1 轮调了 web_search，返回了用户需要的 API 文档链接
2. 经过 5 轮对话后，SnipCompactor 删除第 1 轮的 TOOL result
3. 用户再次询问那个 API，agent 完全不记得搜索结果

**Action**:
- [ ] 在 SnipCompactor 执行前，将被删消息传给 MemoryFlushStrategy 接口
- [ ] DefaultMemoryFlushStrategy: 将被删消息的 TOOL result 写入 Ephemeral Memory（简单、无 LLM 调用）
- [ ] SmartMemoryFlushStrategy: 用 Haiku 判断重要性后选择性写入 Durable Memory（高级，需 LLM 调用）
- [ ] CompactionChain 构造时注入 MemoryFlushStrategy
- **Priority**: P1 — 信息丢失影响用户体验

## VIII. Research Insights Summary

### 8.1 OpenClaw 的核心秘密：Pi Agent Framework 分层

OpenClaw 实际上并不自己实现 agent loop — 核心逻辑由独立的 **Pi agent framework** 提供：
- `pi-ai`: LLM 通信层（跨 provider）
- `pi-agent-core`: Agent loop + tool calling
- `pi-coding-agent`: 完整编码 agent（含 session persistence）

**启示**: Runner 的 agent-kernel 承担了过多职责（LLM 通信 + agent loop + orchestrator + tool system + context management）。OpenClaw 的分层更清晰：
- LLM 通信 → 独立包
- Agent loop → 独立包
- 上层编排 → Gateway 调用 agent 包

Runner 当前的 agent-kernel 可以考虑按这个模式进一步拆分，但短期内模块数量已够多，可作为长期架构演进方向。

### 8.2 2026 年 Agent 架构的 3 大共识

1. **Context 是最稀缺的资源** — 所有成熟框架都在 context management 上投入最多工程量。Claude Code 512K 行中 context compaction 相关代码占比最高。Runner 的 2-level compaction 还有很大提升空间。

2. **工具安全 > 工具数量** — Claude Code 2,592 行 bash 安全检查，23 条规则，18 个被阻止的内建命令。Runner 的 CliTool 完全裸奔。这是最大的技术债。

3. **Agent 基础设施占 98%** — Claude Code 只有 1.6% 是 AI 决策逻辑。其余全是基础设施：权限、恢复、监控、缓存、序列化。Runner 应优先投入基础设施而非新功能。

### 8.3 Runner 的独特优势

1. **ClientTool Alias 系统** — 其他框架均无此能力。同一个工具以多名暴露给 LLM 的设计在端侧设备场景下独特且实用。
2. **Reactive-first 全链路** — 从 Gateway 到 WebSocket 全程 Flux<StreamEvent>，比大多数 Python 框架的回调/协程方案更优。
3. **Outside-in TDD 强制执行** — CLAUDE.md 中的 6 条 UT 规则在开源社区中罕见，特别是 payload 传输链测试要求。
4. **4-layer Orchestrator** — 多数框架是 2 层（router + agent），Runner 的 4 层设计为中断/恢复/子 agent 提供了清晰的职责边界。
