### NEW-001: ExecutorService 资源泄漏 — 三个 Web 组件未 shutdown

**文件**:
- `agent-web/.../gateway/GatewayController.java:49`
- `agent-web/.../websocket/SpringChatWebSocketHandler.java:92-93`
- `agent-web/.../controller/ChatController.java:46`

**问题**: 三个 Spring 组件创建 `Executors.newCachedThreadPool()` 但无 `@PreDestroy` 调用 `.shutdown()`。CachedThreadPool 线程数无上限，长时间运行后线程数持续增长。

**影响**: 生产环境内存泄漏，线程积累导致 OOM。

**Action**:
- [ ] 添加 `@PreDestroy` 方法调用 `executorService.shutdown()`
- [ ] 或将 ExecutorService 注册为 Spring Bean，由 Spring 管理生命周期
- [ ] 考虑替换为 `Executors.newFixedThreadPool()` 或 Virtual Thread executor
- **Priority**: P1

### NEW-002: CliTool StringBuilder 线程安全问题

**文件**: `agent-kernel/.../cli/CliTool.java:89-112`

**问题**: 两个 daemon 线程 (`stdoutReader`, `stderrReader`) 同时写入各自的 `StringBuilder`。虽然当前每个 StringBuilder 只被一个线程写入（stdout 和 stderr 分开），但：
- Process 的 stdout/stderr 在未正确关闭时可能交叉
- 线程异常时 Process 未 `destroyForcibly()`（`catch (IOException ignored)` 静默吞异常）
- 无 try-with-resources 保护 Process 资源

**Action**:
- [ ] 用 try-with-resources 包装 Process
- [ ] 在所有异常路径添加 `process.destroyForcibly()`
- [ ] 捕获的 IOException 至少记录 WARN 日志
- **Priority**: P1

### NEW-003: Observer 异常被静默吞掉

**文件**: `agent-kernel/.../core/ToolCallingLoop.java:498, 512`

**问题**:
```java
catch (Exception ignored) {
    // observer.onPreToolUse / onPostToolUse 异常被完全忽略
}
```

AgentObserver 是唯一的扩展点（用于监控、审计、guardrails），但其异常被完全吞掉。如果 observer 实现了一个"拒绝危险工具调用"的 guardrail，其异常不会阻止工具执行。

**Action**:
- [ ] 区分 `onPreToolUse` 的 "veto" 异常（应阻止执行）和 "reporting" 异常（应记录但继续）
- [ ] 至少记录 `logger.warn("Observer threw", e)` 而非完全忽略
- [ ] 考虑返回 `PreToolUseResult` (PROCEED / REJECT / MODIFY_ARGS) 替代异常控制流
- **Priority**: P1 — 直接影响 guardrail 机制 (TODO-011) 的可行性

### NEW-004: ObjectMapper 每个 Provider 实例重复创建

**文件**:
- `agent-kernel/.../llm/claude/ClaudeProvider.java:65`
- `agent-kernel/.../llm/claude/ClaudeProProvider.java:63`

- [ ] 如需自定义配置，使用 `ObjectMapper.copy()` 创建轻量变体
- **Priority**: P2

### NEW-005: InterruptibleRun 消息列表无界增长

**文件**: `agent-kernel/.../orchestrator/InterruptibleRun.java:51`

**问题**:
```java
private final List<ConversationMessage> messages = Collections.synchronizedList(new ArrayList<>());
```

长时间运行的 agent 经过多次 interrupt/resume 循环，messages 列表持续增长。无最大容量或淘汰策略。

**关联**: 这与 ContextCompactor 的职责重叠——InterruptibleRun 维护的是"中断恢复上下文"，而 ContextCompactor 压缩的是"LLM 请求上下文"。两者之间没有同步机制。

**Action**:
- [ ] 在 InterruptibleRun.resume() 时通过 ContextCompactor 压缩 messages
- [ ] 或设置 maxMessages 上限，超过时截断最旧消息（保留系统消息）
- **Priority**: P2

### NEW-006: DynamicPluginProvider 的 volatile 字段存在复合操作竞态

**文件**: `agent-kernel/.../agent/DynamicPluginProvider.java:30-31`

**问题**:
```java
private volatile WatchService watchService;
private volatile Thread watchThread;
```

`volatile` 保证可见性但不保证原子性。`start()` 和 `stop()` 方法中的 `if (watchService != null) { watchService.close(); }` 不是原子操作，两个线程同时调用可能导致 NPE 或 double close。

**Action**:
- [ ] 使用 `AtomicReference<WatchService>` + `compareAndSet()` 替代 volatile
- [ ] 或添加 `synchronized` 保护 start/stop 方法
- **Priority**: P3 — DynamicPluginProvider 本身已在 deprecated 路径上

### NEW-007: SSE Emitter 超时与 LLM 执行超时不协调

**文件**: `agent-web/.../gateway/GatewayController.java:104`

**问题**:
```java
SseEmitter emitter = new SseEmitter(120000L);  // 2 分钟
```

SSE Emitter 硬编码 120 秒超时，但 LLM 调用（尤其是使用 extended thinking 的场景）可能需要更长时间。超时后 emitter 关闭但 LLM 仍在运行，造成：
- 客户端收到超时错误
- 服务端 LLM 调用的 token 被浪费
- 无法通知客户端真实结果

**Action**:
- [ ] SSE Emitter 超时应从 LLMOptions 或 AgentProfile 的超时配置中读取
- [ ] 添加心跳机制 (定期发送 `event: ping`)，防止网关/代理中间层超时
- [ ] LLM 执行超时与传输层超时应有联动（LLM 超时 → 通知 SSE → 优雅关闭）
- **Priority**: P2

### NEW-009: WebSocketLLMProvider 粗粒度 synchronized

**文件**: `agent-kernel/.../llm/websocket/WebSocketLLMProvider.java:92, 151`

**问题**: `connect()` 和 `disconnect()` 使用方法级 `synchronized`，如果 `connect()` 等待网络响应，会阻塞所有其他同步方法调用。高并发场景下成为瓶颈。

**Action**:
- [ ] 替换为 `ReentrantReadWriteLock`：读操作 (getStatus) 用读锁，写操作 (connect/disconnect) 用写锁
- [ ] 或使用状态机模式：`AtomicReference<ConnectionState>` + CAS 操作
- **Priority**: P3

- [ ] 替换为 `assertThrows(ExpectedException.class, () -> { ... })`
- [ ] 确保异常类型和消息被断言
