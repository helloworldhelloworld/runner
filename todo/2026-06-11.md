### TODO-054: Model Routing — 多模型智能路由

**行业背景**:
- Cursor: Tab model (小模型实时预测) + Agent model (大模型推理) 双模型架构
- Aider: Architect mode（大模型规划 → 小模型执行编辑）
- OpenAI GPT-5: 内置 fast/deep 路由
- 行业数据: 70% 请求降级到小模型 → **60% 成本节省**，质量保持 96%+

**Runner 现状**:
- 每个请求绑定单一 `LLMProvider`，由 `LLMOptions.model` 硬编码
- 无运行时模型切换能力
- 简单查询（"你好"、"帮我总结"）和复杂推理（多步工具调用、代码生成）使用同一模型

**设计方案**:
```
Before:  GatewayRequest → Orchestrator → AgentLoop(fixed provider)
After:   GatewayRequest → Orchestrator → ModelRouter → AgentLoop(selected provider)
                                           ├─ Fast path: Haiku/Sonnet (简单查询)
                                           └─ Deep path: Opus (多步推理/工具调用)
```

**Action**:
- [ ] 新增 `ModelRouter` 接口: `LLMProvider route(GatewayRequest request, AgentProfile profile)`
- [ ] 实现 `RuleBasedModelRouter`: 基于消息长度、工具需求、历史 token 用量等规则路由
- [ ] `AgentProfile` 新增 `preferredModels` 配置 (fast/default/deep)
- [ ] 后续可选: LLM-based router（用小模型判断复杂度再路由）
- **Priority**: P2 — ROI 高但需要多 provider 基础设施就位
- **Effort**: 3d
- **Depends on**: TODO-036 (CostTracker 需先能记录，才能衡量 routing 效果)

### TODO-055: Lazy Tool Loading — 语义工具按需加载

**行业背景**:
- Claude Code: 默认 <20 工具在 context，其余通过 `ToolSearch` deferred 加载（schema 按需获取）
- OpenClaw: TOOLS.md 仅列工具名，schema 按需拉取
- 研究数据: 工具定义超出阈值后产生 "Context Rot" — LLM 选择正确工具的能力退化
- Anthropic 建议: "如果不能用一句话解释 agent 为什么会选 A 而不选 B，那边界不够清晰"

**Runner 现状**:
- `ToolRegistry.getToolDefinitions()` 返回 **全部** 已注册工具的完整 JSON schema
- LLMOptions 携带全量工具定义注入每次 LLM 调用
- MCP 工具扩展后，工具数量可达 50+，每个工具 schema 约 200-500 tokens
- 50 工具 × 350 tokens = **17,500 tokens/轮** 仅用于工具定义

**设计方案**:
```
Phase 1: Tool Budgeting
  - ToolRegistry.getToolDefinitions(maxTools=20) — 按优先级/最近使用返回 top-N
  - 超出 N 的工具仅发送名称+一句话描述（~30 tokens/tool）

Phase 2: Semantic Tool Search
  - 新增 ToolSearchTool（元工具）: LLM 可通过关键词搜索并激活额外工具
  - ToolRegistry.search(query) 已有接口 → 包装为 Tool
```

**Action**:
- [ ] `ToolRegistry` 新增 `getToolDefinitions(int maxTools)` 和 `getToolSummaries()` 方法
- [ ] `LLMOptions` 新增 `maxToolsInContext` 配置（默认 20）
- [ ] 新增 `ToolSearchTool`: `execute({query})` → 返回匹配工具的完整 schema → LLM 后续轮次可使用
- [ ] PromptEngine 在 system prompt 中注入 "Use the tool_search tool to discover additional tools"
- **Priority**: P2 — 工具数量增长后成为必要
- **Effort**: 2d (Phase 1) + 1d (Phase 2)

### TODO-056: Plan-and-Execute 混合模式

**行业背景**:
- 2026 benchmark: Plan-and-Execute 在复杂任务上达 **92% 完成率** vs ReAct 的 **85%**
- Cursor Composer: 先规划多文件变更方案，再逐步执行
- Aider Architect Mode: 大模型出规划 → 小模型出代码
- Anthropic 官方建议: "超过 3-5 步的任务应分离规划与执行"
- 混合模式已成主流: ReAct 处理短任务，Plan-and-Execute 处理复杂任务

**Runner 现状**:
- 纯 ReAct 模式: ToolCallingLoop 每轮 LLM→工具→LLM 循环
- 无显式规划阶段
- 复杂任务（多文件编辑、多步骤工作流）容易 "走偏" — 缺乏全局视角

**设计方案**:
```
Simple task (≤3 tool calls expected):
  → Standard ReAct loop (current behavior)

Complex task (user explicitly requests /plan, or LLM detects complexity):
  → Phase 1: Planner LLM call (no tools, just structured plan output)
  → Phase 2: Executor loop (standard ToolCallingLoop, plan as context)
  → Phase 3: Re-plan if step fails (feedback loop)
```

**Action**:
- [ ] 新增 `PlanningPhase` 类: 接收用户输入 → 调用 LLM 生成结构化计划 (JSON steps[])
- [ ] `AgentLoop` 新增 `runWithPlan()`: 先 plan，再逐步 execute，每步后检查计划完整性
- [ ] 计划作为额外 system prompt 注入 ToolCallingLoop（不改变核心循环）
- [ ] 后续可选: 计划步骤并行执行（scatter-gather 模式）
- **Priority**: P3 — 当前用户场景以简单交互为主
- **Effort**: 3d
- **Note**: 不修改 ToolCallingLoop 核心，仅在外层添加规划阶段

### TODO-057: 自适应重试分类器

**行业背景**:
- 2025 研究: 轻量级分类器预判失败是暂时还是永久，减少 **40% 无效 API 调用**
- Claude Code: 分层恢复 — free recovery (budget reduction) → paid recovery (LLM summarization)
- OpenClaw: 3 次重试 + 指数退避 (1s, 2s, 4s) + circuit breaker
- OWASP: 未检测的无限循环在 2025.11 一个案例中运行了 **11 天** 才被计费数据发现

**Runner 现状**:
- `ResilientLLMProvider.isRetryable()`: 已有 HTTP 状态码判断，但未知异常默认 `return true`（L220）
- 无 circuit breaker: 连续失败不会停止重试
- 无重试预算: 理论上可无限重试
- `CostTracker.record()` 未调用 → 无法基于成本停止重试

**Action**:
- [ ] `isRetryable()` L220 默认改为 `return false`（fail-fast 原则）
- [ ] 新增 `RetryBudget`: 每个 session 最多重试 N 次（默认 10）
- [ ] 新增 `CircuitBreaker`: 连续 M 次失败（默认 3）后熔断，cooldown 后半开探测
- [ ] 结构化异常: `LLMProviderException` 新增 `httpStatusCode` + `errorCategory` 枚举 (RATE_LIMIT, CONTEXT_OVERFLOW, MODEL_ERROR, NETWORK, UNKNOWN)
- [ ] CostTracker 集成: 重试消耗的 token 也要记录
- **Priority**: P1 — 直接影响运维成本和系统稳定性
- **Effort**: 2d
- **Merges**: TODO-041 (isRetryable 修复) + TODO-005 (Circuit Breaker)

### TODO-061: Git Worktree 隔离 — 子 Agent 并行执行

**行业背景**:
- Cursor: 最多 **8 个并行 agent**，每个在独立 git worktree 中工作，互不干扰，结果通过 Git merge 合并
- Claude Code: subagent 可在 worktree 中执行 (`isolation: "worktree"`)，自动清理无变更的 worktree
- 优势: 文件系统隔离（不同 agent 编辑同一文件不冲突）、可丢弃（失败的 agent 不影响主分支）、标准 Git 合并

**Runner 现状**:
- SubagentRuntime 仅支持 ASYNC_SPAWN（异步 spawn 到独立 session）
- 子 agent 共享同一文件系统 → 并行编辑同一文件会冲突
- 无 worktree 概念

**Action**:
- [ ] `SubagentRuntime.spawn()` 新增 `WorktreeIsolation` 选项
- [ ] 实现 `GitWorktreeManager`: 创建/清理 worktree，管理临时分支
- [ ] subagent 完成后自动合并变更或返回 diff

## 本轮关键洞见

1. **98.4% 基础设施定律** — Claude Code 512K 行代码中仅 1.6% 是 AI 决策逻辑，其余是权限、上下文管理、工具路由和恢复逻辑。Runner 当前的投入比例恰好相反：大量关注 agent loop 和 LLM 调用，基础设施严重不足。
2. **二次方成本陷阱** — Agent loop 每轮重发完整历史导致成本二次方增长。一个 10 轮 session 的成本约为单次调用的 50 倍。Prompt Caching (TODO-048) 是唯一能从根本上改变成本曲线的优化。
3. **执行路径分裂是系统性风险** — runner 的 3 条执行路径 (run/runStream/runReactive) 的不一致不仅是技术债务，更是 **每个新功能都需要实现 3 遍** 的隐性成本。这是 P0 项连续 5 轮不动的结构性原因 — 修一个 bug 要改 3 个地方。
4. **沙箱缺失已成行业异常** — 2026 年所有主流 agent 框架都有某种形式的工具执行隔离（Docker/VM/OS-level/Git）。Runner 的 ProcessBuilder 直接执行 + 无验证组合在行业对比中属于最低安全水位。
5. **Steer vs Interrupt 的设计差距** — OpenClaw 的 Steer 模式在当前工具调用完成后注入新消息再继续，而 runner 的 InterruptibleRun 需要完全中断+重建上下文。这导致 runner 的中断成本更高、恢复更慢。考虑在 TODO-038 修复竞态时同步升级为 Steer 模式。
