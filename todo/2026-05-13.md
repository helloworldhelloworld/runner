## Part 1: New Findings from Latest Research (2026-05-13)

### 1.1 OpenClaw 2026.5 架构深度解析

**来源**: OpenClaw GitHub (347K stars), docs.openclaw.ai, 社区分析

#### A. Task Brain — 统一任务账本

OpenClaw 2026.3.31 引入的 Task Brain 是本轮分析中最值得参照的架构升级：

```
Task Brain (SQLite-backed ledger)
├── ACP Tasks        — Agent Control Protocol 标准任务
├── Subagent Tasks   — 子 Agent 生命周期
├── Cron Tasks       — 定时执行（Heartbeat 等）
└── Background CLI   — 后台 CLI 进程管理
```

类比 Kubernetes 的容器调度，Task Brain 统一了四种执行实体的生命周期管理。

**Runner 对比**: SubagentRuntime 只管 subagent；Orchestrator 的 InterruptibleRun 只管主会话。没有统一的任务管理层，cron/background 完全缺失。

#### B. 七阶段 Agent Loop

OpenClaw 的 Pi 运行时使用更精细的 7 阶段循环：

```
1. Normalize    — 多渠道消息标准化（WhatsApp/Telegram/Slack → 统一格式）
2. Route        — 基于消息内容和 Agent 配置决定路由
3. Assemble     — 组装完整上下文包：memory + history + SOUL.md + session state
4. Infer        — LLM 调用（带 provider 选择和 fallback）
5. ReAct        — 工具调用循环（Reason-Act-Observe-Repeat）
6. Load Skills  — 根据上下文动态加载相关 Skill（SKILL.md frontmatter 匹配）
7. Persist      — 会话存储 + memory flush
```

**Runner 对比**: runner 的循环大致覆盖了 3-5 步（Assemble=buildMessages, Infer+ReAct=ToolCallingLoop, Persist=addMessage），但缺少显式的 Normalize（多渠道格式统一）和动态 Skill 加载（runner 的 Skill 是启动时注册的，不根据上下文动态激活）。

#### C. 混合记忆搜索 — 70/30 权重

```
Memory Search Pipeline:
├── Vector Search (70% weight) — cosine similarity via sqlite-vec
├── BM25 Keyword Search (30% weight) — FTS5 full-text search
├── Chunking: ~400 tokens/chunk, 80 token overlap
├── Index: MemoryIndexManager (dirty flag + debounced 1.5s sync)
└── Session indexing: opt-in, debounced, async
```

**Runner 对比**: kernel-memory 也实现了 BM25+Vector 混合搜索，但缺少可配置的权重比例、chunk overlap 策略、和 dirty flag 增量索引优化。

#### D. Steer 模式 — 精细中断注入

```
Traditional Interrupt (Runner):
  User → interrupt() → cancel ALL → resume with new input

OpenClaw Steer:
  User sends new message during tool execution
  → Skip remaining pending tool calls
  → Inject new message BETWEEN current tool result and next LLM call
  → LLM sees: tool_result + new_user_message → responds to both
```

**Runner 对比**: InterruptibleRun.interrupt() 是全量取消（CancellationToken.cancel()），没有"在工具间隙注入"的精细控制。对于长工具链（如连续搜索→分析→生成），用户只能全量打断然后从头开始。

### 1.2 Claude Code 泄露源码系统性分析

**来源**: arXiv:2604.14228 (VILA-Lab), 512K 行 TypeScript 逆向工程社区报告

#### A. 9 步 Pipeline Per Turn

```
1. Settings Resolution  — 多层配置合并（global → project → session）
2. State Init           — 初始化 turn 状态
3. Context Assembly     — 组装消息 + memory + CLAUDE.md
4. Pre-Model Shapers (5 层):
   4a. Budget Reduction  — tool output 超限 → 保存到磁盘，context 中只留引用
   4b. Snip             — 时间维度压缩，删除旧消息块，无总结
   4c. Microcompact     — 热尾巴（最近 N 条完整可见）+ 冷存储（路径引用）
   4d. Context Collapse — 超长历史管理
   4e. Auto-Compact     — 语义压缩：模型生成摘要替换历史（最后手段）
5. Model Call           — 通过 QueryEngine 调用 LLM API
6. Tool Dispatch        — 工具匹配和路由
7. Permission Gate      — 9 步权限检查
8. Tool Execution       — 执行工具
9. Stop Condition       — 判断是否继续循环
```

**Runner 对比**:
- runner 只有 2 层 compaction（Snip + Micro），缺少 Budget Reduction（大 tool output 磁盘化）、Context Collapse、Auto-Compact（LLM 摘要）
- 无 Settings Resolution 层（多层配置合并）
- 无 Permission Gate（工具调用前的权限检查链）

#### B. 7 级权限频谱

```
plan       — 只能观察，不能执行任何工具
default    — 读操作自动允许，写操作需确认
acceptEdits — 读 + 文件编辑自动允许，系统操作需确认
auto       — ML 分类器实时评估每个操作风险
dontAsk    — 自动拒绝所有需要确认的操作（仅 allow 规则通过）
bypassPermissions — 跳过所有检查（沙箱环境专用）
```

**Runner 对比**: ScopedToolRegistry 只有 allow/deny 二元模型（deny 优先），没有风险分级、不支持运行时动态切换权限模式。

#### C. 延迟工具加载 (Deferred Tool Schema)

```
Startup:
  18 个工具标记 shouldDefer: true (LSP, TaskCreate, MCPTool, SkillTool, etc.)
  只有 ToolSearchTool 的 schema 在初始 context 中

Runtime:
  Model 发现需要工具 → 先调 ToolSearchTool → 匹配的工具 schema 动态注入 context
  → Model 再调实际工具

效果: 初始 context < 200K tokens（原本 tool definitions 占数千 token）
```

**Runner 对比**: ToolRegistry 在 AgentLoop 创建时一次性加载所有 tool definitions 到 LLMOptions，无延迟加载机制。当 MCP + CLI + 内置工具总数超过 20 个时，tool definitions 消耗大量 context。

#### D. 自愈记忆 (Self-Healing Memory)

```
memory.md 纠错流程:
1. Agent 发现之前记忆中的事实 F 与新观察 O 矛盾
2. Agent 不仅在对话中纠正，还主动 rewrite memory.md
3. 旧事实 F 被替换为新事实 O
4. 下次会话自动使用更新后的 memory

autoDream 整合:
- 用户空闲时，Agent 后台执行 memory consolidation
- 合并零散观察 → 绝对事实
- 删除逻辑矛盾
- 模糊洞察 → 精确声明
```

**Runner 对比**: MemoryProvider.writeDurable() 只支持追加/覆盖 section，没有智能纠错和整合机制。memory 增长但不会自我清理或纠正。

#### E. QueryEngine — 统一 LLM 网关

```
QueryEngine (46K 行):
├── 所有 LLM API 调用的唯一入口
├── 统一管理: retry, rate limit, context budget, streaming errors
├── 支持 async generator (循环直到 model 停止调用工具)
├── 14 cache-break vectors 监控 (prompt cache 失效检测)
└── 与 compaction pipeline 深度集成
```

**Runner 对比**: LLMProvider 是分散的（ClaudeProvider, OpenRouterProvider 各自处理），ResilientLLMProvider 只包装了 retry 和 health check。缺少统一的 QueryEngine 层来协调 rate limit、cache、context budget。

### 1.3 行业最佳实践 2026 共识

**来源**: Redis AI Agent Architecture Guide, Azure AI Agent Design Patterns, LangGraph 0.4, OpenAI Agents SDK 1.0, CrewAI 0.10 Flows, AWS Strands

#### A. MCP 成为工具通信标准

MCP (Model Context Protocol) 在 2026 年被 VS Code, JetBrains, 及多个第三方平台采纳为行业标准。Runner 已有 agent-mcp 模块，但实现深度有限。

#### B. 三轴记忆模型

```
Industry Consensus (2026):
├── Episodic Memory   — 事件序列记录（对应 runner 的 Session Memory）
├── Semantic Memory   — 泛化事实和模型（对应 runner 的 Durable Memory）
└── Working Memory    — 瞬时决策状态（runner 缺失：当前 context 就是 working memory，但无显式管理）
```

**Runner 差距**: 缺少 Working Memory 的显式管理——当前 tool 结果、决策中间态、环境变量等信息混在 conversation messages 中，没有独立的 working memory slot。

#### C. Event-Driven Agent 架构

```
Three-layer event system (industry pattern):
├── Event Infrastructure  — 事件总线 + 队列
├── Agent Runtime         — 事件循环 + 订阅
└── Governance Layer      — 审计、合规、可观测性

LlamaIndex/LangGraph 模式:
  Agent 发射 typed events → 订阅 event queues → 通过 event chains 传递状态
  每个 Agent 维护 non-blocking local event loop
```

**Runner 对比**: StreamEvent 已经是 typed event 系统，但只用于**输出**（streaming to client），没有用于**内部协调**（Agent 间通信、工具间协调）。

#### D. Guardrails 作为一等公民

```
OpenAI Agents SDK (1.0 GA):
├── Input Guardrails  — 在 Agent 处理前验证用户输入
├── Output Guardrails — 在返回前验证 Agent 输出
└── Tool Guardrails   — 工具调用前后的安全检查

Claude Code:
├── PreToolUse hooks  — 编程式权限决策 (allow/deny/modify)
├── PostToolUse hooks — 结果过滤/审计
└── 7-mode permission spectrum
```

**Runner 对比**: AgentObserver 有 onPreToolUse/onPostToolUse hooks，但仅用于观察（无法阻止工具调用）。soul-safety 只处理心理安全，没有通用 guardrail 框架。

#### E. Agent Handoff 模式成为共识

```
2026 年 handoff 已成为多 Agent 框架的标配:
├── OpenAI Agents SDK — Handoff Tool (显式上下文转交)
├── OpenClaw — delegate pattern (委托专家 Agent)
├── CrewAI — delegation (任务委派)
├── Semantic Kernel — concurrent/handoff/group chat workflows
└── Claude Code — subagent (Fork/Teammate/Worktree 三种模式)
```

**Runner 对比**: SubagentRuntime 的 spawn/wait 模式是"请求-等待"模型，不是"交接"模型。LLM 不能说"这个交给 Agent B 处理，我退出"——它只能 spawn 一个子 agent 然后 wait 结果。
