### TODO-054: Deferred Tool Loading — ToolSearchTool 模式（Claude Code 最高 ROI 模式）

**Reference**: Claude Code 最具创新性的架构模式。工具分为两类：
- **Always-loaded tools**: 高频工具（Read, Edit, Write, Bash, Grep, Glob），完整定义始终在 context 中
- **Deferred tools**: 仅名称发送到 LLM（不含参数 schema）。模型知道工具存在但看不到用法

当 LLM 需要某个能力时，调用 `ToolSearchTool` 按关键词搜索，匹配到的工具 schema 被展开到后续请求中。

**量化效果**:
- System tools context: **14-16k tokens → ~968 tokens**（节省 93%）
- 对于注册了大量 MCP 工具的场景，效果更显著

**Runner 现状**:
- `ToolRegistry.search(keyword)` 已存在（模糊搜索工具名/描述）
- `ToolRegistry.getToolDefinitions()` 始终返回 **全量** 工具定义
- 典型 runner session 有 10-30 个工具，每个 tool definition 约 200-500 tokens
- 全量注入 = 2000-15000 tokens 的 context 开销（**每轮都重复**）

**Claude Code 实现细节**:
```
// 系统 prompt 中 deferred tools 的呈现方式
"The following deferred tools are available via ToolSearch:
 Monitor, NotebookEdit, TaskOutput, WebFetch, WebSearch
 Use ToolSearch to load their schemas before calling them."
```

**Action**:
- [ ] 新增 `ToolSearchTool` 内置工具：接受 keyword 参数，返回匹配工具的完整 schema
- [ ] `ToolRegistry` 新增 `getAlwaysLoadedDefinitions()` 和 `getDeferredToolNames()` 方法
- [ ] `Tool` 接口新增 `default boolean isAlwaysLoaded() { return false; }` 方法
- [ ] `AgentLoop.buildMessages()` 中 system prompt 仅注入 always-loaded 工具的完整定义 + deferred 工具的名称列表
- [ ] ToolSearchTool 调用后，通过 `LLMOptions.additionalToolDefinitions` 动态追加匹配到的工具定义
- [ ] 与 Prompt Caching (TODO-048) 联动：deferred tools 名称列表变化频率低，缓存命中率更高
- **Priority**: P1 — 每 session 节省 93% tool definition tokens，与 Prompt Caching 叠加效果极好
- **Effort**: 3d（ToolSearchTool + ToolRegistry 改造 + acceptance test）
- **Synergy**: TODO-048 (Prompt Caching) — deferred loading 让 system prompt 更稳定，缓存命中率更高

### TODO-056: McpToolClient 连接韧性 — WebSocket 断连后工具调用失败

**代码审查发现**: `WebSocketMcpClientTransport.java:36-43` 明确设计为不自动重连：
```java
// 不在 transport 层自动重连：断开后 isConnected() 返回 false，
// 后续 sendMessage 立即以 IllegalStateException 失败上抛。
```

**问题链**:
1. WebSocket 断连 → `isConnected() = false`
2. `McpToolClient.callToolReactive()` (L185-207) 直接调用 `asyncClient.callTool()` → 无连接检查
3. 用户 mid-session 调用 MCP 工具 → `IllegalStateException: WebSocket not connected` → 工具执行失败
4. ToolCallingLoop 将失败返回给 LLM → LLM 可能反复重试相同工具 → 消耗 token 无意义

**Reference**: 
- Claude Code 的 MCP 客户端在连接丢失时自动重新初始化（transport → connect → initialize → tool list refresh）
- OpenClaw 使用 plugin heartbeat 检测连接健康度

**Action**:
- [ ] `McpToolClient` 新增 `reconnect()` 方法：close → rebuild transport → connect → initialize
- [ ] `callToolReactive()` 在捕获 `IllegalStateException("WebSocket not connected")` 时触发 reconnect + retry（最多 1 次）
- [ ] 新增 `McpToolClient.isHealthy()` 方法供 ToolRegistry 健康检查
- [ ] 考虑 exponential backoff（2s → 4s → 8s → 放弃）
- **Priority**: P1 — MCP 工具在长 session 中的可靠性保障
- **Effort**: 2d

### TODO-058: Observation Masking — 学术验证的低成本 Compaction 策略

**Reference**: JetBrains 2026 研究发现：
- **Observation Masking**（将旧 tool output 替换为占位符）实现了 **52% 成本降低**
- 同时 **solve rate 提升 2.6%**（少反而好 — 过多历史上下文会干扰模型推理）
- 效果优于 LLM summarization（既便宜又更好）

**关键洞见**: "65% of enterprise AI failures in 2025 were attributed to context drift or memory loss during multi-step reasoning, **not** raw context exhaustion" (Zylos AI Research)

**Runner 现状**:
- `SnipCompactor(keepRecentRounds=3)` 直接**删除**旧 TOOL 消息 — 信息完全丢失
- `MicroCompactor(maxChars=2000)` 截断超大消息 — 保留首尾但丢失中间

**提议**: 在 Snip 和 Micro 之间插入 Observation Masking 层：
```
L0: Budget Reduction (TODO-051 L1) — 截断超大单条输出 (free)
L1: Observation Masking (NEW) — 旧 tool output → "[output omitted, N chars]" (free, 学术验证最优)
L2: Snip — 删除更旧的完整 tool 消息 (free, 更激进)
L3: MicroCompact — 截断仍然过大的消息 (free)
L4: Summarization — LLM 摘要 (paid, last resort)
```

**Action**:
- [ ] 新增 `ObservationMaskingCompactor`：将 N 轮之前的 TOOL 消息内容替换为 `"[tool output omitted, was N chars]"`，保留工具名和调用参数
- [ ] 保留 tool 名称和 args 让 LLM 知道"做了什么"，但不占用 context 存"结果是什么"
- [ ] 在 CompactionChain 中插入到 SnipCompactor 之前
- [ ] 配置：`maskAfterRounds=5`（5 轮之后的 tool output 被 mask），`keepRecentRounds=3`（3 轮之前的 tool 消息完全删除）
- **Priority**: P1 — 学术验证的 52% 成本降低 + solve rate 提升，零 LLM 调用成本
- **Effort**: 1d
- **Merges into**: TODO-051 (4-Layer → 5-Layer Compaction Pipeline)

### TODO-059: 三层记忆架构对齐 — Episodic/Semantic/Procedural

**Reference**: 2025-2026 行业共识已收敛到三层记忆分类：
1. **Episodic Memory** — 特定经历（对话历史、任务结果、工具执行记录）
2. **Semantic Memory** — 通用知识和事实（提取的实体、关系、领域知识）
3. **Procedural Memory** — 如何做事（学习到的工作流、工具使用模式、成功策略）

**行业实践**:
- Mem0（2026 年最广泛部署的语义记忆层）：hybrid vector-graph storage + multi-signal retrieval（semantic similarity + keyword matching + entity matching 三路并行打分后融合）
- LangGraph：blackboard state pattern，checkpointing at super-step boundary
- Claude Code KAIROS autoDream：Episodic → Semantic 的定期整理（Orient → Gather → Consolidate → Prune）

**Runner 现状**:
- ✅ Episodic: `MemoryProvider.getHistory()` — 对话历史（session-scoped）
- ⚠️ Semantic: `FileMemoryProvider` ephemeral + durable memory — BM25+Vector 混合搜索已有，但缺少**实体提取**和**关系图谱**
- ❌ Procedural: 完全缺失 — 不记录"哪些工具在什么场景下成功/失败"

**Action**:
- [ ] Phase 1: 在现有 `MemoryProvider` 接口中添加 `writeProceduralMemory(toolName, scenario, outcome)` 方法
- [ ] Phase 1: ToolCallingLoop 在 TOOL_RESULT 事件后记录 procedural memory（工具名 + 调用参数摘要 + 成功/失败 + 耗时）
- [ ] Phase 2: 为 semantic memory 添加实体提取 pipeline（tool result → LLM 提取实体 → 写入 durable memory）
- [ ] Phase 3: 实现 multi-signal retrieval（当前仅 BM25 + vector，缺 entity matching）
- **Priority**: P2 — 长期用户体验和工具使用效率提升
- **Effort**: Phase 1: 2d, Phase 2: 3d, Phase 3: 5d
- **Relates to**: TODO-053 (Memory Consolidation)

### TODO-060: CostTracker 预算检查时序修正 — 防止预算超额 2x

**代码审查发现**: `ToolCallingLoop.java:251-256`
```java
// 预算检查：超预算时优雅退出
if (costTracker != null && costTracker.isOverBudget()) {
    logger.warn("ToolCallingLoop over budget at iteration {} ...", iteration, ...);
    return Flux.empty();
}
```

**问题**: 预算检查发生在 LLM 响应**完成之后**、下一次迭代**开始之前**。如果单次 LLM 调用消耗大量 tokens（如 Opus 4.x 的长回复），一次迭代就可能**超额 2 倍预算**。

**正确时序**:
```
Before (current):  LLM call → get response → record tokens → [next iteration] → check budget
After (proposed):  check budget → LLM call → get response → record tokens → check budget again
```

**依赖**: TODO-036 (CostTracker.record() 必须先接入)

**Action**:
- [ ] 在 LLM 调用**之前**也检查 `isOverBudget()`（防止已超额但未退出的情况）
- [ ] 在 LLM 响应后**立即** record + 检查（防止单次超额 2x）
- [ ] 添加 `CostTracker.hasRemainingBudgetFor(estimatedTokens)` 方法 — 预估下次调用是否会超额
- **Priority**: P1（依赖 TODO-036 先修复）
- **Effort**: 0.5d

### TODO-064: ResilientLLMProvider 异常捕获范围过宽

**代码审查发现**: `ResilientLLMProvider.java:169-190`
```java
} catch (Exception e) {  // 捕获所有 Exception，包括 OOM、StackOverflow 等
    Throwable cause = unwrapException(e);
    attempt++;
    if (attempt > maxRetries || !isRetryable(cause)) { ... }
    // ... retry
}
```

**问题**: `catch (Exception e)` + `isRetryable() default return true` = **任何异常都会被重试**，包括：
- `NullPointerException` → 编程错误，重试无意义
- `ClassCastException` → 类型错误，重试无意义
- `JsonParseException` → 响应格式错误，重试可能有意义（transient）也可能无意义（API 变更）
- `ToolCallingLoopException` → 循环超限，重试无意义

**Reference**: 
- Claude Code: 仅重试 network errors + 429 + 5xx
- OpenAI SDK: `APIConnectionError` + `RateLimitError` + `InternalServerError` 可重试，其余不重试

**Action**:
- [ ] `catch (Exception e)` 改为显式列表：`catch (SocketTimeoutException | ConnectException | HttpRetryableException e)`
- [ ] 或保留 `catch (Exception e)` 但将 `isRetryable()` 默认值从 `return true` 改为 `return false`（**最小改动，最大收益**）
- [ ] 为已知可重试场景显式返回 true：429, 500, 502, 503, 504, `SocketTimeoutException`, `ConnectException`
- **Priority**: P1 — 防止编程错误被静默重试 3 次
- **Effort**: 1d
- **Subsumes**: TODO-041 (isRetryable default)

| **Undercover Mode** | 防止泄露内部信息到公开仓库 | N/A |
| **Circuit Breaker on AutoCompact** | 连续 3 次压缩失败后停止重试 | ❌ 无 circuit breaker |

### JetBrains Observation Masking 研究（2026）

| 指标 | Observation Masking | LLM Summarization | 无 Compaction |
|---|---|---|---|
| 成本 | **-52%** | -40% | baseline |
| Solve Rate | **+2.6%** | +0.8% | baseline |
| LLM 调用 | 0 (free) | 需要额外 API 调用 | 0 |
| 信息保留 | 保留工具名+参数，丢弃输出 | 保留摘要 | 保留全部 |

**关键结论**: **少即是多** — 过多历史上下文会干扰模型推理。Observation Masking 既便宜又更好。

### LLMCompiler 模式（ICML 2024）

将 agent 工具调用计划视为**依赖图**，应用编译器优化：
- 识别可并行的工具调用
- 构建依赖 DAG
- 调度并行执行

**Runner 现状**: ToolExecutor 已支持并行工具执行，但不区分 read-only 和 state-modifying 工具。Claude Code 的分类方式（read-only 并行，state-modifying 串行）是更安全的默认策略。
