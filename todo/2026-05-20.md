#### TODO-035: AgentLoop 三条执行路径不一致 — 架构裂缝

**文件**: `agent-kernel/.../agent/AgentLoop.java`

AgentLoop 暴露三条执行路径，能力矩阵严重不一致：

| 能力 | `run()` (同步) | `runReactive()` (响应式) | `runStream()` (流式回调) |
|------|:---:|:---:|:---:|
| ToolCallingLoop | ✅ | ✅ | ❌ 跳过 |
| CancellationToken | ✅ (via Builder) | ✅ | ❌ |
| CostTracker | ⚠️ 传入但不 record | ⚠️ 同左 | ❌ |
| ContextCompactor | ✅ | ✅ | ❌ |
| Memory search/inject | ✅ | ✅ | ❌ |
| AgentObserver hooks | ✅ | ✅ | ❌ |

`runStream()` (L158-198) 直接调用 `llmProvider.completeStream()` 绕过整个 ToolCallingLoop，意味着：
- 流式回调路径无法执行工具调用 — **功能性 bug**
- 无 context compaction → 长会话可能 400
- 无 observer hooks → 监控盲区
- 无 cancellation → 无法中断

**Root Cause**: `runStream()` 是早期为简单问答场景快速添加的路径，后续 ToolCallingLoop 的完善没有回溯到这里。

**Action**:
- [ ] **方案 A (推荐)**: 废弃 `runStream()`，所有调用方迁移到 `runReactive()`。在 `runStream()` 上标注 `@Deprecated(forRemoval=true)`
- [ ] **方案 B**: 改造 `runStream()` 内部委托给 `runReactive()` + `subscribe(callback bridge)`
- [ ] 审计所有 `runStream()` 调用方（agent-web WebSocket handler 等），确认迁移路径
- **Priority**: P0 — 功能性 bug，任何通过流式回调的请求都无法使用工具

#### TODO-036: CostTracker 完全空壳 — 预算控制是假的

**文件**: 
- `agent-kernel/.../context/CostTracker.java` — 提供 `record(inputTokens, outputTokens)` 和 `isOverBudget()`
- `agent-kernel/.../core/ToolCallingLoop.java` — 每轮检查 `isOverBudget()` 但**从未调用 `record()`**
- `agent-kernel/.../agent/AgentLoop.java` — 构造 CostTracker 但不消费 LLMResponse.UsageInfo

**传输链断裂**: 
```
LLMProvider.complete() → LLMResponse(usageInfo) → [断裂] → CostTracker.record() → isOverBudget()
```

`isOverBudget()` 检查的 consumed 永远是 0，所以：
- **token 预算限制完全无效** — 即使设置 maxBudgetTokens=1000，也永远不会触发
- 对外 API 宣称支持 token budget 但实际是假功能
- Claude Code 在每次 LLM 响应后立即从 `usage` 字段记录消耗

**Action**:
- [ ] 在 `ToolCallingLoop.executeReactiveLoop()` 中，处理 LLM_COMPLETE 事件后调用 `costTracker.record(response.getUsage())`
- [ ] 在 `ToolCallingLoop.executeWithTools()` (同步路径) 中同样注入 record 调用
- [ ] 确保 ClaudeProvider/OpenRouterProvider 的 LLMResponse 正确填充 UsageInfo
- [ ] 添加传输链测试：设置 budget → 执行多轮 → 断言 isOverBudget() 在正确时机触发
- **Priority**: P0 — 宣称的功能完全失效，且影响成本控制

#### TODO-037: ClaudeProvider 消息序列化丢失结构化 content blocks

**文件**: `agent-kernel/.../llm/claude/ClaudeProvider.java:314-333`

`buildMessagesArray()` 将所有消息（含 TOOL 角色）序列化为 `{ role, content: "text" }` 纯文本格式。但 Claude API Messages 规范要求：

**Assistant 消息的 tool_use block:**
```json
{
  "role": "assistant",
  "content": [
    {"type": "text", "text": "I'll search for that."},
    {"type": "tool_use", "id": "toolu_xxx", "name": "search", "input": {"query": "..."}}
  ]
}
```

**User 消息的 tool_result block:**
```json
{
  "role": "user",
  "content": [
    {"type": "tool_result", "tool_use_id": "toolu_xxx", "content": "search results..."}
  ]
}
```

当前实现丢失了：
1. `tool_use_id` 关联 — 多工具并行时 Claude 无法匹配 result 到对应 call
2. `tool_use` content block — assistant 消息的工具调用结构被扁平化为纯文本
3. `is_error` 标志 — 工具执行失败的 result 无法标记为错误

**测试中已设置 metadata**: 测试代码 L130 设置了 `addMetadata("tool_use_id", "id1")`，但生产序列化完全忽略它。

**Impact**: 
- 单工具调用可能偶尔成功（Claude 从上下文推断关联）
- **多工具并行调用几乎必然混淆**（无 ID 关联）
- 可能触发 Claude API 400 错误

**Action**:
- [ ] `buildMessagesArray()` 识别 TOOL 角色消息，生成 `content: [{type: "tool_result", tool_use_id: ..., content: ...}]`
- [ ] 识别 ASSISTANT 角色中包含 tool_use 的消息，生成结构化 content blocks
- [ ] 从 `ConversationMessage.metadata("tool_use_id")` 提取 ID
- [ ] 处理 `is_error` 元数据标志
- [ ] 添加序列化 round-trip 测试：构造多工具对话 → 序列化 → 断言 JSON 结构正确
- **Priority**: P0 — 影响核心功能正确性

#### TODO-038: ClientToolAlias 绕过 ScopedToolRegistry 权限控制

#### TODO-043: 缺乏 Steer 模式 — 中断只能全量取消

**对比**:
- **OpenClaw** 的 `steer` 模式：用户在 agent 运行中发送新消息 → 新消息注入到当前 tool call 之后 → 剩余 pending tool calls 被跳过 → 新消息在下一次 LLM response 前注入
- **Claude Code**: 类似机制，pending tool calls 可部分取消
- **Runner**: InterruptibleRun.interrupt() 是全量取消 + 保存断点 + 等待 resume

Runner 的 interrupt 粒度太粗：用户说 "等等，改搜这个" 时，必须完全取消当前执行再 resume，丢失已完成的工具结果。

**Action**:
- [ ] 在 InterruptibleRun 中添加 `steer(newInput)` 方法（区别于 `interrupt()`）
- [ ] `steer()` 不取消当前执行，而是将 newInput 注入到下一个 tool call gap
- [ ] ToolCallingLoop 每轮迭代前检查 steer queue（类似 CancellationToken 的检查模式）
- [ ] emit AGENT_STEER StreamEvent
- **Priority**: P2 — UX 改进

#### TODO-044: Memory Flush Before Compaction — 防止信息丢失

#### TODO-045: 3-Tier Compaction → 5-Tier Compaction 升级路径

**对比** (Claude Code 的 5 级 compaction):

| Level | Name | Trigger | 成本 | Runner 对应 |
|-------|------|---------|------|------------|
| 1 | Tool Result Budgeting | 每轮 | 零 | ✅ SnipCompactor |
| 2 | MicroCompact | 单消息过大 | 零 | ✅ MicroCompactor |

- [ ] 依赖 TODO-036 (CostTracker) 和 TODO-030 (Token Counter) 提供利用率数据

### III. 外部参照新洞察

#### OpenClaw 2026.5 新发现

**1. Manifest-First Plugin 注册**

OpenClaw 的 plugin 不是直接注册到 agent，而是流经 Gateway 的中央注册表：
```
Plugin manifest → Gateway PluginRegistry → Validation + Security scan → Agent Runtime
```
对比 runner 的 DynamicPluginProvider 直接加载 JAR 到 ToolRegistry，无中间验证层。

**2. Dual-Loop Execution (Stage 1 + Stage 2)**

- Stage 1: ReAct reasoning loop (标准 TAOR)
- Stage 2: Tool result pruning — 15+ 轮前的文件读取结果自动老化删除

对比 runner 的 SnipCompactor 基于"轮数"而非"年龄"删除，更粗粒度。

**3. ClawHub Skill Registry + VirusTotal Scanning**

13,000+ 社区 skill（Markdown 文件），从 2026.2 起集成 VirusTotal 扫描第三方 skill。Runner 没有类似的社区生态或安全扫描机制。

#### Claude Code 泄露源码新发现

**1. StreamingToolExecutor + RWLock 并发模型**

```
LLM streaming ──────────────────────────────────>
              ├─ tool_use block 1 complete ─→ execute(tool1) [read]
              ├─ tool_use block 2 complete ─→ execute(tool2) [read] (并行)
              └─ tool_use block 3 complete ─→ execute(tool3) [write] (等待 read 完成)
```

读工具（file_read, search）并行执行；写工具（file_write, bash）独占执行。全程不等 LLM 流结束。

Runner 的 ToolCallingLoop 等 LLM 流完全结束后才开始任何工具执行 — 浪费了数秒的并行窗口。

**2. Cost Regime System (BATS)**

```java
enum BudgetRegime { HIGH(>=70%), MEDIUM(30-70%), LOW(10-30%), CRITICAL(<10%) }
```

不同 regime 触发不同策略：
- HIGH: 正常执行
- MEDIUM: 启用 MicroCompact
- LOW: 启用 AutoCompact + 限制工具数量
- CRITICAL: 仅保留 system prompt + 最后一轮 + "please wrap up"

**3. Prompt Cache Optimization — 14 Cache-Break Vectors**

Claude Code 监控 14 种使 prompt cache 失效的条件（system prompt 变更、tool list 变更、conversation prefix 变更等），主动避免 cache miss。cache hit 时 input token 成本降低 90%。
