### TODO-054: Guardrails 作为 First-Class Primitive

**Reference**: OpenAI Agents SDK 将 Guardrails 定义为 4 大核心 primitive 之一（Agents/Tools/Handoffs/Guardrails），与 Agent、Tool 同等地位：
- **Input Guardrails**: 在 agent 处理前验证输入（raise `InputGuardrailTripwireTriggered`）
- **Output Guardrails**: 在返回用户前验证输出（raise `OutputGuardrailTripwireTriggered`）
- **Tool Guardrails**: 在 tool 执行前后验证（input + output 两层）
- Guardrails 使用独立 LLM 调用评估安全性
- `RunConfig.input_guardrails` / `RunConfig.output_guardrails` 全局配置

**Claude Agent SDK 对照**:
- 通过 hooks 实现等价功能（PreToolUse → allow/deny/ask/defer）
- 但 hooks 更灵活：20+ 生命周期事件，不仅限于 input/output
- Permission decisions 优先级：deny > defer > ask > allow（多 hook 并行，取最严格）

**Runner 现状**:
- `AgentObserver` 仅有 void callback，无法 block/modify
- 无 input validation（用户输入直接进入 LLM）
- 无 output validation（LLM 输出直接返回用户）
- 无 tool guardrails
- soul-safety 模块存在但未集成到 AgentLoop 管线中

**Action**:
- [ ] 设计 `Guardrail` 接口：`InputGuardrail`、`OutputGuardrail`、`ToolGuardrail`
- [ ] `InputGuardrail.evaluate(userInput)` → `GuardrailResult`（PASS/BLOCK/WARN）
- [ ] `OutputGuardrail.evaluate(llmOutput)` → `GuardrailResult`
- [ ] `ToolGuardrail.evaluateInput(toolName, args)` / `evaluateOutput(toolName, result)` → `GuardrailResult`
- [ ] 集成 `soul-safety` 模块为内置 `InputGuardrail` 实现
- [ ] AgentLoop 在 ToolCallingLoop 入口处执行 InputGuardrail，出口处执行 OutputGuardrail
- [ ] 与 TODO-047 (Hook System) 协调：Guardrails 是 Hooks 的特化应用
- **Priority**: P1 — 安全基线，soul-safety 已有但未接入管线
- **Effort**: 3d（接口设计 + soul-safety 集成 + acceptance test）
- **Relates to**: TODO-047 (Hook System), TODO-044 (Untrusted-by-Default)

### TODO-055: MCP Tool Annotations 支持

**Reference**: MCP 2025-03-26 规范新增 Tool Annotations — 行为元数据提示：
```json
{
  "name": "read_file",
  "annotations": {
    "readOnlyHint": true,
    "destructiveHint": false,
    "idempotentHint": true,
    "openWorldHint": false
  }
}
```

**各框架采用情况**:
- Claude Code: `readOnlyHint` 用于决定并行/串行执行（read-only tools 并行，state-modifying 串行）
- MCP spec: annotations 帮助 host 决定是否显示危险操作警告
- OpenAI SDK: hosted tools 隐式标注（code interpreter = destructive, web search = readOnly）

**Runner 现状**:
- `Tool` 接口无任何 annotation 字段
- `McpToolWrapper` 未传递 MCP server 返回的 annotations
- `ToolExecutor` 无法区分 read-only 和 state-modifying 工具
- 所有工具串行执行，无并行优化

**Action**:
- [ ] `Tool` 接口新增 `ToolAnnotations getAnnotations()` 方法（default: 全 false）
- [ ] `ToolAnnotations` record: `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`
- [ ] `McpToolWrapper` 解析 MCP server 返回的 annotations 并映射
- [ ] 内置工具标注：File/Memory read → readOnly; CLI execute → destructive; search → readOnly+idempotent
- [ ] 为 TODO-056 (Parallel Tool Execution) 提供分类依据
- **Priority**: P1 — MCP 标准合规 + 并行执行前置条件
- **Effort**: 1d
- **Enables**: TODO-056 (Parallel Tool Execution)

### TODO-056: Parallel Tool Execution

**Reference**: Claude Code 并行工具执行策略（泄露源码确认）：
- `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY` 默认 10
- read-only tools (Read, Glob, Grep, MCP readOnly) 并行执行
- state-modifying tools (Edit, Write, Bash) 串行执行
- **Sibling abort**: 如果一个 tool 失败，所有同批 parallel calls 通过 child abort controller 立即取消
- 自定义 tools 通过 `readOnlyHint` 声明是否可并行

**Runner 现状**:
- `ToolExecutor` 串行执行所有工具：`for (toolCall : toolCalls) { tool.execute(args); }`
- LLM 可能单轮返回多个 tool_use blocks，但 runner 按顺序逐个执行
- 无并行优化，无 abort 机制

**LLM 并行 tool_use 行为**:
- Claude 3.5+: 单次响应可包含多个 `tool_use` content blocks
- OpenAI: parallel function calling 是标准行为
- 如果工具是 read-only 的，并行执行可大幅减少延迟

**Action**:
- [ ] `ToolExecutor` 识别同一轮中的多个 tool_use blocks
- [ ] 根据 `ToolAnnotations.readOnlyHint` 分为两组：parallel-safe 和 sequential
- [ ] parallel-safe 组使用 `CompletableFuture.allOf()` 并行执行，带 configurable concurrency limit（默认 5）
- [ ] sequential 组按原顺序执行
- [ ] Sibling abort: 使用 `CancellationToken` 子级，任一 parallel tool 失败时取消同批其他 tools
- [ ] 添加 `parallelToolExecution` 配置开关（默认 true）
- **Priority**: P1 — 显著减少多工具场景延迟
- **Effort**: 2d
- **Depends on**: TODO-055 (Tool Annotations) 提供 readOnlyHint 分类

### TODO-058: MCP Streamable HTTP Transport

**Reference**: MCP 2025-03-26 规范废弃 SSE，改用 Streamable HTTP 作为标准远程传输：
- 单一 HTTP endpoint 同时支持 POST 和 GET

- `Mcp-Session-Id` header 管理会话
- 支持无状态服务器、serverless 部署（AWS Lambda 等）
- SSE 被废弃因为：长连接对 serverless 不友好、需两个 endpoint、与 CDN/API gateway/load balancer 不兼容

**Runner 现状**:
- `agent-mcp` 模块实现了 `WebSocketMcpClientTransport`（基于 WebSocket）
- 未支持 Streamable HTTP transport
- 未支持 SSE transport（已被 MCP 规范废弃）
- 仅支持 stdio transport（通过 ProcessBuilder 启动子进程）

**Action**:
- [ ] 实现 `StreamableHttpMcpClientTransport` — 单 endpoint POST/GET
- [ ] 支持 `Mcp-Session-Id` header 管理
- [ ] 支持 response 类型自动检测：`application/json` vs `text/event-stream`
- [ ] MCP client config 支持 transport 类型选择: `stdio` / `streamable-http` / `websocket`
- [ ] 保持 WebSocket transport 作为 fallback（某些 server 可能不支持 Streamable HTTP）
- **Priority**: P2 — MCP 标准合规，支持远程 MCP servers
- **Effort**: 3d

### TODO-059: Context Degradation Monitoring

**Reference**: Claude Code 6,852 session 数据揭示的 context degradation curve：
- **0-20%**: 全能力，cache 预热期
- **20-40%**: 开始出现微妙退化（丢失早期决策、循环推理）
- **40-50%**: 显著退化区域（建议此处 compact）
- **50%+**: 严重退化（"context rot"，成本飙升，质量明显下降）
- **80%+**: 硬限制逼近，auto-compact 触发

**65% 的企业 AI 失败归因于 context drift，而非模型能力不足**（2025 行业数据）

**Runner 现状**:
- `CostTracker` 跟踪 token 消耗但 record() 未被调用（TODO-036）
- 无 context utilization 百分比计算
- 无 degradation 信号/事件
- 无主动 compact 建议
- ContextCompactor 被动触发，无预防性监控

**Action**:
- [ ] `ContextMonitor` 类：每轮计算 `currentTokens / contextWindowSize` 百分比
- [ ] 发出 `StreamEvent.CONTEXT_WARNING` 事件（新 EventType）：
  - 40% → `CONTEXT_MILD_PRESSURE`（建议 compact）
  - 60% → `CONTEXT_HIGH_PRESSURE`（强烈建议 compact）
  - 80% → `CONTEXT_CRITICAL`（自动触发 compact）
- [ ] 阈值可通过 `AgentProfile.contextPressureThresholds` 配置
- [ ] 与 TODO-051 (4-Layer Compaction) 联动：不同压力级别触发不同层级的 compaction
- **Priority**: P1 — 长会话质量保障，行业数据证实 context drift 是头号失败原因
- **Effort**: 2d
- **Depends on**: TODO-036 (CostTracker.record) — 需要 token 计数数据

### TODO-060: Prompt Caching 3-Layer 结构优化

**Reference**: Claude Code prompt cache 3 层组织（从最稳定到最易变）：
```
Layer 1: System Prompt — 核心指令 + tool definitions
  ↳ 失效条件: tool definitions 变更, Claude Code 升级
  ↳ cache_control: ephemeral 标记在此层末尾

Layer 2: Project Context — CLAUDE.md + auto memory + rules
  ↳ 失效条件: session 开始, /clear, /compact
  ↳ cache_control: ephemeral 标记在此层末尾

Layer 3: Conversation — 消息 + 工具结果
  ↳ 每轮都变（新内容追加），不标记 cache_control
```

**Micro-compact hot/cold path**:
- **Cold path**: 保留最近 N 个 tool results，替换旧的为 placeholder
- **Hot path**（有 cached content 时）: 使用 API `cache_edits` 原地移除引用，保护 cached prefix 不被打断

**14 个 cache-break vectors**: model 切换、effort 变更、fast mode 切换、MCP server 连接/断开、plugin 启用/禁用、deny tool、/compact、Claude Code 升级、session 恢复后重处理 等

**Runner 现状**:
- TODO-048 提出基础 prompt caching 但未实施
- 无分层 cache 结构
- CompactionChain 无 cache-aware 逻辑

**Action**（在 TODO-048 基础上细化）:
- [ ] ClaudeProvider request body 分三层组装：system → project → conversation
- [ ] Layer 1 和 Layer 2 末尾各添加 `cache_control: {"type": "ephemeral"}`
- [ ] Layer 3 不标记（每轮变化）
- [ ] `MicroCompactor` 增加 hot-path 模式：当检测到 cached prefix 时，仅替换 prefix 后的旧 tool results
- [ ] 记录 cache-break 事件日志，帮助诊断缓存失效原因
- [ ] 确保 system prompt + tool definitions 总 tokens > 4096（Opus 最低缓存阈值）
- **Priority**: P0（与 TODO-048 合并，升级方案细节）
- **Effort**: 3d（含 hot/cold path micro-compact）
- **Merges into**: TODO-048

### TODO-061: Layered Loop Composition

**Reference**: arXiv 2604.03515 "Inside the Scaffold" 论文分析了 13 个开源 coding agent 的架构：
- **11/13 agent 使用 layered loop composition**，而非单一 ReAct loop
- 生产级 agent 在 ReAct loop 之上叠加: retry loops, test-repair loops, planning primitives
- Agent 架构更准确地描述为 "loop primitives 的组合沿连续谱分布"
- 范围从: 固定 pipeline → 顺序 ReAct → 分阶段 workflow → 深度优先树搜索 → 完整 MCTS

**Claude Code 实践**: 
- 基础 while loop + tool retry + context compact-and-retry + model fallback
- Plan mode: 先规划再执行（frontier model 规划，cheaper model 执行）

**Runner 现状**:
- 单一 ReAct loop (`ToolCallingLoop`)
- ResilientLLMProvider 有 retry 但无 cost-ordering
- 无 test-repair loop（工具失败后不会自动修复重试）
- 无 planning phase（直接进入工具调用）
- 无 model fallback chain

**Action**:
- [ ] 设计 `LoopPrimitive` 接口：`RetryLoop`, `TestRepairLoop`, `PlanExecuteLoop`
- [ ] `RetryLoop`: 工具执行失败 → 分析错误 → 修正参数 → 重试（max 3 times）
- [ ] `TestRepairLoop`: 代码修改后自动运行测试 → 测试失败 → 分析 → 修复 → 重测
- [ ] `PlanExecuteLoop`: 先让 LLM 生成步骤计划 → 逐步执行 → 回报进度
- [ ] `ToolCallingLoop` 作为基础层，上层 loop primitives 可叠加组合
- [ ] 配置驱动: `AgentProfile.loopPrimitives` 声明启用哪些 loop 层
- **Priority**: P2 — 长期架构演进方向
- **Effort**: 5d（RetryLoop + TestRepairLoop）
- **Note**: 目前 runner 的单一 ReAct 足以覆盖基础场景，此项为进阶优化

### TODO-064: Error Classification & Cost-First Recovery

**Reference**: Claude Code error recovery 策略 — 成本排序原则：
```
Level 1: Free recovery — 重试相同请求（transient errors: rate limit, timeout）
Level 2: Cheap recovery — compact context + retry（context_length_exceeded）
Level 3: Moderate recovery — model fallback（primary model unavailable → cheaper model）
Level 4: Expensive recovery — LLM 分析错误 + 修正参数 + retry
Level 5: User escalation — 无法自动恢复，请求用户介入
```

**Runner 现状**:
- `ResilientLLMProvider.isRetryable()` 返回 `true`（TODO-041: 所有错误都重试，无分类）
- 无 context_length_exceeded 处理（TODO-045: compact-and-retry 未实现）
- 无 model fallback（TODO-062）
- 无 cost-based 优先级排序

**Action**:
- [ ] `LLMProviderException` 新增 `ErrorCategory` enum: `TRANSIENT`, `CONTEXT_OVERFLOW`, `MODEL_UNAVAILABLE`, `VALIDATION`, `SAFETY_BLOCK`, `UNKNOWN`
- [ ] 根据 HTTP status + error message 自动分类: 429 → TRANSIENT, `context_length_exceeded` → CONTEXT_OVERFLOW, 400 → VALIDATION, etc.
- [ ] `ResilientLLMProvider` recovery chain 按成本排序:
  1. TRANSIENT → retry with exponential backoff + jitter
  2. CONTEXT_OVERFLOW → compact-and-retry (TODO-045/051)
  3. MODEL_UNAVAILABLE → model fallback (TODO-062)
  4. VALIDATION → fail fast (don't retry)
  5. SAFETY_BLOCK → fail fast + notify user
- [ ] 记录 recovery 成本指标（retries count, compactions triggered, fallbacks used）
- **Priority**: P1 — 生产稳定性 + 成本控制
- **Effort**: 2d
- **Merges**: TODO-041 (isRetryable)
- **Depends on**: TODO-062 (Model Fallback) for level 3, TODO-051 (Compaction) for level 2

## Continuous Analysis Notes

- **频率**: 每日一份 `YYYY-MM-DD.md`
- **收敛**: 已落地的 todo → `docs/decisions/` ADR；已放弃的标 ~~strikethrough~~
- **trigger**: 外部重要变更 / 代码审查发现新问题 → 立刻新增条目
- **本轮关键洞见**:
  1. **Parallel Tool Execution 是被忽视的性能瓶颈** — 所有主流框架（Claude Code/SDK、OpenAI SDK、LangGraph）都支持 read-only tools 并行执行，runner 全串行是显著差距
  2. **Guardrails 应作为独立 primitive** — OpenAI SDK 将 Guardrails 与 Agent/Tool/Handoff 并列为 4 大核心概念之一，runner 的 soul-safety 模块已有但未集成到管线中是浪费
  3. **Context degradation 是量化的** — Claude Code 6852 session 数据证实 40-50% context 利用率开始显著退化，runner 无任何监控手段
  4. **MCP Tool Annotations 是并行执行的前置条件** — readOnlyHint 标注决定了哪些工具可以安全并行，这是一个低成本（1d）高回报的改动
  5. **Error classification 是 model fallback 和 compact-and-retry 的前置条件** — 当前 isRetryable() 默认 true 导致所有错误无差别重试，需要先分类才能分流
  6. **Loop composition 是长期演进方向** — 11/13 生产级 coding agent 使用多层 loop 组合，单一 ReAct 不够

- **P0 5 轮未动的行动建议**: 建议 hard freeze 所有新功能开发，集中 4 周 sprint 清理 P0 债务。按 Sprint 1-4 顺序执行可在 4 周内解决 11 个 TODO（含自动解决的 3 个）。
