### TODO-054: MCP WebSocket Transport 资源泄漏 — HttpClient + Scheduler 未跟踪关闭

**文件**: `agent-mcp/.../transport/WebSocketMcpClientTransport.java`

**问题**: 新增的 WebSocket transport 存在两个资源管理隐患：

1. **HttpClient 每次 connect() 新建但从不关闭** (L97-99):
   ```java
   HttpClient httpClient = HttpClient.newBuilder()
       .connectTimeout(connectTimeout)
       .build();
   ```
   JDK 11+ 的 `HttpClient` 内部持有 NIO selector thread pool + connection pool。每次 connect() 创建新实例但无 close()，重连场景下线程泄漏。

2. **ScheduledExecutorService 是实例级字段** (L54-59):
   `scheduler` 在构造时创建，`closeGracefully()` 中 `shutdownNow()` — 但如果 transport 从未 connect() 就被 GC，scheduler 线程永不回收（daemon=true 缓解但不彻底）。

3. **InboundListener.buffer 非线程安全** (L173):
   `StringBuilder buffer` 在 WebSocket.Listener 回调中使用，JDK WebSocket 规范保证 `onText` 不会并发调用同一 Listener，但如果 `onClose`/`onError` 与 `onText` 交叉，buffer 可能处于不一致状态。

**Reference**: Claude Code Rust 重写中，WebSocket client 使用 `Arc<Mutex<>>` 保护共享状态 + `Drop` trait 自动清理资源。OpenClaw 的 transport 层使用连接池 + 引用计数。

**Action**:
- [ ] HttpClient 提升为实例字段，connect() 复用；closeGracefully() 中 close() 释放
- [ ] 或使用 HttpClient.newBuilder() 一次，connect()/reconnect() 共享
- [ ] `closeGracefully()` 中确保 scheduler.awaitTermination() 后再关闭 WebSocket
- [ ] 考虑 `buffer.setLength(0)` 放在 `onClose`/`onError` 中做防御性清理
- **Priority**: P1 — 长时间运行场景下的资源泄漏
- **Effort**: 1d

### TODO-056: Anthropic Compaction API 接入 — 替代自研 L4 Summarization

**Reference**: Anthropic 2026 年发布 production-ready Compaction API:
- 自动检测 context 利用率，在适当时机触发 compaction
- 支持 Claude API、AWS Bedrock、Google Vertex AI、Microsoft Foundry
- Zero Data Retention (ZDR) 兼容
- 替代自研 LLM summarization，降低维护成本

**2026 社区共识**:
- **Trigger-based compaction at 70%**: 当 context 利用率达到 70% 时主动触发（而非等到 overflow 被动触发）
- **Anchored iterative summarization**: 将新摘要合并到持久化 state 中（而非每次全量重建），准确性 + 连续性显著优于 full-reconstruction
- **成本排序**: free truncation → micro → paid summarization → paid full-rewrite（与 Claude Code 5-layer 一致）
- **65% 企业 AI 失败归因于 context drift/memory loss**，而非 raw context 耗尽

**Runner 适用分析**:
- L1-L3（Budget Reduction + Snip + Micro）保持自研（free 操作，无需 API）
- L4（Summarization）可以考虑接入 Anthropic Compaction API 而非自研
- 70% 阈值触发: 在 AgentLoop.buildMessages() 中检测 token 占用率，达到 70% 主动触发 L1-L3
- Overflow 触发: 捕获 400 context_length_exceeded → emergency compact（L1-L4 全量）→ retry

**Action**:
- [ ] 在 `ContextCompactor` 中添加 `utilizationRatio()` 方法，基于 `CostTracker` 已记录的 token 数 / `LLMOptions.maxContextTokens` 计算
- [ ] 当 utilization > 70% 时，主动触发 L1-L3 compaction（free，不等 overflow）
- [ ] 评估 Anthropic Compaction API 是否适合作为 L4 实现（vs 自研 summarization prompt）
- [ ] 如接入 API: 在 `ClaudeProvider` 层面处理，对 `ContextCompactor` 透明
- [ ] 如自研: 实现 `SummarizationCompactor`，使用 anchored iterative summarization 策略
- **Priority**: P1 — 长会话稳定性 + 65% 企业失败归因于此
- **Effort**: 2d（70% 触发 + L1-L3 proactive）+ 3d（L4 实现，API 或自研）
- **Depends on**: TODO-036 (CostTracker.record) 修复后才能计算 utilization
- **Extends**: TODO-051

### TODO-057: 四层栈标准化 — model → runtime → harness → agent

**Reference**: 2026 AI agent 社区已收敛到统一四层栈模型：

```
Layer 4: Agent        — 任务级逻辑（profiles, routing, delegation）
Layer 3: Harness      — 非 AI 基础设施（hooks, permissions, compaction, cost tracking, observability）
Layer 2: Runtime      — 核心循环（agent loop, tool calling loop, streaming）
Layer 1: Model        — LLM provider abstraction（Claude, OpenRouter, etc.）
```

**GSD 2、LangChain Deep Agents、独立创作者教程** 全部独立分解出相同的四层栈。这不是巧合，是对 AI agent 系统本质复杂度的共识。

**Runner 现状映射**:

| 四层栈 | Runner 对应 | 完备度 |
|---|---|---|
| Agent (L4) | `Orchestrator`, `AgentProfile`, `SubagentRuntime` | ✅ 80% (缺 handoff/delegate) |
| Harness (L3) | `AgentObserver`, `CompactionChain`, `CostTracker` | ⚠️ 30% (hooks=void, compaction=2层, cost=空壳) |
| Runtime (L2) | `AgentLoop`, `ToolCallingLoop`, `ToolExecutor` | ⚠️ 60% (3 路径不一致, 无 timeout) |
| Model (L1) | `LLMProvider`, `ClaudeProvider`, `OpenRouterProvider` | ✅ 70% (缺 native reactive, prompt cache) |

**关键洞见**: runner 的 **Harness 层（L3）是最薄弱的环节**，仅 30% 完备。而 Claude Code 泄露源码的分析（VILA-Lab）揭示：**1.6% AI / 98.4% 基础设施** — 绝大部分代码量和复杂度在 Harness 层。runner 的投入分布恰好相反。

**Action**:
- [ ] 在 `docs/architecture.md` 中明确标注四层栈映射
- [ ] Harness 层（L3）作为 P0 投资重点，具体分解为：
  - Hooks: TODO-047/055
  - Compaction: TODO-051/056
  - Cost: TODO-036/048
  - Permissions: TODO-050
  - Observability: TODO-008
- [ ] 确保新代码/新功能归入正确的层级（避免 Harness 逻辑散落在 Runtime 中）
- **Priority**: P1 — 架构方向性指导
- **Effort**: 1d（文档）+ 持续（按层投资）

### TODO-058: Subagent Fan-Out 能力差距 — runner 1:1 vs Claude Code 1:1000

**Reference**: Claude Code v2.1.154+ 引入 research preview 级 subagent fan-out:
- Claude 编写 JavaScript 编排脚本
- Background runtime 将脚本扇出到 **最多 1000 个 subagent**
- 中间状态保存在脚本变量中，**不占用 context window**
- 每个 subagent 有独立 scoped conversation

**OpenClaw ACP**:
- `sessions_spawn` 异步 spawn 到独立 session
- `sessions_send` 直接消息通信
- Gateway 统一路由、后台任务状态、delivery、bindings、policy
- Harness 拥有 provider login、model catalog、filesystem 行为、native tools

**Runner 现状**:
- `SpawnSubagentTool` + `WaitSubagentTool` = 1:1 spawn/wait 模式
- `SubagentRuntime` 使用 `ConcurrentHashMap` 内存管理
- 无批量 fan-out、无编排脚本、无跨 session 通信
- SubagentRun 状态重启即丢失

**Action**:
- [ ] 短期: `SpawnSubagentTool` 支持批量 spawn（接受 agent list 参数，返回 run IDs）
- [ ] 中期: `WaitSubagentTool` 支持 `waitAll(runIds)` / `waitAny(runIds)` 语义
- [ ] 长期: 评估编排脚本模式（intermediate state outside context window 是关键创新）
- [ ] 与 TODO-046 (Task Brain) 结合：SubagentRun 持久化到 SQLite
- **Priority**: P2 — 当前 1:1 模式足够覆盖大部分场景，1:N 是差异化能力
- **Effort**: 2d（批量 spawn + waitAll）+ 5d（编排脚本模式）
