## 一、工具系统优化

### 1.1 延迟工具加载（Deferred Tool Loading）
- **现状**：`ToolRegistry` 启动时加载全部工具 schema，所有 `ToolDefinition` 一次性注入 `LLMOptions.toolDefinitions`，占用 context window
- **参考**：Claude Code 的 `ToolSearch` 机制——工具 schema 按需加载，未 fetch 的工具只有名字，不占 context
- **优化方案**：
  - [ ] `ToolRegistry` 增加 `getDeferredDefinitions()` 方法，返回仅含 name+description 的轻量列表
  - [ ] 新增 `ToolSearchTool`，LLM 可通过关键字搜索并动态加载完整 schema
  - [ ] `LLMOptions` 支持 `deferredToolNames` 字段，只传轻量描述给 LLM
  - [ ] `ToolCallingLoop` 在检测到 deferred tool 调用时，自动 fetch schema 并重新 prompt
- **影响**：大幅减少 context 消耗，工具数量不再受 context window 限制
- **优先级**：P0（工具数量增长后的瓶颈）

### 1.2 工具权限分层（Layered Tool Permissions）
- **现状**：`ScopedToolRegistry` 仅有 deny > allow 二元过滤，无权限提示/审批机制
- **参考**：Claude Code 的三层权限模型 auto-allow → user-configurable → always-confirm
- **优化方案**：
  - [ ] `Tool` 接口增加 `PermissionLevel` 枚举（AUTO, CONFIGURABLE, ALWAYS_CONFIRM）
  - [ ] `ToolExecutor` 在执行前检查权限级别，ALWAYS_CONFIRM 类工具通过 `AgentObserver.onPreToolUse()` 发送审批事件
  - [ ] 前端（agent-web）支持权限审批流的 WebSocket 事件
- **优先级**：P1（安全性增强，BashTool 等高危工具需要）

### 1.3 工具沙箱执行（Tool Sandboxing）
- **现状**：`BashTool` 直接执行 shell 命令，无沙箱隔离
- **参考**：Claude Code 的 sandbox 模式、容器化执行
- **优化方案**：
  - [ ] `BashTool` 增加沙箱模式（基于 Linux namespace 或 Docker 容器）
  - [ ] 工具审计日志：所有工具执行记录到 `ToolAuditLog`（工具名、参数、结果、耗时、调用者 agentId）
- **优先级**：P1

## 二、Context 管理优化

### 2.1 Compaction Pipeline 增强
- **现状**：`CompactionChain` 组合 `SnipCompactor(3)` + `MicroCompactor(2000)`，但策略固定
- **参考**：LangGraph 的 checkpointing + 多策略组合；社区实践中的 importance scoring
- **优化方案**：
  - [ ] 新增 `SummaryCompactor`：调用 LLM 对被删除的历史消息生成摘要，保留语义信息
  - [ ] 新增 `PriorityCompactor`：按消息重要性评分（系统消息 > 用户消息 > 工具结果）选择性压缩
  - [ ] `CompactionChain` 支持动态配置策略优先级，按 token budget 自适应选择压缩深度
  - [ ] 工具结果截断优化：保留结构化摘要而非简单首尾截断
- **优先级**：P0（长对话场景的核心痛点）

### 2.2 Checkpointing 与 Replay
- **现状**：`InterruptibleRun` 支持 interrupt/resume，但无持久化检查点
- **参考**：LangGraph 的 SQLite/Postgres/Redis checkpointer，支持 time-travel debugging
- **优化方案**：
  - [ ] 新增 `CheckpointStore` 接口（save/load/list snapshots）
  - [ ] `AgentLoop` 在每轮 tool calling 迭代后自动保存 checkpoint
  - [ ] 支持从任意 checkpoint 恢复执行（用于调试和故障恢复）
  - [ ] 配合 `StreamEvent` 实现 event replay 能力
- **优先级**：P2（调试和容错增强）

## 三、多 Agent 编排优化

### 3.1 Agent 编排模式扩展
- **现状**：`SubagentRuntime` 基于 spawn/wait 模式，类似 fork-join
- **参考**：LangGraph 的 StateGraph（图状态机）、OpenAI Agents SDK 的 Handoff 模式
- **优化方案**：
  - [ ] 新增 `HandoffTool`：Agent A 可以将完整对话上下文移交给 Agent B（不同于 spawn 的独立上下文）
  - [ ] 新增 `AgentPipeline`：支持顺序编排多个 Agent（Agent A 输出 → Agent B 输入 → Agent C 输入）
  - [ ] 考虑引入轻量级 StateGraph：定义 Agent 间的条件路由（if/else 分支、循环）
- **影响**：当前 spawn/wait 适合并行任务，但不适合需要上下文传递的顺序/条件编排
- **优先级**：P1

### 3.2 Agent Composability
- **现状**：Agent 通过 `AgentProfile` 配置，但组合能力有限
- **参考**：LangGraph sub-graphs、OpenAI agent-as-tool
- **优化方案**：
  - [ ] `AgentProfile` 支持 `childAgents` 配置，自动注册子 Agent 可用的 spawn/wait 工具
  - [ ] Agent 可作为 Tool 暴露给其他 Agent（agent-as-tool 模式），简化调用方式
- **优先级**：P2

## 四、LLM Provider 韧性

### 4.1 多 Provider 容错
- **现状**：`ResilientLLMProvider` 存在但 Claude 和 OpenRouter 之间无自动 fallback
- **参考**：LiteLLM 的 unified interface + automatic failover、Circuit Breaker 模式
- **优化方案**：
  - [ ] `ResilientLLMProvider` 增加 fallback chain 配置：Claude → OpenRouter → WebSocket
  - [ ] 引入 Circuit Breaker（基于 Resilience4j 或自实现）：连续 N 次失败后自动切换 provider
  - [ ] 支持 provider 健康检查（定期 ping）和自动恢复
  - [ ] 重试策略统一：exponential backoff（2s, 4s, 8s, 16s），最多 4 次
- **优先级**：P0（生产环境必需）

### 4.2 Token 计数精确化
- **现状**：`CostTracker` 使用近似 token 计数
- **参考**：Claude API 返回的 `usage.input_tokens` / `usage.output_tokens`
- **优化方案**：
  - [ ] `LLMResponse` 解析实际 API 返回的 token 用量，回写 `CostTracker`
  - [ ] 近似计数仅用于预判（是否可能超 budget），实际扣减使用 API 返回值
- **优先级**：P1

## 五、内存与状态管理

### 5.1 分层内存架构
- **现状**：三层内存（Session / Ephemeral / Durable），但缺少语义搜索和实体记忆
- **参考**：CrewAI 的四层内存（short-term / long-term / entity / semantic）；向量检索
- **优化方案**：
  - [ ] `kernel-memory` 的 BM25 检索增加向量检索通道（embedding + cosine similarity）
  - [ ] 新增 `EntityMemory`：从对话中提取实体关系（人名、项目名、技术栈），构建知识图谱
  - [ ] `MemoryProvider` 接口扩展 `search(query, topK)` 方法，支持语义检索
  - [ ] 跨 session 的记忆共享机制（同一用户不同 session 间的知识迁移）
- **优先级**：P1（长期交互场景的核心能力）

### 5.2 SessionKey 校验
- **现状**：sessionKey 命名空间隔离依赖调用方正确构造，无校验
- **优化方案**：
  - [ ] `SessionKeyBuilder` 工具类，强制使用 builder 模式构造 sessionKey
  - [ ] `MemoryProvider` 在 save/load 时校验 sessionKey 格式
- **优先级**：P2

## 六、可观测性

### 6.1 结构化 Tracing
- **现状**：`Tracer` / `SpanContext` 存在但功能有限，`CostTracker` 仅跟踪 token
- **参考**：OpenAI Agents SDK 的 native tracing、OpenTelemetry 标准
- **优化方案**：
  - [ ] `Tracer` 对齐 OpenTelemetry Span 模型：traceId, spanId, parentSpanId, attributes, events
  - [ ] 每个 AgentLoop 执行自动创建 Span，ToolCallingLoop 每轮迭代创建子 Span
  - [ ] Subagent 的 Span 自动关联父 Agent 的 traceId
  - [ ] 导出适配器：Jaeger / Zipkin / OTLP
  - [ ] `StreamEvent.TRACE` 事件携带 SpanContext，前端可展示调用链路图
- **优先级**：P1（生产环境调试必需）

### 6.2 指标收集（Metrics）
- **优化方案**：
  - [ ] 工具调用频率、耗时、成功率
  - [ ] LLM 调用延迟、token 消耗趋势
  - [ ] Agent 生命周期统计（创建、完成、中断、超时）
  - [ ] 暴露 Prometheus 端点（Spring Boot Actuator + Micrometer）
- **优先级**：P2

## 七、代码质量与技术债

### 7.1 废弃包清理
- **现状**：`.instruction`、`.skill`、`.plugin` 包标记 deprecated 但仍存在
- **优化方案**：
  - [ ] 所有 deprecated 类添加 `@Deprecated(forRemoval = true, since = "0.2.0")` 注解
  - [ ] 创建迁移指南文档 `docs/guides/migration-from-deprecated.md`
  - [ ] 下一个 major 版本移除
- **优先级**：P2

### 7.2 依赖版本统一
- **现状**：SQLite JDBC 版本不一致（agent-web 用 3.44.1.0，kernel-memory/soul-user 用 3.45.1.0）
- **优化方案**：
  - [ ] 所有依赖版本收敛到 parent pom.xml 的 `<dependencyManagement>`
  - [ ] 定期依赖升级扫描（Dependabot 或 Renovate）
- **优先级**：P2

### 7.3 集成测试补全
- **现状**：192 个测试类，但缺少 multi-agent interrupt/resume 集成测试
- **优化方案**：
  - [ ] 新增 `OrchestratorInterruptResumeAcceptanceTest`：模拟用户中断 + 恢复的完整流程
  - [ ] 新增 `SubagentCascadeStopAcceptanceTest`：验证级联停止的正确性
  - [ ] 新增 `CompactionChainAcceptanceTest`：验证长对话场景下的压缩效果
- **优先级**：P1

### 7.4 ToolContext 类型安全
- **现状**：`ToolContext.metadata` 是 `Map<String, Object>`，类型不安全
- **参考**：OpenAI Agents SDK 的 typed context variables
- **优化方案**：
  - [ ] 新增 `TypedContextKey<T>` 泛型 key，替代 string key
  - [ ] `ToolContext` 提供 `<T> T get(TypedContextKey<T> key)` 方法
  - [ ] 渐进式迁移：保留旧 API，新增类型安全 API
- **优先级**：P2

## 八、Guardrails 与安全

### 8.1 输入输出护栏
- **现状**：`soul-safety` 有 crisis detection，但无通用的 input/output validation 层
- **参考**：OpenAI Agents SDK 的 Guardrails（input/output validation，可短路执行）
- **优化方案**：
  - [ ] 新增 `Guardrail` 接口：`validate(input/output) → GuardrailResult(pass/fail/warn)`
  - [ ] `AgentLoop` 在 LLM 调用前后分别执行 input/output guardrails
  - [ ] 内置 guardrails：敏感信息检测（API key、密码）、输出格式校验、长度限制
  - [ ] Guardrail 失败可配置为阻断（abort）或警告（warn + continue）
- **优先级**：P1

## 九、MCP 增强

### 9.1 MCP Resource & Prompt 原语支持
- **现状**：`agent-mcp` 仅桥接 MCP tools，不支持 MCP 的 Resource 和 Prompt 原语
- **参考**：MCP 规范定义了 Tools / Resources / Prompts 三大原语
- **优化方案**：
  - [ ] `McpResourceProvider`：将 MCP Resources 映射为 `MemoryProvider` 可检索的内容
  - [ ] `McpPromptProvider`：将 MCP Prompts 映射为 `Skill` 可使用的 prompt 模板
  - [ ] MCP 服务器连接超时保护（启动时避免阻塞）
- **优先级**：P2
