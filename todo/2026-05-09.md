## 一、工具系统优化

### 1.1 延迟工具加载（Deferred Tool Loading）
- **现状**：`ToolRegistry` 启动时加载全部工具 schema，所有 `ToolDefinition` 一次性注入 `LLMOptions.toolDefinitions`，占用 context window
- **参考**：
  - Claude Code：~40 tools 注册，但 schema 按需加载。`ToolSearch` 工具接受关键字查询，返回匹配工具的完整 JSONSchema，未 fetch 的工具仅存名字不占 context
  - OpenClaw：Capability-based plugin 系统，按 registration behavior 分类（plain/hybrid/hook-only/non-capability），ClawHub 注册表支持语义搜索（向量嵌入索引）
- **优化方案**：
  - [ ] `ToolRegistry` 增加 `getDeferredDefinitions()` 方法，返回仅含 name+description 的轻量列表
  - [ ] 新增 `ToolSearchTool`（参考 Claude Code 实现），LLM 通过关键字/语义搜索动态加载完整 schema
  - [ ] `LLMOptions` 支持 `deferredToolNames` 字段，仅传轻量描述给 LLM
  - [ ] `ToolCallingLoop` 在检测到 deferred tool 调用时，自动 fetch schema 并重新 prompt
  - [ ] 参考 OpenClaw ClawHub，考虑工具 schema 的版本化和语义索引
- **影响**：大幅减少 context 消耗，工具数量不再受 context window 限制
- **优先级**：P0（工具数量增长后的瓶颈）

### 1.2 工具权限分层（Layered Tool Permissions）
- **现状**：`ScopedToolRegistry` 仅有 deny > allow 二元过滤，无权限提示/审批机制
- **参考**：
  - Claude Code（源码泄露）：**7 种权限模式** + ML 自动分类器（93% 自动审批率）。关键设计——推理与权限执行分离：模型决定要做什么，另一个系统决定是否允许（即使模型被 jailbreak 也无法绕过安全检查，因为是不同代码路径）
  - Claude Code Hook Pipeline：生命周期事件钩子（PreToolUse, UserPromptSubmit, PermissionRequest），exit code 0=允许, 2=阻断, 其他=警告继续
  - OpenClaw：Gateway 信任模型——本地连接自动审批，远程连接需签名 challenge nonce，设备 token 在配对后发放
- **优化方案**：
  - [ ] `Tool` 接口增加 `PermissionLevel` 枚举（AUTO, CONFIGURABLE, ALWAYS_CONFIRM）
  - [ ] 新增 `PermissionGate` 接口（参考 Claude Code），将权限判定从工具执行中解耦
  - [ ] `ToolExecutor` 在执行前查询 `PermissionGate`，ALWAYS_CONFIRM 类工具发送审批事件到前端
  - [ ] `AgentObserver.onPreToolUse()` hook 支持 exit code 语义（allow/block/warn）
  - [ ] 前端（agent-web）支持权限审批流的 WebSocket 事件
- **优先级**：P0（安全性核心，Claude Code 将推理与权限执行分离的设计值得参考）

### 1.3 工具沙箱执行（Tool Sandboxing）
- **现状**：`BashTool` 直接执行 shell 命令，无沙箱隔离
- **参考**：
  - Claude Code：完整 sandbox 模式，environment-gated 和 feature-gated 工具注册
  - OpenAI Agents SDK v0.14.0：Sandbox Agents，使用 configured filesystems 的计算环境
- **优化方案**：
  - [ ] `BashTool` 增加沙箱模式（基于 Linux namespace 或 Docker 容器）
  - [ ] 工具审计日志：所有工具执行记录到 `ToolAuditLog`（工具名、参数、结果、耗时、调用者 agentId）
  - [ ] 工具注册支持 environment-gate（不同环境暴露不同工具集）
- **优先级**：P1

## 二、Context 管理优化

### 2.1 五层 Compaction Pipeline（对标 Claude Code）
- **现状**：`CompactionChain` 组合 `SnipCompactor(3)` + `MicroCompactor(2000)`，仅 2 层策略
- **参考**：Claude Code 源码泄露揭示的 **5 层上下文压缩流水线**（每次 API 调用前顺序执行，最便宜的先运行）：
  1. **Budget Reduction**：工具输出超 50K 字符时，全文写磁盘，context 仅保留 ~2KB 预览 + 文件路径
  2. **Snip**：删除较旧的历史片段（受 `HISTORY_SNIP` feature flag 控制）
  3. **Microcompact**：细粒度压缩，可选 cache-aware 模式（受 `CACHED_MICROCOMPACT` flag 控制）
  4. **Context Collapse**：对话历史的读时投影——替换 `messagesForQuery` 为折叠视图，不修改完整历史
  5. **Auto-Compact**：context 超阈值时触发模型生成摘要（用户可配置阈值）
  - 设计原则："defer as long as possible, keep it as cheap as possible, escalate in stages"
  - **Session Memory 创新**：后台进程持续维护结构化 markdown 笔记。压缩需要时直接使用这些预维护的笔记作为摘要——无需额外 LLM 调用
- **优化方案**：
  - [ ] **Layer 1 - BudgetReductionCompactor**：工具结果超阈值时写磁盘，context 仅保留摘要+路径引用
  - [ ] **Layer 2 - SnipCompactor（已有）**：增加 feature flag 控制，保留 N 轮可配置
  - [ ] **Layer 3 - MicroCompactor（已有）**：增加 cache-aware 模式，避免压缩已被 LLM 缓存的 prefix
  - [ ] **Layer 4 - ContextCollapseCompactor**：读时投影，不修改原始历史，折叠为精简视图
  - [ ] **Layer 5 - AutoCompactor**：context 超阈值触发 LLM 摘要，阈值可配置
  - [ ] **Session Memory**：后台异步维护结构化笔记（类似 Claude Code），压缩时直接使用预维护笔记替代实时 LLM 摘要
  - [ ] `CompactionChain` 支持 feature flag 动态开关每层策略
- **影响**：从 2 层升级为 5 层渐进式压缩，显著提升长对话 context 利用效率
- **优先级**：P0（最高杠杆优化点——Claude Code 98.4% 是确定性基础设施，context 管理是核心）

### 2.2 Checkpointing 与 Replay
- **现状**：`InterruptibleRun` 支持 interrupt/resume，但无持久化检查点
- **参考**：
  - LangGraph：SQLite/Postgres/Redis checkpointer，支持 time-travel debugging
  - 新兴模式 Durable Execution（Temporal/Cadence）：工作流从检查点恢复，崩溃或网络问题后继续
- **优化方案**：
  - [ ] 新增 `CheckpointStore` 接口（save/load/list snapshots）
  - [ ] `AgentLoop` 在每轮 tool calling 迭代后自动保存 checkpoint
  - [ ] 支持从任意 checkpoint 恢复执行（用于调试和故障恢复）
  - [ ] 配合 `StreamEvent` 实现 event replay 能力（event sourcing 模式）
- **优先级**：P2（调试和容错增强）

## 三、多 Agent 编排优化

### 3.1 Lane Queue 并发控制（对标 OpenClaw）
- **现状**：`SubagentRuntime` 使用 `Executors.newFixedThreadPool(maxSpawnDepth)` 管理并发，无细粒度队列
- **参考**：OpenClaw 的 **Lane Queue System**——关键架构创新：
  - Global Lane (main)：可配 maxConcurrent（默认 4）
  - Session Lane（per session key）：并发 1（严格串行）
  - Sub-agent Lane：并发 8
  - Cron Lane：与 main 并行
  - 原子性保证：agent 完成当前 thought-action-observation 周期后才接收下一条消息
  - 串行优先设计：刻意对比默认并行系统，防止竞态条件
- **优化方案**：
  - [ ] 新增 `LaneQueue` 抽象：可配并发度的任务队列，按 session/agent/cron 分 lane
  - [ ] `SubagentRuntime` 迁移到 `LaneQueue`，支持 per-session 串行 + cross-session 并行
  - [ ] 原子性保证：每个 ToolCallingLoop 迭代是原子单元，新消息在迭代间注入
  - [ ] Cron Lane 支持定时任务（心跳、内存整理、健康检查）
- **优先级**：P1（并发正确性的基础设施）

### 3.2 Agent 编排模式扩展
- **现状**：`SubagentRuntime` 基于 spawn/wait 模式，类似 fork-join
- **参考**：
  - OpenAI Agents SDK：Manager 模式（中央编排器调用子 agent 作为 tool）+ Handoff 模式（peer agent 间转移控制+对话状态）
  - LangGraph：StateGraph 图状态机（条件边 + reducer-driven state）
  - OpenClaw：Session-based message passing（sessions_list/history/send/spawn），无中央编排器
  - Claude Code：Agent Teams——一个 session 作为 team lead，通过共享任务列表协调，队友在各自 context window 运行
- **优化方案**：
  - [ ] 新增 `HandoffTool`：Agent A 将完整对话上下文移交给 Agent B（对比 spawn 的独立上下文）
  - [ ] 新增 `AgentPipeline`：顺序编排（A 输出 → B 输入 → C 输入）
  - [ ] 新增 `SessionMessageTool`：参考 OpenClaw 的 sessions_send，Agent 间异步消息传递
  - [ ] 新增 Agent Teams 模式：team lead + shared task list + 独立 context worker
- **影响**：补充 spawn/wait 之外的编排维度——上下文传递、消息传递、任务协调
- **优先级**：P1

### 3.3 Agent Composability
- **现状**：Agent 通过 `AgentProfile` 配置，但组合能力有限
- **参考**：
  - LangGraph sub-graphs
  - OpenAI agent-as-tool
  - OpenClaw workspace 配置文件（AGENTS.md 定义 agent、TOOLS.md 定义能力）
  - Claude Code 的 `.claude/agents/` 目录（Markdown + YAML frontmatter 声明式 agent 定义）
- **优化方案**：
  - [ ] 支持声明式 Agent 定义：Markdown + YAML frontmatter 或纯 YAML 文件
  - [ ] `AgentProfile` 支持 `childAgents` 配置，自动注册子 Agent 可用的 spawn/wait 工具
  - [ ] Agent 可作为 Tool 暴露给其他 Agent（agent-as-tool 模式）
- **优先级**：P2

## 五、内存与状态管理

### 5.1 QMD 混合检索引擎（对标 OpenClaw）
- **现状**：`kernel-memory` 有 BM25 检索 + 向量检索，三层内存（Session / Ephemeral / Durable）
- **参考**：OpenClaw 的 **QMD (Query-Memory-Document) Engine**：
  - 混合搜索：BM25 关键字搜索 + 向量语义搜索并行执行
  - Reciprocal Rank Fusion 合并两路结果
  - 本地 LLM re-ranking（无需 API key）
  - 召回率从 ~45% 提升到 ~92%
  - 全部本地运行，零外部依赖
  - 默认后端：SQLite + FTS5 + sqlite-vec（单 binary RAG stack）
- **runner 已有基础**：`kernel-memory` 已有 BM25 和向量检索，SQLite 后端
- **优化方案**：
  - [ ] 实现 Reciprocal Rank Fusion：合并 BM25 和向量检索结果的排序融合算法
  - [ ] 增加 re-ranking 层：可选本地模型或 LLM API 对 top-N 结果重排序
  - [ ] 基准测试：对比当前召回率 vs QMD 模式的提升
  - [ ] 新增 `EntityMemory`：从对话提取实体关系（人名、项目名、技术栈），构建知识图谱
  - [ ] 跨 session 记忆共享机制（同一用户不同 session 间的知识迁移）
- **优先级**：P1（长期交互场景核心能力，runner 已有基础可快速迭代）

### 5.2 三层自愈记忆（对标 Claude Code）
- **现状**：内存直接存储在 `MemoryProvider`，无分层加载策略
- **参考**：Claude Code 源码泄露揭示的 **三层自愈记忆架构**：
  - **Index 层**：便宜，始终加载（目录/摘要信息）
  - **Topic 层**：按需获取（仅相关话题时加载）
  - **Transcript 层**：从不直接加载（原始对话记录）
  - 设计目标：保持工作记忆干净，同时不丢失对历史信息的访问能力
- **优化方案**：
  - [ ] `MemoryProvider` 接口增加分层加载 API：`loadIndex()`, `loadTopic(topicId)`, `loadTranscript(transcriptId)`
  - [ ] Session Memory 后台维护：异步更新 index 和 topic 摘要
  - [ ] context 组装时仅加载 index + 相关 topic，transcript 作为工具可按需检索
- **优先级**：P1

### 5.3 SessionKey 校验
- **现状**：sessionKey 命名空间隔离依赖调用方正确构造，无校验
- **优化方案**：
  - [ ] `SessionKeyBuilder` 工具类，强制使用 builder 模式构造 sessionKey
  - [ ] `MemoryProvider` 在 save/load 时校验 sessionKey 格式
- **优先级**：P2

## 附录 A：参考架构深度对比

| 维度 | runner 现状 | Claude Code（源码泄露） | OpenClaw | LangGraph | OpenAI Agents SDK |
|------|------------|----------------------|----------|-----------|-------------------|
| Agent Loop | while 循环 + Reactor Flux | AsyncGenerator while(true), 7 个 yield 点 | ReAct + Lane Queue 串行 | Graph nodes + 条件边 | Handoff chains |
| 工具加载 | 全量加载 | ~40 tools, 延迟加载 ToolSearch | Capability plugins, ClawHub 语义索引 | 全量 | 全量 + auto-schema |
| 权限模型 | deny > allow | 7 模式 + ML 分类器 (93% 自动) | Gateway 信任模型 + nonce | 无 | Guardrails |
| Context 压缩 | 2 层 (Snip+Micro) | 5 层流水线 + Session Memory | Filesystem + QMD | Reducer state + Checkpoint | 无 |
| 内存 | 三层 (Session/Ephemeral/Durable) | 三层自愈 (Index/Topic/Transcript) | Filesystem MD + SQLite + QMD | Checkpoint persistence | Per-run ephemeral |
| 多 Agent | spawn/wait fork-join | Agent Teams + 共享任务列表 | Session message passing | Explicit graph topology | Manager + Handoff |
| 并发控制 | FixedThreadPool | 单线程 + h2A 双缓冲 | Lane Queue (4 种 lane) | Per-node streaming | 无显式控制 |
| 流式 | Flux\<StreamEvent\> | AsyncGenerator yield + h2A | Event-driven 状态机 + 心跳 | Per-node token streaming | Full streaming |

| 可扩展性 | 5 种 ToolSource | MCP + plugins + skills + hooks | Capabilities + skills + hooks + A2A | Custom nodes/edges | Tools + handoffs + guardrails |
| 类型安全 | Map\<String,Object\> | TypeScript 原生 | TypeBox schemas | TypedDict + Annotated | Pydantic |
