### TODO-054: MCP WebSocket Transport 会话重初始化缺失

**文件**: `agent-mcp/.../transport/WebSocketMcpClientTransport.java:38-40`

**问题**: WebSocket transport 的 reconnection 逻辑在 transport 层重建 WebSocket 连接，但 javadoc 明确声明：
> "断连重连仅在 transport 层重建 WebSocket 连接；MCP 会话级别的重新 initialize 不在本实现范围内（v1）。"

这意味着 reconnect 后：
- MCP 会话状态可能已失效（server 端可能已重启、session 过期）
- Server 端的工具列表可能已变更，但 client 侧使用的仍是旧的 `discoveredTools`
- `progressToken` 路由器中的未完成 token 可能悬空

**Reference**:
- MCP 2026 Roadmap 明确 "session creation and resumption" 是四大优先项之一
- OpenClaw 的 MCP client 在 reconnect 后自动触发 `initialize()` + `tools/list` 刷新

**Impact**: WebSocket 断连恢复后工具调用可能静默失败或返回陈旧结果。

**Action**:
- [ ] `WebSocketMcpClientTransport` reconnect 成功后通知上层 `McpToolClient`
- [ ] `McpToolClient` 收到 reconnect 通知后自动触发 `asyncClient.initialize()` + `refreshTools(registeredRegistry)`
- [ ] 添加 reconnect 事件回调接口（`OnReconnectListener`）
- [ ] 清理 `progressRouter` 和 `loggingRouter` 中的悬空 token
- **Priority**: P1 — WebSocket 场景下的可靠性保障
- **Effort**: 1-2d

### TODO-055: MCP Sampling Handler 安全风险 — LLM 反向代理注入

**文件**: `agent-mcp/.../McpToolClient.java:77-84` (Builder.samplingHandler)

**问题**: `samplingHandler` 允许 MCP Server 在 `tools/call` 处理过程中向 Client 发送 `sampling/createMessage` 请求，要求 Client 协助生成 LLM 响应。这本质上是一个 **LLM 反向代理通道**。

如果 MCP Server 被攻击者控制（或本身是不受信任的第三方服务），可以：
1. **Token 消耗攻击** — 在一次 tools/call 中发送大量 sampling 请求，消耗 client 的 LLM token 预算
2. **Prompt 注入** — 通过 createMessage 的 `messages` 字段注入恶意 prompt，引导 client 的 LLM 生成有害内容
3. **信息泄露** — createMessage 的 response 可能包含 client 侧的敏感上下文

**当前实现**: `Mono.fromCallable(() -> sampling.apply(request))` 无任何保护措施。

**Reference**:
- OWASP Agentic AI Top 10 — ASI03 (Tool Misuse): "agents misusing or abusing tools through unsafe composition"
- OpenClaw v2026.5.18: sampling 请求需要 `hooks.allowConversationAccess: true` 显式 opt-in
- Claude Code: MCP server 输出统一标记为 untrusted

**Action**:
- [ ] 添加 sampling request rate limiter（每次 tools/call 最多 N 次 sampling 请求）
- [ ] 添加 sampling request token budget（独立于主 session 的 CostTracker）
- [ ] createMessage request 的 messages 字段经过 sanitize（去除注入向量）
- [ ] logging: 记录每个 sampling 请求的 server name + token 消耗
- [ ] 可选: `Builder.samplingPolicy(SamplingPolicy)` — ALLOW_ALL / RATE_LIMITED / DENY
- **Priority**: P1 — 新增攻击面
- **Effort**: 1d

### TODO-061: AgentLoop.run() Sync 路径完整性修复（049 的快速前置步骤）

**文件**: `agent-kernel/.../agent/AgentLoop.java:117-123`

**问题**: 本轮再次确认 `AgentLoop.run()` 构建 ToolCallingLoop 时：
```java
ToolCallingLoop loop = ToolCallingLoop.builder()
    .provider(llmProvider)
    .toolExecutor(toolExecutor)
    .maxIterations(maxToolIterations)
    .build();   // ← 缺少 cancellationToken, costTracker, observers, tracer
```

对比 `runReactive()` (L244-252)：
```java
ToolCallingLoop.Builder loopBuilder = ToolCallingLoop.builder()
    .provider(llmProvider)
    .toolExecutor(toolExecutor)
    .maxIterations(maxToolIterations)
    .observers(observers);   // ← 有 observers
if (cancellationToken != null) {
    loopBuilder.cancellationToken(cancellationToken);  // ← 有 cancellationToken
}
```

reactive 路径也缺少 `costTracker` 和 `tracer`！

**完整性 Matrix (5-28 确认版)**:

| Builder 参数 | run() sync | runReactive() | 应有 |
|---|---|---|---|
| provider | ✅ | ✅ | ✅ |
| toolExecutor | ✅ | ✅ | ✅ |
| maxIterations | ✅ | ✅ | ✅ |
| observers | ❌ **缺失** | ✅ | ✅ |
| cancellationToken | ❌ **缺失** | ✅ | ✅ |
| costTracker | ❌ **缺失** | ❌ **缺失** | ✅ |
| tracer | ❌ **缺失** | ❌ **缺失** | ✅ |

**新发现**: 即使是 reactive 路径也缺少 costTracker 和 tracer 注入！这意味着：
- CostTracker 即使有人调用 record()，也不会被传到 ToolCallingLoop
- Tracer 在 ToolCallingLoop 中使用 NOOP（默认值），所有 span 都是空操作

**Action**:
- [ ] `run()` 路径补齐所有 Builder 参数（observers, cancellationToken）
- [ ] `runReactive()` 路径补齐 costTracker + tracer
- [ ] AgentLoop.Builder 添加 `tracer(Tracer)` 和 `costTracker(CostTracker)` 参数
- [ ] 写 acceptance test: 验证 sync 路径的 PreToolUse hook 被触发
- [ ] 写 acceptance test: 验证 reactive 路径的 CostTracker.record() 被调用
- **Priority**: P0 — 这是 TODO-035/036/049 的最小修复版本
- **Effort**: 0.5d（不含 TODO-049 的完整统一重构）
- **Quick win**: 即使不做 TODO-049 的完整统一，也能先补齐参数传递
