### TODO-054: ClaudeProvider 序列化三重缺陷（阻塞 Multi-Turn Tool Calling）

**文件**: `agent-kernel/.../llm/claude/ClaudeProvider.java:263-347`

**本轮逐行审查发现三个相互关联的序列化缺陷，共同导致 Claude API 的 multi-turn tool calling 完全无法工作：**

#### 缺陷 A: tool_result 格式错误（L314-332, L338-348）

```java
// 现状（L341）：TOOL 消息被当作 plain text user message
case TOOL:
    return "user";  // ← 错误！Claude API 要求 tool_result 是 content block

// buildMessagesArray() L327：直接用 textContent
messageNode.put("content", msg.getTextContent());
```

**Claude API 正确格式**:
```json
{
  "role": "user",
  "content": [
    {
      "type": "tool_result",
      "tool_use_id": "toolu_xxx",
      "content": "执行结果文本"
    }
  ]
}
```

**Runner 发送的格式**: `{"role": "user", "content": "执行结果文本"}` — 无 tool_use_id，无 tool_result 类型标记。

#### 缺陷 B: assistant 消息中 tool_calls 历史丢失（L324-328）

```java
// buildMessagesArray() 对 ASSISTANT 消息也只取 textContent
messageNode.put("content", msg.getTextContent());
// 但 LLM 返回的 assistant 消息可能包含 tool_use content blocks
// metadata 中有 tool_calls 但从未序列化到请求 body
```

**Claude API 要求**: 当 assistant 消息包含 tool_use 时，必须序列化为 content 数组（含 text + tool_use blocks），否则 API 返回 400 `invalid_request_error`。

#### 缺陷 C: system prompt 格式不支持 content array（L282-284）

```java
root.put("system", systemPrompt);  // 字符串格式
```

**Prompt caching 需要**: `system` 必须是 content block 数组格式才能添加 `cache_control` 标记。

```json
{
  "system": [
    {
      "type": "text",
      "text": "...",
      "cache_control": {"type": "ephemeral"}
    }
  ]
}
```

**影响**:
- 缺陷 A+B 导致 multi-turn tool calling 实际上无法工作（第二轮 LLM 调用会 400 或产生混乱的结果）
- 缺陷 C 阻塞 TODO-048（Prompt Caching）的实现
- 三个缺陷需要一起修复才有意义

**Action**:
- [ ] `buildMessagesArray()` 重构：TOOL 消息序列化为 `{"role":"user","content":[{"type":"tool_result","tool_use_id":"...","content":"..."}]}`
- [ ] ASSISTANT 消息序列化检查 metadata 中的 tool_calls，存在时序列化为 content 数组（text + tool_use blocks）
- [ ] `system` 从 string 改为 content block array 格式
- [ ] 添加序列化往返测试：构造多轮 tool 对话 → 序列化 → 反序列化 → 验证 tool_use_id 对应关系
- **Priority**: **P0** — 阻塞所有涉及 Claude API multi-turn tool calling 的路径
- **Effort**: 2d（含测试）
- **Blocks**: TODO-048 (Prompt Caching 依赖 system content array 格式)

### TODO-060: CliTool 命令注入 — args 拆分绕过

**文件**: `agent-kernel/.../cli/CliTool.java:149-169`

```java
private List<String> buildCommand(Path entryPoint, Map<String, Object> args) {
    // ...
    Object argsObj = args.get("args");
    if (argsObj instanceof String argsStr && !argsStr.isBlank()) {
        for (String arg : argsStr.split("\\s+")) {
            command.add(arg);  // ← 直接添加用户/LLM 提供的参数
        }
    }
    // 支持任意 key=value 形式的参数
    args.forEach((key, value) -> {
        if (!"args".equals(key) && value != null) {
            command.add("--" + key);
            command.add(value.toString());  // ← 值直接传入

    });
    return command;
}
```

**问题**:
1. LLM 可以传入任意 args 字符串，通过 shell metacharacter 注入命令

4. 无路径遍历检查（entryPoint 已限制在 cliDirectory 下，但 args 中可能包含 `../../` 路径）

**Claude Code 对照**: 23 项 Bash 安全检查，包括：
- 命令黑名单（`rm -rf /`, `sudo`, `dd`, `mkfs`, `chmod 777`）
- 管道/重定向检测（`|`, `>`, `>>`, `;`, `&&`, `||`）
- Shell metacharacter 转义
- 路径遍历检测

**Action**:
- [ ] 添加参数消毒：移除 shell metacharacters（`;`, `|`, `>`, `<`, `` ` ``, `$(`, `&`）
- [ ] 添加命令黑名单检查（配置化）
- [ ] 添加路径遍历检测（`../` 检查）
- [ ] 考虑将 CliTool 的 `executeStreaming` 包裹在 Docker container 中（中期方案）
- **Priority**: P0 — 安全漏洞
- **Effort**: 1d（参数消毒 + 黑名单）

### TODO-062: Lazy Skill/Tool Loading — OpenClaw 核心架构差异

**Reference**: OpenClaw 最核心的架构决策之一 — 13,000+ skills 不膨胀 system prompt。

**OpenClaw 三层加载模型**:
```
Layer 1: Metadata (always in context)
  - Skill name + ~100 char description
  - 13,000 skills × 100 chars ≈ 1.3M chars → 仍需筛选

Layer 2: Full SKILL.md (loaded on trigger)
  - 当 model 判断需要某 skill 时读取完整内容
  - 通过 tool call 触发: read_skill(name)

Layer 3: Bundled Resources (executed without context injection)
  - 工具执行时使用，不读入 LLM context
```

**Runner 现状**:
- AgentLoop 构造器（L78-86）一次性将所有 `toolRegistry.getEnabled()` 注册为 Skill
- LLMOptions.toolDefinitions 包含所有 enabled 工具的完整 JSON Schema
- 随着工具数量增长，system prompt 和 tool definitions 线性膨胀
- 典型 20 个工具 × 500 chars/tool = 10K chars；100 个工具 = 50K chars（超出 prompt cache 有效范围）

**Claude Code 对照**: 默认 <20 tools 在 context 中，其余通过 `ToolSearch` 按需激活。

**Action**:
- [ ] 短期: ToolRegistry 支持 `toolLoadingMode` 配置（EAGER / LAZY）
- [ ] 短期: LAZY 模式下，LLMOptions.toolDefinitions 仅包含 compact 描述（name + description），不含 input_schema
- [ ] 中期: 新增 `tool_search` 内置工具，让 LLM 按关键词搜索可用工具（ToolRegistry.search 已存在但未暴露给 LLM）
- [ ] 中期: 当 LLM 调用 `tool_search` 找到目标工具后，动态将完整 schema 注入到后续请求的 toolDefinitions
- [ ] 长期: 按 AgentProfile 配置 always-loaded vs on-demand 工具列表
- **Priority**: P2 — 当前工具数量较少（<30），暂不紧急；超过 50 个工具时会成为 prompt token 瓶颈
- **Effort**: 2d（短期 + 中期）
- **Reference**: OpenClaw Skills Docs, Claude Code ToolSearch Pattern

## Updated External Research Insights

### OpenClaw 2026.5 关键新变化（相比 05-22 增量）

**项目概况更新**: GitHub 370K+ stars，MIT 许可证，创建者 Peter Steinberger (@steipete)。核心架构是 **hub-and-spoke**，以 Gateway 为中心的控制面板连接 20+ 消息通道（WhatsApp, Telegram, Slack, Discord, Signal, iMessage, IRC, Teams 等）。

**Agent Loop 核心流程（序列化 per-session，避免工具竞态）**:
1. Intake（消息接收）→ 2. Context Assembly（session 历史 + 4 组件 system prompt）→ 3. Model Inference（流式调用）→ 4. Tool Execution（拦截 tool calls）→ 5. Streaming Replies（平台适配格式化）→ 6. Persistence（session index 更新）

**关键设计决策 — Lazy Skill Loading（与 runner 差异最大的点）**:
- System prompt 仅包含 **compact skill list**（每个 ~100 字符的 name + description），不注入完整 skill 内容
- 当 model 决定需要某 skill 时，**按需读取** 完整 `SKILL.md`
- 13,000+ 社区 skills 不会膨胀 base prompt
- 三层加载: Metadata（始终在 context）→ Full SKILL.md（触发时加载）→ Bundled resources（执行时使用，不读入 context）

### Claude Code 泄露源码深度分析（512K Lines TypeScript, 1906 Files）

**规模**: 2026-03-31 通过 npm package `@anthropic-ai/claude-code` v2.1.88 的 source map 意外暴露。基于 Bun 运行时，自定义 React 终端渲染器。

**Agent Loop 核心** (`query.ts`, 1729 行): async generator `queryLoop` + `while(true)` 循环。关键特性：
- 工具调用 **mid-stream 检测** — 不等完整响应就开始执行工具
- 并行工具执行 when possible
- ~40 个 discrete tools，每个携带自己的 permission logic、concurrency declarations、progress reporting、UI rendering

**Permission Model** (6 级):
`default` → `acceptEdits` → `plan` → `dontAsk` → `bypassPermissions` + auto mode (model-based risk classifier)

**隐藏特性**:
- **KAIROS** — always-on background agent，使用 `autoDream` 在用户空闲时进行 memory consolidation
- **Stealth Mode** — 在 public open-source repos 中隐藏内部信息
- 44 个 hidden feature flags
- 内部 model codenames: Capybara = Claude 4.6 variant, Fennec = Opus 4.6

**Claw Code**: 社区 clean-room Python + Rust 重写（48K+ stars），将 512K 行 TypeScript 缩减至 ~20K 行 Rust，保留了 agent loop、40+ tools、on-demand skill loading、context compression、subagent spawning。

**第 13 个 Harness Pattern: Defensive Serialization**

Claude Code provider 层的序列化具有以下防御特性：
1. **tool_result 严格类型化** — 每个 tool_result 必须包含 `tool_use_id`，且与前序 assistant 消息的 `tool_use.id` 一一对应
2. **content block array** — 所有消息的 content 都使用 array 格式（即使只有一个 text block），为未来扩展（image、file、thinking）预留
3. **tool_calls 往返保真** — assistant 消息序列化时保留完整的 tool_use blocks，确保上下文窗口中的 tool calling 历史可追溯
4. **streaming reassembly safeguards** — 流式解析中处理 partial JSON（`input_json_delta` 可能在任意 Unicode 边界断开）、空 delta、乱序 event

**Runner 对照**: 以上 4 点全部缺失。TODO-054 就是修复前 3 点。第 4 点 runner 的 completeStream() L213 有 `currentToolJson.append(delta.get("partial_json").asText())`，但无 Unicode 边界处理和乱序检测。

## 2026 AI Agent 框架最佳实践（跨框架共识）

基于 LangGraph 0.4+、AutoGen/AG2/MAF 1.0、CrewAI 0.10+、MCP 1.2、Google ADK 1.0 的综合分析：

### 10 条生产级 Agent 设计原则

| # | 原则 | Runner 状态 | 优先级 |
|---|---|---|---|
| 1 | **Streaming-first** — SSE 增量渲染，mid-stream tool call 检测 | ✅ Flux\<StreamEvent\> | - |
| 2 | **Context budget awareness** — 多层 compaction + on-demand loading + cache-aware cost tracking | ⚠️ 2 层 compaction，无 cache tracking | P0 |
| 3 | **Tool-first extensibility** — tools 携带 permission logic + concurrency decl + progress reporting | ⚠️ Tool 接口齐全但无 permission logic | P1 |
| 4 | **Serialized agent loops** — per-session 串行避免竞态和状态腐化 | ⚠️ reactive 自然串行但无显式约束 | P2 |
| 5 | **On-demand skill loading** — metadata 始终在 context，full content 按需加载 | ❌ 一次性全量注入（TODO-058） | P2 |
| 6 | **Multi-layer permission models** — per-tool risk classification + escalation paths | ❌ 仅 ScopedToolRegistry deny/allow | P1 |
| 7 | **Observability built in** — OTEL spans across all agent operations | ❌ 自定义 Tracer，无 OTEL SDK | P1 |
| 8 | **Human-in-the-loop checkpoints** — critical decisions 非 error-only | ❌ 无交互中断机制（MCP 1.2 Elicitation） | P2 |
| 9 | **Cost controls** — per-request limits, max iteration counts, real-time budget monitoring | ⚠️ CostTracker 存在但 record() 从未调用 | P0 |
| 10 | **Protocol standardization** — MCP for tools, A2A for cross-agent | ⚠️ MCP 0.17（1.2 未跟进）；无 A2A | P2 |

### 框架级洞见

- **LangGraph**: 状态管理是生产 agent 事故的 #1 原因（60%+ incidents）。Runner 的 InMemoryProvider 在生产环境中不够用，kernel-memory 的 FileMemoryProvider + SQLite 是正确方向。
- **AutoGen/AG2 → MAF**: 微软将 AutoGen 和 Semantic Kernel 合并为 Microsoft Agent Framework 1.0 GA。核心抽象：Plugins（可扩展性）+ Workflows（协作流程图，含分支/检查点/人类干预）。Runner 的 Orchestrator 类似但缺少 Workflow 抽象。
- **CrewAI**: 团队经常 prototype with CrewAI 然后 **migrate to LangGraph** for production。结构化知识库集成将 delegation accuracy 从 0.33 提升到 0.73。Runner 的 PromptEngine + SkillRegistry 可以参考这个模式。
- **MCP 2026 Roadmap**: Transport evolution for horizontal scaling; agent communication with retry semantics; enterprise readiness (audit trails, SSO, gateway patterns)。Runner 的 agent-mcp 基于 MCP 0.17，需要跟进 1.2。
