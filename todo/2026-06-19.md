## 2. 现在能立刻做的（不需硬件，按优先级）

### 2.1 首响延迟（M1 唯一真风险，🔴）

阶段 1 工具已落（instrument + eager 首块 + 门控 bench）。剩余按依赖排序：

1. **跑 bench 填数**（需 DashScope key）
   - 做什么：`LATENCY_SPIKE=1 OPENROUTER_API_KEY=… OPENROUTER_BASE_URL=… OPENROUTER_MODEL=qwen-plus mvn -pl agent-kernel test -Dtest=LatencySpikeBench`
   - 为什么：定主导段（预期 LLM_TTFT），量 eager 把 chunk_form 降多少。
   - 验收：`docs/latency-spike-results.md` 的 P50/P95/P99 表填满 + 主导段结论。
   - 依赖：DashScope key（仅你有）。
2. **判 eager 接不接生产**（依赖 1 的数）
   - 做什么：若 eager 显著降 chunk_form，把 `FirstChunkPolicy.eagerDefault()` 接进 agent-web `PostProcessorConfig` 的 speakable Bean，按语音 persona/部署开关。
   - 验收：真容器测试证开关生效；升 ADR 记决策。
   - 依赖：bench 数。
3. **max-wait 首块切** ✅（2026-06-19 落）
   - 做了什么：`FirstChunkPolicy` 补时间维度 `maxWaitMillis`——自首个 `TEXT_DELTA` 起墙钟到点仍未发首块即整段
     flush（reactive：上游与 timeout 信号 merge + `takeUntilOther` 取消，首块发出/上游终止即停表，不挂尾延迟）。
   - 为什么：`maxChars` 只约束字符不约束墙钟；长 token 间隔下没标点也没到字符上限会卡首块，max-wait 兜底。
   - 验收：✅ 虚拟时钟确定性测试（`SpeakableChunkProcessorTest` 3 个新例，零真 sleep）+ agent-kernel `mvn clean test` 1105 绿。
     决策记 [ADR-013](../docs/decisions/013-first-chunk-timed-flush.md)。默认未开（`maxWaitMillis=0`），是否接生产看 bench（item 1/2）。
4. **预生成 / speculative**（partial 转写即启 LLM）—— 需 gateway 配合，归 §4/后续。
5. **阶段 2-4 全链 TTFA harness**（EOU / STT-final / TTS-TTFB 隔离 + 端到端）—— 进 voice-gateway，见 §4。
