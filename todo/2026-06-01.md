### TODO-055: MCP WebSocket Transport — 三个残留设计隐患

**文件**: `agent-mcp/.../transport/WebSocketMcpClientTransport.java`

新代码质量高（握手同步、心跳保活、断连语义清晰），但逐行审查发现 3 个待改进项：

#### 55a: 并发状态管理依赖 volatile 而非显式锁

```java
private volatile WebSocket webSocket;      // L63
private volatile boolean connected;         // L64
private volatile boolean closed;            // L65
```

`onOpen` 中先 `webSocket = ws` 再 `connected = true` 再 `open.complete(null)` (L174-182)，
但 `sendMessage` 中检查 `!connected || ws == null` (L126)。
虽然 volatile 保证可见性，但组合状态更新非原子：
- 线程 A 在 `onClose` 中 `connected = false` (L209)
- 线程 B 在 `sendMessage` 中检查 `connected = true`（旧值），继续发送
- 发送到已关闭的 WebSocket → `IllegalStateException` 从 `ws.sendText()` 抛出

风险：实际场景中低概率（心跳周期 30s >> 竞态窗口），但在高频工具调用下可能触发。

#### 55b: `closeGracefully()` 的 `sendClose` 未等待完成

```java
ws.sendClose(WebSocket.NORMAL_CLOSURE, "");  // L149 — fire-and-forget
```

`sendClose` 返回 `CompletableFuture<WebSocket>`，但被忽略。如果 close 帧未发送完就 `scheduler.shutdownNow()`，可能导致非优雅断连。

#### 55c: `InboundListener.buffer` 非线程安全

```java
private final StringBuilder buffer = new StringBuilder();  // L166
```

JDK WebSocket spec 不保证 `onText` 在同一线程被调用。如果多条消息并发到达（MCP server 推送通知 + 响应），`buffer.append()` + `buffer.setLength(0)` 可能交错。

**Action**:
- [ ] 55a: 考虑用 `ReentrantLock` 保护 `connected`/`webSocket`/`closed` 三态组合
- [ ] 55b: `ws.sendClose().thenRun(() -> scheduler.shutdownNow())` 或至少 `.join(connectTimeout)`
- [ ] 55c: `InboundListener` 加 `@GuardedBy` 注释说明线程安全假设，或改用 `StringBuffer`
- **Priority**: P2 — 低概率竞态，但对生产环境有意义
- **Effort**: 1d

### TODO-057: MCP 协议演进 — Streamable HTTP 与 WebSocket 双 Transport 的战略定位

**背景**: MCP 协议 2026 年有两个 transport 方向：
1. **Streamable HTTP** (官方默认) — 无状态短连接 + SSE，每次请求独立 HTTP
2. **WebSocket** (社区推动) — 长连接复用，减少连接开销

Runner 刚实现了 WebSocket transport (`WebSocketMcpClientTransport`)。但需要明确：

**行业趋势观察**:
- Claude Code 使用 stdio transport（本地进程）为主，远程用 Streamable HTTP
- OpenClaw 使用 Docker 容器级 MCP server，stdio 为主
- MCP 官方 SDK 推荐 Streamable HTTP 作为默认 transport
- WebSocket 适合高频工具调用场景（如代码补全、实时搜索）

**Runner 现状**:
- `McpToolClient` 已支持 stdio、Streamable HTTP、WebSocket 三种 transport
- WebSocket transport 有良好的集成测试覆盖（MiniWebSocketServer + round-trip test）
- 但 `McpToolClient` 的重连策略仍是"上层决定"，无内置重连策略接口

**Action**:
- [ ] 定义 `ReconnectionPolicy` 接口（NoReconnect, ExponentialBackoff, LinearBackoff）
- [ ] `McpToolClient` 在检测到断连后，根据 policy 决定是否自动重建 + 重新 initialize
- [ ] 为 WebSocket transport 添加 TLS/WSS 支持验证（当前仅测试 ws://）
- [ ] 考虑 transport 自动选择策略：优先 WebSocket（如有），fallback 到 Streamable HTTP
- **Priority**: P2 — 功能增强
- **Effort**: 2d

### Claude Code 泄露源码关键架构模式 (2026.6 更新 — v2.1.150+)

| Pattern | 描述 | Runner 现状 |
|---|---|---|

**Prompt Caching 3 层 Prefix 架构** (关键新发现):
```
Layer 1: System Prompt (变化最少 — 仅 MCP 连接/升级时变)
Layer 2: Project Context (CLAUDE.md, auto memory — session 开始时读取, 中途不刷新)
Layer 3: Conversation (每轮变化)
```
设计原则：上层变化越少越好 → 缓存命中率越高。CLAUDE.md 中途编辑故意不生效就是为了保护 cache prefix。

**工具执行并行优化** (新发现):
Claude Code 在 `content_block_stop`(tool_use block) 到达时即刻开始工具执行，不等 `message_stop`。同一消息内多个工具调用可并行执行，减少感知延迟。

### 2026 年中开源框架趋势共识

1. **Provider 抽象趋同**: Vercel AI SDK 的 `doStream()` 单方法抽象成为模式。多个框架收敛到"只实现一个 stream 方法，sync 是 stream 的 blocking wrapper"。这与 TODO-049 的方向完全一致。

2. **OTEL 成为标配 (GenAI 语义约定 v1.41)**: OpenClaw、Strands、OpenAI SDK、Vercel AI SDK 均已 OTEL first-class。标准化 `gen_ai.*` 属性 (agent, workflow, tool, model spans + token-usage metrics)。Datadog/Honeycomb/New Relic 已支持。自定义 tracing 方案被逐步淘汰。

3. **Agent-as-Tool + Handoff 双模式普及**:
   - OpenAI SDK: Handoff (转交) + Agent-as-Tool (内联) + Sandbox 执行
   - Microsoft Agent Framework 1.0: 5 种编排 (Sequential/Concurrent/Handoff/Group Chat/Magentic-One)
   - Google ADK: Sequential/Parallel/Loop/Coordinator-Specialist + AutoFlow (LLM 驱动委派)
   - CrewAI: Sequential/Hierarchical/Consensual + Flows
   - Runner 仅有 spawn 模式显得单一

4. **安全成为一等公民 (OWASP Agentic AI Top 10)**:
   - ASI01: Agent Goal Hijacking (指令注入防御)
   - ASI02: Tool Misuse (LLM 视为不可信客户端)
   - ASI05: Unexpected Code Execution (生成与执行分离; 沙箱隔离)
   - ASI06: Memory & Context Poisoning (租户隔离; 过期机制)
   - 核心原则: **Least Agency** — 最小授权

5. **Prompt Caching ROI 极高**: Anthropic 5min TTL 下，交互式 session 几乎每轮命中缓存。3 层 prefix 架构 (system→project→conversation)。cache_control 最多 4 个断点。write +25% / read -90%。

6. **MCP + A2A 双协议标准**: MCP (工具访问层) + A2A (agent-to-agent 通信) 均由 Linux Foundation AAIF 治理。IBM ACP 已并入 A2A。Runner 的 MCP 支持（三种 transport + sampling）是重要优势，但缺少 A2A 支持。

7. **Compaction + Durable Event Log 模式**: Anthropic Agent SDK 的 compaction (auto-summarize) + 持久化 event log (`getEvents()` 可访问任何历史 tool result) 成为长运行 agent 的标准方案。

8. **Java 生态 AI Agent 框架**: Spring AI (最成熟, Micrometer 可观测, A2A 支持), LangChain4j (1.x `langchain4j-agentic` 模块), Google ADK (Java 支持), Google Genkit。Runner 可参照这些框架的 Java 惯用模式。

### TODO-062: A2A (Agent-to-Agent) 协议支持 — 行业标准对齐

**背景**: IBM ACP 已合并入 Google 主导的 A2A 协议（Linux Foundation AAIF 治理）。A2A v1.2 稳定版已被 150+ 组织采用（Microsoft, AWS, Salesforce, SAP）。

**A2A 核心**:

**与 MCP 的关系**: MCP 是工具访问层（agent↔tool），A2A 是 agent 通信层（agent↔agent）。两者互补。

**Runner 现状**: SubagentRuntime 仅支持内部 subagent spawn，无标准化 agent-to-agent 通信。

### TODO-063: Claude Code Dynamic Workflows 模式启示 — 编排脚本外置

**背景**: Claude Code 2026.5 引入 Dynamic Workflows — LLM 生成 JavaScript 编排脚本，独立 runtime 执行，最多 1000 subagent (16 并发)。

- 大规模并行任务（如代码审查、批量重构）缺乏协调机制

- [ ] 评估 "LLM 生成 + 独立执行" 编排模式的可行性
