## 三、新发现 — 本轮深度分析

### TODO-054: Selective Tool Injection — 解决 prompt 膨胀与 token 浪费

**外部参照**:
- Claude Code: 默认 ≤20 tools 注入 prompt，超出部分通过 `search_tools` 工具按需发现
- OpenClaw: 按当前 turn 相关性选择 skill 注入，session 开始时 snapshot skill 集合
- 行业共识: tool definitions 是 prompt 中增长最快的部分（典型 30-80 tokens/tool），50 tools = 1500-4000 tokens

**Runner 现状**:
- `ToolRegistry.getToolDefinitions()` 返回所有注册工具的 JSON Schema
- AgentLoop 在 `buildMessages()` 时将全量 tool definitions 注入 `LLMOptions.toolDefinitions`
- 当前工具数量（内置 + MCP + CLI）可能达到 30-50 个
- 每轮重传 1500-4000 tokens 的 tool definitions，且大部分工具当前 turn 不会用到
- 结合 prompt caching 5min TTL，tool definitions 变更会打断缓存

**Action**:
- [ ] 引入 `ToolSelector` 接口：`List<ToolDefinition> selectTools(ConversationContext context, List<ToolDefinition> all)`
- [ ] 默认实现 `TopNToolSelector`：最常用 N 个工具 + 最近使用过的工具
- [ ] 内置 `search_tools` meta-tool：LLM 可通过此工具发现和激活未注入的工具
- [ ] `ScopedToolRegistry` 在 `getToolDefinitions()` 时应用 ToolSelector 过滤
- [ ] Tool definitions 排序稳定化（保持 cache-friendly order），避免打断 prompt cache
- **Priority**: P1 — 与 TODO-048(Prompt Caching) 协同效果倍增
- **Effort**: 2d
- **Synergy**: TODO-048 (Prompt Caching) — 减少 tool definitions 变更频率提高缓存命中率

### TODO-055: Lane Queue / Serial Session Execution — 并发安全基座

**外部参照**:
- OpenClaw Lane Queue: session 级 strict serial concurrency=1，核心架构创新
  - 全局 lane: 可配置并发数
  - Session lane: 严格串行（concurrency=1），agent 完成当前 TAOR 循环才消费下一消息
  - Sub-agent lane: concurrency=8
  - Cron lane: 与主 lane 并行
- 高优先级 interrupt: 安全终止执行线程 + 文件系统回滚到 "Known Good" snapshot
- 效果: 消除整类竞态条件和工具冲突

**Runner 现状**:
- Orchestrator + InterruptibleRun 有 interrupt/resume 概念
- 但无显式的 "session 级串行保证"：如果同一 session 同时收到两条消息，两条会并发进入 AgentLoop
- WebSocket gateway 的消息调度依赖 Vert.x event loop，但 AgentLoop 执行在 boundedElastic 线程池
- 长时间工具执行期间来新请求，行为未定义（可能并发执行，可能覆盖状态）
- InterruptibleRun 有 check-then-act 竞态（TODO-038）

**Action**:
- [ ] 引入 `SessionLane` 概念：每个 sessionKey 对应一个单线程队列
- [ ] Orchestrator/Gateway 入口处将请求入队，而非直接 dispatch
- [ ] 队列消费者串行执行，确保同一 session 同一时间只有一个 TAOR 循环
- [ ] 高优先级 interrupt 可跳过队列直接终止当前执行
- [ ] 考虑 sub-agent 独立 lane（参考 OpenClaw concurrency=8）
- [ ] 可选：interrupt 后状态回滚（需要与 MemoryProvider 配合做 checkpoint/rollback）
- **Priority**: P1 — 并发安全是生产必备条件
- **Effort**: 3d
- **Blocks**: 无显式依赖，但隐式影响所有并发场景

### TODO-058: Server-Side Tool Execution Timeout — 补全超时保护

**代码审查发现**:
- ToolExecutor L149: `tool.execute()` 直接调用，无超时包裹
- ToolExecutor L374: `tool.executeReactive()` 直接调用，无超时包裹

### TODO-060: Provider-Agnostic Streaming — ClaudeProvider Native Reactive

**代码审查确认**:
- `ClaudeProvider` 无 `completeStreamReactive()` override
- 当前使用 `LLMProvider` 接口默认实现：callback-based `completeStream()` → Flux bridge
- Bridge 层引入额外延迟 + backpressure 语义丢失

**外部参照**:
- Vercel AI SDK: 仅要求 provider 实现 `doStream()` 方法，sync 是 stream 的 blocking wrapper
- OpenClaw: Agent Runtime 原生流式，非 bridge

**Runner 独特需求**:
- Claude API 返回 SSE 流（Server-Sent Events），天然适合 Flux mapping
- OpenRouter API 同样返回 SSE 流
- 当前 bridge 层的问题：
  1. callback sink 无法感知下游 backpressure
  2. 取消信号传递有延迟（需等 callback 返回）
  3. 错误处理路径不一致（callback exception vs Flux.error）

**Action**:
- [ ] `ClaudeProvider.completeStreamReactive()` 原生实现：OkHttp SSE → Flux.create() with onCancel
- [ ] `OpenRouterProvider.completeStreamReactive()` 同理
- [ ] 删除 `LLMProvider` 接口中 callback-based `completeStream()` 的默认 bridge 实现
- [ ] `completeStream()` 的默认实现改为 `completeStreamReactive()` 的 callback wrapper（反转 bridge 方向）
- [ ] 保持 `completeStream()` 作为向后兼容 API，但标记 `@Deprecated(forRemoval=true)`
- **Priority**: P1 — 流式性能和正确性
- **Effort**: 2d
- **Merges**: TODO-039
