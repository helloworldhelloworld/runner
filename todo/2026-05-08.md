### NEW-001: CliTool 进程 IO 线程泄漏 (Resource Leak)

**文件**: `agent-kernel/.../cli/CliTool.java:88-128`

```java
Thread stdoutReader = new Thread(() -> {
    try (BufferedReader reader = ...) {
        // ...
    } catch (IOException ignored) {}  // ← 静默吞异常
}, "cli-stdout-" + getName());
stdoutReader.setDaemon(true);

// 超时后:
process.destroyForcibly();
stdoutReader.interrupt();   // ← 仅设中断标志
stderrReader.interrupt();
// ... 无保证清理
stdoutReader.join(1000);    // ← 仅等1秒，线程可能仍存活
```

**问题**:
1. IOException 被静默吞掉（L96, L109），无法诊断 stream 读取失败
2. 超时后 interrupt + join(1000) 不保证线程终止，daemon 线程可能泄漏
3. 未关闭 process.getInputStream() / getErrorStream()，可能导致 fd 泄漏

**Action**:
- [ ] `catch (IOException ignored)` → `catch (IOException e) { logger.debug("...", e); }`
- [ ] 超时后显式关闭 process streams：`process.getInputStream().close(); process.getErrorStream().close()`
- [ ] join 后检查 isAlive()，如仍存活则 log warn
- **Priority**: P1 — fd 泄漏在高并发场景下可导致 "too many open files"

### NEW-003: StreamingTool.execute() 中 blockFirst() — Reactive 反模式

**文件**: `agent-kernel/.../agent/StreamingTool.java:44-47`

```java
public ToolResult execute(Map<String, Object> args) {
    ToolResultChunk chunk = executeReactive(args)
        .filter(c -> c.getType() == ToolResultChunk.ChunkType.COMPLETE || ...)
        .blockFirst();  // ← 阻塞调用，Reactor 上下文中可能死锁
```

**问题**:
- `blockFirst()` 在 Reactor non-blocking 线程上调用可导致 `IllegalStateException` 或死锁
- Reactor 3.x 严格模式下会直接抛 `BlockingOperationError`

**Reference**: Reactor 官方文档明确禁止在 Scheduler.single/parallel 线程上 block。

**Action**:
- [ ] StreamingTool.execute() 添加 `subscribeOn(Schedulers.boundedElastic())` 包装
- [ ] 或完全去除 execute() 的 block 路径，改为在 ToolExecutor 层面处理同步/异步分支
- **Priority**: P1 — 可能触发 Reactor 3.x 的 BlockingOperationError

### NEW-004: ResilientLLMProvider 重试用 Thread.sleep() 阻塞线程

**文件**: `agent-kernel/.../llm/ResilientLLMProvider.java:227-232`

```java
private void sleep(long ms) {
    try {
        Thread.sleep(ms);  // ← 阻塞执行线程
    } catch (InterruptedException ie) {
        Thread.currentThread().interrupt();
    }
}
```

**调用点**: L99（completeStream retry loop）, L187（complete retry loop）

**问题**: 在高并发下，重试退避阻塞 executor 线程（每次 1s-4s），可耗尽 bounded-elastic 或 cached 线程池。

**Reference**: 
- Vercel AI SDK 用 `setTimeout` 非阻塞重试
- Reactor 标准做法是 `Mono.delay(Duration) → flatMap(retry)`

**Action**:
- [ ] 同步路径 `complete()` 的 sleep 可保留（已在阻塞上下文）
- [ ] 流式路径 `completeStream()` 的重试改用 Reactor `retryWhen(Retry.backoff(maxRetries, Duration.ofSeconds(1)))`
- [ ] 或在 `completeStreamReactive()` 中用 `retryWhen` 原子操作
- **Priority**: P2

## Part 2: 外部框架最新研究洞察

### OpenClaw 2026.5 新发现

基于最新社区讨论和文档更新：

**1. Conversation Checkpointing（对话检查点）**
- OpenClaw 新增对话快照功能：任意时刻保存完整对话状态（消息、工具状态、agent 上下文）
- 支持 "time-travel debugging"——回退到任意检查点重新执行
- **Runner 差距**: 无检查点机制；InterruptibleRun 只保存"最新断点"，无法回退
- **借鉴**: 可在 MemoryProvider 层面添加 `checkpoint(sessionKey)` / `restore(checkpointId)` 接口

**2. Tool Schema Lazy Loading**
- TOOLS.md 只列工具名称和一句话描述
- 完整 JSON Schema 按需加载（LLM 决定调用时才 fetch）
- 节省 60%+ tool definitions 的 token 开销
- **Runner 差距**: ToolRegistry.getToolDefinitions() 一次性返回所有工具的完整 schema
- **借鉴**: 分层 tool discovery——先发送名称+描述，LLM 决定用哪个后再发送完整 schema

**3. Graduated Permission Model（渐进式权限）**
- Level 0: 只读操作（搜索、阅读）— 自动允许
- Level 1: 可逆写操作（文件编辑、git commit）— 首次确认后记住
- Level 2: 不可逆操作（git push、API 调用）— 每次确认
- Level 3: 危险操作（rm -rf、数据库 DDL）— 每次确认 + 二次确认
- **Runner 差距**: ScopedToolRegistry 是 binary 的（allow/deny），无风险分级
- **New TODO**: 给 Tool 接口添加 `RiskLevel` 枚举，ToolExecutor 根据 level 决定是否需要用户确认

### Claude Code 架构深度分析（最新补充）

基于 VILA-Lab 学术论文 (arXiv:2604.14228) 和多份社区逆向报告的综合：

**1. 5-Level Compaction Cascade**
```
Level 1: Snip — 删除旧 tool results（保留最近 N 轮）
Level 2: Micro — 截断大 tool result（head + tail + [snipped X chars]）
Level 3: Summarize — fork 子 LLM 生成对话摘要替换原文
Level 4: Forget — 删除非关键消息（仅保留 system + 最近 3 轮）
Level 5: Reset — 只保留 system prompt + 摘要，完全重置
```
- **Runner 现状**: 只有 Level 1 (Snip) + Level 2 (Micro)
- **差距**: 缺少 Level 3-5 的自动升级策略；长会话最终仍会溢出

**2. Unified Message Format（统一消息格式）**
- Claude Code 内部所有消息都是 `Message` 对象，包含：
  - `role`, `content` (structured blocks), `cache_control`, `metadata`
  - assistant 消息的 content 是 `[{type: "text", text: "..."}, {type: "tool_use", id: "...", name: "...", input: {...}}]`
- **Runner 现状**: `ConversationMessage` 的 content 是 `String`，tool_use 信息在 metadata 中松散存储
- **影响**: 这就是 ClaudeProvider tool_result 格式 bug 的根因——ConversationMessage 设计不支持 structured content blocks

**3. Tool Risk Classification + ML Permission Classifier**
- 静态分类：23 条 bash 安全规则 + tool risk level
- 动态分类：ML classifier 评估当前 tool call 在上下文中的风险
- 7 种权限模式：from "全自动" to "每次确认"
- **Runner 现状**: 无 tool risk classification

**4. Agent-as-OS 模式**
- Claude Code 的本质是：LLM = CPU, Tools = Syscalls, Context = RAM, Compaction = Virtual Memory
- 44 个 feature flags 控制"OS 功能"的启用（如 KAIROS daemon = 后台进程、autoDream = 记忆整合 cron）
- **Runner 启示**: 可以将 agent loop 视为"进程调度器"，subagent 视为"子进程"，这个心智模型有助于架构设计

## Part 3: Structural Content Blocks — 根因分析与设计建议

这是本轮分析的**最重要发现**：`ConversationMessage.content` 是 `String` 这一设计决策是多个已知 bug 的共同根因。

### 影响链

```
ConversationMessage.content = String
  ├── ClaudeProvider tool_result 格式 bug（P0 TODO-003补充）
  │     └── 无法携带 tool_use_id → 多工具并行时 Claude 混淆
  ├── Extended Thinking 无法实现（P2 TODO-025）
  │     └── thinking block 是 structured content，String 无法表达
  ├── Streaming Tool Use 信息丢失（P2 TODO-026）
  │     └── input_json_delta 无处存放
  ├── 图片/文件多模态支持受限
  │     └── image content block 需要 structured format
  └── Memory compaction 精度低
        └── 无法区分 text vs tool_use vs tool_result，只能按字符串处理
```

### 建议设计

```java
public sealed interface ContentBlock {
    record TextBlock(String text) implements ContentBlock {}
    record ToolUseBlock(String id, String name, Map<String,Object> input) implements ContentBlock {}
    record ToolResultBlock(String toolUseId, String content, boolean isError) implements ContentBlock {}
    record ThinkingBlock(String thinking) implements ContentBlock {}
    record ImageBlock(String mediaType, String base64Data) implements ContentBlock {}
}

public class ConversationMessage {
    private final String role;
    private final List<ContentBlock> content;  // ← structured
    private final Map<String, Object> metadata;
}
```

**Action**:
- [ ] 引入 `ContentBlock` sealed interface（Java 21 支持）
- [ ] `ConversationMessage.content` 从 `String` 改为 `List<ContentBlock>`
- [ ] 保留 `getTextContent()` 便利方法（提取所有 TextBlock 拼接）
- [ ] 逐步迁移 ClaudeProvider、ToolCallingLoop、MemoryProvider 到 structured 模式
- **Priority**: P0 — 这是解锁 tool_result 格式修复、Extended Thinking、多模态的前提

## Part 4.5: New Architecture Patterns from Cross-Framework Research（本轮新增的框架级 TODO）

以下为基于 10+ 框架最新实践提炼的**新架构 TODO**，此前分析未覆盖。

### NEW-014: Three-Tier Guardrails (Input / Output / Tool)

**Reference**: OpenAI Agents SDK 1.0 GA 的三层 guardrail 系统

**现状**: `AgentObserver` 提供 onPreToolUse/onPostToolUse 钩子，但**只有观察能力，无拦截能力**——无法拒绝工具调用或终止 agent 执行。`soul-safety/CrisisDetector` 只是被动检测。

**设计**:
```java
public interface InputGuardrail {
    GuardrailResult validate(GatewayRequest request);
    boolean runInParallel(); // true = 与 agent 并行运行，FAIL 时取消 agent
}
public interface OutputGuardrail {
    GuardrailResult validate(AgentResponse response);
}
public interface ToolGuardrail {
    GuardrailResult validateBefore(String toolName, Map<String, Object> args);
    GuardrailResult validateAfter(String toolName, ToolResult result);
}
// GuardrailResult: PASS | FAIL(reason) | REPLACE(newOutput)
```

**Action**:
- [ ] 定义 Guardrail 接口层次（可与现有 AgentObserver 共存）
- [ ] InputGuardrail 接入 Orchestrator（agent 启动前）
- [ ] ToolGuardrail 接入 ToolExecutor（工具执行前后）
- [ ] OutputGuardrail 接入 Gateway（响应返回前）
- [ ] soul-safety/CrisisDetector 实现 InputGuardrail 接口，获得**拦截**能力
- [ ] 新增 GUARDRAIL_BLOCKED StreamEvent 类型
- **Priority**: P1 — 安全关键；与 TODO-001/002 形成互补

### NEW-015: Tool Circuit Breaker（工具熔断器）

**Reference**: 生产环境 Agent 框架（AG2, Cloudflare AI Review）的共识模式

**现状**: ToolExecutor 执行工具后直接返回结果/错误，无重试、无熔断。一个有 bug 的 MCP server 或被限流的 API 可导致 agent 在无限重试中烧完 token budget。

**设计**:
```java
public class ResilientToolExecutor implements ToolExecutor {
    private final ToolExecutor delegate;
    private final Map<String, CircuitBreaker> breakers; // per tool name
    // CircuitBreaker: CLOSED → OPEN (3 consecutive failures) → HALF_OPEN (test recovery)
}
```

**Action**:
- [ ] 创建 CircuitBreaker 状态机（CLOSED/OPEN/HALF_OPEN）
- [ ] ResilientToolExecutor 包装现有 ToolExecutor
- [ ] 工具执行失败 3 次（可配置）后自动熔断，返回 "tool temporarily unavailable" 让 LLM 自适应
- [ ] 新增 TOOL_CIRCUIT_OPEN / TOOL_CIRCUIT_CLOSE StreamEvent
- [ ] 可选：质量熔断（HTTP 200 但语义空结果 3 次也触发）
- **Priority**: P2

### NEW-016: Budget-Aware Agent Loop (BATS Pattern)

**Reference**: BATS 研究（Budget-Aware Tool Selection, 2025.11）— 证明可在 10x 更低成本下达到相当准确率

**现状**: CostTracker 有 `isOverBudget()` 硬停机制，但（1）record() 从未被调用所以永远不触发，（2）即使修复后也是突然终止，无软降级。

**设计**: 在每次 LLM 调用前，根据 token budget 剩余比例注入不同的行为指令：
```
HIGH   (>=70% remaining): 正常模式
MEDIUM (30-70%):          "偏好简洁回答，避免探索性工具调用"
LOW    (10-30%):          "仅使用关键工具，准备总结"
CRITICAL (<10%):          "立即给出最终答案，不再调用工具"
```

**Action**:
- [ ] CostTracker 添加 `SpendingRegime getRegime()` 方法
- [ ] AgentLoop.buildMessages() 在 system prompt 后注入 budget status 消息
- [ ] 新增 BUDGET_REGIME_CHANGE StreamEvent
- [ ] 前端可展示 budget 指示器
- **Priority**: P2（依赖 TODO-010 CostTracker record() 先修复）

### NEW-018: Durable Execution with Checkpoint/Resume

**Reference**: LangGraph 1.0 旗舰功能 — 每个 graph node 执行后自动 checkpoint 到可插拔后端

**现状**: InterruptibleRun 只在内存中保存断点。JVM 重启/容器回收后，运行状态完全丢失。

**设计**:
```java
record Checkpoint(String threadId, int stepIndex, List<ConversationMessage> messages,
                  CostTracker.Snapshot costState, Map<String, Object> metadata, long timestamp) {}

interface CheckpointStore {
    void save(Checkpoint checkpoint);
    Optional<Checkpoint> load(String threadId);
    List<Checkpoint> listByThread(String threadId); // time-travel
}
```

**Action**:
- [ ] 定义 Checkpoint + CheckpointStore 接口
- [ ] InMemoryCheckpointStore (dev) + JdbcCheckpointStore (prod)
- [ ] ToolCallingLoop 每轮工具执行后 checkpoint（"super-step" 边界）
- [ ] InterruptibleRun.resume() 优先从 CheckpointStore 恢复
- [ ] 新增 CHECKPOINT_SAVED StreamEvent
- **Priority**: P3（当前需求场景不强，但架构价值高）
