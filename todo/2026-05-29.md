### TODO-054: MCP WebSocket Transport 实现优化（代码审查发现）

**审查范围**: `WebSocketMcpClientTransport.java` (306 行)

**发现 5 个问题**:

1. **HttpClient 重建泄漏** — `connect()` 每次创建新 `HttpClient`（L90-92），reconnect 时重复创建。HttpClient 内部有线程池，未关闭会泄漏。
   - 修复：HttpClient 提升为实例字段，connect() 复用；closeGracefully() 中关闭。

2. **InboundListener.buffer 线程安全** — `StringBuilder buffer` 在异步 WebSocket callback 中使用（L144），JDK WebSocket.Listener 的 `onText` 在同一 WebSocket 上保证串行调用，但 reconnect 后新 WebSocket 与旧 Listener 并发存在时有竞态窗口。
   - 修复：每次 connect() 创建新 InboundListener 实例。

3. **ScheduledExecutorService 不共享** — 每个 transport 实例创建独立单线程 scheduler（L55-59），多 MCP server 场景浪费线程。
   - 建议：提供 `Builder.scheduler(ScheduledExecutorService)` 允许外部注入共享 scheduler。

4. **Reconnect 不触发 MCP re-initialize** — 注释明确说明"v1 限制"（L39），但 MCP 2026-07-28 RC 的 Stateless core 意味着 reconnect 后需重新 negotiate capabilities。
   - 与 MCP spec 对齐：reconnect 后自动触发 `asyncClient.initialize()` 或通知上层 McpToolClient。

5. **closeGracefully() 阻塞风险** — `ws.sendClose()` 返回 CompletableFuture 但未等待完成（L128），scheduler.shutdownNow() 可能打断正在发送的 close frame。
   - 修复：`ws.sendClose().toCompletableFuture().orTimeout(5, SECONDS).exceptionally(...)` 后再 shutdownNow。

**Action**:
- [ ] HttpClient 提升为实例字段，avoid per-connect 泄漏
- [ ] connect() 创建新 InboundListener 避免 buffer 竞态
- [ ] 提供 `Builder.scheduler()` 注入点
- [ ] closeGracefully() 等待 close frame 发送完成
- [ ] 后续版本：reconnect 后通知上层重新 initialize（需配合 McpToolClient）
- **Priority**: P1 — 生产级 WebSocket 连接的稳定性保障
- **Effort**: 1d

### TODO-055: ExecOsApiTool 安全审计 — 无沙箱 OS API 执行

**审查范围**: `ExecOsApiTool.java` (81 行)

**关键发现**:

`ExecOsApiTool` 通过 `ClientToolDispatcher` 将 OS API 调用派发到端侧执行，LLM 可通过 `apiName` 参数指定任意 OS API。虽然实际执行在端侧（client-side），但存在以下风险：

1. **apiName 无白名单** — 任何 LLM 生成的 `apiName` 字符串都会被转发到端侧执行（L38-40），依赖端侧做验证。
   - 对照 Claude Code: 每个工具调用经过 Permission Pipeline（deny by default）
   - 对照 OpenClaw: ACP 的 approval boundary 要求用户确认高风险操作

2. **参数透传无消毒** — `params` Map 直接透传（L42-47），可能包含注入攻击向量。

3. **错误信息泄漏** — `errorMsg` 直接返回（L66-68），可能暴露端侧系统信息。

**与 TODO-047 (Hook System) 的关系**: 如果有 PreToolUse hook + HookDecision(DENY/ASK)，可以在 server 侧拦截高风险 OS API 调用，而非完全依赖端侧防护。

**Action**:
- [ ] 添加 `apiName` 白名单/黑名单配置（`ExecOsApiTool.allowedApis` / `ExecOsApiTool.deniedApis`）
- [ ] 高风险 API（文件删除、进程管理、网络配置等）默认 deny
- [ ] 参数消毒：深度遍历 params Map 检查嵌套攻击向量
- [ ] 错误信息脱敏：不返回原始 errorMsg，返回通用错误码
- **Priority**: P1 — 与 TODO-001/050 对齐，OS API 执行是高风险路径
- **Effort**: 1d
- **Blocks on**: TODO-047 (Hook System) 可提供统一拦截，但短期独立实现

### TODO-057: Claude Code Dynamic Workflows 启示 — 编排脚本化 vs Context-Resident 编排

**Reference**: Claude Code Dynamic Workflows（2026-05-28 research preview）

**关键架构洞见**:

Claude Code Dynamic Workflows 的核心突破：**编排计划从 model context 移到可执行代码**。

```
传统 multi-agent:   Orchestrator LLM context 中维护 plan → 每轮消耗 tokens → context 膨胀
Dynamic Workflows:  Claude 生成 JS 编排脚本 → background runtime 执行 → model context 只收最终结果
```

**关键数据**:
- 最多 1000 个 subagents/run，16 并发
- 编排逻辑（循环、分支、agent 数量决策）在脚本变量中，不占 model context
- Understand → Change → Verify 三阶段 loop
- Refutation pass：一组 agent 验证，另一组尝试反驳，只有 survive 的结论才返回
- 收敛驱动：不是固定步数 pipeline，而是跑到答案不再变化为止

**Runner 现状**:
- SubagentRuntime 支持 async spawn + wait，但 Orchestrator 层的编排逻辑在 LLM context 中
- 无 "script-based orchestration" 概念
- 无 refutation/verification loop
- 无收敛检测

**与 runner 的适用性分析**:

Runner 目前的规模和用例（交互式 AI 助手）不需要 1000 subagent 级别的编排。但 Dynamic Workflows 的几个设计原则值得借鉴：

1. **Understand-Change-Verify pattern** — runner 的 multi-agent 缺少 verify 阶段。建议：AgentProfile 支持 `verificationAgentId` 字段，任务完成后自动 spawn 验证 agent。
2. **编排逻辑外置** — 长期方向，当 runner 需要复杂编排时（如自动代码审查、多步测试），编排逻辑不应驻留在 LLM context。
3. **收敛驱动而非固定步数** — ToolCallingLoop 的 `maxIterations` 是固定上限，可补充 "连续 N 轮无新 tool call → 提前退出" 的收敛检测。

**Action**:
- [ ] 短期：ToolCallingLoop 增加收敛检测（连续 2 轮 stopReason=end_turn 且无 tool call → 提前退出），替代纯 maxIterations 硬编码
- [ ] 中期：AgentProfile 增加 `verificationAgentId` 字段，支持 Understand-Change-Verify pattern
- [ ] 长期：设计 `WorkflowScript` 接口，支持将编排逻辑从 LLM context 移到外部脚本执行
- **Priority**: P3 — 架构前瞻，非当前瓶颈
- **Effort**: 1d（收敛检测）+ 设计文档（Verify pattern + WorkflowScript）

### TODO-058: Permission Pipeline 三层分离（Claude Code Rust 架构核心模式）

**Reference**: Claude Code Rust 重写架构 — model→permission→tool 三层分离

**Claude Code Permission Pipeline**:
```
Model Layer:      Claude 决定尝试哪个工具 + 什么参数
Permission Layer: 每个 tool invocation 过 permission system（deny by default）
Tool Layer:       通过 permission 后才执行
```

> "The default behavior is to deny or ask rather than allow silently."

**Runner 现状**:
- `ScopedToolRegistry` 有 deny > allow 二级过滤（AgentProfile.toolDenyList / toolAllowList）
- 但过滤发生在 **注册时**（静态），而非 **调用时**（动态）
- 无 per-invocation permission check — 一旦 tool 在 registry 中可见，LLM 可无限制调用
- 无 "ask user" 机制（对高风险操作请求用户确认）
- 无 "deny by default" — 默认所有注册 tool 都可调用

**与 TODO-047 (Hook System) 的关系**:
TODO-047 的 `HookDecision(ALLOW/DENY/ASK/MODIFY)` 本质上就是 Permission Pipeline 的运行时层。两者合并为统一设计：

```
Layer 1 (Static):  ScopedToolRegistry — 注册时过滤（现有）
Layer 2 (Dynamic): PermissionGate — 调用时检查（新增，TODO-047 HookDecision 的具体化）
Layer 3 (Runtime): Tool.execute() — 通过 L1+L2 后才执行
```

**Action**:
- [ ] 将 TODO-047 的 HookDecision 设计具体化为 `PermissionGate` 接口
- [ ] `PermissionGate.check(toolName, args, context)` 返回 `PermissionDecision(ALLOW/DENY/ASK/MODIFY)`
- [ ] ToolCallingLoop 在 firePreToolUse 后增加 `permissionGate.check()` 分支
- [ ] 默认 `PermissionGate` 实现：所有 tool ALLOW（向后兼容），可配置为 deny-by-default
- [ ] 高风险 tool 标记：`@ToolFunction(riskLevel=HIGH)` → 自动触发 ASK
- **Priority**: P1 — 与 TODO-047 合并实施，是安全架构的核心
- **Effort**: 包含在 TODO-047 的 3-5d 中
- **Merges with**: TODO-047 (Hook System)

## Additional Research Insights (2026 Industry Convergence)

### BATS Budget Framework — CostTracker 升级方向

**Reference**: BATS framework (2025.11) — 已成为 token 预算管理的标准模型

4 级支出策略：
- **HIGH** (>=70% remaining): 正常执行，允许昂贵工具
- **MEDIUM** (30-70%): 开始优化，历史轨迹替换为摘要
- **LOW** (10-30%): 限制 LLM 调用，优先 free compaction
- **CRITICAL** (<10%): 仅允许必要操作，触发 emergency compact

**Runner CostTracker 现状**: 只有 `maxBudgetTokens` + `isOverBudget()`（boolean），无分级策略。
**Action**: TODO-036 修复后，参考 BATS 在 CostTracker 添加 `SpendingRegime` 枚举 + `getRegime()` 方法。

### Memory Pointer Pattern — 大 Tool Output 处理

**Reference**: 跨框架共识 — 大 tool output 不应驻留 context

核心思路：tool output 超过阈值（如 200KB）时，写入外部存储，context 中只保留短引用指针（<100 bytes）。后续 LLM 需要时通过 tool call 按需读取。

**Runner 适用性**: TODO-051 L1 BudgetReductionCompactor 的截断方式可升级为 pointer 模式。

### Context Compaction 阈值 — 83.5% 触发

**Reference**: Claude Code 在 context 达到 83.5% 容量时触发 auto-compaction

**Runner 现状**: CompactionChain 无自动触发机制，依赖外部调用。
**Action**: 在 TODO-051 中加入自动触发：ToolCallingLoop 每轮检查 token 使用率，>83% 时自动触发 CompactionChain。

### A2A (Agent2Agent) Protocol — 多 Agent 互操作标准

**Reference**: Google 发起的 A2A 协议（2025.4），现归 Linux Foundation 管理，150+ 组织参与。HTTP + SSE + JSON-RPC 2.0 transport，Agent Cards 声明能力。

与 MCP 互补关系：MCP = agent-to-tool，A2A = agent-to-agent。

**Runner 长期方向**: TODO-052 (Agent Handoff) + TODO-060 (Task Brain) 的远期对外通信层，可考虑 A2A 兼容。

### Spring AI ToolCallingManager — 动态工具解析

**Reference**: Spring AI 的 `ToolCallingManager` + `ToolCallbackResolver` 支持运行时动态解析工具，以及 Tool Argument Augmenter（运行时增强工具参数 schema）。

**Runner 对比**: ToolRegistry 是静态注册 + 扫描模式。缺少运行时 resolve 和参数增强能力。
**与 TODO-047/058 的关系**: Permission Pipeline 可同时在 resolve 阶段做权限检查。

### Claude Code Agent Loop — 88 行核心 vs 51.2 万行基础设施

**关键数据**: Agent loop 核心仅 88 行（1.6%），剩余 98.4% 是确定性基础设施（permission gate、context management、tool routing、recovery logic）。

**启示**: runner 的 ToolCallingLoop + AgentLoop 核心逻辑同样简洁，瓶颈在基础设施层（compaction、permission、cost tracking、hook system）— 正是 P0 债务集中区域。
