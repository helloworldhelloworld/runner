### TODO-054: AgentConfig Provider Wiring 绕过 SPI 注册表

**发现**: `LLMProviderFactory` 已改为 ServiceLoader-based SPI（干净的注册表 + fail-fast 重名检测），但 `AgentConfig.java` 的 provider 创建完全绕过它：

```java
// AgentConfig.java L154-159 — 手动 switch/case
case "openrouter":
    return new ResilientLLMProvider(
        new OpenRouterProvider(apiKey, model, baseUrl), 2, 1000);
```

**问题**:
- SPI 注册表里只有 ClaudeProviderSpi，OpenRouterProvider 没有对应的 Spi 实现
- AgentConfig 手动链式 `new ResilientLLMProvider(new XxxProvider(...))` — 装饰器组合硬编码
- 新增 Provider 仍需改 AgentConfig 的 switch/case，SPI 注册变成摆设
- 与 TODO-010 (LLMProviderChainBuilder 无注册机制) 相关联

**Action**:
- [ ] 为 OpenRouterProvider 创建 `OpenRouterProviderSpi implements LLMProviderSpi`
- [ ] AgentConfig 改为通过 `LLMProviderFactory.create(providerType, apiKey, model)` 创建基础 provider
- [ ] 引入 `LLMProviderChainBuilder`：`factory.create(type) → chain.wrap(resilient, dynamic, tracing)` — 装饰器按 order 配置
- [ ] 保留 `@Value` 配置作为参数来源，但 Provider 选择走 SPI
- **Priority**: P2 — 架构一致性，非阻塞性
- **Effort**: 1d
- **Related**: TODO-010 (原始装饰器组合无注册机制)

### TODO-057: Prompt Cache Stability — Stable-Before-Volatile Ordering

**Reference**: OpenClaw v2026.5.31 的 prompt caching 架构采用关键设计原则：
- **Stable workspace project-context files ordered BEFORE HEARTBEAT.md** — 稳定内容在前，易变内容在后
- **System-prompt fingerprints normalized** — 语义不变的 prompt 共享 KV cache 跨 turn
- 设计目标：最大化 prompt cache hit rate

**Claude Code 实践补充**:
- 14 种 cache-break vectors（tool definitions 变更、system prompt 修改、image 增删等都打断缓存）
- `cache_control` 标记放在 system prompt 末尾和 tool definitions 末尾

**Runner 现状**:
- `PromptEngine.build()` 组装顺序：base prompt + active skills + durable memory + memory snippets
- **问题**: memory snippets（每轮变化）和 skill prompts（可能动态激活）排在 system prompt 末尾
- 这意味着即使启用 prompt caching (TODO-048)，每轮变化的 memory snippets 都会打断缓存

**提议的 cache-friendly 排序**:
```
System Prompt (cache boundary ①):
  1. Base prompt (稳定 — 只随部署变更)
  2. Tool definitions (相对稳定 — 工具集不常变)
  3. Durable memory (稳定 — 长期知识)
  ── cache_control: ephemeral ──
  4. Active skill prompts (半稳定 — 按 session 变化)
  5. Ephemeral memory snippets (易变 — 每轮变化)

Messages (cache boundary ②):
  6. Conversation history (增量增长)
  ── cache_control: ephemeral ──
  7. Latest user message (每轮变化)
```

**Action**:
- [ ] `PromptEngine.build()` 重排组装顺序：base → tools → durable → skills → ephemeral
- [ ] 在 system prompt 最后一个稳定 block 后标记 cache_control（需 TODO-048 先完成）
- [ ] Tool definitions 独立为 system message block（不混入 base prompt text）
- [ ] 添加 system-prompt fingerprint 缓存（SHA256 of stable blocks → 跳过不必要的重新组装）
- **Priority**: P1 — 这是 TODO-048 (Prompt Caching) 的前置优化，决定缓存命中率
- **Effort**: 1d
- **Depends on**: TODO-048 (Prompt Caching 基础实现)

### TODO-058: MCP Integration 与 Tool Ecosystem 统一 — ToolSourceProvider 扩展

**发现**: MCP WebSocket transport 已落地，但 MCP 工具与本地工具的统一还有 gap：

**当前 MCP 集成路径**:
```
McpToolClient → McpAsyncClient → transport(SSE/WebSocket) → MCP Server
  ↓ listTools()
McpToolWrapper (implements Tool) → ToolRegistry
```

**Gap 分析**:
1. **MCP 工具发现是一次性的** — `listTools()` 在启动时调用一次，运行时 MCP server 新增工具不会自动同步
2. **MCP 工具无 lazy loading** — 所有 MCP 工具在启动时全部加载到 ToolRegistry
3. **McpToolSourceProvider 无 start()/stop()** — 虽然 AgentConfig 调用了其他 ToolSourceProvider 的生命周期方法，MCP 工具走独立路径
4. **Sampling handler 已支持** (PR#153)，但 MCP Roots 和 Resources 未集成

**OpenClaw 对照**:
- MCP tools 通过 ACP runtime 动态发现
- Tool definitions 变更会触发 cache-break（影响 prompt caching）
- Plugin 生命周期统一管理

**Action**:
- [ ] `McpToolSourceProvider implements ToolSourceProvider` — 统一 MCP 工具发现到 ToolSourceProvider 生态
- [ ] 支持 MCP `notifications/tools/list_changed` 通知 — 运行时工具热更新
- [ ] Tool definitions 变更时发出 event（为 prompt cache invalidation 预留）
- [ ] 考虑 lazy MCP tool loading — 仅在 LLM 首次请求时 listTools()
- **Priority**: P2 — 工具生态一致性
- **Effort**: 2d

### TODO-063: Deferred Tool Loading — MCP Tool Search 模式

**Reference**: Claude Code 2026.1 引入的 MCP Tool Search 解决了 context pollution 问题：
- 超过 10K tokens 的工具标记 `defer_loading: true` — 仅工具名称消耗 context
- Tool Search 元工具按需发现（每次查询 3-5 个，~3K tokens）
- **85% token overhead 减少**（50+ 工具场景：~77K → ~8.7K tokens）
- Opus 4 准确率：49% → 74%（with Tool Search）

**Runner 现状**:
- `ToolRegistry.getToolDefinitions()` 返回全量工具定义，全部塞入 LLMOptions
- MCP 工具在启动时一次性全部加载
- 20+ 工具时 tool definitions 可能占用 5000+ tokens
- 无按需工具发现机制

**Action**:
- [ ] 设计 `DeferredToolRegistry` — 区分 eager-loaded 和 deferred tools
- [ ] Deferred tools 仅在 LLMOptions.toolDefinitions 中暴露名称+简短描述
- [ ] 内置 `ToolSearchTool` — LLM 通过关键词搜索发现所需工具（复用 `ToolRegistry.search(keyword)` 已有实现）
- [ ] 发现后的工具定义在当前轮次动态注入
- [ ] 可配置阈值：工具数量 > N 时自动启用 deferred loading
- **Priority**: P1 — 直接降低 token 消耗 + 提高 LLM 工具选择准确率
- **Effort**: 2d
- **Reference**: Claude Code MCP Tool Search pattern

### TODO-060: Three-Tier Guardrails（对标 OpenAI Agents SDK）

**Reference**: OpenAI Agents SDK 定义了三层 guardrail 体系：
1. **Input Guardrails** — 在用户输入上运行，与 agent 并行；仅在链中第一个 agent 上触发。覆盖 jailbreak 检测、相关性验证、关键词过滤。
2. **Output Guardrails** — 仅在生成最终输出的 agent 上运行。Agent 先行生成输出，guardrail 并发检查。
3. **Tool Guardrails** — 在每个 tool 调用上运行：调用前 input guardrail + 调用后 output guardrail。

**与 runner Hook System 的关系**:
- TODO-047 (3-Tier Hook) 关注的是 hook handler 的执行能力层（Command/Prompt/Agent）
- TODO-060 关注的是 guardrail 的检查位置（Input/Output/Tool）
- 两者互补：guardrail 决定"在哪里检查"，hook handler 决定"用什么方式检查"

**Action**:
- [ ] 定义 `Guardrail` 接口（`check(context) → GuardrailResult(PASS/FAIL/WARN)`）
- [ ] 支持三个挂载点：`InputGuardrail`（gateway 层）、`OutputGuardrail`（LLM 响应后）、`ToolGuardrail`（工具调用前后）
- [ ] Guardrail 与 Hook System (TODO-047) 集成：guardrail 作为 hook handler 的一种实现
- [ ] 内置 guardrail：输入长度限制、输出敏感信息过滤、工具参数验证
- **Priority**: P2 — 安全增强，依赖 TODO-047 先落地
- **Effort**: 2d
