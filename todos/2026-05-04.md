# Architecture Optimization TODOs — 2026-05-04

> 基于 OpenClaw 2026.4 架构、Claude Code 泄露源码分析、以及 LangGraph/CrewAI/Spring AI/OpenAI Agents SDK 等社区最佳实践，结合 runner 现有架构的深度审查，总结以下待优化项。

---

## 一、遗留代码清理（Legacy Debt）

### TODO-001: 移除 `plugin` 包的核心耦合
- **现状**: `PluginFunction` 仍被 `LLMOptions.tools`、`ToolExecutor.functionRegistry`、`ClaudeToolDefinition`、`agent-sdk/Plugin` 直接引用。架构文档标注 `.plugin` 为 **Legacy**，但核心代码路径仍依赖它。
- **影响**: `LLMOptions` 同时持有 `List<PluginFunction> tools`（旧）和 `List<Map<String, Object>> toolDefinitions`（新），两套工具定义并存造成混乱。
- **建议**: 
  1. `LLMOptions` 移除 `List<PluginFunction> tools` 字段，统一为 `toolDefinitions`
  2. `ToolExecutor` 移除 `functionRegistry: Map<String, PluginFunction>`，统一走 `ToolRegistry`
  3. `agent-sdk/Plugin` 重构为 `Tool` 接口的简化包装
- **优先级**: P0（阻塞其他重构）
- **参考**: Claude Code 源码中工具系统完全统一为单一 `Tool` 抽象，无遗留分支

### TODO-002: 清理 `instruction` 包（已标记 @Deprecated）
- **现状**: `agent-web` 的 `AgentConfig`、`ChatService`、`SimpleInstructionPackage` 仍引用 `InstructionRegistry`、`ProviderAdapterFactory`、`ClaudeSkillAdapter`
- **建议**: 迁移至 `PromptEngine` + `prompt/Skill` 统一入口，删除整个 `instruction` 包
- **优先级**: P1

### TODO-003: 清理 `skill` 包（已标记 @Deprecated）
- **现状**: `com.lightweightai.kernel.skill.Skill` 与 `com.lightweightai.kernel.prompt.Skill` 命名冲突。`AgentConfig` 和 `ClaudeSkillAdapter` 仍引用旧版。
- **建议**: 统一到 `prompt/Skill`，删除 `skill` 包的 `Skill`/`SkillLoader`/`SkillRegistry`
- **优先级**: P1

## 二、架构分层优化

### TODO-004: ToolCallingLoop 构造函数膨胀（Telescoping Constructor）
- **现状**: `ToolCallingLoop` 有 7 个嵌套构造函数（从 3 参到 7 参），违背 Builder 模式规范。虽然有 Builder，但多个构造函数仍被保留。
- **建议**: 将所有构造函数设为 `private`/`package-private`，仅通过 Builder 创建。
- **参考**: Claude Code 的 ToolLoop 仅暴露 Builder，内部构造函数全部 private
- **优先级**: P2

### TODO-005: `AgentLoop` 内部硬编码 `PromptEngine` 创建
- **现状**: `AgentLoop` 构造函数内部 `new PromptEngine.builder()...build()`，且将所有 `Tool` 自动注册为 `Skill`。这造成：
  1. PromptEngine 不可从外部注入/mock
  2. Tool → Skill 的转换是 AgentLoop 的隐含职责，违背单一职责
- **建议**: PromptEngine 从 Builder 注入，Tool→Skill 转换移到 AgentFactory 或独立的 SkillAdapter
- **参考**: OpenClaw 的 AgentCore 接收预构建的 PromptContext，不自行构造
- **优先级**: P1

### TODO-006: Orchestrator 通过 hack 获取 MemoryProvider
- **现状**: `Orchestrator.getMemoryProvider(agent)` 注释写"AgentLoop 当前没有暴露 memoryProvider getter，暂时通过 AgentFactory 的共享引用获取"
- **建议**: `AgentLoop` 暴露只读 `getMemoryProvider()` 方法，或在 AgentFactory.create() 返回值中捆绑 MemoryProvider 引用
- **优先级**: P1

## 三、上下文管理增强

### TODO-007: ContextCompactor 缺乏 token 感知
- **现状**: `SnipCompactor` 按轮次删、`MicroCompactor` 按字符数截断。两者都不感知实际 token 数。Context window 可能仍然溢出（中文字符 token 比远高于英文）。
- **建议**: 
  1. 引入 `TokenCounter` 接口（已有 stub 在 `ModelCapability` 中但未实现）
  2. Compactor 链在执行前估算总 token 数，按模型 context window 动态调整
  3. 参考 Claude Code 的 compaction 策略：先摘要旧对话，再截断，最后删除
- **参考**: OpenClaw 使用「Summarize → Snip → Truncate」三级策略，每级都有 token 预算
- **优先级**: P0（context 溢出会直接导致 LLM 调用失败）

### TODO-008: `TokenCounter` 实现缺失
- **现状**: `ClaudeModelCapability` 和 `OpenRouterModelCapability` 中的 `getTokenCounter()` 都是 `// TODO` 返回 null
- **建议**: 集成 tiktoken-java 或调用 Claude /count_tokens API
- **优先级**: P0（TODO-007 的前置依赖）

### TODO-009: CostTracker 未接入 ToolCallingLoop Reactive 路径
- **现状**: `CostTracker` 在 `ToolCallingLoop.executeReactiveLoop()` 中只做了 `isOverBudget()` 检查，但从未被 `record()` 调用。`LLMResponse` 返回后没有代码调用 `costTracker.record(inputTokens, outputTokens)`。
- **建议**: 在 `LLM_COMPLETE` 事件处理中自动 record，或在 ResilientLLMProvider 层统一 record
- **优先级**: P1

## 四、多 Agent 编排增强

### TODO-010: Agent 间通信机制缺失
- **现状**: SubagentRuntime 支持 spawn/wait/list，但 agent 之间只能通过 "spawn 时传 task 字符串 → 完成后读 result 字符串" 通信。没有：
  1. Agent 间共享中间状态（shared blackboard）
  2. Agent 间推送消息（message passing）
  3. Agent 间协作工作流（workflow graph）
- **参考**: 
  - LangGraph：状态图 + 共享 State + 条件路由
  - CrewAI：Task 依赖链 + 委派
  - OpenAI Agents SDK：Handoff 模式（agent 将控制权转交另一个 agent）
  - Claude Code：agent 完成后将结果注入 parent context
- **建议**: 引入轻量级 Handoff 机制（agent 主动将控制权+上下文交给另一个 agent），作为 spawn/wait 的补充
- **优先级**: P2

### TODO-011: AgentRouter 只有 MetadataAgentRouter 一种实现
- **现状**: 路由仅依赖 `GatewayRequest.metadata("agentId")`，无智能路由
- **建议**: 
  1. 基于意图的路由（LLM 判断用户意图 → 选择最合适的 agent）
  2. 基于能力的路由（匹配 agent 的 toolAllowList 和用户请求的 tool 需求）
  3. 参考 OpenClaw 的 IntentRouter + CapabilityRouter 双层路由
- **优先级**: P2

### TODO-012: SubagentRuntime 使用固定线程池
- **现状**: `Executors.newFixedThreadPool(maxConcurrent)` — 阻塞式执行，与 Reactive 架构矛盾
- **建议**: 子 agent 的 `run()` 是阻塞的，但应改为调用 `runReactive()` + `subscribeOn(boundedElastic)`，与主链路一致
- **参考**: Claude Code 的 subagent 全部在 reactive pipeline 内，无独立线程池
- **优先级**: P1

- **现状**: `LLMProvider.completeStreamReactive()` 默认实现使用 `Flux.create(sink -> ...)`，callback-based 桥接无法传递背压信号
- **建议**: 各 Provider 原生实现 Flux 返回（ClaudeProvider 已做到），确保 `Flux.create` 只是 fallback
- **参考**: Spring AI 的 StreamingChatModel 返回原生 Flux

## 十一、基于 Claude Code 泄露源码的额外洞察

> Claude Code 源码于 2026.3.31 因 npm source map 泄露（v2.1.88），约 1,900 个 TypeScript 文件 / 512,000 行代码。
> 学术分析见 VILA-Lab arXiv:2604.14228《Dive into Claude Code》。
> **核心发现：仅 1.6% 代码是 AI 决策逻辑，98.4% 是确定性基础设施。**

### TODO-028: 引入五层 Context Compaction（对齐 Claude Code）
- **现状**: runner 只有 Snip + Micro 两级压缩
- **Claude Code 实现**: 五层 cascade，按成本从低到高依次执行：
  1. **Budget Reduction** — 超大 tool output 单独截断
  2. **Snip** — 删除整块旧消息（零 API 成本，高信息损失）
  3. **Microcompact** — 清理过时的 tool results（如 30 分钟前的文件读取）
  4. **Context Collapse** — 读时投影，不破坏原始数据
  5. **Auto-Compact** — 最后手段：发送全量历史给 LLM 生成摘要（预留 13K token buffer，最多 20K token summary）
- **设计原则**: lazy degradation — 最温和的策略先执行，不够再升级
- **建议**: runner 的 CompactionChain 扩展为 5 级，特别是补充 Budget Reduction（单个 tool output 截断）和 Auto-Compact（LLM 摘要）
- **优先级**: P0（与 TODO-007 合并实施）

### TODO-029: 三层记忆架构（对齐 Claude Code MEMORY.md 模式）
- **现状**: runner 的 MemoryProvider 有三层但实现粗糙（session/ephemeral/durable）
- **Claude Code 实现**:
  1. **MEMORY.md** — 轻量指针索引（每条 ~150 chars），始终加载到 context
  2. **Topic Files** — 实际知识存储，按需读取，不同时全部加载
  3. **Raw Transcripts** — 永远不重读全文，只按关键词 grep
  4. Session Memory 是后台进程持续维护的结构化 markdown 笔记；compaction 触发时直接用这些笔记作摘要（无需额外 LLM 调用）
- **建议**: runner 的 `writeEphemeral()` 改为持续后台结构化笔记；`writeDurable()` 改为指针索引 + topic files 分离
- **优先级**: P1

### TODO-030: 权限系统增强（对齐 Claude Code 七级权限模式）
- **现状**: runner 的工具权限只有 ScopedToolRegistry 的 allow/deny list
- **Claude Code 实现**: 七级权限模式 + ML 分类器，Bash 权限链有 25+ 验证器（regex + shell-quote parsing + tree-sitter AST）
- **OpenClaw 实现**: 五级策略链（global → provider → agent → session → sandbox）
- **建议**: 至少增加 session-level 和 sandbox-level 权限控制，工具执行前走策略链
- **优先级**: P2

### TODO-031: Subagent 执行模型丰富化（对齐 Claude Code Fork/Teammate/Worktree）
- **现状**: runner 的 SubagentRuntime 只有一种 spawn 模式（异步执行 + wait）
- **Claude Code 三种模式**:
  1. **Fork** — 轻量 spawn，简单任务
  2. **Teammate** — 协作执行
  3. **Worktree** — Git worktree 隔离，复杂并行开发
- **建议**: 至少区分 lightweight fork 和 isolated worktree 两种模式
- **优先级**: P3

## 十二、基于 OpenClaw 架构的额外洞察

> OpenClaw（原 Clawdbot/Moltbot）：145K+ stars，300+ contributors，2025.11 首发
> 核心定位：24/7 自主运行的个人 AI 助手，通过消息平台（WhatsApp/Telegram/Discord）交互

### TODO-032: 引入 Plugin 生命周期钩子（对齐 OpenClaw 完整 lifecycle hooks）
- **现状**: runner 的 AgentObserver 只有 6 个生命周期回调（onAgentStart/onLLMRequest/onLLMResponse/onAgentComplete/onError/onPreToolUse/onPostToolUse）
- **OpenClaw 实现**: 完整 14 个钩子：`before_agent_start`, `agent_end`, `before_compaction`, `after_compaction`, `before_tool_call`, `after_tool_call`, `tool_result_persist`, `message_received`, `message_sending`, `message_sent`, `session_start`, `session_end`, `gateway_start`, `gateway_stop`
- **缺失的关键钩子**: `before_compaction`/`after_compaction`（compaction 前后可注入自定义逻辑）、`session_start`/`session_end`（会话生命周期管理）
- **建议**: 扩展 AgentObserver 增加 compaction 和 session 生命周期回调
- **优先级**: P2

### TODO-033: System Prompt 模块化组装（对齐 OpenClaw Bootstrap Files）
- **现状**: runner 的 system prompt 由 PromptEngine 拼接（base prompt + skills + memory snippets），但不够模块化
- **OpenClaw 实现**: 多个独立 bootstrap 文件注入：IDENTITY.md, SOUL.md, TOOLS.md, AGENTS.md, USER.md, MEMORY.md, HEARTBEAT.md，每个有独立的 token 预算（`bootstrapMaxChars`）
- **建议**: 引入 PromptSection 的 token 预算机制，每个 section 有独立的 maxChars 限制
- **优先级**: P2

### TODO-034: 工具社区生态 / Registry（对齐 OpenClaw ClawHub）
- **现状**: runner 的工具只有内部注册（ManualToolProvider/DynamicPluginProvider/McpToolSourceProvider）
- **OpenClaw 实现**: ClawHub 社区注册中心（5,700+ community-built skills），可远程下载安装
- **建议**: 长期目标 — 支持从远程 registry 发现和安装工具（类似 npm registry for tools）
- **优先级**: P3
