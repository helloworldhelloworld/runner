## 二、现状架构痛点（2026-06-25 重新盘点）

### P0 — 影响主链路正确性/稳定性

#### P0-1 Context Compaction 只完成 2/5 层

**现状**：`CompactionChain(SnipCompactor(3), MicroCompactor(2000))` — 仅覆盖 Claude Code 五层 pipeline 的第 2、3 层。

**缺失层**：
- **Budget Reduction（第 1 层）**：单条 tool output 超过阈值时，替换为摘要指针（最便宜，应最先执行）。当前 `MicroCompactor` 只做截断，不做摘要替换。
- **Context Collapse（第 4 层）**：当对话极长（超过 N 轮）时，将前半段折叠为一条 SYSTEM 摘要，保留最近 M 轮完整上下文。
- **Auto-Compact（第 5 层）**：fork 一个子 LLM 生成对话语义摘要，作为最后手段。

**风险**：长会话（>20 轮 + 大 tool output）仍可能超 context window，Snip+Micro 不够。

**目标**：
1. 新增 `BudgetReductionCompactor`（在 chain 最前）：单条 > N chars 的 TOOL 消息替换为 `[tool output: {toolName}, {charCount} chars, key: {hash}]` + 前 200 chars 预览
2. 新增 `ContextCollapseCompactor`（Snip 之后）：超过阈值轮数时，将旧轮合并为一条 SYSTEM 角色摘要
3. 新增 `AutoCompactor`（chain 最后）：基于子 LLM 调用生成对话摘要；需要 `LLMProvider` 注入

**落点**：`agent-kernel/context/` 包；`CompactionChain` 构建时按 cheapest-first 顺序注入

#### P0-2 TokenCounter TODO 长期悬空

**现状**：`ClaudeModelCapability:75` 和 `OpenRouterModelCapability:77` 的 token counter 都是 TODO。

**影响**：`CostTracker` 虽已实现，但若 LLM 返回的 usage 字段为空（某些 provider 不返回），cost tracking 失效。且无法在请求前估算 token 数以决定是否需要 compact。

**目标**：
1. 实现 `ClaudeTokenCounter`：基于 Anthropic token counting API 或 tiktoken 兼容库
2. 实现 `OpenRouterTokenCounter`：从 response usage 字段提取
3. `ContextCompactor` 增加 `estimateTokens(messages)` 预检方法，compaction 前判断是否需要压缩

### P1 — 扩展性与可观测性

#### P1-1 Subagent 模型单一，缺 Fork/Worktree 隔离

**现状**：`SubagentRuntime` 只有 spawn/wait/list，每个 subagent 都是全新 context + 全新 tool allowlist。

**与 Claude Code 差距**：
- **Fork**：子 agent 继承父 context 前缀，复用 Anthropic prompt cache（成本降 ~90%）。runner 的 subagent 每次从零构建 system prompt。
- **Worktree**：子 agent 在独立 git worktree 中编辑文件，避免并发写冲突。runner 无文件系统隔离。
- **Teammate**：peer-to-peer 消息路由 + 共享任务列表。runner 只有 parent→child 单向通信。

**目标**：
1. `SpawnRequest` 增加 `mode` 枚举：`SPAWN`（现有）、`FORK`（继承父 messages 前缀）、`WORKTREE`（git worktree 隔离）
2. Fork 模式：`AgentFactory.createForked(parentLoop, task)` → 复用父 `systemPrompt` + 历史消息前缀
3. Worktree 隔离：`WorktreeManager.create()` / `cleanup()` 作为 SPI，spawn 时自动创建

#### P1-2 Real-Time Steering 缺失

**现状**：`InterruptibleRun.interrupt()` 只能 cancel 当前执行 → 保存部分结果 → resume 时从头重新进入 loop。

**Claude Code 模式**：h2A 双缓冲队列，用户可在 agent 执行中**追加指令**而不打断当前执行。agent 在下一轮 tool iteration 时检查队列，将新指令注入 context。

**目标**：
1. `InterruptibleRun` 增加 `injectMessage(GatewayRequest)` 方法
2. `ToolCallingLoop` 每轮迭代时检查 `messageQueue`，若非空则追加到 conversation 并在下一轮 LLM 调用中包含
3. 不打断当前 tool 执行，仅在 LLM 调用间隙注入

#### P1-3 Prompt Cache 意识缺失

**现状**：`CompactionChain` 压缩时可能重排/删除 system prompt 前缀中的消息，导致 Anthropic prompt cache miss。

**目标**：
1. `SnipCompactor` 在删除消息时保持 system prompt + 前 N 条 USER/ASSISTANT 消息不变（cache prefix stability）
2. 新增 `CacheAwareCompactor`（或在 Snip 中加逻辑）：标记 "cache anchor" 消息，compaction 不得移除或重排
3. `LLMOptions` 增加 `cacheControl` 配置，ClaudeProvider 在请求体中注入 `cache_control: {type: "ephemeral"}` 标记

#### P1-4 Hook Handler 外部注册机制

**现状**：`AgentObserver` 是 Java 接口，只能通过代码注册。无法在不改代码的情况下添加 shell/webhook/agent handler。

**Claude Code 对比**：12 个事件 + 4 种 handler 类型（command/http/prompt/agent），通过 settings.json 配置。

**目标**：
1. 新增 `HookHandler` 接口：`handle(HookEvent)` → `HookResult`（ALLOW / BLOCK / MODIFY）
2. 实现 `CommandHookHandler`（执行 shell 命令）、`HttpHookHandler`（POST webhook）
3. 通过 `application.yml` 配置 hook 绑定：`hooks.preToolUse[0].type=command, hooks.preToolUse[0].command="audit.sh"`
4. `AgentObserver` adapter 桥接现有接口到新 Hook 系统

#### P1-5 MemoryProvider 全同步阻塞

**现状**：`search(query)` 和 `getHistory(sessionId, limit)` 都是同步阻塞。BM25+vector 检索在 kernel-memory 中可能耗时较长。

**影响**：`AgentLoop.build()` 中调用 `memoryProvider.search()` 会阻塞 reactive 线程。

**目标**：
1. `MemoryProvider` 增加 `default Mono<List<MemorySearchResult>> searchReactive(query)` — 默认委托同步方法 + `Schedulers.boundedElastic()`
2. `AgentLoop` prompt 构建改为 reactive pipeline：`memoryProvider.searchReactive()` → `promptEngine.build()` → `compactor.compact()`
3. 保持同步方法向后兼容

#### P1-6 Observation Masking（保留推理 trace 的工具输出替换）

**现状**：`SnipCompactor` 直接删除整条 TOOL 消息。

**Anthropic Compaction API 模式**：将旧工具输出替换为占位符 `[Previous tool result for {toolName}: see earlier context]`，保留 ASSISTANT 消息中的推理 trace。这比删除好——LLM 仍能看到"曾经调用过 X 工具"的事实。

**目标**：
1. `SnipCompactor` 改为将超龄 TOOL 消息替换为占位符（而非删除），保留 toolName + callId + 首行摘要
2. ASSISTANT 消息中的推理文本永远保留（现已如此，无需改动）

### P2 — 治理与长期演进

#### P2-1 Feature Flag 系统

**现状**：无任何 feature flag 机制。所有新特性（speakableChunk、emotion、barge-in）通过 Spring `@ConditionalOnProperty` 开关。

**Claude Code**：44 个 feature flag + condition evaluator，统一管理。

**目标**：
1. 最小 `FeatureFlags` bean：`Map<String, Boolean>` 从 `application.yml` + env var 加载
2. `isEnabled(String flag)` + `getFlags()` API
3. 渐进迁移：现有 `@ConditionalOnProperty` 开关逐步纳入 FeatureFlags 统一管理

#### P2-2 Observability OTel 桥接

**现状**：`Tracer` + `SpanExporter` 接口齐全，但无生产级 exporter。`SpanContext` 在调用链中传递但不落地。

**目标**：
1. 新增 `agent-observability` 模块（可选依赖）
2. `OtelSpanExporter` 实现 `SpanExporter` → 将 `Span` 转为 OTel span 并导出到 Jaeger/Zipkin/OTLP
3. `agent-web` 通过 `@ConditionalOnClass` 自动装配

#### P2-3 Provider 装饰器链注册机制

**现状**：`GatewayConfig` 中手动 `new ResilientLLMProvider(new DynamicLLMProvider(base))`。

**目标**：
1. `LLMProviderChainBuilder`：按 `@Order` 自动发现所有 `LLMProviderDecorator` bean
2. 配置驱动：`llm.decorators.retry.enabled=true`、`llm.decorators.budget.enabled=true`

#### P2-4 Memory-Wiki 结构化知识

**现状**：`MemoryProvider.writeDurable(section, content)` 是扁平写入，无版本、无 CRUD 查询。

**OpenClaw Memory-Wiki**：持久化结构化条目 + agent 可 CRUD + 跨 session 存活 + 搜索。

**目标**：
1. `MemoryProvider` 增加 `KnowledgeEntry` 概念：key + content + tags + version + timestamp
2. `writeKnowledge(key, content, tags)` / `readKnowledge(key)` / `searchKnowledge(query)` / `listKnowledge()`
3. 默认实现基于 SQLite（kernel-memory 已有 SQLite 依赖）

#### P2-5 Session Branching（对话分叉/回退）

**现状**：无 session 分支机制。一旦执行了高风险操作，无法回退到操作前状态。

**OpenClaw**：fork 对话 → 尝试 → 失败则 restore 先前 checkpoint。

**目标**：
1. `SessionManager` 增加 `checkpoint(sessionId)` → `checkpointId` / `restore(checkpointId)`
2. `InterruptibleRun` 在高风险工具执行前自动 checkpoint（由 `ToolPolicy` + `RiskLevel.SYSTEM` 触发）

#### P2-6 SKILL.md 标准兼容

**现状**：runner 的 Skill 是 Java 接口 + Builder，不兼容 agentskills.io 标准。

**行业趋势**：Claude Code + OpenAI Codex + OpenClaw 共享 `SKILL.md` 格式（纯 Markdown + metadata front matter）。

**目标**：
1. 新增 `SkillMarkdownLoader`：解析 `SKILL.md` 文件为 `Skill` 对象
2. `PromptEngine` 支持从 `skills/` 目录自动扫描 `.md` 文件
3. 保持 Java Skill 接口向后兼容

#### P2-7 审计日志持久化

**现状**：`AgentObserver` 的 `onPreToolUse`/`onPostToolUse` 调用链在内存中，无持久化。

**最佳实践**（Microsoft Agent Governance Toolkit）：read/write/destructive 三级权限 + 审计日志持久化 + 可追溯。

**目标**：
1. `AuditLogger` bean：记录 toolName + args（脱敏）+ riskLevel + decision + timestamp + sessionId + agentId
2. 默认写入文件（JSON Lines），生产可接 ELK/OTLP
