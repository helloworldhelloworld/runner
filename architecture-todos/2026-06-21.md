## 二、现状架构痛点（2026-06-21 更新）

### P0 — 影响主链路正确性/稳定性

1. **Auto-compact（第三级压缩）缺失** `context/`
   - 症状：Snip+Micro 只删/截断旧消息，信息不可逆丢失；超长会话知识会断崖消失。
   - 参考：Claude Code fork sub-agent 生成对话摘要 → 替换旧轮次；OpenClaw 向量化归档。
   - 目标：`AutoCompactor` 实现——token 预算逼近阈值时，fork 一个轻量 LLM 调用对最旧 N 轮生成摘要，用一条 SYSTEM 消息替换；保留 Snip/Micro 作为兜底。
   - 落点：`ContextCompactor` chain 中排第三，SnipCompactor → MicroCompactor → AutoCompactor。
   - 风险：fork LLM 有延迟+成本，需限频（每会话最多 N 次 auto-compact）。

2. **Interactive Permission Confirmation 缺失** `agent/ToolPolicy.java`
   - 症状：ToolPolicy 是纯代码决策（ALLOW/DENY/ABSTAIN），高风险工具（SYSTEM 级）执行时无法暂停等待用户确认。
   - 参考：Claw Code 3-tier (Allow/Deny/Prompt)；Claude Code `PreToolUse` hook 可 reject。
   - 目标：`ToolPolicy.Decision` 增加 `PROMPT` 值；`ToolCallingLoop` 遇到 PROMPT 时 emit `StreamEvent(TOOL_PERMISSION_REQUEST)` 并挂起直到 Gateway 收到确认帧。
   - 约束：additive-only（新增 enum 值 + 新增事件类型），不破坏现有 ALLOW/DENY/ABSTAIN 语义。

### P1 — 扩展性与可观测性

3. **外部 Hook Handler 生态缺失**
   - 现状：`AgentObserver` 是 Java 接口，只能 Spring Bean 实现；不支持 shell command / HTTP webhook / 子 agent handler。
   - 参考：Claude Code 12 事件 × 4 handler 类型（command/http/prompt/agent）。
   - 目标：`HookHandler` SPI with `CommandHookHandler`（spawn process）+ `HttpHookHandler`（POST webhook）+ 配置驱动注册。
   - MVP：至少支持 `PreToolUse` + `PostToolUse` 两个事件的外部 command handler（覆盖安全审计场景）。

4. **LLMProvider 装饰器链无注册机制**
   - 现状：`GatewayConfig` 中 `new DynamicLLMProvider(new ResilientLLMProvider(base))`，顺序靠人记。
   - 目标：`LLMProviderChainBuilder` + `@Order` 注解；配置驱动开关（retry/budget/tracing/caching）。
   - 参考：OpenClaw auth profile rotation chain。

5. **MCP 健康监控与 proactive reconnect 缺失**
   - 现状：ADR-011 定义了连接韧性模式，但无主动健康探针；断线检测依赖 IO 异常。
   - 参考：OpenClaw MCPorter 周期性 ping + 自动重连 + 状态报告。
   - 目标：`McpConnectionMonitor` 周期性发 `ping` JSON-RPC；连续失败 N 次 → auto-reconnect + emit `StreamEvent(MCP_RECONNECT)`。

6. **Tool Result Caching 缺失**
   - 现状：每次 tool call 都真实执行，即使参数完全相同（如重复读同一文件）。
   - 目标：`CachingToolExecutor` 装饰器；基于 `(toolName, argHash)` 的 LRU cache；标记 `Tool.isCacheable()` 的工具才缓存。
   - 收益：减少 IO + 降低 token 消耗（避免重复大结果占 context）。

7. **MemoryProvider 全同步阻塞** `memory/MemoryProvider.java`
   - 症状：BM25 + vector 混合检索阻塞 AgentLoop 主线程；大索引下延迟不可控。
   - 目标：增加 `searchReactive()` 返回 `Mono<List<SearchResult>>`；`AgentLoop.prepareContext` 改为 reactive 流水线；内部用 `Schedulers.boundedElastic()` 隔离。

8. **Streaming Backpressure 未显式处理**
   - 现状：WebSocket handler 直接 subscribe Flux，慢客户端会导致内存堆积。
   - 目标：`onBackpressureBuffer(256, DROP_OLDEST)` + `WARN` 日志；或 Vert.x 的 `writeQueueFull` 信号反压。

### P2 — 治理与长期演进

9. **Feature Flag 系统仍然缺失**
   - 目标不变：最小 `FeatureFlags` bean，基于 `application.yml` + env var；新增特性（如 Auto-compact、Interactive Permission）全部 flag 控制。
   - 参考：Claude Code 44 个 flag + condition evaluator。

10. **Observability / OTel 导出未实现**
    - 现状：`SpanContext` / `TraceContext` / `Tracer` 有骨架；trace export 未桥接 OTel。
    - 目标：`spring-boot-starter-actuator` + Micrometer + OTel bridge；Agent 粒度指标（tool call latency p99, compaction 频率, cost per session）。

11. **Structured Output Validation 缺失**
    - 现状：LLM 输出仅靠 JSON parse 提取 tool call；malformed JSON → 整轮重试。
    - 目标：支持 `response_format: { type: "json_schema" }` 对 Claude/OpenRouter API 的 constrained decoding；fallback 为 JSON-repair + retry。

12. **Conversation Branching / Checkpoint 无概念**
    - 现状：对话是线性链；SubagentRuntime 隔离了子 agent context，但主 agent 无分叉/快照能力。
    - 目标（远期）：`ConversationCheckpoint`（snapshot 全部 messages + tool state）→ 可 fork 探索多路径 → merge 回主线。
    - 参考：LangGraph state snapshots；OpenHands event stream persist。

13. **Multi-key API Rotation / Fallback 不支持**
    - 现状：`ResilientLLMProvider` 只对单一 provider 做重试。
    - 目标：`RotatingApiKeyProvider` 持有 N 个 key，429/quota-exceeded 时自动轮转；配合 `FallbackChainProvider` 按优先级级联多 provider。
    - 参考：OpenClaw auth profile rotation + exponential backoff。

14. **集中 Test Fakes 包缺失**
    - 现状：`CapturingLLMProvider` 存在但分散在测试类中；无统一 fakes 目录。
    - 参考：Claw Code 有 `test-support` crate with `MockPermissionPrompter`, `FakeToolExecutor`, `CapturingApiClient`。
    - 目标：新增 `agent-kernel/src/test/java/.../testfixtures/` 包，集中共享 fakes（`CapturingLLMProvider`, `FakeMemoryProvider`, `StubToolRegistry`）。

## 四、架构演进方向判断

### 当前定位 vs 参照物定位

| 维度 | runner | OpenClaw | Claw Code |
|---|---|---|---|
| 核心场景 | 心理咨询 + 实体机器人 + AI kernel | 全渠道个人助理 | 编程辅助 CLI |
| 语言 | Java 21 + Spring Boot | TypeScript | Rust + Python |
| 多 Agent | 4 层 Orchestrator + SubagentRuntime | Gateway → Agent Router → Multi-agent | 简单 subagent spawn |
| MCP | Stdio + SSE + streamable_http | 全 transport + MCPorter 生命周期 | 6 transport |
| 实体化 | 有（Minion：语音+视觉+动作） | 无 | 无 |
| 上下文管理 | Snip + Micro（缺 Auto） | 向量化归档 + LLM 摘要 | 三层对齐 Claude Code |

### 不应盲目对齐的点

1. **OpenClaw 的 25+ channel adapter** — runner 场景不需要；WebSocket + REST 足够。
2. **Claw Code 的 Rust 编译期安全** — Java 生态不适用；依靠 TDD + sealed interface 即可。
3. **ClawHub skill marketplace** — runner 是 self-hosted；本地 `ToolSourceProvider` SPI 足够。

### 应重点对齐的点

1. **Auto-compact** — 直接影响长会话用户体验（心理咨询场景高频长对话）。
2. **Interactive Permission** — 实体机器人执行 SYSTEM 工具必须有人在环确认。
3. **MCP 健康监控** — Minion 的 Pi 设备网络不稳定，必须主动探测。
4. **API key rotation** — 生产环境单 key 有 quota 风险。
5. **OTel 可观测性** — 多 agent + 多 MCP server 的调试必须有分布式 trace。

## 五、补充发现（深度研究后追加）

### 5.1 Claude Code 实际为 5 层 Compaction（非 3 层）

此前认知为 Snip / Micro / Auto 三层。深入分析后确认是 **5 层管线**，每次 LLM 调用前按成本从低到高依次执行：

| 层 | 名称 | 作用 | runner 现状 |
|---|---|---|---|
| 1 | Budget Reduction | 裁剪低价值内容（空 tool result、重复 schema） | ❌ 无 |
| 2 | Snip | 删除旧 TOOL 消息 | ✅ SnipCompactor |
| 3 | Microcompact | 就地压缩大 tool result（保留首尾 200 chars） | ✅ MicroCompactor |
| 4 | Context Collapse | 超长历史折叠为结构化摘要 | ❌ 无 |
| 5 | Auto-Compact | 语义压缩——fork 子 LLM 生成摘要替换 | ❌ 无 |

**启示**：runner 的 P0-1（Auto-compact）应拆为两步——先做 Context Collapse（规则驱动、零成本），再做 Auto-Compact（LLM 驱动、有延迟/成本）。

### 5.2 MCP 2026 Roadmap — 向无状态核心演进

MCP 2026-07-28 Release Candidate 是自发布以来最大改动：

| 变更 | 影响 | runner 应对 |
|---|---|---|
| **移除 `Mcp-Session-Id` + `initialize/initialized` 握手** | Server 可水平扩展、负载均衡透明 | `McpToolClient` 的 initialize 逻辑需适配；当前实现强依赖 session |
| **Elicitation** | Server 可中途向用户请求输入（无需持久连接） | 为 Interactive Permission 提供标准载体 |
| **Structured Output** | Tool result 可携带 schema-typed 语义结构 | `ToolResult` 可扩展 `structuredContent` 字段 |
| **Tasks Extension** | 长时间运行任务管理（进度、取消、恢复） | 与 SubagentRuntime 的 long-running task 天然对齐 |
| **MCP Apps** | Server 渲染 UI | 远期——runner 侧不急 |

**行动项**：启动 `McpToolClient` 对 stateless MCP 2026 spec 的兼容性评估（T-07 追加）。

### 5.3 Spring AI 2.0 Composable Tool Calling — Advisor 模式

Spring AI 2.0（2026-06-15 GA）引入 `ToolCallingAdvisor` 作为 middleware：

```
ChatClient → [Advisor chain] → LLM
              ↓
  ToolCallingAdvisor → intercept → execute tool → re-inject → loop
  MemoryAdvisor → manage history
  GuardrailAdvisor → validate output
```

**对 runner 的启示**：
- runner 的 `StreamPostProcessor` pipeline 是 response 侧 middleware（类似 Spring AI 的 ResponseAdvisor）。
- 但 runner **缺 request 侧 middleware**——没有 "pre-LLM-call" 的统一拦截点来做 guardrails / context injection / tool filtering。
- `AgentObserver.onPreToolUse` 是 tool 级别，不是 LLM-call 级别。
- **新增 P1 条目**：考虑引入 `LLMCallAdvisor` 接口（pre/post LLM call hook chain）。

### 5.4 OpenHands Event Sourcing — Agent 即纯函数

OpenHands V1 架构核心：**Agent = pure function(event_history) → next_event**。

| 特征 | OpenHands | runner |
|---|---|---|
| 状态模型 | 不可变 event log + 唯一 mutable ConversationState | 可变 MemoryProvider + mutable AgentLoop 内部状态 |
| 可重放性 | 完全确定性 replay | 无 replay 能力 |
| Checkpoint | Event log snapshot → fork/resume | 无 |
| 调试 | Time-travel（回放任意时刻） | 只有 trace log |

**判断**：全面重构为 event sourcing 成本过高且不匹配 runner 的实时流式场景。但可借鉴其 **checkpoint 概念**：
- 在 `ToolCallingLoop` 每轮迭代后 snapshot 当前 messages + tool state → `ConversationCheckpoint`
- 长任务崩溃后可从最近 checkpoint 恢复，而非从头重跑
- 与 MCP 2026 Tasks Extension 的 resume 语义一致

### 5.5 行业共识：确定性基础设施 > AI 决策脚手架

Claude Code、OpenClaw、OpenHands 三大项目的共同架构哲学：

> *"The most successful agent architectures invest heavily in deterministic infrastructure (permissions, context management, error recovery, sandboxing) rather than complex AI decision scaffolding, trusting that increasingly capable models benefit more from a rich operational environment than from rigid control flow constraints."*

runner 当前方向**正确**（TAOR 循环 + 工具优先 + 流式事件），但在"确定性基础设施"的深度上仍有差距：
- 权限系统：只有代码级 ToolPolicy，无运行时确认 → P0-2 待补
- 上下文管理：2/5 层 → 需补 Budget Reduction + Context Collapse + Auto-Compact
- 错误恢复：`ResilientLLMProvider` 仅重试，无 checkpoint/resume → P2-12 待补
