## 二、现状架构待优化点（新增 + 延续）

### P0 — 影响主链路正确性/稳定性/性能

#### NEW-01: Compaction 压力阈值 + Auto-Compact（第三层摘要）
- **症状**：runner 的 Snip + Micro 两层 compaction 是"被动调用"，没有基于 token 压力的分级触发机制。长会话中可能在 compaction 之前已经超限。
- **参考**：Claude Code ACC 五级阈值（70%/80%/85%/90%/99%）；Google ADK 内置 Event Compaction。
- **目标**：
  1. `ContextCompactor` 增加 `pressureLevel()` 计算（当前 token / 模型 context window）
  2. 新增 `AutoCompactor`：fork 子 LLM 生成对话摘要，re-inject 高价值项（活跃文件、tool schema、plan）
  3. `CompactionChain` 按压力阈值分级触发：<70% 不压缩 → 70% Snip → 80% Micro → 85% Auto → 99% 截断
- **风险**：Auto-Compact 引入额外 LLM 调用成本；需要 `ContextCompactor.estimateTokens()` SPI
- **落点**：`agent-kernel/.../context/`

#### NEW-02: 工具并行执行 + DAG 编排
- **症状**：`ToolCallingLoop` 对同一轮 LLM 返回的多个 tool_call 逐个顺序执行；无 DAG 依赖分析。
- **参考**：LLMCompiler (ICML 2024) 3.7× 延迟降低；OpenAI/Claude 原生并行 tool calling；LangGraph Fan-out/Fan-in + `Send()`。
- **目标**：
  1. 当 LLM 一轮返回多个 tool_call 且无依赖时，`Flux.merge()` 并行执行
  2. 可选 DAG 模式：`ToolDependencyAnalyzer` 构建工具调用拓扑，按层并行
  3. 单工具失败时其他工具不受影响，失败结果以 TOOL_ERROR 回传模型
- **落点**：`agent-kernel/.../core/ToolCallingLoop.java`

#### NEW-03: Resilience 全链路（Circuit Breaker + Fallback Chain + Graceful Degradation）
- **症状**：`ResilientLLMProvider` 仅有 retry with backoff，无 circuit breaker、无 model fallback、无 graceful degradation。工具执行无重试/熔断。
- **参考**：业界标准分层：Graceful Degradation → Fallback Chain → Circuit Breaker → Retry+Backoff+Jitter → LLM API。
- **目标**：
  1. 引入 `CircuitBreaker`（Resilience4j 或轻量自实现）：5 次失败 / 60s → 断路 → 半开测试
  2. `FallbackLLMProvider`：主模型失败 → 备用模型 → 缓存响应 → 友好降级消息
  3. 工具执行增加 `ToolRetryPolicy`（可配置的 retryable exception + 最大次数）
  4. 多 agent 场景：子 agent 故障不级联父 agent（隔离舱壁模式）
- **落点**：`agent-kernel/.../llm/`, `agent-kernel/.../core/ToolExecutor.java`

#### NEW-04: Lazy Tool Loading（按需工具 Schema 注入）
- **症状**：`ToolRegistry.getToolDefinitions()` 每次返回全量工具 schema，随工具增多消耗越来越多 context token。
- **参考**：Claude Code `ENABLE_TOOL_SEARCH` flag；当工具数 >N 时切换为"检索+按需加载"模式。
- **目标**：
  1. 配置阈值（如 >15 个工具时）自动切换为 lazy 模式
  2. Lazy 模式下 context 中只注入 tool name + 简短描述，完整 schema 按需加载
  3. 新增内置 `ToolSearchTool`，LLM 可通过该工具搜索可用工具
- **落点**：`agent-kernel/.../agent/ToolRegistry.java`

#### NEW-05: Memory Providence Labels（记忆来源追踪）
- **症状**：`MemoryProvider` 存储的 message 无来源标签，无法区分用户输入、工具结果、LLM 推理、外部注入。
- **参考**：OpenClaw v2026.6.1 Memory Providence Labels。
- **目标**：
  1. `ConversationMessage` 增加 `ProvenanceTag` 枚举：USER_INPUT / TOOL_RESULT / LLM_REASONING / SYSTEM_INJECT / EXTERNAL_DOC
  2. Compaction 策略可按 provenance 差异化处理（如 TOOL_RESULT 优先压缩，USER_INPUT 保留更久）
  3. 审计场景下可追踪每条记忆的完整来源链
- **落点**：`agent-kernel/.../llm/ConversationMessage.java`, `agent-kernel/.../context/`

#### NEW-06: StreamEvent 状态管理事件 + AG-UI 协议对齐
- **症状**：StreamEvent 缺少 STATE_SNAPSHOT / STATE_DELTA 类事件，客户端无法做增量状态同步。
- **参考**：AG-UI Protocol 17 种事件类型，特别是 `STATE_SNAPSHOT`（全量状态快照）、`STATE_DELTA`（JSON Patch 增量）、`MESSAGES_SNAPSHOT`（会话历史重同步）、`INTERRUPT`（暂停等待用户确认）。
- **目标**：
  1. StreamEvent.EventType 新增：`STATE_SNAPSHOT` / `STATE_DELTA` / `MESSAGES_SNAPSHOT`
  2. `INTERRUPT` 复用现有 `AGENT_INTERRUPT` 或新增独立类型
  3. STATE_DELTA 采用 JSON Patch (RFC 6902) 格式
  4. 客户端可通过 STATE_SNAPSHOT 做初始同步 / 断线重连后恢复
- **落点**：`agent-kernel/.../core/StreamEvent.java`, `agent-web/.../websocket/`

#### NEW-07: Input/Output Guardrails 架构
- **症状**：runner 有 ToolPolicy（运行时权限），但缺少 input guardrails（用户输入验证、prompt injection 检测）和 output guardrails（输出安全检查）。
- **参考**：OpenAI Agents SDK 内置 Guardrails（input/output）；Anthropic 分层安全（deny-first + classifier + sandbox）；soul-safety 模块已有内容过滤但未集成到 Gateway 层。
- **目标**：
  1. `Guardrail` 接口：`validate(input/output) → GuardrailResult(PASS/BLOCK/WARN)`
  2. `InputGuardrail`：prompt injection 检测 + 敏感信息过滤 + 策略分类
  3. `OutputGuardrail`：危险命令检测 + PII 泄漏防护
  4. Gateway 层统一拦截：请求进入 → InputGuardrail → Agent 处理 → OutputGuardrail → 响应
  5. 与 soul-safety 模块整合：复用已有 crisis detection + content filtering
- **落点**：`agent-kernel/.../gateway/`, `soul-safety`

#### NEW-08: Subagent 崩溃恢复 + Zombie 清理
- **症状**：`SubagentRuntime` 无崩溃恢复机制；子 agent 挂起可能变成 zombie（占用执行通道 11+ 分钟）。
- **参考**：OpenClaw v2026.6.1 subagent 崩溃恢复（workspace 隔离 + session lock 超时释放 + stale continuation 避免）。
- **目标**：
  1. 子 agent 超时自动取消（可配置 timeout per spawn request）
  2. Session lock 超时释放（防止 stale lock 阻塞后续请求）
  3. 崩溃后部分结果保存（已完成的工具调用结果不丢失）
  4. 父 agent 收到 SUBAGENT_ERROR 后可选重试或降级
- **落点**：`agent-kernel/.../orchestrator/SubagentRuntime.java`

#### NEW-09: 四层记忆模型对齐（CoALA 框架）
- **症状**：runner 仅有 session memory + file-based long-term memory，缺乏结构化的记忆分层。
- **参考**：CoALA 框架（Princeton 2023）四层记忆：Working（in-context） / Episodic（经历日志） / Semantic（结构化知识） / Procedural（技能与规则）；MemoryOS（NeurIPS 2025）三层层次存储。
- **目标**：
  1. Working Memory = 当前 context window（已有）
  2. Episodic Memory = append-only 事件日志 + 检索（基于 kernel-memory 扩展）
  3. Semantic Memory = 结构化知识图谱 / 实体存储（新增）
  4. Procedural Memory = 已学技能 + 规则（整合 learn 包的 `SkillExtractor` 输出）
  5. 跨 session 的 read-before-reasoning, write-after-acting 循环
- **落点**：`kernel-memory`

#### NEW-10: 事件溯源 + 会话审计链
- **症状**：agent 决策过程无完整审计链；不同于 OpenClaw 的 "可证明哪个 agent 做了什么"。
- **参考**：事件溯源（Event Sourcing）作为 agentic AI 的自然基础；Claude Code append-only JSONL 会话记录；OpenClaw durable session chains。
- **目标**：
  1. 会话事件 append-only 日志（JSONL 格式）：每个 StreamEvent 持久化
  2. `SessionAuditLog`：who（agentId）/ what（event type）/ when（timestamp）/ with（tool/model）/ why（provenance）
  3. 支持事件重放（replay from log → 重建状态）
  4. 检查点快照（每 N 个事件 or 每次 compaction 前）避免全量重放
- **落点**：`agent-kernel/.../trace/`, `kernel-memory`

#### NEW-11: Channel 抽象层（多渠道统一入口）
- **症状**：agent-web 仅支持 REST/SSE/WebSocket 三种传输方式，无渠道（Channel）级抽象。
- **参考**：OpenClaw Multi-Channel Inbox（20+ 渠道统一抽象）。
- **目标**：
  1. `Channel` 接口：`send(message)` / `receive() → Flux<InboundMessage>` / `metadata()`
  2. 内置实现：`WebSocketChannel` / `RestChannel` / `SseChannel`
  3. 可扩展：第三方集成（Telegram / Slack / WeChat）作为独立模块
  4. Gateway 从面向传输协议改为面向 Channel
- **落点**：`agent-web`，可能新增 `agent-channel` 模块

#### NEW-12: Workflow Agent（无 LLM 编排 agent）
- **症状**：runner 所有 agent 都需要 LLM 驱动，简单的顺序/并行/循环编排也走 LLM 调用，浪费 token。
- **参考**：Google ADK 三类 agent（LLM Agent / Workflow Agent / Custom Agent）；Workflow Agent（Sequential/Parallel/Loop）不需要 LLM。
- **目标**：
  1. `WorkflowAgent` 基类：无 LLM 调用，纯确定性编排
  2. `SequentialAgent`：按序执行子任务列表
  3. `ParallelAgent`：并行执行子任务，barrier 等待全部完成
  4. `LoopAgent`：重复执行直到条件满足
  5. 可与 LLM Agent 混合编排（Orchestrator 统一调度）
- **落点**：`agent-kernel/.../orchestrator/` 或新增 `agent-workflow` 模块

## 四、架构反模式自查清单

基于 2026 年业界反模式研究，runner 需自查：

| 反模式 | 描述 | runner 风险 | 检查方法 |
|---|---|---|---|
| **Context Explosion** | 子 agent 看到全部父历史，token 暴涨 | ⚠️ 中 — SubagentRuntime 需确认 context 隔离程度 | 检查 SpawnSubagentTool 是否传递父 context |
| **Zombie Subagent** | 子 agent 挂起 11+ 分钟，占用执行通道 | ⚠️ 高 — 无超时自动取消 | 审查 SubagentRuntime 超时配置 |
| **Tool Sprawl** | 30+ 工具注入 context，降低 tool 选择准确率 | ⚠️ 中 — MCP 动态注册可能带来大量工具 | 统计当前最大 tool 数量 |
| **Schema Drift** | 工具定义变更但 agent 理解未更新 | ⚠️ 低 — MCP 工具通过 tools/list 动态获取 | 检查 McpToolWrapper 刷新机制 |
| **Monolithic Prompt** | 所有指令塞进单个 system prompt | ⚠️ 中 — PromptAssembler 未生产使用 | 度量最大 system prompt token 数 |
| **Memory Leak** | 无界日志/事件堆积导致 OOM | ⚠️ 中 — 需检查 MemoryProvider 是否有 eviction | 压测长会话内存占用 |
