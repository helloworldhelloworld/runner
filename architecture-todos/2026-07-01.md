## 一、外部参照物要点速览（2026-07 更新）

### 1.1 Claude Code 源码泄露 — 对 runner 的新启示

基于泄露源码更深入分析后，识别出以下 runner 尚未对齐的关键设计：

| 设计点 | Claude Code 实现 | runner 现状差距 |
|---|---|---|
| **Auto Compaction（第三层）** | fork 子 agent 生成对话摘要，压缩比远超 Snip/Micro | runner 只有 Snip+Micro，长会话（100+ 轮）仍会撞 context 上限 |
| **Prompt Caching** | 利用 Anthropic API 的 prompt caching（`cache_control: ephemeral`），system prompt + 前 N 条消息标记缓存，显著降低延迟和成本 | runner 完全没有 prompt caching 支持；每次请求全量发送 system prompt |
| **Structured Output / Tool Choice** | `tool_choice: { type: "tool", name: "..." }` 强制模型调用特定工具；JSON Schema 约束输出 | runner 的 `LLMOptions` 无 `toolChoice` 字段；无法强制/禁止特定工具调用 |
| **Pre-flight Token Counting** | 发送前精确计算 token，超预算先压缩再发 | `TokenCounter` 只有接口无实现；`CostTracker` 是事后追踪而非事前预防 |
| **速率限制 & 退避** | 指数退避 + jitter + 429/529 特殊处理 + 并发令牌桶 | `ResilientLLMProvider` 有重试但无速率限制、无令牌桶、无 429 专项处理 |
| **多模态消息规范化** | 统一的 ContentBlock 数组（text/image/tool_use/tool_result），不混类型 | runner 的 `ConversationMessage` 有 `ImageContent` 但 content 模型偏简单，`ContentBlock` 继承体系不完整 |
| **Permission System** | 4 级权限模型（auto/approve/deny/ask）+ 基于 glob 的路径权限 | runner 的 `ToolPolicy`(ALLOW/DENY/ABSTAIN) 粒度较粗，无路径级别、无用户确认交互 |

### 1.2 OpenClaw 2026.6 架构演进

| 新能力 | 设计要点 | runner 对标差距 |
|---|---|---|
| **ACP (Agent Communication Protocol)** | Agent 间标准化通信协议，支持跨进程/跨网络 agent 协作；内建 discovery + capability negotiation | runner 的 SubagentRuntime 是 in-process 的，无跨进程/跨网络能力 |
| **向量记忆增量同步** | 文件变更 → 增量 re-chunk → 增量 re-embed → SQLite-vec 更新 | `kernel-memory` 的 vector 实现是全量重建，无增量 |
| **Multi-Channel Inbox 20+ 渠道** | 统一抽象 ChannelAdapter，WhatsApp/Telegram/Slack/Discord/Feishu/WeChat/Matrix | runner 仅 WebSocket/REST/SSE，无渠道抽象层 |
| **插件热加载 + 沙箱** | Wasm 沙箱 / Docker 隔离 / 权限声明式控制 | `DynamicPluginProvider` 有 jar 热加载但无沙箱隔离 |
| **Conversation Branching** | 对话树（branch/merge），支持"假设性"对话分支 | runner 对话是线性的，无分支/合并 |

### 1.3 社区最佳实践（LangGraph / CrewAI / Spring AI / AutoGen 2025-2026）

| 实践 | 来源 | runner 对标 |
|---|---|---|
| **Graph-based Agent Orchestration** | LangGraph — 将 agent 步骤建模为有向图节点，支持条件分支、循环、并行执行 | runner 的 Orchestrator 是线性 loop + subagent spawn，无图式编排 |
| **Structured State Machine** | LangGraph StateGraph — 显式状态定义 + checkpoint + replay | runner 无 checkpoint/replay，InterruptibleRun 状态管理仅限 interrupt/resume |
| **Delegation Pattern (Crew)** | CrewAI — 角色明确的 Agent 组，Task 驱动委派，支持层级/协作两种模式 | runner 有 AgentProfile + SubagentRuntime，但缺少 Task 级别的编排单元 |
| **Guardrails / Input-Output Validation** | Spring AI / NeMo Guardrails — 模型输入输出的结构化校验（内容安全、格式合规、事实一致性） | runner 的 `soul-safety`(crisis detection) 仅覆盖安全层面，无通用 guardrail 管道 |
| **Tool Error Recovery** | AutoGen — 工具执行失败后自动重试/降级/人工介入策略 | runner 的 `ToolExecutor` 失败直接返回 error ToolResult，无重试/降级 |
| **Observability-first** | Spring AI + OpenTelemetry — 原生 OTel span，LLM 调用 / tool 执行 / token 消耗全部自动 instrument | runner 有 Span 骨架但未桥接 OTel；LLM 调用延迟 / token 分布无处可看 |
| **Streaming Backpressure** | Reactor best practice — 下游慢消费时上游感知并调速 | runner 的 `Flux<StreamEvent>` 无 backpressure 策略；WS 慢客户端可能导致 OOM |
| **Idempotent Tool Execution** | 社区共识 — 工具应声明幂等性，重试安全 | runner 的 `Tool` 接口无幂等标记 |

## 二、现状架构痛点（2026-07-01 重新排序）

### P0 — 影响主链路稳定性 / 成本

1. **TokenCounter 无实现 → CostTracker 无法事前预防溢出** `agent-kernel/.../llm/TokenCounter.java`
   - 症状：`TokenCounter` 接口存在但无任何实现类；`CostTracker` 只能事后追踪已消耗 token，不能在发送前估算是否会超限。
   - 参考：Claude Code 发送前精确计算 token 数，超预算触发 compaction。
   - 目标：实现 `ApproximateTokenCounter`（字符数 / 4 的近似估算）+ `ClaudeTokenCounter`（基于 tiktoken 或 Anthropic API 的精确实现）；`AgentLoop.buildMessages()` 在 compaction 后用 counter 验证 < model max context。
   - 落点：`ContextCompactor.compact()` 改为接收 `TokenCounter` + `maxContextTokens` 参数，循环压缩直到 fit。

2. **Auto Compaction（第三层压缩）缺失** `agent-kernel/.../context/`
   - 症状：Snip + Micro 对超长会话（100+ 轮）不够用。Snip 只删旧工具结果，Micro 只截断大 result；对话正文永远保留，终究撞上限。
   - 参考：Claude Code 的 Auto Compaction fork 子 agent 生成摘要，压缩比 10:1。
   - 目标：`AutoCompactor implements ContextCompactor`，当 token 数超过阈值时调用 LLMProvider（小模型）生成对话摘要，替换原消息序列。`CompactionChain` 扩展为 `Snip → Micro → Auto` 三级。
   - 依赖：P0-1 TokenCounter 实现。

3. **Prompt Caching 支持缺失** `agent-kernel/.../llm/claude/ClaudeProvider.java`
   - 症状：每次请求全量发送 system prompt（可能数千 token），不利用 Anthropic API 的 prompt caching。
   - 参考：Claude Code 在 system prompt 和前 N 条消息上标记 `cache_control: { type: "ephemeral" }`，5 分钟 TTL 内节省 ~90% 输入 token 成本。
   - 目标：`ClaudeProvider` 在构建请求体时自动为 system prompt 块和前 K 条历史消息添加 `cache_control`。`LLMOptions` 增加 `promptCachingEnabled` 开关。
   - 收益：对频繁对话的场景（minion 具身化、长会话），成本和延迟均显著降低。

4. **Streaming Backpressure 缺失** `agent-web/.../websocket/`
   - 症状：`Flux<StreamEvent>` → WebSocket 推送，无 backpressure 策略。慢客户端（如弱网 Pi 设备）会导致事件在内存堆积。
   - 参考：Reactor 最佳实践 — `onBackpressureBuffer(maxSize, dropOldest)` + `publishOn(boundedElastic)`。
   - 目标：WebSocket handler 添加 backpressure buffer，超限时丢弃最旧的 TEXT_DELTA（保留 TOOL_RESULT 等关键事件）。

### P1 — 扩展性与可观测性

5. **LLM Provider 装饰器组合无注册机制** `agent-web/.../config/GatewayConfig.java`
   - 延续 04-08 P2-10，仍未落地。`ResilientLLMProvider` + `DynamicLLMProvider` 手动链式 new。
   - 目标：`LLMProviderChainBuilder` 按 `@Order` 注册装饰器；配置驱动开关（retry/budget/tracing/caching）。

6. **速率限制 & 429 退避策略** `agent-kernel/.../llm/ResilientLLMProvider.java`
   - 症状：`ResilientLLMProvider` 有重试（固定次数），但无速率限制、无令牌桶、无 429/529 状态码专项处理（指数退避 + jitter）。
   - 参考：Claude Code 对 429 采用递增退避 + jitter；对 529(overloaded) 有更长退避；并发控制令牌桶。
   - 目标：扩展 `ResilientLLMProvider` 增加 `RateLimiter`（令牌桶）+ `RetryPolicy`（区分 429/500/529 的退避策略）。

7. **LLMOptions 缺少 toolChoice 字段** `agent-kernel/.../llm/LLMOptions.java`
   - 症状：无法强制模型调用特定工具或禁止工具调用（`tool_choice: none/auto/{ type: "tool", name: "X" }`）。
   - 参考：Claude API 和 OpenAI API 均支持 tool_choice。
   - 目标：`LLMOptions.Builder.toolChoice(ToolChoice)` —— `ToolChoice` 枚举/sealed class: `AUTO | NONE | SPECIFIC(toolName)`。各 Provider 在构建请求体时映射。

8. **OpenTelemetry 桥接** `agent-kernel/.../trace/`
   - 延续 04-08 P2-14。`SpanExporter` SPI 已有，但只到 StreamEvent/Console，无 OTel 标准导出。
   - 目标：`OtelSpanExporter implements SpanExporter`，将内部 `Span` 转为 OTel `Span`，对接 Jaeger/Zipkin/OTLP。依赖 `opentelemetry-api` + `opentelemetry-sdk`。
   - 落点：`agent-web` 增加 `OtelAutoConfiguration`，`@ConditionalOnClass(OpenTelemetry.class)` 自动注册。

9. **SessionManager 缺少 TTL 与生命周期回调** `agent-kernel/.../gateway/SessionManager.java`
   - 延续 04-08 P1-6。无超时清理，内存中的 session 永不过期。
   - 目标：`SessionManager` 增加 `setTtl(Duration)` + 后台清理线程；增加 `SessionListener`(onCreated/onExpired/onClosed) 回调接口。

10. **HookHandler 抽象层** `agent-kernel/.../agent/AgentObserver.java`
    - 延续 04-08 P1-5 的未完成部分。`AgentObserver` 有 7 个事件但只支持 Java 代码内 hook。
    - 参考：Claude Code 支持 command/http/prompt/agent 四种 handler 类型。
    - 目标：`HookHandler` 接口 + `ShellHookHandler`（exec 外部命令）+ `HttpHookHandler`（POST webhook）。配置驱动：`app.hooks.preToolUse[0].type=shell, command="..."` 。
    - 优先级降低：对 minion 场景非刚需，但对生产级可观测性和安全审计有价值。

### P2 — 治理与长期演进

11. **MemoryProvider 全同步阻塞** `agent-kernel/.../memory/MemoryProvider.java`
    - 延续 04-08 P2-12。`search()` 在 AgentLoop 线程上阻塞。
    - 目标：增加 `default Mono<List<MemorySearchResult>> searchReactive(query)` 默认方法（回退到同步）；`AgentLoop.prepareContext` 改为 reactive 流水线。
    - 短期缓解：`search()` 调用包在 `Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic())`。

12. **Feature Flag 系统** 全库缺失
    - 延续 04-08 P2-13。
    - 目标：`FeatureFlags` bean，从 `application.yml`（`app.features.*`）+ 环境变量读取 `Map<String, Boolean>`。新特性用 `@ConditionalOnProperty("app.features.xxx")` 闸控。
    - MVP：不需要动态推送，yml + env 足够。

13. **Tool 幂等性标记 & 错误恢复** `agent-kernel/.../agent/Tool.java`
    - 症状：`Tool` 接口无幂等标记；`ToolExecutor` 失败直接返回 error ToolResult，无重试/降级策略。
    - 参考：AutoGen 工具错误恢复策略；社区共识 — 工具应声明幂等性。
    - 目标：`Tool.isIdempotent()` default false；`ToolExecutor` 对 idempotent tool 的瞬态失败自动重试 1 次。

14. **Guardrail 管道** `soul-safety/` 之外
    - 症状：`soul-safety` 仅做 crisis detection，无通用的输入/输出校验管道（内容安全、格式合规、PII 过滤、事实一致性）。
    - 参考：Spring AI Advisor chain / NeMo Guardrails — 输入 → [guardrail chain] → LLM → [guardrail chain] → 输出。
    - 目标：`GuardrailChain`（有序的 `Guardrail` 列表），在 `AgentLoop` 的 LLM 调用前后分别执行。`Guardrail` 接口：`GuardrailResult check(messages/response)` → `PASS | BLOCK(reason) | TRANSFORM(modified)`。
    - 落点：`soul-safety` 的 CrisisDetector 作为第一个 `Guardrail` 实现迁入。

15. **ContentBlock 类型体系不完整** `agent-kernel/.../llm/`
    - 症状：`ConversationMessage` 有 `content(String)` + `imageContents(List<ImageContent>)` + `contentBlocks(List<ContentBlock>)` 三条路径，容易混用。`ContentBlock` 只有 `TextContent` + `ImageContent` 两个子类。
    - 参考：Claude API 的 content 是统一的 `ContentBlock[]`，类型包括 text/image/tool_use/tool_result/document。
    - 目标：统一为 `ContentBlock` sealed hierarchy：`TextBlock | ImageBlock | ToolUseBlock | ToolResultBlock | DocumentBlock`。`ConversationMessage` 只保留 `List<ContentBlock> content()`，废弃 `content(String)` 的 getter。
    - 风险：这是一个深层重构，涉及所有 Provider + ToolCallingLoop + Serializer。需谨慎分期。

## 四、行业趋同信号

学术研究 [arXiv:2604.03515]("Inside the Scaffold: A Source-Code Taxonomy of Coding Agent Architectures") 分析了 13 个开源 agent 框架，发现**所有现代 agentic 系统收敛于以下 7 点**：

1. 异步 generator-based agent loop（fire-and-forget 工具执行）
2. MCP 作为外部工具发现与调用标准
3. Streaming events 作为一等公民（非字符串 trace）
4. Scoped tool registries，deny > allow 语义
5. Context budget 追踪 + compaction 防溢出
6. 有权限的执行（human approval / sandboxing / rate limit）
7. Session-scoped memory 隔离

**runner 在 #2-#5 和 #7 上已对齐；#1 部分对齐（Reactor Flux 而非 generator，等效）；#6 尚缺运行时人工确认交互（ToolPolicy 是静态配置）。**
