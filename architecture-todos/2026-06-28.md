## 二、现状架构痛点（2026-06-28 盘点）

> 延续 P0/P1/P2 三级。P0 = 影响主链路正确性/稳定性；P1 = 扩展性与可观测性；P2 = 长期演进与治理。

### P0 — 主链路关键差距

**1. Context Compaction 仅覆盖 5 层中的 2 层** `agent-kernel/.../context/`

- **现状**：Snip（删旧 tool result）+ Micro（截断大 tool result）+ CompactionChain 串联。
- **差距**：
  - (a) **BudgetReduction**（Layer 1）：个别 tool output 超出阈值时就地替换为摘要/指针，在 Snip 之前运行，阻止巨大 tool 结果进入 context。
  - (b) **ContextCollapse**（Layer 4）：对老历史结构化重组——归档旧 span、投影压缩视图，比 Snip 删除更精细、比 AutoCompact 便宜。
  - (c) **AutoCompact**（Layer 5）：fork 子 LLM 调用生成 ≤20K token 的结构化摘要；触发阈值 = contextWindow − max(maxOutputTokens, 20K) − 13K buffer；配合 **compaction 断路器**（连续 3 次失败熔断）。
- **目标**：`CompactionChain` 扩展为 5 层：`BudgetReductionCompactor` → `SnipCompactor` → `MicroCompactor` → `ContextCollapseCompactor` → `AutoCompactor`。AutoCompactor 依赖 LLMProvider 做 summarize 调用。
- **落点**：`ContextCompactor` 接口不变（additive），新增 3 个实现类 + `CompactionChain` 组装顺序更新。

**2. Memory flush before compaction 缺失** `agent-kernel/.../agent/AgentLoop.java`

- **现状**：compaction 直接删除/截断旧消息，可能丢失有价值上下文。
- **差距**：Claude Code & OpenClaw 都在 compaction 前触发一个 agentic turn 持久化关键信息。
- **目标**：在 `CompactionChain.compact()` 触发前，调用 `MemoryProvider.flush(extractedSummary)` 将 compaction 即将删除的内容中有价值的部分写入 durable memory。
- **落点**：`AgentLoop.executeChat` 中 compaction 前增加 flush 钩子。

**3. 并发工具执行缺读写分类** `agent-kernel/.../core/ToolCallingLoop.java`

- **现状**：`ToolExecutor` 支持 parallel execution（`executeAll`），但不区分只读 vs 写操作。
- **差距**：Claude Code 将 Read/Glob/Grep/MCP-read 标记为可并发，Edit/Write/Bash 标记为须串行。
- **目标**：在 `Tool` 接口增加 `default boolean isReadOnly() { return riskLevel() == RiskLevel.SAFE; }` 方法（additive）；`ToolExecutor` 按此分组——同批只读工具并发、写工具串行、写工具与其后的读工具也串行。
- **注意**：SAFE 不完全等于 read-only（如 MCP SAFE 工具可能有副作用），需要 `@ReadOnly` 注解或 MCP `readOnlyHint` 映射。

### P1 — 扩展性与可观测性

**4. 模块化 System Prompt 缺"模式"切换** `agent-kernel/.../prompt/PromptEngine.java`

- **现状**：`PromptSection` 有 id/order/condition/render，但没有 mode 概念。
- **差距**：
  - Claude Code 有 Plan/Auto/Learning/Default 4 种模式，动态加载不同 prompt 段（plan mode +142~1297 tokens）。
  - OpenClaw 有 SOUL.md/IDENTITY.md/USER.md/TOOLS.md/AGENTS.md 有序加载。
- **目标**：引入 `PromptMode` enum（DEFAULT/PLAN/AUTO/LEARNING）+ `PromptSection.condition` 支持 mode-based 条件装配。外部 markdown 文件（类似 SOUL.md）可作为 `PromptSection` 加载，实现 workspace-first 配置。

**5. Skill 按需加载（节省 token）** `agent-kernel/.../prompt/PromptEngine.java`

- **现状**：所有 active skill 的 systemPrompt 全量拼入 system prompt。
- **差距**：OpenClaw 仅展示 skill 的 name/description 列表；agent 判断相关时才读取完整 SKILL.md。
- **目标**：`PromptEngine.build()` 默认只注入 skill 摘要列表（name + description + 激活条件）；通过 `loadSkillDetail(skillId)` tool 让 LLM 按需加载完整内容。预估节省 30-60% skill token 开销。

**6. Session 自动记忆提取** `agent-kernel/.../memory/`

- **现状**：memory 完全被动——只有手动 write 或 skill-generated 记忆。
- **差距**：Claude Code 在 ~10K token 后自动提取 session memory（structured markdown），每 ~5K token 或每 3 次 tool call 更新。
- **目标**：新增 `SessionMemoryExtractor`（AgentObserver 实现）在 ToolCallingLoop 的 `onPostToolUse` 中按阈值触发异步摘要提取，写入 `MemoryProvider`。

**7. SessionManager 生命周期完整化** `agent-kernel/.../gateway/SessionManager.java`

- **现状**：接口只有基本的 get/create；无 TTL、无 lifecycle hooks。
- **差距**：OpenClaw Gateway 有完整的 session lifecycle（create → active → idle → timeout → cleanup）。
- **目标**：拓展 `SessionManager` 增加 `onStart(SessionContext)`/`onStop(SessionContext)`/`onTimeout(SessionContext)`；默认实现 `InMemorySessionManager` 带 TTL 清理（已有 Orchestrator activeRuns TTL，需统一到 SessionManager 层）。

**8. OpenTelemetry 桥接** `agent-kernel/.../trace/`

- **现状**：`SpanExporter` SPI + `StreamEventSpanExporter`（内部）+ `ConsoleSpanExporter`（调试）。
- **差距**：无标准 OTel exporter；无法接入 Jaeger/Zipkin/Datadog/Grafana Tempo。
- **目标**：新增 `OtelSpanExporter` 实现，将内部 `SpanContext`/`Trace` 转为 OTel `io.opentelemetry.api.trace.Span`；通过 `opentelemetry-exporter-otlp` 推送。需要新增 `opentelemetry-api` + `opentelemetry-sdk` 依赖。

**9. Tool.executeReactive 真流式** `agent-kernel/.../agent/Tool.java`

- **现状**：默认实现包装同步 `execute()` 为单 chunk `Flux`。
- **差距**：文件读取、HTTP、shell 命令天然支持增量输出；Claude Code 的 StreamingToolExecutor 可以在 LLM 流中 tool_use 块出现时立即启动工具。
- **目标**：新增 `StreamingTool` 抽象基类，基于 `Flux.create(sink -> ...)` 按块推送；Shell/HTTP/FileRead 工具继承此类。同时支持 early-start 模式——LLM 流中 tool_use 参数完成即启动，不等整条回复结束。

### P2 — 长期演进与治理

**10. Feature Flag 系统** 全库无相关代码

- **目标**：最小 `FeatureFlags` bean，基于 `application.yml` + env var + 运行时 toggle；`Map<String, Boolean>` + `isEnabled(flag)` API。
- **参考**：Claude Code 44 个 flag；OpenClaw 的实验性 feature 控制。
- **落点**：所有新增实验性功能（如 AutoCompact、SessionMemoryExtractor、Skill 按需加载）用 flag 控制上线。

**11. MemoryProvider 异步化** `agent-kernel/.../memory/MemoryProvider.java`

- **现状**：BM25 + vector 混合检索全同步阻塞 AgentLoop 线程。
- **目标**：增加 `Mono<List<MemoryEntry>> searchReactive(query)` 和 `CompletableFuture<List<MemoryEntry>> searchAsync(query)`；`AgentLoop.prepareContext` 改为 reactive pipeline。`kernel-memory` 内部用 virtual thread 或 Schedulers.boundedElastic() 隔离。

**12. LLMProvider 装饰器注册机制** `agent-web/.../config/GatewayConfig.java`

- **现状**：Resilient/Dynamic/Tracing 等装饰器在 GatewayConfig 手动链式 new，顺序靠人记。
- **目标**：`LLMProviderChainBuilder` + `@Order` 注解自动发现、排序、组合装饰器；配置驱动开关。

**13. A2A（Agent-to-Agent）协议支持**

- **差距**：Google A2A 成为 MCP 的互补标准（MCP = agent↔tool，A2A = agent↔agent）。
- **现状**：runner 的 SubagentRuntime 仅支持进程内 subagent；无跨进程/跨服务 agent 通信协议。
- **目标**：评估 A2A 规范；在 `Orchestrator` 层增加 `A2AClient` 适配器，允许 subagent spawn 到远程 A2A-compatible agent。

**14. MCP Server 能力（反向暴露）** `agent-mcp`

- **现状**：runner 只是 MCP client（连接外部 MCP server 获取工具）。
- **差距**：OpenClaw MCPorter 支持反向暴露为 MCP server，让 Claude Code/Cursor/Windsurf 直接调用 runner 的能力。
- **目标**：`agent-mcp` 新增 `McpToolServer` 模块，将 runner 的 `ToolRegistry` 中选定的工具暴露为 MCP server 端点（stdio + streamable_http）。

**15. Evaluation Framework**

- **差距**：2026 共识——"评估先于生产"。LangSmith/Braintrust/Patronus 等评估框架成标配。
- **目标**：建立基础 eval harness：输入 scenario → agent 执行 → 评估 tool call sequence / 最终结果 / token 消耗 / 延迟。
- **落点**：基于现有 acceptance test 框架扩展，新增 `agent-eval` 模块或 `test/eval/` 目录。

**16. Tool Sandbox / 隔离执行**

- **差距**：Claude Code 用 tree-sitter AST 分析 shell 命令安全性；OpenClaw 支持 Docker 沙箱模式。
- **现状**：runner 有 RiskLevel + ToolPolicy 但无实际沙箱隔离。
- **目标**：评估 Java 进程隔离（ProcessBuilder + seccomp-bpf）或 Docker 容器化执行 SYSTEM 级工具。MVP：`SandboxedToolExecutor` 包装层，将 SYSTEM 级工具在独立进程/容器中执行。

**17. 后台记忆整合（Dreaming）** `kernel-memory`

- **差距**：Claude Code 的 autoDream + OpenClaw 的 Memory Dreaming。
- **现状**：runner 无后台记忆处理。
- **目标**：`MemoryConsolidator` 后台任务（基于 `TriggerSource` cron），定期扫描短期 session memory，提取高价值信息合并到 durable memory 层。
