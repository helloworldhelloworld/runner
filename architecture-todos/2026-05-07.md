## 一、外部参照物要点速览（增量）

### 1.1 OpenClaw 2026.5 新架构特征

| 设计点 | 实现方式 | 对 runner 的启示 |
|---|---|---|
| **Task Brain（统一任务账本）** | SQLite-backed 单一任务管理层，合并 ACP tasks、subagent、cron jobs、background processes 到统一账本 | runner 的 SubagentRuntime (ConcurrentHashMap) + Orchestrator (InterruptibleRun map) + ToolCallingLoop 是三套独立状态管理，无统一视图；可参考 Task Brain 统一任务生命周期 |
| **Node-Graph 执行模型** | 用有向图取代传统 loop 执行，节点 = Agent/Tool，边 = 条件路由，支持循环与分支 | runner 的 ToolCallingLoop 是线性 ReAct loop；Orchestrator 是单一路由；缺少 DAG 工作流能力（TODO-029 已记录但未评估） |
| **eBPF 内核级安全沙箱** | 每个 Skill 附带 `clawmanifest.json` 声明 filesystem paths + network endpoints + shell commands（SHA256 pinned），runtime 通过 eBPF 探针 SIGKILL 越权进程 | runner 的 CliTool 零安全检查（TODO-001 P0），应先落地 command denylist + 工作目录限制，长期考虑 container 或 seccomp 隔离 |
| **四层架构** | Gateway（调度）→ Nodes（硬件交互）→ Channels（消息平台）→ Skills（能力插件） | runner 的分层（kernel → tools/mcp/memory → web）类似但 Channel 层缺失；如未来需多渠道（微信/钉钉/飞书），需提前规划 Channel 抽象 |
| **clawmanifest.json 能力声明** | 工具显式声明自己需要的权限，运行时执行最小权限原则 | runner 的 Tool 接口无权限声明字段；ScopedToolRegistry 只做 allow/deny，不做细粒度资源声明 |

### 1.2 Claude Code 泄露源码深度分析（增量）

| 设计点 | 实现方式 | 对 runner 的启示 |
|---|---|---|
| **5 层 Compaction 级联** | Budget Reduction → Snip → Microcompact → Context Collapse → Auto-Compact，按成本从低到高依次尝试 | runner 只有 2 层（Snip + Micro）；缺少 Budget Reduction（单个 tool output 超限裁剪）、Context Collapse（超长历史压缩）、Auto-Compact（LLM 生成摘要） |
| **Self-Healing Memory (MEMORY.md)** | 轻量指针索引（~150 chars/line），永久加载到 context；指向外部文件的详细内容 | runner 的 MemoryProvider 没有"指针索引"概念，search() 直接返回全文；context 中 memory 占用不可控 |
| **autoDream 记忆整合** | fork 一个受限子 agent，合并多会话观察、移除矛盾、将模糊笔记转化为确认事实，压缩到 <200 行 / 25KB | runner 完全没有记忆整合机制；ephemeral 和 durable memory 只增不减（TODO-021 已记录） |
| **Tool 独立权限等级** | 每个 tool 定义自己的 input schema + permission level + execution logic，无共享可变状态；BashTool 和 FileReadTool 虽在同一 registry 但权限等级不同 | runner 的 Tool 接口无 permission/risk level 字段；所有工具权限等同（TODO-015 已记录） |
| **Anti-Distillation 机制** | `ANTI_DISTILLATION_CC` flag → 注入 fake tool definitions 到 API 请求，污染竞品训练数据 | runner 无此需求，但说明 **编译时 feature flag** 的基础设施是其他高级功能的前提 |
| **14 Cache-Break Vector 监控** | 主动监控 14 种可能使 prompt cache 失效的条件，优化 cache hit rate | runner 尚未实现 prompt caching（TODO-024），更谈不上 cache 命中率监控 |

## 补充：深度研究新增发现

> 来自对 OpenClaw 源码（DeepWiki 分析）、Claude Code 官方工程博客、Spring AI / Google ADK 最新文档的交叉比对。

### 新发现 1：OpenClaw 收敛检测（Convergence Detection）

OpenClaw agent loop 在每次迭代后计算前后状态的语义相似度，若 observations + thoughts + actions 连续两轮 >85% 相似，则强制终止防止无限循环。

**runner 对比**: ToolCallingLoop 仅靠 `maxIterations` 硬上限 + `CostTracker.isOverBudget()`（且后者完全失效）。缺少语义级收敛检测。

**Action**: 在 ToolCallingLoop 迭代间增加"输出相似度"检测，连续 N 轮高相似度时提前退出并发出 `AGENT_CONVERGED` 事件。**Priority**: P2。

### 新发现 2：Claude Code Tool Search（按需加载工具 Schema）

Claude Code 不在启动时加载所有工具 schema 到 context，而是提供 **Tool Search Tool**，模型按需搜索和发现工具。对于注册了大量 MCP tools 的场景，可大幅减少 context 占用。

**runner 对比**: ToolRegistry.getToolDefinitions() 一次性将所有 enabled 工具的 schema 注入 LLMOptions。当 MCP server 暴露 50+ tools 时，context 开销显著。

**Action**: 实现 `ToolSearchTool`（内置 tool），根据查询关键词返回匹配工具的 schema；LLMOptions 仅注入 top-N 最相关工具 + ToolSearchTool 本身。**Priority**: P2（已有 TODO-012 类似，此处更具体）。

### 新发现 3：Claude Code 四层扩展成本模型

Claude Code 的扩展机制按 context 成本排序：Hooks (零) → Skills (最小) → Plugins (中等) → MCP servers (高)。这个"成本意识"指导了扩展点的选择。

**runner 启示**: 当前 5 种 ToolSourceProvider 未区分 context 成本。应在 ToolSourceProvider 或 Tool 级别标注 `contextCostHint`，让 ToolSearchTool 和 ContextCompactor 做出成本最优决策。

### 新发现 4：Spring AI 已集成 A2A 协议

Spring AI 通过 `spring-ai-a2a` 模块已提供 A2A Java SDK 的 Spring Boot autoconfiguration，支持 HTTP / SSE / JSON-RPC transport。runner 作为 Java 项目可直接复用。

**Action**: 评估 `spring-ai-a2a` 作为 TODO-019 (A2A Protocol Readiness) 的实现路径。**Priority**: P3。

### 新发现 5：BATS 预算分级模式

多个框架收敛到四级预算模式：**HIGH** (>=70% 剩余) → **MEDIUM** (30-70%) → **LOW** (10-30%) → **CRITICAL** (<10%)。每级对应不同的 compaction 策略和工具执行策略。

**runner 对比**: CostTracker 只有 binary `isOverBudget()`。应改为 `getBudgetRegime()` 返回枚举值，不同 regime 触发不同行为（如 LOW 时触发 Micro compaction，CRITICAL 时触发 Auto-Compact）。

**Action**: CostTracker 增加 `BudgetRegime` 枚举 + `getRegime()` 方法；CompactionChain 根据 regime 选择 compaction 策略。**Priority**: P1（与 P0-2 CostTracker 修复可同步进行）。
