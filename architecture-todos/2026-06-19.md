## 一、外部参照物最新要点

### 1.1 Claude Code 泄露源码 + Agent SDK 官方文档（2026.6 综合）

上次审计（04-08）聚焦在泄漏事件本身；本轮新增两类增量信息：

#### A. Agent SDK 官方规范化的设计模式

Claude Code Agent SDK 已将内部模式作为公开 API 固化，这些是 runner 可以直接对标的生产级模式：

| 设计模式 | SDK 实现 | runner 现状 | 差距 |
|---|---|---|---|
| **Deferred Tool Loading (ToolSearch)** | MCP 工具 schema 默认延迟加载；仅在 LLM 请求时通过 `ToolSearch` 按需拉取 | 所有 MCP 工具 schema 在启动时全量加载到 context | **缺失**：大量 MCP server 场景下 context 浪费严重 |
| **Effort Level 分级** | `low/medium/high/xhigh/max` 五档推理深度，可按 subagent 单独设置 | `LLMOptions` 无 effort 参数 | **缺失**：无法按任务复杂度调配成本 |
| **Permission Mode 体系** | `default/acceptEdits/plan/dontAsk/auto/bypassPermissions` 六种模式 + `allowed_tools`/`disallowed_tools` 规则 + scope 语法 `Bash(npm *)` | `ToolPolicy` 已有 ALLOW/DENY/ABSTAIN + `byRiskLevel` | **部分对齐**：缺 `plan` 模式（只读探索）和 scope 细粒度语法 |
| **Parallel vs Sequential Tool Execution** | 只读工具并行，写操作顺序；自定义工具通过 `readOnlyHint` 注解控制 | `ToolExecutor` 支持并行但无只读/写分类 | **缺失**：无智能并行策略 |
| **ResultMessage Subtype 体系** | `success/error_max_turns/error_max_budget_usd/error_during_execution` + `stop_reason` | `AgentResponse` 有 `stopReason` 但无结构化 subtype | **缺失**：调用方无法区分"正常结束"与"预算耗尽" |
| **Automatic Compaction + compact_boundary 事件** | 接近 context 上限时自动 compact，发射 `compact_boundary` 系统事件 | `ContextCompactor` 已实现但调用点仅在 `AgentLoop.buildMessages()` 前；无 `compact_boundary` 事件 | **部分对齐**：缺事件通知 + 缺 CLAUDE.md 风格的"compaction 保留指令" |
| **Session Resume / Fork** | `session_id` 可恢复完整 context；fork 创建分支会话 | 无 session resume；`SessionManager` 无 fork 概念 | **缺失** |
| **PreCompact Hook** | 在 compact 前触发，允许归档完整 transcript | `AgentObserver` 无 `onPreCompact` 事件 | **缺失** |

#### B. 隐藏 Feature Flags 揭示的方向性设计

| Feature Flag | 能力 | 对 runner 的参考价值 |
|---|---|---|
| **KAIROS** | 常驻后台 daemon + autoDream 记忆整理（4 阶段：Orient→Gather→Consolidate→Prune） | runner 的 `SkillGeneratorObserver` 仅在单次会话内学习；缺少跨会话记忆整理与主动唤醒 |
| **ULTRAPLAN** | 远程 Opus 容器做 30 分钟深度规划，专治"步骤一错全链崩"的架构任务 | runner 没有"规划模式"——`PromptEngine` 无法切换 plan/execute 双阶段 |
| **COORDINATOR_MODE** | 单 agent → coordinator + N workers + 共享 team memory + mailbox 审批链 | runner 的 `SubagentRuntime` 已有 spawn/wait，但缺 coordinator 角色 + shared team memory + mailbox 审批 |
| **DREAM** | append-only 日志 + 4 阶段整理（Orient/Gather/Consolidate/Prune）+ 独占工具 | runner 的 `MemoryProvider` 有 ephemeral/durable 分层但无自动整理周期 |

### 1.2 OpenClaw 2026.6 架构演进

OpenClaw 从 04 月至今的关键演进：

| 演进点 | 具体变化 | 对 runner 的启示 |
|---|---|---|
| **Bootstrap File 分离** | `SOUL.md`（人格）、`AGENTS.md`（规则）、`USER.md`（用户画像）、`IDENTITY.md`（身份）、`TOOLS.md`（环境注释）、`MEMORY.md`（学到的模式）——每个文件各管一事 | runner 用 `PromptEngine` 将所有关注点拼成一个 system prompt；无分文件、分关注点的结构 |
| **Provider Plugin 重构** | 从硬编码升级为 Provider plugin 系统：动态注册 Anthropic/OpenAI/本地模型 | runner 已通过 `LLMProviderSpi` 解决 ✅ |
| **Memory 向量化** | 400-token chunk + 80-token overlap → embedding → sqlite-vec；文件即记忆 | runner 的 `kernel-memory` 有 BM25+vector 但 chunk 策略未见精细化 |
| **ACP (Agent Communication Protocol) Dispatch** | 默认启用 ACP 运行时，嵌入 acpx 插件 | runner 无 agent 间标准通信协议；subagent 靠 tool result 回传 |
| **ClawHub 技能市场** | bundled / managed / workspace 三层 skill 来源 | runner 的 Skill 仅本地注册；无远程 skill 仓库概念 |

### 1.3 社区最佳实践（2026 H1 综合）

| 实践 | 关键洞察 | runner 现状 |
|---|---|---|
| **Prompt Caching 优化** | 静态 prompt 部分缓存后每次调用成本降 50-90%；优化目标从"最小化 context"变为"最大化 cache hit rate"——保持 prefix 稳定、append-only、确定性更新 | runner 无 prompt caching 策略；每次 `PromptEngine.build()` 可能因 memory search 结果不同导致 prefix 不稳定 |
| **Context Engineering 四原则** | Write（编写指令）→ Select（选择相关 context）→ Compress（压缩 token 浪费）→ Isolate（隔离无关 context） | runner 在 Write 和 Compress（SnipCompactor）上已有；Select 和 Isolate 薄弱 |
| **Subagent 隔离作为 context 管理手段** | 子 agent 独立 context + 只返回最终结果 = 父 context 仅增长一条 tool_result | runner 的 SubagentRuntime 已实现隔离，但尚未将其作为"context 管理策略"主动运用 |
| **Tool Schema Deferred Loading** | 每个 MCP server 工具 schema 占用 context；延迟加载 + 按需搜索是生产标配 | 全量加载 |
| **统一记忆系统** | Context + Retrieval + Compression 统一为单一可寻址层（Letta/Mem0 方向） | runner 的三层（session / ephemeral / durable）概念正确但互不打通 |

## 二、现状架构痛点盘点（新增 + 未关闭合并）

### P0 — 影响主链路正确性 / 成本 / 生产可用性

| # | 痛点 | 参照来源 | 现状详情 |
|---|---|---|---|
| **P0-1** | **Deferred Tool Loading 缺失** | Claude Agent SDK ToolSearch | 所有 MCP 工具 schema 启动时全量注入 context；随 MCP server 增多，base context 膨胀，挤占对话空间。Claude Code 默认延迟加载 MCP schema，仅 `ToolSearch` 按需拉取。 |
| **P0-2** | **Prompt Caching 策略缺失** | Anthropic API / 社区 | `PromptEngine.build()` 每次因 memory search 结果变化导致 system prompt 前缀不稳定；无法利用 Claude API 的 prompt caching（cache_control 标记），每次全价付 input tokens。 |
| **P0-3** | **AgentResponse 无结构化终止类型** | Claude Agent SDK ResultMessage | 调用方无法区分"任务完成"、"token 预算耗尽"、"最大轮次"、"执行异常"。目前只有 `stopReason` 字符串，语义不明确。 |
| **P0-4** | **ToolExecutor 无智能并行策略** | Claude Agent SDK parallel tool execution | 当前要么全并行要么全顺序；缺少根据 `readOnlyHint` / `RiskLevel` 自动决定并行 vs 顺序的逻辑。写操作并行可能导致状态冲突。 |

### P1 — 扩展性 / 可观测性 / 开发体验

| # | 痛点 | 参照来源 | 现状详情 |
|---|---|---|---|
| **P1-1** | **模块化 System Prompt 仍未解决** | Claude Code 110+ prompt 片段 / OpenClaw Bootstrap Files | `PromptSection` 已废弃，`PromptAssembler` 不存在；base + durable + skills 硬拼。无法按模式（Plan/Execute/Learn）条件装配。（延续自 04-08 P1-7） |
| **P1-2** | **Session Resume / Fork 缺失** | Claude Agent SDK session management | 无法通过 session_id 恢复完整对话 context；无法 fork 会话做分支探索。对于长任务和中断恢复场景是硬伤。 |
| **P1-3** | **ToolPolicy 缺 Scope 细粒度语法** | Claude Agent SDK `Bash(npm *)` | 当前 ToolPolicy 按工具名整体 ALLOW/DENY；无法表达"允许 Bash 执行 npm 相关命令但禁止 rm -rf"这类细粒度规则。 |
| **P1-4** | **Effort Level（推理深度分级）缺失** | Claude Agent SDK effort | `LLMOptions` 无 effort 参数；所有任务同等推理深度，简单查询也用 max reasoning。 |
| **P1-5** | **PreCompact Hook 缺失** | Claude Agent SDK hooks | `AgentObserver` 无 `onPreCompact` 事件；compact 前无法归档完整 transcript 或执行自定义逻辑。 |
| **P1-6** | **Compact Boundary 事件缺失** | Claude Agent SDK StreamEvent | `ContextCompactor` 执行后不发射任何 `StreamEvent`；下游（UI/日志）无法感知 compaction 发生。 |
| **P1-7** | **SessionManager 缺 onTimeout + TTL** | OpenClaw Gateway session 管理 | 已有 `onSessionStart`/`onSessionStop` 但无超时清理；长期闲置 session 会泄漏内存。（延续自 04-08 P1-6） |

### P2 — 治理 / 长期演进 / 对标前沿

| # | 痛点 | 参照来源 | 现状详情 |
|---|---|---|---|
| **P2-1** | **LLMProvider 装饰器链无注册机制** | 通用模式 | `AgentConfig` 里手动 `new ResilientLLMProvider(base)`；无 chain builder 按 order 组装。（延续自 04-08 P2-10） |
| **P2-2** | **MemoryProvider 全同步阻塞** | 社区 async patterns | `search()` 返回 `List<MemorySearchResult>`；无 reactive 变体。BM25+vector 检索阻塞 AgentLoop 线程。（延续自 04-08 P2-12） |
| **P2-3** | **Feature Flag 系统缺失** | Claude Code 44 flags | 无灰度发布能力；新特性只能硬编码开关。（延续自 04-08 P2-13） |
| **P2-4** | **Coordinator 模式缺失** | Claude Code COORDINATOR_MODE | `SubagentRuntime` 有 spawn/wait 但无 coordinator 角色；多 agent 场景下缺少统一任务分配 + shared team memory + mailbox 审批链。 |
| **P2-5** | **跨会话记忆整理（DREAM 模式）缺失** | Claude Code KAIROS + autoDream | `MemoryProvider` 有 ephemeral/durable 分层但无自动整理周期；长期运行后 ephemeral 记忆累积无剪枝。 |
| **P2-6** | **Agent 间标准通信协议缺失** | OpenClaw ACP | subagent 间仅靠 tool result 回传；无结构化的 agent-to-agent 消息协议。 |
| **P2-7** | **远程 Skill 仓库 / 市场** | OpenClaw ClawHub | Skill 仅本地注册；无发现、安装、版本管理远程 skill 的能力。 |
| **P2-8** | **Bootstrap 上下文分文件管理** | OpenClaw SOUL.md/AGENTS.md/USER.md/MEMORY.md | 所有 bootstrap context 混在 `PromptEngine` 一次性拼接；无分关注点的文件结构，不利于非开发者维护 agent 人格/规则。 |

## 五、架构合理性总评

### 做得好的方面

1. **核心 Agent Loop 模式成熟** — `AgentLoop` + `ToolCallingLoop` 的 TAOR 循环 + `CancellationToken` 中断 + `CostTracker` 预算，与 Claude Code 的核心模式高度对齐。
2. **四层 Orchestrator 架构清晰** — Profile → Registry → Orchestrator → SubagentRuntime 分层合理，职责边界明确。
3. **ToolPolicy 可组合设计** — `chain()` / `byRiskLevel()` / `allowList()` / `denyList()` 的 Decision 三值逻辑（ALLOW/DENY/ABSTAIN）优于简单黑白名单。
4. **Reactive-First 贯穿** — `Flux<StreamEvent>` 从 LLM 到 WebSocket 端到端统一，stream post-processing pipeline 可组合。
5. **Docs-First + TDD 纪律** — 12 个 ADR、outside-in 测试规则、public API stability 约束，在开源 agent 框架中少见。

### 主要差距（与 Claude Code + OpenClaw 对标）

1. **Context 经济性** — 缺 deferred tool loading + prompt caching + compact boundary 事件。Claude Code 在此投入了 98.4% 的代码量（基础设施 vs AI 逻辑比）。
2. **运行模式多样性** — 缺 plan mode、effort level、coordinator mode。只有单一执行模式。
3. **Session 持久化** — 无 resume/fork，长任务场景脆弱。
4. **Bootstrap 结构化** — 对比 OpenClaw 的 SOUL.md/AGENTS.md/USER.md 等分文件模式，runner 的 PromptEngine 将所有关注点混在一起，不利于非开发者维护。
