# 架构优化 Todo — 2026-04-08

> 参照对象：OpenClaw (2026.4 版本) + Claude Code 源码泄露（v2.1.88 源码泄漏事件，~51.2 万行 TypeScript）
> 当前分析基线：runner 现有 12 个模块架构

## 一、外部参照物要点速览

### 1.1 Claude Code 源码泄露揭示的关键设计

| 设计点 | 实现方式 | 对 runner 的启示 |
|---|---|---|
| **QueryEngine 双层循环** | 外层 `ask()` 入口 + 内层 `queryLoop` 工具循环；单个 4.6 万行模块统一处理 LLM 调用、流式、缓存、重试、速率限制、上下文预算 | runner 的 `AgentLoop` + `ToolCallingLoop` 职责切分合理，但缺少"上下文预算管理"与"流式错误统一处理" |
| **消息不可变快照** | 维护可变 message 数组用于持久化/UI；每次进入 query loop 时对 API 请求传入 compact 后的不可变快照 | runner 的 `MemoryProvider.getHistory()` 直接暴露可变引用；Gateway/AgentLoop 之间没有"快照"概念 |
| **三层 Compaction 策略** | (1) **Snip compact**：删除旧工具结果；(2) **Microcompact**：就地压缩大工具结果；(3) **Autocompact**：fork 子 agent 生成对话摘要 | runner 完全没有 compaction，长会话会直接爆 context |
| **TAOR 循环（Think-Act-Observe-Repeat）** | 编排器完全不感知"代码/文件"，只跑循环，由模型决定何时停止 | runner 的 `ToolCallingLoop` 已是 TAOR 模型，但 `maxIterations` 硬编码、没有 token 预算退出条件 |
| **模块化 System Prompt** | 110+ 独立 prompt 字符串，按激活特性条件组装；base ~269 tokens，auto/plan/learning 模式动态加载 | runner 的 `PromptEngine` 将 base + memory + skill 硬拼，没有"模式"与"条件段"概念 |
| **Hook 生命周期（12 个事件）** | SessionStart / UserPromptSubmit / PreToolUse / PostToolUse / Stop / SubagentStop / Notification / PreCompact 等；支持 command/http/prompt/agent 四种 handler | runner 有 `AgentObserver` 但全代码无调用点，更没有 PreToolUse 这类拦截 |
| **Subagent 隔离** | 子 agent = 独立上下文 + tool allowlist + model 选择 + 独立记忆；通过 `description` 触发委派 | runner 完全没有 subagent 概念 |
| **隐藏 Feature Flag** | 44 个 feature flag + 20+ 未发布特性：后台 24/7 agent、orchestrator/worker、cron、voice、playwright browser、sleep/self-resume | runner 没有 feature flag 系统，新特性只能硬编码 |

### 1.2 OpenClaw 2026.4 架构要点

| 层 | 职责 | 关键特征 |
|---|---|---|
| **Gateway（控制平面）** | 长连 WebSocket 服务；管理 session、channel、tool dispatch、事件 | 绑定 127.0.0.1:18789；loopback-only；Control UI + WebChat 同端口 |
| **Agent Runtime** | 端到端跑 AI loop，装配 context、调用 model、执行 tool、持久化 | ACP dispatch 默认开启；ACP runtime 嵌入 acpx 插件 |
| **Multi-Channel Inbox** | WhatsApp/Telegram/Slack/Discord/Feishu/WeChat/Matrix 等 20+ 渠道 | 统一消息抽象 |
| **Memory** | 向量索引 Markdown（~400 token chunk + 80 token overlap）→ OpenAI/Gemini/Local GGUF embedding → SQLite + sqlite-vec | 文件即记忆；增量同步 |
| **Orchestrator 子组件** | 顶层控制器，从 gateway 收事件 → 选 agent → 管理任务序列 | 与 Agent Runtime 分离 |

## 二、现状架构痛点（对齐后盘点）

按"架构合理性差距"排序，P0 最高。

### P0 — 影响主链路正确性/稳定性

1. **Context Compaction 完全缺失** `agent-kernel/.../AgentLoop.java`, `PromptEngine.java`
   - 症状：长会话无上限堆 message；超过模型 context 直接 400。
   - 参考：Claude Code 三层 compaction（Snip / Micro / Auto）。
   - 目标：新增 `ContextCompactor` 接口，默认实现 Snip（删除最老工具结果），后续补 Micro（就地压缩单个大 tool_result）与 Auto（fork 子 LLM 摘要）。
   - 落点：`AgentLoop.executeChat` 在构建 prompt 前调用；`ToolCallingLoop` 每轮迭代后检查 token 预算。

2. **消息链路没有"不可变快照"边界** `MemoryProvider.java`, `AgentLoop.java`
   - 症状：`getHistory()` 返回可变 `List<Message>`，持久化历史和 API 请求视图混用，compaction 无法安全做。
   - 目标：引入 `MessageSnapshot`（immutable），API 调用路径只接受 snapshot；持久化路径保留可变数组。
   - 对齐：Claude Code 双层架构。

3. **Token 预算 / 成本追踪全无** `ClaudeModelCapability.java`, `OpenRouterModelCapability.java`
   - 症状：代码中 TODO；`ResilientLLMProvider` 只管重试，不管预算。
   - 目标：`TokenCounter` SPI + `CostTracker` 装饰器；`ChatOptions` 加 `maxBudgetTokens`；超预算触发 compaction 或优雅中止。

4. **LLMProviderFactory 硬编码 switch** `LLMProviderFactory.java:25-42`
   - 症状：仅支持 claude/anthropic；OpenAI TODO；扩展必须改核心类。
   - 目标：改为 `ServiceLoader<LLMProviderFactory>` SPI 注册表；命名冲突 fail-fast；`@ConditionalOnProperty` 驱动 Spring 装配。

### P1 — 扩展性与可观测性

5. **Hook / Lifecycle 生态空缺** `AgentObserver.java`（已定义，无调用点）
   - 目标：参考 Claude Code 12 事件，最小落地 6 个：`SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PostToolUse`、`PreCompact`、`Stop`。
   - 落点：`ToolCallingLoop.invokeTool` 前后埋 `PreToolUse`/`PostToolUse`；Gateway 会话开关埋 `SessionStart`/`Stop`。
   - Handler 抽象：`HookHandler`（interface） + `CommandHookHandler`（shell） + `HttpHookHandler`（webhook） + `AgentHookHandler`（内部 bean）。

6. **SessionManager 接口太薄** `agent-kernel/.../gateway/SessionManager.java`
   - 症状：无 `onStart`/`onStop`/`onTimeout` 生命周期；无异步清理；无超时 TTL。
   - 目标：拓展接口 + 默认 `InMemorySessionManager` 实现；`SessionContext` 包含 deviceId / channelId / userId / budget 信息。
   - 对齐：OpenClaw Gateway 的 session 管理模型。

7. **模块化 System Prompt 缺失** `PromptEngine.java`
   - 症状：base + durable + skills 硬拼，无法按模式/能力条件装配。
   - 目标：引入 `PromptSection`（id, order, condition, render）+ `PromptAssembler`；支持 Plan/Auto/Learning 类"模式"开关；CLAUDE.md 对应本项目的项目级指令片段可按会话加载。

8. **Tool.executeReactive 默认实现是假流式** `Tool.java:52`
   - 症状：非 MCP 工具统一包装为单个 COMPLETE chunk；文件读取、长任务无真实流式。
   - 目标：为文件读、HTTP、shell 这类工具提供 `StreamingTool` 基类，基于 Flux.create 按块推送；保留现有 `execute()` 作为便利方法。

### P2 — 治理与长期演进

9. **Subagent / Delegation 机制空白** 全库无相关概念
   - 目标：新增 `AgentDelegator`，允许 Tool 实现触发一个隔离 loop（独立 context、独立 tool allowlist、独立 model）。
   - MVP：一个内置 `DelegateTool`，参数为 `description` + `prompt`，调用方式与 Claude Code 的 Agent tool 一致。
   - 隔离：结果以 `ToolResultChunk` 回传父 loop，不污染父 context 的中间步骤。

10. **`DynamicLLMProvider` / Resilient 等装饰器组合无注册机制** `agent-web`
    - 症状：装饰器在 GatewayConfig 里手动链式 new；顺序靠人记。
    - 目标：`LLMProviderChainBuilder` 按 `order` 注册装饰器；配置驱动开关（retry/budget/tracing/caching）。

11. **ToolSourceProvider 生命周期没有接入点** `ToolSourceProvider.java:22-32`
    - 症状：`start()`/`stop()` 方法定义了但无人调用；动态工具加载不可能。
    - 目标：`ToolRegistry` 在 Spring `@PostConstruct` 聚合所有 `ToolSourceProvider` bean 并调用 `start()`；`@PreDestroy` 反向 `stop()`；通过 `ToolRegistryListener` 推送增量。

12. **MemoryProvider 全同步阻塞** `MemoryProvider.java`
    - 症状：BM25 + vector 混合检索阻塞 AgentLoop 线程。
    - 目标：增加 `searchAsync`/`searchReactive`；`AgentLoop.prepareContext` 改为 reactive 流水线；`kernel-memory` 内部用 virtual thread 或 scheduler 隔离。

13. **Feature Flag 系统缺失**
    - 目标：最小 `FeatureFlags` bean，基于 `application.yml` + env var；为未来灰度发布预留。
    - 参考：Claude Code 44 个内置 flag 的 Map<String, Boolean> + condition evaluator 模式。

14. **Observability / Tracer 只有骨架**
    - 症状：`StreamEvent.trace()` 有字段但没有统一 exporter；`SpanContext` 只传递不落地。
    - 目标：OpenTelemetry 桥接：`AgentSpanExporter` 将 `StreamEvent.TRACE` 转为 OTel span；prompt/tool 调用作为 child span。
