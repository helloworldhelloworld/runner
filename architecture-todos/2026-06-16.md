### 1.6 上下文工程四策略框架（Write / Select / Compress / Isolate）

| 策略 | 含义 | runner 覆盖 | 差距 |
|---|---|---|---|
| **Write** | 持久化信息到上下文窗口之外（工作备忘录/scratchpad） | MemoryProvider(Session/Ephemeral/Durable) | ⚠️ 无 agent 工作备忘录（scratchpad），中间推理步骤只在 context 内 |

## 二、现状架构痛点盘点（P0 / P1 / P2 三级）

### P0 — 影响主链路正确性 / 稳定性

#### P0-1 Auto Compaction 仍缺失
- **症状**：Snip+Micro 只能删/截工具结果；超长纯对话（无工具调用）无法压缩；长会话最终仍溢出。
- **参考**：Claude Code 第三层 Auto = fork 子 agent 生成对话摘要替换原消息；OpenClaw `generateSummary()` 默认 16K 预算。
- **目标**：新增 `AutoCompactor` 实现（fork 子 LLM 调用，将 N 轮旧对话压缩为单条摘要消息），挂入 CompactionChain 末尾。
- **前置**：需要一个轻量 LLM 调用入口（可复用 LLMProvider，不经 ToolCallingLoop）。
- **落点**：`agent-kernel/.../context/AutoCompactor.java`

#### P0-2 命令执行安全验证缺失
- **症状**：CLI 工具、shell_exec 等工具直接执行命令，无安全校验；面临命令注入、路径遍历风险。
- **参考**：Claude Code `bashSecurity.ts` 2500 行 + 23 条规则；OWASP Agentic Top 10 工具误用风险。
- **目标**：新增 `CommandValidator` SPI，在 `CliTool`/shell 工具执行前校验命令合法性（黑名单命令、路径限制、参数净化）。
- **落点**：`agent-kernel/.../cli/CommandValidator.java` + `DefaultCommandValidator.java`

#### P0-3 工具执行阶段缺少二次权限校验
- **症状**：ToolPolicy 在工具列举/展示阶段过滤（`ScopedToolRegistry.getToolDefinitions()`），但 ToolExecutor 执行时不再校验 args；LLM 可能传入未预期参数。
- **参考**：Zero-Trust Agentic Runtime "每次调用经过授权"；Claude Code 七种权限模式。
- **目标**：`ToolExecutor.invoke()` 增加 `ToolPolicy.evaluate(request_with_args)` 二次校验；`ToolPolicyRequest` 已携带 args 字段（列举时 null，执行前非 null）。
- **落点**：`agent-kernel/.../core/ToolExecutor.java`

### P1 — 扩展性与可观测性

#### P1-1 Hook 生命周期不完整
- **症状**：AgentObserver 只有 PreToolUse/PostToolUse 真正接入；SessionStart/Stop/PreCompact 无调用点。
- **参考**：Claude Code 12 个 hook 事件 + 4 种 handler（command/http/prompt/agent）；OpenClaw 支持 session/gateway/tool 三级 hook。
- **目标**：
  1. Gateway 层埋 `onSessionStart`/`onSessionStop`
  2. ContextCompactor 调用前埋 `onPreCompact`
  3. AgentLoop 完成/异常时埋 `onAgentComplete`/`onError`（已定义未调用）
  4. 新增 `HookHandler` SPI 支持 shell command handler（对标 Claude Code hooks）
- **落点**：`Gateway.java`, `AgentLoop.java`, `ContextCompactor.java`

#### P1-2 System Prompt 模块化不足
- **症状**：base + durable + skills 硬拼字符串，无法按模式/条件装配；durable memory 全量注入浪费 token。
- **参考**：Claude Code 110+ 独立 prompt section 按条件装配（base 269 tokens，模式动态加载）；OpenClaw skills 元数据优先。
- **目标**：
  1. 引入 `PromptSection`（id, order, condition, content）+ `PromptAssembler` 替代硬拼
  2. Skill 分两段：metadata（始终在 system prompt）+ body（模型按需读取），参考 OpenClaw 的 token 节省策略
  3. Durable memory 按相关性截取，不全量注入
- **落点**：`agent-kernel/.../prompt/PromptSection.java`, `PromptAssembler.java`

#### P1-3 MemoryProvider 全同步阻塞（延续 P2-12）
- **症状**：BM25 + vector 混合检索阻塞 AgentLoop 线程；大索引场景延迟高。
- **参考**：OpenClaw SQLite FTS5 + 异步查询；社区普遍采用 async retrieval。
- **目标**：新增 `searchReactive(query)` 返回 `Mono<List<MemorySearchResult>>`；AgentLoop.prepareContext 改为 reactive 管道。
- **落点**：`MemoryProvider.java`（default method），`kernel-memory`

#### P1-4 SessionManager 生命周期薄弱（延续 P1-6）
- **症状**：无 `onStart`/`onStop`/`onTimeout` 回调；无 TTL 自动清理；无持久化。
- **参考**：OpenClaw Gateway session 管理（lane queue + lifecycle）；Claude Code append-only session storage。
- **目标**：
  1. 扩展 `SessionManager` 接口：`SessionContext`（deviceId/channelId/userId/budget）
  2. Lane Queue 模式：同 session 请求串行执行，防并发竞态
  3. 可选持久化（SQLite/文件），支持会话恢复
- **落点**：`agent-kernel/.../gateway/SessionManager.java`, `SessionContext.java`

#### P1-5 Observability / OTel 集成缺失（延续 P2-14）
- **症状**：Tracer/SpanContext 骨架存在但无 exporter；TRACE 事件只有内部日志。
- **参考**：OpenClaw OpenClawBus RFC（分离事件总线）；社区 OTel agent instrumentation 趋势。
- **目标**：
  1. `AgentSpanExporter` 将 StreamEvent.TRACE 转为 OTel span
  2. LLM 调用、工具调用、compaction 作为 child span
  3. 可选事件总线（EventBus）供外部消费者订阅，不限于 WebSocket/SSE
- **落点**：`agent-kernel/.../trace/OTelBridge.java`

#### P1-6 结构化输出约束缺失
- **症状**：LLM 返回格式完全依赖 prompt 引导，无法强制 JSON schema。
- **参考**：Anthropic Agent SDK / OpenAI 结构化输出（response_format）；Claude 原生支持 tool_use 结构化返回。
- **目标**：`LLMOptions` 新增 `responseFormat`（json_schema/text）；`ClaudeProvider` 和 `OpenRouterProvider` 映射到各自 API 参数。
- **落点**：`LLMOptions.java`, `ClaudeProvider.java`, `OpenRouterProvider.java`

### P2 — 治理与长期演进

#### P2-1 Feature Flag 系统缺失（延续 P2-13）
- **症状**：新特性只能硬编码开关（如 `app.voice.speakable-chunk.enabled`），无统一管理。
- **参考**：Claude Code 44 个 feature flag + condition evaluator。
- **目标**：`FeatureFlags` bean，基于 `application.yml` + env var；统一 `isEnabled(flagName)` API。
- **落点**：`agent-kernel/.../FeatureFlags.java` 或 `agent-web` 配置层

#### P2-2 LLMProvider 装饰器注册机制（延续 P2-10）
- **症状**：retry/budget/tracing 装饰器手动链式 new；顺序靠人记。
- **目标**：`LLMProviderChainBuilder` 按 order 注册装饰器；配置驱动开关。
- **落点**：`agent-web/.../config/LLMProviderChainBuilder.java`

#### P2-3 记忆投毒防护
- **症状**：外部 MCP 工具返回值直接进入 context，无净化；恶意工具可注入 prompt injection。
- **参考**：OWASP Agentic Top 10 "Memory Poisoning"；AgentSafe 权限级分类 + HierarCache。
- **目标**：工具结果进入 context 前经 `ResultSanitizer` 过滤（去除明显的 prompt injection 模式、超长结果截断）。
- **落点**：`agent-kernel/.../core/ResultSanitizer.java`

#### P2-4 级联失败断路器
- **症状**：SubagentRuntime cascade-stop 能级联停止，但无"断路器"模式（连续失败后暂停 spawn）。
- **参考**：OWASP "Cascading Failures"；微服务 circuit breaker 模式。
- **目标**：SubagentRuntime 新增简易断路器：连续 N 次 subagent 失败后拒绝新 spawn，cooldown 后恢复。
- **落点**：`agent-kernel/.../orchestrator/SubagentRuntime.java`

#### P2-5 Subagent 资源隔离
- **症状**：子 agent 与父 agent 共享 JVM 资源，无文件系统/内存隔离。
- **参考**：Claude Code worktree 隔离（独立 git worktree）。
- **目标**：设计层面预留隔离接口 `SubagentSandbox`；MVP 可通过临时目录 + 受限 ToolPolicy 近似隔离。
- **落点**：`agent-kernel/.../orchestrator/SubagentSandbox.java`（接口草案）

#### P2-6 常驻后台 Agent 模式
- **症状**：TriggerSource 能推送请求，但没有"常驻 agent"概念（如 Claude Code 的 KAIROS，OpenClaw 的 scheduling）。
- **目标**：基于 TriggerSource + cron 表达式的 `ScheduledTriggerSource`，支持定时巡检、自动执行。
- **落点**：`agent-kernel/.../orchestrator/ScheduledTriggerSource.java`

#### P2-7 ToolSourceProvider.start/stop 生命周期仍未全面接入
- **症状**：start()/stop() 在架构文档中标记"@PreDestroy 时调用 stop()"，但实际接入程度待验证。
- **目标**：审计所有 ToolSourceProvider 实现，确保 start/stop 对称调用；DynamicPluginProvider 的 stop() 应释放 FileWatcher。
- **落点**：`ToolRegistry.java`, 各 `*ToolSourceProvider.java`

## 三、架构合理性深度分析（新增维度）

### 3.1 runner vs Claude Code vs OpenClaw 架构对比矩阵

| 维度 | Claude Code | OpenClaw | runner | 差距评估 |
|---|---|---|---|---|
| **Agent Loop** | while-loop + 五层 compaction | intake→context→inference→tool→stream→persist | AgentLoop + ToolCallingLoop (TAOR) + Snip/Micro | ⚠️ compaction 两层 vs 五层 |
| **事件系统** | SSE delta + 内部事件 | stream: tool/assistant/lifecycle | StreamEvent 闭合枚举 + 工厂方法 | ✅ runner 设计更严谨（ADR-005） |
| **工具权限** | 7 模式 + ML 分类器 | 5 级级联（global→sandbox） | ToolPolicy 三值链式（deny/allow/abstain） | ⚠️ 缺动态协商和 session/sandbox 级别 |
| **多 Agent** | Subagent + worktree 隔离 | Orchestrator + max 5 children | 4 层 Orchestrator + SubagentRuntime | ✅ runner 架构完整度高 |
| **上下文管理** | 5 层 compaction + auto 摘要 | compaction + keepRecentTokens | Snip + Micro + CostTracker | ⚠️ 缺 Auto 和紧急截断 |
| **记忆** | memory.md 指针索引 + 三层 | SQLite FTS5 + Markdown + git | Session/Ephemeral/Durable + BM25+vector | ⚠️ 缺导航索引；全同步 |
| **扩展机制** | MCP+Plugins+Skills+Hooks | MCP+Skills+ClawHub+Hooks | MCP+CLI+Skills+AgentObserver | ⚠️ Hooks 不完整；无注册表 |
| **安全** | bashSecurity 2500行 + 23规则 | 多级沙箱 + Docker 网络隔离 | ToolPolicy + RiskLevel | 🔴 命令验证完全缺失 |
| **可观测性** | 内置 trace + 98.4% 基础设施 | OpenClawBus RFC | Tracer 骨架 + TRACE 事件 | ⚠️ 无 OTel 导出 |
| **Feature Flag** | 44 个 + evaluator | - | 无 | ⚠️ 新特性无灰度能力 |
| **自学习** | 无公开 | 无公开 | learn 包 SkillGeneratorObserver | ✅ runner 领先 |
| **具身化** | 无 | 无 | Minion 四阶段（M0-M3） | ✅ runner 独有 |

### 3.2 runner 的架构优势（应保持/强化）

1. **StreamEvent 闭合枚举**（ADR-005）——比 Claude Code 字符串事件和 OpenClaw stream 标签更类型安全
2. **Outside-in TDD + 传输链测试纪律**——CLAUDE.md 6 条 UT 规则是业界领先的实践
3. **ToolPolicy 三值决策 + chain 组合**——比简单 allow/deny 列表更灵活
4. **learn 包自学习技能萃取**——Claude Code 和 OpenClaw 均无此能力
5. **Minion 具身化架构**（双平面 + 三轨 Realizer）——独创设计，无竞品
6. **RiskLevel 跨 MCP 边界恢复**（ADR-007）——解决了 MCP 协议的安全元数据丢失问题

### 3.3 需要警惕的架构反模式

1. **同步阻塞热路径**：MemoryProvider.search() 在 AgentLoop 线程同步阻塞 → 大索引场景性能瓶颈
2. **System Prompt 膨胀**：Skill 全量注入 + Durable Memory 全量注入 → 长 system prompt 挤占 context 预算
3. **单层安全**：工具权限只在列举阶段过滤，执行阶段无二次校验 → LLM 可传入恶意 args
4. **SessionManager 无状态**：无持久化、无 TTL、无并发控制 → 生产环境不可靠

## 五、新发现的架构优化方向（来自深度研究）

### 5.1 Spring AI 2.0 Advisor Chain 启示

Spring AI 2.0 的核心架构创新是将工具调用循环提升为 Advisor Chain 中的可组合中间件：

```
Request → [MemoryAdvisor] → [GuardrailAdvisor] → [ToolCallingAdvisor] → [LogAdvisor] → LLM
```

**对 runner 的启示**：runner 当前的 `AgentObserver` 是简单回调接口，`StreamPostProcessor` 只处理输出侧。可考虑统一为双向 Interceptor/Advisor 链：
- 请求侧：memory 注入 → 安全检查 → context 预算检查 → 工具定义过滤
- 响应侧：compaction → result sanitize → post-process → serialize

**优先级**：P2（架构演进方向，非紧急）

### 5.2 Progressive Tool Disclosure（渐进式工具暴露）

当工具数量多时，全量注册到每次 LLM 请求浪费 token 且混淆模型。Spring AI 2.0 的 `ToolSearchToolCallingAdvisor` 只暴露一个"搜索工具"元工具，模型按需检索相关工具。

**对 runner 的启示**：`ToolRegistry.search(keyword)` 已有模糊检索能力；可新增一个 `ToolSearchTool` 让 LLM 按需发现工具，而非全量注入 `getToolDefinitions()`。

**优先级**：P1（工具数量增长后直接影响 token 效率和模型选择准确性）

### 5.3 Agent Scratchpad（工作备忘录）

上下文工程 Write 策略的核心实现：agent 在执行过程中维护结构化备忘录，跟踪任务状态、假设、中间结果。备忘录持久化在上下文窗口之外，compaction 时不丢失。

**对 runner 的启示**：当前所有中间推理步骤只在 context 内，compaction 后可能丢失关键信息（65% 企业 AI 失败归因于上下文漂移/记忆丢失）。可新增 `AgentScratchpad`，SnipCompactor 在删除旧消息前先将关键信息写入 scratchpad。

**优先级**：P1（直接影响长会话质量）

### 5.4 渐进式压缩策略

社区共识：在 70% context 容量时开始温和压缩，而非 95% 时紧急压缩。多阶段递进：
- 70%：Snip 旧工具结果
- 80%：Micro 截断大结果
- 90%：Auto 摘要旧对话
- 95%：紧急截断

**对 runner 的启示**：当前 CompactionChain 在 `buildMessages()` 后无条件执行 Snip+Micro；缺少 token 计数触发的渐进策略。需要在 CompactionChain 中加入 token 计数器，按阈值分级启用不同级别的压缩。

**优先级**：P0（与 Auto Compaction 配合，防止长会话溢出）

### 5.5 人机确认流程（Human-in-the-Loop）

Google ADK 的 `ToolConfirmation`、OpenAI Agents SDK 的 Guardrails、LangGraph 的 HITL interrupt：所有主流框架都支持高危工具执行前的用户确认。

**对 runner 的启示**：ToolPolicy 只做 ALLOW/DENY 二值决策；缺少 `CONFIRM` 第四状态（暂停执行，等待用户确认）。可扩展 `ToolPolicy.Decision` 新增 `CONFIRM`，`ToolCallingLoop` 在收到 CONFIRM 时发出新 StreamEvent（`TOOL_CONFIRM_REQUIRED`）并暂停。

**优先级**：P1（安全关键场景必需）

### 5.6 Prompt Cache 优化

Anthropic prompt caching 使静态 prompt 部分（system prompt + 工具定义）的重复调用成本降低 50-90%。优化目标从"最小化 context size"转为"最大化 cache hit rate"。

**对 runner 的启示**：当前 ClaudeProvider 未利用 prompt caching API。system prompt + 工具定义是高度稳定的，应标记为 cacheable。

**优先级**：P1（直接降低 API 成本）
