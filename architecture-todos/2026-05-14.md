## 一、外部参照物要点速览（2026-05 最新）

### 1.1 Claude Code 源码泄露 — 架构纵深分析

基于 VILA-Lab 学术论文 (arXiv:2604.14228) "Dive into Claude Code: The Design Space of Today's and Future AI Agent Systems" 的系统性分析，以及多篇逆向工程报告的交叉验证：

#### 五层架构模型

```
Surface Layer     ─ Interactive CLI, Headless CLI, Agent SDK, IDE/Desktop/Browser, UI/renderer
Core Layer        ─ Agent loop, Compaction pipeline
Safety Layer      ─ Permission system (auto-mode classifier), Hook pipeline, Extensibility
State Layer       ─ Context assembly, Runtime state, Session persistence, CLAUDE.md + memory, Sidechain transcripts
Backend Layer     ─ Execution backends, External resources
```

| 设计点 | Claude Code 实现 | Runner 现状 | 差距评估 |
|--------|-----------------|-------------|----------|
| **代码比例** | 1.6% AI 逻辑 + 98.4% 基础设施（512K 行） | ~13K 行 agent-kernel，基础设施薄弱 | 需要大量基础设施投入（observability, resilience, permission） |
| **五级 Compaction** | MicroCompact → AutoCompact(92%阈值) → Context Collapse → Session Memory → Full Compact | 二级（Snip + Micro），无阈值触发 | 缺少自动触发机制 + LLM 摘要级 compaction |
| **三层 Memory 指针系统** | MEMORY.md 指针索引（~150 char/line） → topic-specific 文件按需加载 → 原始对话不重载 | 三层 Memory（Session/Ephemeral/Durable）但无指针索引 | Memory 检索效率可优化 |
| **Self-Healing Memory** | Agent 发现错误时主动改写 memory 文件 | 无 memory 自修正机制 | 长期运行场景下 memory 会积累错误 |
| **autoDream 记忆整合** | 用户空闲时执行 memory consolidation：合并矛盾、去冗余、观察→事实转化 | 无背景整合 | TODO-021 已记录 |
| **14 Cache-Break Vectors** | 主动监控 14 种 prompt cache 失效条件，优化 cache hit rate | 完全未实现 prompt caching | TODO-024，成本优化关键 |
| **StreamingToolExecutor + RWLock** | 模型流式输出时即开始执行已完成的 tool_use blocks；读操作并行，写操作独占 | 等 LLM 流完成后才执行工具 | TODO-032 |
| **23 条 Bash 安全检查** | 2,592 行 bashSecurity.ts，18 个 Zsh 内建命令阻止，Unicode 零宽字符/IFS null-byte 注入检测 | CliTool 无安全检查 | TODO-001 严重性需再次提升 |
| **Permission 7-mode + ML** | 7 种权限模式 + ML 分类器判定工具风险 | ScopedToolRegistry deny > allow 二元模型 | TODO-015 |
| **KAIROS Daemon** | 永驻后台 agent，ASSISTANT_BLOCKING_BUDGET_MS 超时自动 background，autoDream 整合 | 无后台 agent | TODO-014 |
| **108+ Feature Flags** | 44 编译时 + 108 gated modules，灰度发布 | 无 feature flag | TODO-034 |

#### Claude Code 新发现（本次研究新增）

1. **Sidechain Transcripts**: Claude Code 不直接重载原始对话，而是搜索 sidechain transcripts 中的特定标识符 — Runner 完全无此概念
2. **Cache-Aware Context Assembly**: 每次 LLM 调用前评估 context 变化是否会破坏 prompt cache — Runner 无此优化
3. **Graduated Permission with Learning**: 权限系统从用户行为中学习，自动调整工具的权限级别 — Runner 的 deny > allow 是静态的
4. **Blocking Budget**: KAIROS 的 ASSISTANT_BLOCKING_BUDGET_MS 机制防止单线程 agent 被长时间工具调用阻塞 — Runner 的 ToolCallingLoop 无此保护

### 1.2 OpenClaw 2026.5 架构要点

| 层 | 职责 | 最新进展 |
|---|---|---|
| **Gateway（控制平面）** | WebSocket 18789 端口；session/channel/tool dispatch/事件 | 121 advisories，最高风险面 |

#### OpenClaw 新发现（本次研究新增）

1. **Task Brain 统一任务层**: 这是 2026 年最大架构变更 — 将 agent protocol tasks、subagents、cron jobs、background processes 统一为一个 SQLite-backed ledger。Runner 的 SubagentRuntime + InterruptibleRun + 无 cron 是分散的
2. **Steer 模式精细中断**: 用户中断时不是全量取消，而是在 tool 间隙注入新消息，跳过剩余 pending tools — Runner 的 InterruptibleRun.interrupt() 是粗粒度的全量取消
3. **安全隐患暴露**: 121 个安全 advisory，Gateway WebSocket 是最高风险面 — 启示 runner 的 Vert.x WebSocket 也需要安全审计
4. **SOUL.md / TOOLS.md 分离**: 角色人格 vs 工具元数据分离，tools 只列名称按需加载 schema（token 高效）

## 三、本日新增发现

### 新发现 1: ClientToolAlias 机制的架构隐患

新增的 `ClientToolAliasRegistry` 使用了全局静态单例 + 懒加载模式：

```java
// ClientToolAliasRegistry.java — 全局单例
private static final ClientToolAliasRegistry INSTANCE = new ClientToolAliasRegistry();
```

**问题**:
- 全局单例与 Spring DI 容器无集成，测试时无法替换
- `PropertiesClientToolAliasSource` 从 classpath 加载 properties 文件，不支持 Spring `@Value` / `@ConfigurationProperties`
- 与 ToolRegistry (Spring bean) + ScopedToolRegistry 的 DI 模式不一致
- 多 Agent 场景下所有 Agent 共享同一 alias 注册表，无法 per-Agent 配置

**建议**:
- [ ] 将 `ClientToolAliasRegistry` 改为 Spring bean，通过构造注入 `List<ClientToolAliasSource>`
- [ ] 或保留 SPI pattern 但添加 AgentProfile 级别的 alias overlay
- **Priority**: P2

### 新发现 2: ExecOsApiTool 安全风险

`ExecOsApiTool` 执行 OS API 调用，但：
- 无参数白名单验证（任意 apiName + params）
- 与 TODO-001 (BashTool Sandboxing) 同类风险但更隐蔽
- 30s 超时是 Java 层面的，OS 进程可能不受限

**建议**:
- [ ] 为 ExecOsApiTool 添加 apiName 白名单
- [ ] 与 CliTool 共享安全框架（统一的 CommandSanitizer）
- **Priority**: P0 — 安全相关

### 新发现 3: Task Brain 统一任务层缺失

OpenClaw 2026.3.31 引入的 Task Brain 是其最大架构变更 — SQLite-backed 统一任务账本合并了：
- Agent protocol tasks
- Subagent runs
- Cron/scheduled jobs
- Background processes

Runner 当前分散为：
- `InterruptibleRun` (per-session state machine)
- `SubagentRuntime.activeRuns` (ConcurrentHashMap)
- 无 cron/scheduled job
- 无统一查询/管理 API

**建议**:
- [ ] 设计 `TaskLedger` 接口，统一管理所有异步任务的生命周期
- [ ] 用 SQLite 或内存实现，支持 query by status/agentId/type
- [ ] 合并 InterruptibleRun 和 SubagentRuntime 的状态跟踪到 TaskLedger
- **Priority**: P2 — 架构整洁性

### 新发现 4: Cache-Aware Context Assembly 模式

Claude Code 在每次 LLM 调用前评估 context 变化是否会破坏 prompt cache，并监控 14 种 cache-break vectors。Runner 完全无此优化。

即使先实现 TODO-024 (Prompt Caching)，如果不做 cache-aware assembly，cache hit rate 可能很低。

**建议**:
- [ ] 在 PromptEngine 中跟踪上次 LLM 调用时 system prompt + tools 的 hash
- [ ] 如果 hash 未变，确保 content block 顺序不变以最大化 cache hit
- [ ] 记录 cache_creation vs cache_read token 比例作为优化指标
- **Priority**: P1 — 与 TODO-024 配套

### 新发现 5: Steer 模式（精细中断）

OpenClaw 的 steer 模式在 runner 中完全无对应。当前 InterruptibleRun 的 interrupt() 是全量取消 + 重新 resume 模式，这意味着：
- 已完成的 tool 调用结果被浪费（cancel 后重走）
- 用户等待时间长（从头开始而非从断点续）

**建议**:
- [ ] 在 ToolCallingLoop 的 tool 执行间隙检查"pending user message queue"
- [ ] 如有新消息，将其注入 context 而非取消整个 run
- [ ] 保留已完成的 tool results，仅跳过尚未执行的 pending tools
- **Priority**: P2 — 用户体验优化
