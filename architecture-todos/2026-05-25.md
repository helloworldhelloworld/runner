## 二、新外部参照物要点速览

### 2.1 "Dive into Claude Code" 论文核心发现 (arxiv 2604.14228)

**5 核心价值 → 13 设计原则**:

| 价值 | 设计原则 | Runner 对比 |
|---|---|---|
| **Human Decision Authority** | 分层权限（7 模式 + ML 分类器）; 可审计决策链; HITL 中断 | ⚠️ deny > allow 二级; 无 ML 分类器; InterruptibleRun 有但无审计日志 |
| **Safety & Security** | 沙箱隔离; 不可变快照; 零信任工具输出 | ❌ 无沙箱; MessageSnapshot 已有; 工具输出无消毒 |
| **Reliable Execution** | Circuit breaker; compact-and-retry; graceful degradation | ❌ ResilientLLMProvider 仅重试; 无 circuit breaker; 无 compact-and-retry |
| **Capability Amplification** | 按需工具加载; 4 层扩展性(hooks/skills/plugins/MCP); subagent 委派 | ⚠️ 5 种 ToolSourceProvider 但全量加载; hook 系统空壳; subagent 仅 spawn |
| **Contextual Adaptability** | 模块化 prompt 组装; 5 层 compaction 级联; cache-aware 压缩 | ⚠️ PromptEngine 硬拼; 2 层 compaction; 无 prompt cache |

**7 组件 × 5 架构层**:

```
Layer 5: Execution Environment  — sandbox, network policy, filesystem ACL
Layer 4: State & Persistence    — append-only session store, tiered memory, checkpoints
Layer 3: Tools                  — tool registry, permission gate, sandbox wrapper
Layer 2: Permission System      — 7-mode classifier, deny-first, hook pipeline
Layer 1: Agent Loop             — queryLoop(), context budget, compaction cascade
Layer 0: Interfaces             — CLI/IDE/Web, transport-agnostic
```

**Runner 的层对应**:
- Layer 5: ❌ 无执行沙箱层
- Layer 4: ⚠️ MemoryProvider 3 层但无 checkpoint; 无 append-only session store
- Layer 3: ✅ ToolRegistry + ScopedToolRegistry + ToolSourceProvider
- Layer 2: ⚠️ AgentObserver 空壳; 无 permission classifier
- Layer 1: ✅ AgentLoop + ToolCallingLoop; ⚠️ compaction 2 层
- Layer 0: ✅ Gateway + WebSocket/REST/SSE

**关键数据点**: 1.6% AI 决策 vs 98.4% 运行基座 → Runner 当前 harness 成熟度不足

### 2.2 OpenClaw Lobster Workflow Engine (2026.5)

| 特性 | 描述 | Runner 对比 |
|---|---|---|
| **DAG 编排** | 工作流是 skill invocation 的 DAG；边 = 依赖；无依赖的任务并行 | ❌ 仅有线性 ToolCallingLoop |
| **Sub-lobster** | 嵌套工作流支持 + 可选循环（Ralph Loop），sub-workflow 作为 step | ❌ SubagentRuntime 是异步 spawn，无嵌套工作流 |
| **Human Approval Gate** | 工作流步骤间可插入人工审批点 | ❌ 无工作流级 HITL |
| **状态 + 回滚** | 工作流维护状态，支持失败回滚 | ❌ InterruptibleRun 仅保存会话状态 |
| **确定性 vs LLM 驱动** | Lobster = 确定性编排; Agent = LLM 驱动 — 二者正交互补 | ⚠️ Runner 仅有 LLM 驱动路径 |

**核心洞见**: 生产级 agent 框架需要**两种编排模式并存** — LLM 驱动（适合探索性任务）和确定性 DAG（适合可预测的多步流程）。

### 2.3 LangGraph v0.4 Checkpoint 系统 (2026.4)

| 特性 | 描述 | Runner 对比 |
|---|---|---|
| **每步 Checkpoint** | 图执行每个 super-step 自动保存状态快照 | ❌ 无 checkpoint 机制 |
| **Crash Recovery** | 进程崩溃后从最后 checkpoint 恢复，已完成节点不重跑 | ❌ 进程崩溃 = 状态全丢 |
| **Time Travel** | 回溯到任意历史 checkpoint，修改后 fork 新执行路径 | ❌ 无 time travel |
| **HITL Interrupt** | v0.4 将 interrupt 作为 invoke() 的直接返回值，UI 层直接消费 | ⚠️ InterruptibleRun 有中断但非结构化返回 |
| **Thread 隔离** | Checkpoint 按 thread_id 组织，支持多会话并行 | ✅ Session Key Namespace 已有 |
| **持久化后端** | MemorySaver(dev) / SQLite / PostgreSQL | ⚠️ InMemory + File, 无结构化持久化 |

**限制**: Checkpoint ≠ Durable Execution — 无 supervisor / watchdog / heartbeat（Diagrid 2026 分析）

## 三、新发现的架构待优化点

### TODO-054: DAG 式确定性工作流引擎（对标 OpenClaw Lobster）

**问题**: Runner 仅有 LLM 驱动的 ToolCallingLoop。对于确定性、可预测的多步流程（如"检索 → 分析 → 生成报告 → 发送"），强制走 LLM 循环既浪费 token 又不可靠。

**参考**:
- OpenClaw Lobster: DAG of skill invocations, parallel execution for independent tasks, human approval gates, state persistence, rollback
- Sub-lobsters: nested workflows with loop conditions
- LangGraph: graph-based stateful workflow with checkpoints

**设计方向**:
```
WorkflowEngine (新接口，与 AgentLoop 正交)
  ├── Workflow           — DAG 定义（YAML/JSON/Builder）
  ├── WorkflowStep       — 单步: skill/tool invocation + condition + timeout
  ├── WorkflowExecutor   — DAG scheduler (topological sort + parallel dispatch)
  ├── ApprovalGate       — HITL 审批节点
  ├── WorkflowState      — 可序列化执行状态（支持 resume/rollback）
  └── SubWorkflow        — 嵌套工作流引用
```

**与 SubagentRuntime 的关系**: SubagentRuntime 管理 LLM 驱动的 agent 实例；WorkflowEngine 管理确定性步骤序列。两者可组合：workflow step 可以是"spawn a subagent"。

**Action**:
- [ ] 设计 `Workflow` 接口和 `WorkflowStep` 模型
- [ ] 实现 `WorkflowExecutor` 基于 topological sort 的 DAG 执行器
- [ ] 支持 `ApprovalGate` 节点（阻塞直到外部 approve/reject）
- [ ] WorkflowState 可序列化，支持 crash recovery
- [ ] 可选：YAML 定义格式（参考 Lobster DSL）
- **Priority**: P2 — 当前 LLM 循环满足大多数场景，DAG 编排是进阶能力
- **Effort**: 5-8d
- **Module**: 新模块 `agent-workflow` 或 agent-kernel 新包 `.workflow`

### TODO-055: Tool 按需加载 / Lazy Tool Registry（对标 Claude Code ENABLE_TOOL_SEARCH）

**问题**: 当前 ToolRegistry 在每轮 LLM 调用时将**所有已注册工具**的 JSON Schema 发送到 context。随着 MCP tools 增长（OpenClaw 生态已有 500+ MCP server），工具定义可能占用 5000-20000 tokens，导致：
1. Context 浪费：大部分工具本轮不会被使用
2. Prompt cache 频繁失效：工具增减即打断缓存
3. LLM 选择困难：工具过多时模型选择准确率下降

**参考**:
- Claude Code: 默认 < 20 tools in context; `ENABLE_TOOL_SEARCH` flag 开启按需搜索激活
- Claude Code "Dive into Claude Code" 论文: lazy tool loading 作为 13 个设计原则之一
- ToolRegistry.search(keyword) 已存在但仅作为管理 API，未用于 LLM 路径

**设计方向**:
```
ToolRegistry (已有)
  └── LazyToolLoadingStrategy (新)
        ├── EAGER    — 当前行为，全量加载（默认）
        ├── TOP_N    — 按使用频率/相关性取 top N 工具
        ├── SEARCH   — 内置 "search_tools" meta-tool，LLM 主动搜索
        └── HYBRID   — 核心工具 eager + 长尾工具 search

内置 SearchToolsTool:
  input: { query: string }
  output: { tools: ToolDefinition[] }
  → LLM 调用此工具搜索相关工具 → ToolRegistry 动态注入到当前轮次的 toolDefinitions
```

**Action**:
- [ ] ToolRegistry 新增 `getToolDefinitions(LoadingStrategy, context)` 方法
- [ ] 实现 `SearchToolsTool` 内置 meta-tool
- [ ] LLMOptions 新增 `toolLoadingStrategy` 配置
- [ ] AgentProfile 可配置 `coreTools`（始终加载）和 `searchableTools`（按需）
- [ ] 统计 tool invocation 频率用于 TOP_N 策略
- **Priority**: P1 — 直接影响 prompt cache 命中率(TODO-048) 和 context 效率
- **Effort**: 3d
- **Depends on**: TODO-048 (Prompt Caching) 实现后效果更显著

### TODO-056: 结构化 Permission Tier（对标 Claude Code 7-mode Permission System）

**问题**: 当前工具权限模型仅有 deny list > allow list 二级过滤（ScopedToolRegistry），所有通过过滤的工具拥有相同权限级别。无法区分"只读查询"和"修改文件"的风险差异。

**参考**:
- Claude Code: 7 种权限模式 + ML 分类器
  - Mode 0: All auto (dev trust)
  - Mode 1-5: 分级自动/确认（read auto, write ask, execute deny 等）
  - Mode 6: All ask (maximum safety)
  - ML classifier: 基于工具名 + 参数推断 intent
- OWASP Agentic AI: "Configure access controls and approval workflows during initial setup"

**设计方向**:
```
ToolPermissionTier 枚举:
  READ        — 只读操作（搜索、查询、读文件）→ 自动放行
  MODIFY      — 修改操作（写文件、更新数据）→ 可配置确认
  EXECUTE     — 执行操作（运行命令、调用外部 API）→ 默认需确认
  DESTRUCTIVE — 破坏性操作（删除、覆盖）→ 强制确认

Tool 接口新增:
  default ToolPermissionTier getPermissionTier() { return EXECUTE; }

PermissionPolicy (新接口):
  PermissionDecision evaluate(Tool, Map<String, Object> args, AgentProfile)
  → ALLOW / ASK / DENY

PermissionDecision 与 HookDecision (TODO-047) 统一
```

**Action**:
- [ ] Tool 接口新增 `getPermissionTier()` 默认方法
- [ ] 定义 `PermissionPolicy` 接口 + `DefaultPermissionPolicy`（基于 tier + profile 配置）
- [ ] AgentProfile 新增 `permissionMode`（对应 Claude Code 的 7-mode 简化版）
- [ ] ToolCallingLoop 在工具执行前查询 PermissionPolicy
- [ ] 后续可插入 rule-based classifier（暂不做 ML）
- **Priority**: P1 — 与 TODO-047 (Hook System) 和 TODO-050 (Sandbox) 协同
- **Effort**: 2-3d
- **Synergy**: 与 TODO-047 的 HookDecision 统一；与 TODO-050 的 sandbox 分级对应

### TODO-057: Checkpoint 持久化 + Crash Recovery（对标 LangGraph v0.4）

**问题**: Runner 的 InterruptibleRun 在内存中维护会话状态（messages list, accumulatedText, phase）。进程崩溃或 JVM OOM 后，所有进行中的会话状态完全丢失。

**参考**:
- LangGraph v0.4: 每个 super-step 自动 checkpoint → SQLite/PostgreSQL 持久化 → crash 后从最后 checkpoint 恢复
- 限制（Diagrid 分析）: Checkpoint ≠ Durable Execution; 无 supervisor/watchdog
- OpenClaw: Lobster 工作流维护可序列化状态，支持 resume/rollback

**设计方向**:
```
Checkpointer (新接口)
  ├── save(sessionKey, CheckpointData)   — 每轮 LLM 调用后保存
  ├── load(sessionKey) → Optional<CheckpointData>  — 启动时恢复
  ├── list(sessionKey) → List<CheckpointMeta>  — time travel 用
  └── delete(sessionKey, checkpointId)

CheckpointData:
  ├── messages: List<ConversationMessage>
  ├── accumulatedText: String
  ├── phase: RunPhase
  ├── costTrackerState: CostTrackerSnapshot
  ├── toolCallHistory: List<ToolCallRecord>
  └── timestamp: Instant

存储后端:
  ├── InMemoryCheckpointer  — 测试用
  ├── SQLiteCheckpointer    — 默认，复用 kernel-memory 的 SQLite
  └── 可扩展: PostgreSQL / Redis
```

**Action**:
- [ ] 设计 `Checkpointer` 接口 + `CheckpointData` 模型
- [ ] InterruptibleRun 在每轮 ToolCallingLoop 迭代后调用 `checkpointer.save()`
- [ ] Orchestrator 启动时扫描未完成的 checkpoint，提供恢复入口
- [ ] 可选：checkpoint 压缩（保留最近 N 个，旧的合并）
- [ ] 可选：time-travel API（回溯到历史 checkpoint 重新执行）
- **Priority**: P2 — 当前单实例部署，crash recovery 不是首要问题，但随着 agent 运行时长增加会成为痛点
- **Effort**: 3-5d
- **Module**: agent-kernel `.checkpoint` 新包

### TODO-058: Context Budget 分配策略（对标 "context 管理作为架构关注点"）

**问题**: Zylos AI 2026 调研发现 **65% 的企业 AI 失败归因于 context drift 或 memory loss**。Runner 当前 context 构建是简单拼接（system prompt + history + tool results），无预算分配。当 history 过长或 tool results 过大时，system prompt 指令可能被"挤出"有效注意力窗口。

**参考**:
- Claude Code: 5 层 compaction cascade，成本排序；Budget Reduction 作为第一层
- "Dive into Claude Code" 论文: context management 作为 13 设计原则之一
- 研究共识: context 性能在 ~32K tokens 后显著下降

**设计方向**:
```
ContextBudgetAllocator (新接口)
  allocate(totalBudget, components) → Map<ContextComponent, int>

ContextComponent 枚举:
  SYSTEM_PROMPT     — 固定预留（最高优先级，不压缩）
  TOOL_DEFINITIONS  — 固定预留（与 system prompt 一起缓存）
  DURABLE_MEMORY    — 高优先级（长期知识）
  RECENT_HISTORY    — 中优先级（最近 N 轮）
  OLD_HISTORY       — 低优先级（可压缩/丢弃）
  TOOL_RESULTS      — 最低优先级（可截断/丢弃）

默认分配策略（以 200K context window 为例）:
  SYSTEM_PROMPT:    保留 100%（~2K-8K tokens）
  TOOL_DEFINITIONS: 保留 100%（~1K-5K tokens，lazy loading 后更少）
  DURABLE_MEMORY:   保留 100%（~1K tokens）
  RECENT_HISTORY:   最多 60% 剩余空间
  OLD_HISTORY:      最多 20% 剩余空间
  TOOL_RESULTS:     最多 20% 剩余空间（超出截断）
```

**Action**:
- [ ] 定义 `ContextBudgetAllocator` 接口和 `DefaultContextBudgetAllocator`
- [ ] AgentLoop.buildMessages() 在拼接前调用 allocator 获取各组件预算
- [ ] CompactionChain 根据预算决定各层压缩力度
- [ ] 可选：LLMOptions 新增 `contextBudgetPolicy` 配置
- [ ] 监控指标：各组件实际占用 vs 预算（接入 TODO-008 OTel）
- **Priority**: P1 — 直接影响长会话质量和 LLM 推理准确性
- **Effort**: 2-3d
- **Depends on**: TODO-051 (4-Layer Compaction) 作为执行层

### TODO-060: Append-Only Session Store + 审计日志（对标 Claude Code Session Persistence）

**参考**:
- Claude Code: append-only session storage 作为架构设计原则

```
SessionEvent:
  ├── USER_INPUT(text)
  ├── LLM_REQUEST(messages, options)
  ├── LLM_RESPONSE(response, usage)
  ├── TOOL_CALL(toolName, args)
  ├── TOOL_RESULT(toolName, result)
  ├── HOOK_DECISION(hookName, decision)
  ├── CHECKPOINT(checkpointId)
  └── ERROR(throwable)
```

**Action**:
- [ ] 设计 `SessionStore` 接口（append-only 语义）
- [ ] 实现 SQLite-backed SessionStore（复用 kernel-memory SQLite）
- [ ] AgentLoop / ToolCallingLoop 在关键节点 append SessionEvent
- [ ] 可选：Web UI 展示完整 session 审计日志
- [ ] 可选：SessionEvent 作为 Checkpoint 数据源（TODO-057 协同）

### TODO-062: 工具循环检测 + Proactive Compaction 阈值（OpenClaw + 行业共识）

**问题 1 — 工具循环**: LLM 可能陷入反复调用同一工具的死循环（如重复搜索相同内容），浪费 token 且阻塞 session。

**问题 2 — 响应式 Compaction**: 当前 CompactionChain 在 buildMessages() 时执行，但无主动触发阈值。行业共识（ACON 框架）建议在 **60-70% context 利用率**时主动触发 compaction，而非等到溢出。

**参考**:
- OpenClaw: tool-loop detection 防止无限循环
- ACON Framework (2026): 配对轨迹分析，26-54% peak token 使用降低
- 行业共识: 60-70% threshold 主动 compact，比溢出后 emergency compact 更稳定

**Action**:
- [ ] ToolCallingLoop 新增 tool-call 频率检测：同一工具连续 N 次调用（默认 3）→ 警告 LLM + 可配置 break
- [ ] ContextCompactor 新增 `shouldCompact(messages, contextLimit)` 方法，在 60-70% 利用率时返回 true
- [ ] AgentLoop.buildMessages() 前检查 `shouldCompact()`，主动触发而非仅在构建时被动执行
- **Priority**: P1
- **Effort**: 1-2d

### TODO-063: Subagent Teammate + Worktree 模式（Claude Code 3 模型）

**参考**: Claude Code 泄露源码确认存在 3 种 subagent 执行模型:
1. **Fork**: 继承父 context + tools，快速聚焦的 worker → **Runner 已有（SpawnSubagentTool）**
2. **Teammate**: 独立 context window，可共享发现和互相挑战，team lead 协调 → **Runner 缺失**
3. **Worktree**: 文件系统隔离（git worktree），每个 agent 拥有不同文件集 → **Runner 缺失**

**与 TODO-052 的关系**: TODO-052 提出 Delegate + Handoff 两种模式（对标 OpenAI SDK），本 TODO 补充 Teammate + Worktree 两种模式（对标 Claude Code），形成完整的 5 模式 subagent 能力。

**Action**:
- [ ] SubagentRuntime 支持 `SpawnMode` 扩展: `ASYNC_FORK`, `SYNC_DELEGATE`, `HANDOFF`, `TEAMMATE`, `WORKTREE`
- [ ] Teammate 模式: 多个 subagent 共享 message channel（发布/订阅），team lead 汇总
- [ ] Worktree 模式: 需结合 git worktree 或文件系统 namespace 隔离
- **Priority**: P3 — 当前 spawn 满足大部分场景
- **Effort**: 5-8d
