# 架构优化分析 — 2026-06-17

> **研究来源**: OpenClaw 架构 (v2026.4, 247K+ stars)、Claude Code 泄露源码分析 (513K LoC TypeScript)、
> Claude Agent SDK 官方文档、Spring AI 2.0、LangGraph/CrewAI/AutoGen 最佳实践、
> Dive into Claude Code (arXiv 2604.14228)、业界生产级 Agent 部署经验。
>
> **分析对象**: runner (Lightweight AI Kernel) 当前架构 — 11 个 Maven 模块,
> 以 `agent-kernel` 为基座的 Reactive Agent Orchestration 框架。

---

## 一、总体评价

runner 的架构基底扎实：Reactive Flux 全链路流式、四层 Orchestrator、ToolPolicy/RiskLevel 三值决策、
Outside-in TDD、闭合枚举 StreamEvent、SPI-based provider discovery。这些在业界都属于正确决策。

但与 Claude Code (生产级 512K LoC 代理)、OpenClaw (247K stars 开源 Agent) 以及
Spring AI 2.0 / LangGraph 等前沿框架对比后，发现以下系统性差距：

| 维度 | runner 现状 | 业界标杆 | 差距等级 |
|------|-----------|---------|---------|
| Context 压缩 | 2 层 (Snip+Micro) | Claude Code 5 层渐进式 | 🔴 高 |
| 权限模型 | ToolPolicy 三值 | Claude Code 7 模式 + ML 分类器 | 🟡 中 |
| 成本管理 | Token 计数 | USD 预算 + per-agent 预算隔离 | 🟡 中 |
| 记忆架构 | 三层但无自动整合 | OpenClaw daily logs + Claude Code autoDream | 🟡 中 |
| 工具加载 | 全量预加载 | Claude Code ToolSearch 懒加载 | 🟡 中 |
| Hook 系统 | AgentObserver 10 钩子 | Claude Code 27 钩子 + 4 结果码 | 🟡 中 |
| Session 管理 | 命名空间隔离 | Resume/Fork/Continue 模式 | 🟡 中 |
| 错误恢复 | CancellationToken | 4 层防御 (重试/降级/分类/检查点) | 🟡 中 |
| Workspace 配置 | 代码级配置 | OpenClaw SOUL.md 声明式 | 🟢 低 |
| 可观测性 | Tracer + TRACE 事件 | 全链路 trace + 成本 + 速率限制 | 🟡 中 |

## 二、TODO 清单 (按优先级排序)

### P0 — Context 压缩管道升级 (影响: 长对话可用性)

**问题**: runner 仅有 SnipCompactor (删老轮 TOOL 消息) + MicroCompactor (截断长内容)，共 2 层。
Claude Code 采用 5 层渐进式压缩管道: Budget Reduction → Snip → Microcompact → Context Collapse → Auto-Compact，
每层成本递增("cheapest first, heaviest last")。长对话场景下 runner 要么信息丢失过多 (Snip 直接删)，
要么 context 溢出 (无语义摘要兜底)。

**TODO**:

- [ ] **T-001 Budget Reduction 层**: 在 CompactionChain 最前端加入 per-tool output size cap，
  截断单次工具输出超出阈值的内容 (如文件读取 > 10K chars)，零 API 调用。
  - 位置: `agent-kernel/.context/BudgetReductionCompactor`
  - 参考: Claude Code query.ts:365 的 budget reduction shaper

- [ ] **T-002 Context Collapse 层**: 在 Micro 之后、Auto 之前加入分阶段折叠层——
  将旧消息块替换为压缩视图 (保留 summary + key decisions)，但不删除原始数据。
  支持"展开"操作回溯原始上下文。
  - 位置: `agent-kernel/.context/ContextCollapseCompactor`
  - 参考: Claude Code 的 Context Collapse — "reduces message blocks in stages, creates collapsed view without touching originals"

- [ ] **T-003 Auto-Compact (语义摘要) 层**: 当 context 接近窗口上限 (如 80%) 时触发，
  预留 ~13K token buffer，生成 ≤20K token 的结构化会话摘要。
  摘要必须保留: 当前任务目标、已修改文件路径、测试结果、关键决策及理由。
  - 位置: `agent-kernel/.context/AutoCompactCompactor`
  - 新增 `StreamEvent.EventType.COMPACT_BOUNDARY` 标记压缩发生
  - 参考: Claude Code Auto-Compact + Agent SDK `compact_boundary` 系统消息

- [ ] **T-004 CompactionChain 5 层组装**: 更新 `AgentFactory` 默认 CompactionChain 为
  `BudgetReduction → Snip(3) → Micro(2000) → ContextCollapse → AutoCompact`

### P1 — 权限模型增强 (影响: 自动化安全性)

**问题**: 当前 ToolPolicy (ALLOW/DENY/ABSTAIN) + RiskLevel (SAFE/WRITE/SYSTEM) 提供了基础的工具权限控制，
但缺少 Claude Code 的多模式权限和自动审批能力。生产场景需要更细粒度的控制。

**TODO**:

- [ ] **T-005 Permission Mode 枚举**: 新增 `PermissionMode` 枚举:
  `DEFAULT` / `ACCEPT_EDITS` / `PLAN` / `DONT_ASK` / `AUTO` / `BYPASS`，
  在 `AgentProfile` 中可配置。影响 ScopedToolRegistry 的默认决策行为。
  - `DEFAULT`: 未匹配规则的工具需确认
  - `ACCEPT_EDITS`: 自动放行文件编辑和常见文件系统命令
  - `PLAN`: 仅允许只读工具，编辑类工具全需确认
  - `AUTO`: 基于规则/分类器自动审批 (见 T-006)
  - `BYPASS`: 无沙箱环境全放行

- [ ] **T-006 规则化工具自动审批**: 在 `AUTO` 模式下，实现一个轻量级审批分类器
  (初期基于规则: 工具名 + RiskLevel + 参数模式匹配; 后期可升级为 ML 分类器)，
  判断工具调用是否与用户意图一致。
  - 位置: `agent-kernel/.agent/ToolApprovalClassifier`
  - 参考: Claude Code auto mode 使用独立轻量 LLM 调用做分类

- [ ] **T-007 Scoped Tool 权限语法**: 支持 `"Bash(npm *)"` 这类带参数模式的工具权限规则，
  允许只放行特定参数范围的工具调用。
  - 扩展 `ToolPolicy` 评估逻辑，支持 glob pattern 匹配工具参数

### P1 — 成本与预算管理增强 (影响: 生产可控性)

**问题**: CostTracker 仅做 token 计数，缺少 USD 级别的成本追踪、per-agent 预算隔离、
结果中的成本报告。Claude Code 的 `maxBudgetUsd` 是生产级 Agent 的标配。

**TODO**:

- [ ] **T-008 USD 成本追踪**: 扩展 CostTracker 支持按模型定价计算 USD 成本
  (`inputTokens * inputPrice + outputTokens * outputPrice`)，可配置各模型单价表。
  - 新增 `CostTracker.getTotalCostUsd()`
  - `LLMOptions` 新增 `maxBudgetUsd` 字段，与 `maxBudgetTokens` 并行生效

- [ ] **T-009 Per-Agent 预算隔离**: Subagent spawn 时从父 Agent 预算中分配子预算，
  子 Agent 耗尽预算时独立停止，不影响父 Agent。
  - `SubagentRuntime.spawn()` 传递 `budgetUsd` 参数
  - 防止 subagent 失控消耗

- [ ] **T-010 成本报告**: `AgentResponse` 新增 `totalCostUsd` / `tokenUsage` / `numTurns` 字段，
  在每次 Agent 完成时输出成本摘要。
  - 参考: Claude Code `ResultMessage` 包含 `total_cost_usd`, `usage`, `num_turns`, `session_id`

### P1 — 记忆架构增强 (影响: 长期上下文保持)

**问题**: runner 三层记忆 (Session / Ephemeral / Durable) 缺少:
(1) 时间感知的记忆加载 (OpenClaw 的 today+yesterday 模式);
(2) 记忆自动整合 (Claude Code KAIROS autoDream);
(3) 遗忘机制。

**TODO**:

- [ ] **T-011 时间感知记忆加载**: 启动 session 时自动加载 today + yesterday 的 daily logs
  到 system prompt，提供近期时间上下文。超过 2 天的 logs 只在 search 时命中。
  - 位置: `kernel-memory` 的 `FileMemoryManager`
  - 参考: OpenClaw daily logs (memory/YYYY-MM-DD.md) at session start

- [ ] **T-012 记忆整合 (Dream Mode)**: 实现定期记忆整合 —— 扫描最近 session logs，
  合并矛盾观点、去除噪音、将模糊洞察转化为确定性事实，
  压缩到持久记忆 (Durable Memory) 中。
  - 可作为 `TriggerSource` 实现: 定时触发整合任务
  - 参考: Claude Code KAIROS autoDream 四阶段: Orient → Gather → Consolidate → Prune
  - 上限: 持久记忆 ≤ 25KB / 200 lines

- [ ] **T-013 遗忘机制**: 为每个记忆层设计 TTL 或衰减策略:
  - Session Memory: 会话结束后可选持久化
  - Ephemeral Memory: 30 天后自动归档或删除
  - Durable Memory: 通过 Dream Mode 定期精炼，保持上限

### P2 — 工具加载优化 (影响: context 占用)

**问题**: 当前所有 ToolSourceProvider 在启动时全量加载工具 schema 到每次 LLM 请求中。
当工具数量增多 (特别是多个 MCP server)，工具定义本身会消耗大量 context。

**TODO**:

- [ ] **T-014 工具延迟加载 (ToolSearch)**: 实现 `ToolSearchTool` —— 一个内置工具，
  让 LLM 按需搜索和加载其他工具的 schema，而非预加载全部。
  - 启动时只加载核心工具 (Read/Write/Bash 等) 的完整 schema
  - 其他工具仅注册 name + description (轻量摘要)
  - LLM 调用 `tool_search(query)` 时动态加载完整 schema
  - 位置: `agent-kernel/.agent/ToolSearchTool`
  - 参考: Claude Code ToolSearch "defers MCP tool schemas by default, loads on demand"

- [ ] **T-015 MCP 工具懒加载**: MCP server 连接后，仅缓存工具 name/description 列表，
  完整 JSON Schema 在首次使用时按需拉取。
  - 位置: `agent-mcp/McpToolSourceProvider`

### P2 — Hook/事件系统扩展 (影响: 可扩展性)

**问题**: AgentObserver 提供 10 个钩子，但缺少关键生命周期事件
(PreCompact, SessionStart/End, UserPromptSubmit 等)。
且钩子不支持 4 结果码 (allow/deny/ask/defer)，无法在 hook 层面阻止工具调用。

**TODO**:

- [ ] **T-016 PreToolUse 4 结果码**: `onPreToolUse` 返回值从 void 改为
  `ToolUseDecision {ALLOW, DENY, ASK, DEFER}`。
  DENY 阻止执行并返回拒绝消息给 LLM; ASK 挂起等待外部确认; DEFER 跳过此 hook 继续链。
  - 兼容: 默认返回 ALLOW，旧实现不受影响
  - 参考: Claude Code PreToolUse hook 的 4 结果码

- [ ] **T-017 扩展 Hook 事件**: 新增以下 AgentObserver 钩子:
  - `onPreCompact(trigger: MANUAL|AUTO)` — 压缩前拦截，可归档全文
  - `onSessionStart(sessionId, agentId)` / `onSessionEnd(sessionId, result)`
  - `onUserPromptSubmit(prompt)` — 可注入额外 context
  - `onSubagentStart(parentId, childId)` / `onSubagentStop(childId, result)`
  - `onRateLimit(provider, retryAfterMs)` — 速率限制通知
  - 参考: Claude Code 27 hook events + 12+ event types

- [ ] **T-018 Hook 配置文件化**: 支持通过 `settings.json` 或类似配置文件声明 hook 脚本，
  而非必须在 Java 代码中实现 AgentObserver。
  - 参考: Claude Code `.claude/settings.json` 中的 hooks 配置

## 四、实施路线建议

### Phase 1 (近期, 1-2 周): Context 压缩 + 成本管理
- T-001 ~ T-004 (5 层压缩管道)
- T-008 ~ T-010 (USD 成本追踪)
- T-021 (结构化结果类型)

**理由**: 长对话 context 溢出是当前最大的生产风险。成本追踪是上线必备。

### Phase 2 (中期, 3-4 周): 权限 + Hook + 错误恢复
- T-005 ~ T-007 (权限模式增强)
- T-016 ~ T-017 (Hook 4 结果码 + 事件扩展)
- T-022 ~ T-023 (LLM 重试 + 工具重试)
- T-024 (Effort Level)

**理由**: 安全性和稳定性是从开发到生产的必经之路。

### Phase 3 (远期, 5-8 周): 高级功能
- T-014 ~ T-015 (工具懒加载)
- T-011 ~ T-013 (记忆增强)
- T-019 ~ T-020 (Session Resume/Fork)
- T-025 ~ T-026 (Workspace 配置)
- T-027 ~ T-033 (自学习/可观测性/Subagent 优化)

**理由**: 这些是差异化竞争力，但不阻塞基本生产可用性。

---

## 五、runner 的独有优势 (保持并强化)

1. **全双工打断接续 (InterruptibleRun)** — Claude Code / OpenClaw 均无原生等价物
2. **具身化架构 (Minion)** — 独一无二的 brain-in-cloud + 媒体/大脑双平面设计
3. **Reactor Flux 全链路** — 比 Claude Code 的回调式更现代
4. **4 层 Orchestrator + SubagentRuntime** — 比 Claude Code 的 depth-limited subagent 更灵活
5. **ToolPolicy 可组合三值决策** — 架构正确，只需在此基础上扩展
6. **StreamEvent 闭合枚举** — 类型安全，优于字符串约定
7. **Outside-in TDD 纪律** — 在所有参照框架中属于最严格的测试规范
8. **RiskLevel 跨 MCP 边界恢复 (ADR-007)** — 业界罕见的跨进程安全传播
