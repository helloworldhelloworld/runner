## 一、外部参考资料盘点

### 1. OpenClaw（开源 Agent 框架，Claude Code 设计参考之一）
关键设计要点：
- **Harness / Runner / Agent 三层分离**：harness 负责 IO 与权限沙箱，runner 负责生命周期与 hook，agent 只关心"思考-工具-再思考"循环。
- **Tool 调用统一为 JSONSchema**，本地工具与 MCP 工具走同一 dispatcher，避免双轨。
- **System reminder 机制**：在工具结果中插入 `<system-reminder>` 注入临时上下文（todo 提醒、日期、安全策略），不污染历史 message。
- **Deferred tools / ToolSearch**：超大工具池下按需加载工具 schema，控制 prompt 体积。
- **Skill = prompt 片段 + 可选 hook**，由 trigger 词或显式 `/skill` 激活。
- **Hook 体系**：SessionStart / PreToolUse / PostToolUse / UserPromptSubmit，全部由 harness 执行，不依赖 LLM 自觉。

### 2. Claude Code 泄露源码 / 公开逆向分析
关键模式：
- **极简 Agent Loop**：单一主循环 + 单一消息数组 + 工具调用直接续 LLM，不引入 DAG / Planner。
- **流式优先**：所有 IO 走 `AsyncIterable<Event>`，工具自身也可流式产出 progress。
- **Permission Mode**：plan / acceptEdits / bypassPermissions / default，由 harness 拦截而不是 prompt 层。
- **上下文压缩**：超过阈值时对早期消息做 summarization，保留最近 N 轮原文 + 摘要。
- **Todo 工具是"伪工具"**：本质是把 Agent 的工作记忆暴露成结构化对象，让 LLM 自管理进度。
- **Hooks 用 settings.json 配置**，PreToolUse 可阻断、PostToolUse 可注入文本。
- **CLAUDE.md / project memory** 自动注入 system prompt 顶部。

### 3. 2025–2026 开源社区最佳实践
- **MCP（Model Context Protocol）已成事实标准**：本地工具、远程工具、resource、prompt template 全部走 MCP；Spring AI 1.0 / LangChain4j 1.x 都有官方 MCP client。
- **Reactive vs Virtual Threads**：JDK 21+ 虚拟线程让"同步代码 + 阻塞 IO"重新可行，纯 Reactor 链不再是唯一答案；新趋势是 **Reactor 流式 IO + 虚拟线程执行工具体**。
- **Structured Output / Tool Use 收敛**：tool call 与 JSON mode 走同一 schema 校验层（如 jsonschema-validator）。
- **Observability**：OpenTelemetry GenAI semantic conventions 1.27 起稳定，`gen_ai.system / gen_ai.request.model / gen_ai.usage.*` 应埋点。
- **Token / Cost accounting** 内建到 provider 层，而非业务层后处理。
- **Session State**：从"内存 Map"转向 SQLite/Postgres + WAL，便于 resume；CrewAI / LangGraph 都已落地 checkpointer。
- **Sub-agent / fan-out**：主 agent 通过 `spawn_agent` 工具开子上下文做并行研究，结果回流主 loop。
- **Prompt caching**：Anthropic prompt cache 已普及，system prompt + tools schema 应放进 cache breakpoint。

## 二、runner 现有架构对照分析

### 已经做对的部分（保持）
1. `agent-kernel` 零内部依赖、`agent-web` 单一 assembly —— 模块边界清晰，符合 Clean Architecture。
2. `Tool` 接口直接对齐 LLM function calling，MCP 工具通过 `McpToolWrapper` 走同一 registry —— 与 OpenClaw 同构。
3. `Flux<StreamEvent>` 统一流式抽象（ADR-001）—— 符合主流方向。
4. `AgentLoop + ToolCallingLoop` 显式而非抽象 Kernel（ADR-003）—— 与 Claude Code 极简循环一致。
5. 三层 Memory（Session / Ephemeral / Durable）+ BM25 —— 比单一 vector store 更务实。
6. 显式的 PromptEngine 组装，Skill 可触发 —— 类似 Claude Code 的 skill 机制。

### 待优化点（与外部最佳实践的 gap）

| # | 类别 | 问题 | 影响 |
|---|---|---|---|
| G1 | Legacy 包袱 | `agent-kernel.plugin` 仍存在，`ToolExecutor` 有 Plugin fallback 分支 | 双轨 dispatch，新人易写错；ADR-002 已决议，应彻底清除 |
| G2 | Hook 缺失 | 没有 PreToolUse / PostToolUse / SessionStart hook 体系 | 安全审计、权限拦截、自动测试都要在业务代码硬编码 |
| G3 | Permission Mode 缺失 | 没有 plan / acceptEdits 等模式概念 | 工具副作用全靠工具自己判断，不能集中管控 |
| G4 | 上下文压缩缺失 | 长会话只能截断或全量送入 | Token 浪费 + 早期上下文丢失 |
| G5 | Todo 工具缺失 | LLM 没有结构化进度记忆 | 多步任务易遗漏、状态散落在自然语言里 |
| G6 | System-reminder 通道缺失 | 时间、安全策略、临时提示全部塞进 system prompt | system prompt 越来越长，无法做到"仅当本轮注入" |
| G7 | Prompt cache 未利用 | ClaudeProvider 未设置 cache_control breakpoint | 每轮 system prompt + tools schema 全量计费 |
| G8 | Token / Cost 埋点散乱 | 没有看到 provider 层统一的 usage 累积 | 难以做配额、限流、成本告警 |
| G9 | OTel GenAI 语义未对齐 | `.trace` 包是自定义命名 | 无法直接接入主流观测后端 |
| G10 | Sub-agent 缺失 | 没有 spawn 子 agent 的工具 | 无法并行研究 / 隔离上下文 |
| G11 | 工具按需加载缺失 | 所有 tool schema 一次性进 prompt | 工具池一旦超过 30+ 就会显著吃 token |
| G12 | LLMProvider 接口过宽 | 同时暴露 sync / async / callback / reactive 四种模式（架构.md L69-76） | 实现者负担重，违反 ISP；应只保留 reactive，其他用 adapter 派生 |
| G13 | Session 持久化弱 | `SessionManager` 实现细节未明，怀疑是内存 Map | 服务重启即失忆，无法 resume |
| G14 | MCP 双向能力 | 当前只用 MCP 的 tool；resource / prompt / sampling 未利用 | 没有完整对齐 MCP 标准 |
| G15 | 虚拟线程未用 | 工具体执行仍走 Reactor scheduler | JDK21+ 下可用 `Schedulers.fromExecutor(virtualThreadExecutor)` 简化阻塞 IO 工具 |
| G16 | CLAUDE.md 等价物缺失 | runner 没有"项目级 memory 自动注入"的约定 | 多项目部署时 prompt 复用差 |
| G17 | 模块爆炸风险 | soul-safety / soul-assessment / soul-user 三个垂直域硬编码进主仓 | 应抽成 plugin 包或独立仓，agent-kernel 只暴露 SPI |
| G18 | `agent-plugin-example` 与 ADR-002 矛盾 | 既然 Plugin 是 legacy，example 也应迁到 Tool | 给新人错误信号 |
| G19 | StreamPostProcessor 链路语义不清 | 文档未说明顺序、错误传播、是否可短路 | 难扩展 |
| G20 | Skill 自动触发机制风险 | "trigger 词"易误触发，缺乏置信度阈值 | 应改为 LLM-as-router 或 embedding 相似度 |

## 三点六、外部调研子 agent 返回后的二次校订

调研结果（OpenClaw / Claude Code 2026-04 npm sourcemap 泄露 / Spring AI 2026-01 系列 / LangGraph / OpenAI Agents SDK / Google ADK / MCP 2026 路线图）已返回，主要补强如下：

### 新增/细化的外部模式
1. **OpenClaw 实情**（之前只是粗略印象，现确认）
   - 由 Peter Steinberger 维护，MIT 协议，2026-04 已 15K stars / 200+ contributors。
   - **SOUL.md** 是 agent 人格/行为的声明式配置；社区 `awesome-openclaw-agents` 仓有 162 个模板。**这与本仓 `soul-*` 命名巧合但语义不同**——本仓是"心理咨询"的 soul，OpenClaw 是 agent persona 的 soul；命名建议二选一以避免混淆。
   - **AGENTS.md** = 仓库级 agent 指令文件（OpenClaw 版的 CLAUDE.md）。
   - **Heartbeat daemon**：自治调度，agent 不只是 request/response，而是长跑后台服务。
   - 多渠道 transport 抽象（22+ IM 平台），统一 `Channel` 接口。
2. **Claude Code 2026-04 泄露（510K 行 TypeScript，via misconfigured sourcemap）**
   - **三层上下文压缩**：MicroCompact（本地编辑级，零 API 成本）→ AutoCompact（接近 token 上限触发，预留 buffer）→ Full Compact（全量压缩 + 选择性文件再注入）。**G4 的实现模板就是这个三层。**
   - **MEMORY.md** = 永远加载的 ~150 字符/行的 *指针索引*；具体 topic 文件按需拉取。
   - **autoDream** = 沙箱化的子 agent 在空闲期对 memory 做去重/消歧/合并，**隔离运行避免污染主上下文**。
   - **per-tool permission level**：每个 Tool 自带 permission 字段，而不是全局策略 —— 与 G3 的"Permission Mode"互补。
   - **并行工具执行**：模型一轮内独立的 tool call 用 `Flux.merge` 并发执行，不串行。
   - **Anti-distillation**：system prompt 注入假工具定义干扰竞品蒸馏。
   - **KAIROS**（未发布 feature flag）：daemon 模式 + cron + 自唤醒 + Orchestrator Claude 管理多个 worker Claude。
3. **2026 主流框架格局**
   - **OpenAI Agents SDK（2025-03）的 Handoffs**：显式上下文转交，区别于 fan-out。
   - **Google ADK（2025-04）的 A2A 协议**：可发现并调用 LangGraph / CrewAI 的 agent；Spring AI 2026-01 已落地 A2A bridge。
   - **LangGraph 的显式 typed state**：被普遍称为"最值得抄的设计" —— 每步可 inspect / replay / patch，是 human-in-the-loop 的基础。
4. **Spring AI 2026-01 系列**
   - **Agent Skills**：按需加载的 Markdown + script + resource 文件夹 —— 与本仓 `example-skills/` 方向一致，但本仓是预加载，应改为按需。
   - **Advisors**：LLM 调用链的中间件 —— 本仓的 `StreamPostProcessor` 只覆盖了出向，入向（prompt 改写、工具名重写、权限拦截）缺失。
5. **MCP 2026 路线图**
   - 命名空间隔离（不同子 agent 看到不同工具集）、长跑异步操作（断连重连）、中央 Registry（带版本和验证元数据）。
