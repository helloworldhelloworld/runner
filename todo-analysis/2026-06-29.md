## 一、Context Management — 从 2 层压缩升级到 3+ 层 [HIGH]

### 现状
runner 当前仅有 2 层压缩: `SnipCompactor(keepRecentRounds=3)` + `MicroCompactor(maxChars=2000)`，是静态链，不感知 context 容量。

### 对标

| 对标 | runner | 差距 |
|------|--------|------|
| Claude Code MicroCompact | MicroCompactor | 基本对齐 |
| Claude Code AutoCompact (动态触发 ~92% fill, 生成 20K token 结构化摘要, 3 次失败熔断) | 无 | **缺失** |
| Claude Code Full Compact (全会话压缩 + 选择性文件重注入, 压缩后预算重置为 50K) | 无 | **缺失** |
| Claude Code context fill 监控 + 阈值触发 | CompactionChain 无感知 | **缺失** |
| Claude Code PreCompact hook (压缩前存档/自定义) | AgentObserver 无此 hook | **缺失** |

### TODO
- [ ] **T-CTX-01**: 实现 `AutoCompactor` — 在 context 接近上限 (~90%) 时触发，调用 LLM 生成结构化会话摘要 (≤20K tokens)，保留最近交互和关键决策
- [ ] **T-CTX-02**: 实现 `FullCompactor` — 全会话压缩 + 选择性文件重注入 (每文件 ≤5K tokens) + 活跃 plan/skill 保留
- [ ] **T-CTX-03**: `CompactionChain` 改为 context-budget-aware — 根据当前 fill 比例动态选择策略 (低: Snip+Micro, 高: Auto, 极高: Full)
- [ ] **T-CTX-04**: 添加压缩熔断器 — 连续 N 次压缩失败后停止重试，发 ERROR 事件
- [ ] **T-CTX-05**: 添加 `onPreCompact` hook 到 `AgentObserver` — 压缩前允许归档完整会话

## 二、Subagent 执行模型 — 从单一模式到 Fork/Teammate/Worktree [HIGH]

### 现状
runner 的 `SubagentRuntime` 仅支持一种 spawn 模式: 创建独立 AgentLoop，session key 隔离。

### 对标

| Claude Code 模型 | 说明 | runner |
|-----------------|------|--------|
| **Fork** | 继承父 context (byte-for-byte 副本, prompt caching 优化); spawn 5 个 agent 的 token 成本 ≈ 1 个顺序执行 | **缺失** |
| **Teammate** | 独立 worker, 父 messages 清零, 从零建立自己的 history | 当前模式近似 |
| **Worktree** | 隔离修饰器, 创建 git worktree 使文件操作不影响父 checkout | **缺失** |
| 嵌套 subagent (5 层深) | subagent 可以 spawn 自己的 subagent | 有 maxSpawnDepth，已支持 |
| Subagent 前台/后台执行 | 前台阻塞/后台并发，权限 prompt 透传 | 仅后台 + wait |

### TODO
- [ ] **T-SUB-01**: 实现 Fork 执行模式 — subagent 继承父 context prefix, 利用 LLM API prompt caching 降低 token 成本
- [ ] **T-SUB-02**: 实现 Worktree 隔离修饰器 — 创建临时 git worktree, agent 文件操作在独立 checkout 中, 完成后合并或清理
- [ ] **T-SUB-03**: Subagent 前台模式支持 — 允许 spawn 后阻塞等待完成 (当前仅 async spawn + wait)
- [ ] **T-SUB-04**: Subagent 恢复 (resume) — 通过 sessionKey 恢复已有 subagent 的对话上下文

## 六、Prompt Caching 优化 [HIGH]

### 现状
runner 的 `ClaudeProvider` 构建请求体时未显式优化 prompt caching。消息顺序和 cache_control 标记未针对 API prompt caching 机制优化。

### TODO

- [ ] **T-CACHE-02**: 消息排列优化 — 确保 system prompt → tool definitions → static context → dynamic history 的顺序以最大化 prefix match
- [ ] **T-CACHE-03**: Fork subagent 共享父 context prefix — 实现 T-SUB-01 时确保 byte-for-byte prefix 匹配
- [ ] **T-CACHE-04**: 添加 cache hit rate 监控指标到 CostTracker

## 二十、Error-as-Observation 自愈模式 [MEDIUM]

### 现状
runner 的 `ToolExecutor` 在工具失败时返回 `ToolResult.error(message)`，LLM 能看到错误消息。但缺少结构化错误分类和重试引导。

### 对标
- **Claude Code**: `is_error: true` + 清晰错误消息让 LLM 自主修正参数或换工具
- **LangGraph**: RetryPolicy (指数退避) + TimeoutPolicy + error_handler 三原语
- **SHIELDA (arXiv:2508.07935)**: 36 种异常类型 × 12 agent 制品的结构化分类, 支持跨阶段根因追溯
- **Graph-Based Self-Healing Router (arXiv:2603.01548)**: 工具故障时 Dijkstra 最短路径重路由, 亚毫秒恢复

### TODO
- [ ] **T-ERR-01**: 结构化错误分类 — ToolResult 错误附带 errorType (TRANSIENT / PERMANENT / AUTH / TIMEOUT)
- [ ] **T-ERR-02**: 错误消息引导 — 错误信息包含建议修正动作 ("参数 X 应为 Y 格式" 而非 "参数无效")
- [ ] **T-ERR-03**: 工具替代路由 — 当工具持续失败时, 自动建议 LLM 使用替代工具或路径
