# ADR-021：冻结源码的受控验收证据包

- 日期：2026-09-06
- 状态：Accepted（受控开发工作流已实现并验收）
- 前置：[ADR-017](017-versioned-harness-improvement-loop.md)、[ADR-020](020-foreground-subagent-cancellation.md)

## 问题

现有验证结果散落在临时日志与测试目录，Git HEAD 没有包含未提交代码，旧报告无法说明当前运行框架
是否仍是被测内容。直接扩展 Skill 的 TestRun 无法覆盖工具、取消、编排等系统级变更。

## 决策

1. 首批以仓库开发工具交付 `scripts/improvement_loop.py`，使用 Python 标准库，提供 capture、evaluate、
   verify、run 与 replay 命令。它执行受控 Maven/native 验收，不引入在线服务、模型优化依赖或新 kernel 公共 API。
2. capture 从 Git 工作区读取已跟踪及未被忽略的未跟踪文件，保留未提交内容和执行位；忽略生成的
   ci-results，不读取 .git、本地 `.worktrees/` 容器、构建输出和被忽略的运行数据。拒绝软链接及输出目录位于源仓库内部。
   在新目录保存源码副本、逐文件 SHA-256、候选摘要与来源 HEAD；摘要来自实际副本，不只来自 HEAD。
3. 验收定义使用版本化 JSON，声明 Maven 模块、必跑测试类、必需的运行证据、超时、反馈和预期行为。
   评测摘要绑定定义、测试源码/资源及执行脚本。验证器修改也使旧评测失效。
4. evaluate 校验副本后，在该副本执行 clean test，不在仍可编辑的源仓库中运行；命令采用参数数组。
   仅支持明确声明的 Maven 执行器。每个必跑测试类必须实际执行且无跳过；构建失败、超时、零用例、
   缺少必需证据或内容绑定不一致均不得形成通过报告。完成后再次校验输入。
5. 报告保存候选/评测摘要、实际命令、JUnit 用例与失败内容、运行证据、环境与实际 classpath 依赖摘要，
   并输出开发交接文档。每个输出文件也有摘要，verify 重新核对；可额外对比当前工作区，修改代码、
   未跟踪文件或验收定义后不能沿用旧结果。结果只表示该受控验收通过，不授权发布或宣称线上质量改善。
   replay 从原包复制已校验的源码与定义到新包，保留候选/评测摘要并重新执行；不复用旧构建结果，
   不要求当前工作区还保留原内容，也不覆盖原报告。
   Maven/JVM 版本从同一次验收进程的 `--show-version` 输出采集；不另起具有独立短超时的
   版本探针，让冷启动耗时仍受声明的整次执行期限管理。
6. 首个样本复用真实 Gateway→Orchestrator→子任务链，只有远端 LLM/设备受控。输出实际 Provider
   消息/工具定义、取消状态、执行器收到的参数和工具回包；把“取消后拒绝旧调用”和“正常完成仍允许
   独立子任务工作”一起验收。证据由用例显式导出，不把模型声明的成功当作设备执行证据。
7. CI 把工具自检、冻结候选和全仓构建视为三个独立阶段。前一阶段失败时，后续不依赖它的阶段仍执行；
   依赖不满足的阶段明确记为 `skipped`，不能让 shell 短路留下含混空值。最终门禁在结果与失败证据
   保存后统一判定。
8. 每次 CI 在任何测试前以本次触发提交、分支和 run ID 初始化结果目录并替换旧 `build.log`。
   `latest.json` 绑定触发 SHA，逐阶段记录 `passed`、`failed` 或 `skipped`、退出码以及冻结候选/评测摘要；
   JSON 由标准库序列化，不能把日志文本直接拼接成不可信 JSON。仓库回写和可下载 artifact 都只包含
   本次运行产物，前序失败不得重新发布旧日志。
9. 冻结候选包无论成功或失败都作为 CI artifact 保存，至少包含 `candidate.json`、`evaluation.json`、
   `report.json`、`build.log`、`handoff.md` 和已生成的 `evidence/`。artifact 名包含 run ID 与触发 SHA；
   外层 job 失败不能替代包内逐用例原因，缺失报告本身必须作为失败事实保留。

## 验收与边界

先由 CLI/文件系统跨边界测试证明未提交内容、测试内容与证据绑定，再验证完整 native 样本。
覆盖副本/报告篡改、缺失证据、测试失败/跳过、旧报告对新工作区失效及输出路径边界。
脚本测试加入现有 CI；Java 用例进入全量 clean test。

这是可信本地开发/CI 的完整性检查，不是签名或运行恶意候选的沙箱。数据源是受控测试，线上用户
轨迹仍依赖 A/D 身份与存储隔离。当前不负责动态生产装配、发布切换、自动诊断建议、云模型质量评分
或 Pi 实机验收；外部依赖记录实际解析结果，可复现性仍受其可用性约束。

CI 的 `ci-results/` 是最近一次触发提交的阶段摘要，不是历史归档；完整失败细节以该次运行的 artifact
为准。push 可回写摘要，pull request 不回写分支，但两者都必须上传本次运行产物。CI 不注入付费模型
凭据，冻结候选和常规构建均不得把网络模型调用当作自动化验收的一部分。

使用说明与最终验证见[操作文档](../guides/improvement-loop.md)和[实施进展](../design/runner-minion-system-evolution.md#124-2026-09-06-实施进展与续接点)。
