# ADR-016：Pi 本地交互运行时与状态归属

状态：Proposed（2026-09-06）。本文记录目标方案，实施按[系统演进路线](../system-architecture.md#7-演进路线按能力交付按依赖推进)推进。

## Context

[ADR-006](006-minion-embodiment-architecture.md)确立远端大脑、媒体绕开 JVM、设备侧 Realizer；
它对独立 Voice Gateway 服务与 Pi 瘦身体的描述，尚未反映当前本地组合入口。
`gateway_voice_duplex.py` 已直接组合 body 采音、云语音客户端和本地播放，MCP 入口与
Realizer 则尚未共享明确的设备所有者。[ADR-015](015-voice-turn-cancellation.md)解决轮次
关联和取消增量后，播放事实、表现仲裁和统一历史成为后续需要明确的责任边界。

## Proposed decision

1. 保留四仓，近期支持远端 runner、一个受监督的 Pi 应用入口和双眼固件实例。
   voice-gateway 是独立媒体/交互模块，优先与 body 同进程组合；按实际故障隔离需求
   拆进程时，使用本地 IPC 访问设备的唯一所有者。
2. voice-gateway 掌握输入完成、轮次、插话与跟进；body 掌握采集源、播放队列、
   播放游标、设备状态与执行仲裁。MCP 与 Realizer 调同一个设备实例。MCU 掌握渲染细节。
3. 保留输入、生成、播放三组并行状态，以 sessionId、turnId、语句及动作标识关联。
   本地取消先作废目标轮输出并保留新输入；远端确认、动作停止和副作用结果分别处理。
4. runner 的会话边界统一保存输入、生成计划与实际结果；Pi 提供播放和执行事实，
   JSONL 用于现场诊断。后续回执增量定义明确事件/协议，通过稳定 ID 幂等合并。
5. runner 保持通用模块依赖与公共 API 稳定。执行上下文贯穿身份、设备、授权、
   取消、预算及追踪；同一会话绑定一个 ChatHandler 与一套历史归属。

## Relationship to earlier decisions

- 延续 ADR-006 D1/D2 的远端语义、媒体隔离，D4 的本地 Realizer，以及 ADR-009 的 MCU 渲染。
- 提议细化 ADR-006 D3/D5 的部署和职责：Pi 本地运行交互与云语音客户端，独立模块不必是独立远端服务。
- 延续 ADR-007/008/011 的 MCP、风险信息与连接恢复；本地设备保护和动作反馈另有责任。
- 以 ADR-012/015 现行文本契约和兼容方式为起点；播放回执和能力语义需后续增量协议。
- ADR-014 的替换位置仍是 ChatHandler；切换前验证完整会话管理及真实协议。

## Alternatives and trade-offs

独立远端媒体服务适合共享媒体接入的规模，但当前单台桌面设备入口已本地组合，先拆服务
会增加取消、部署与调试边界。同进程组合减少边界，代价是需显式监督阻塞 SDK/驱动任务；
驱动故障隔离可后续局部拆进程。两个入口各自持有播放和串口会产生竞争，因此必须先确定
所有权，再决定部署形式。

LiveKit、Pipecat、ROS 2 和端到端语音模型可分别替换适当层，采用前应以相同场景证明收益；
保留轮次、实际结果、工具和设备控制契约，避免同时替换多个关键层。

## Acceptance

生产装配缺少相机、舵机或眼睛链路时，工具须返回可消费的不可用错误；模拟成功与日志告警
不能当作真实执行结果。串口写入只记录提交事实，固件执行确认与可见显示效果分别验收。

先验证唯一采集/播放/设备实例、旧轮取消不影响新输入、MCP 与 Realizer 仲裁，再验证
实际语句播放驱动表现、播放结果进入下一轮上下文。真实框架与受控对端的自动化和
Pi 实机声学/设备验收分别记录。实施不以“新增一个类”或“接口可调用”作为完成条件。
