# Runner 运行框架改进闭环：落地设计与系统样本

日期：2026-09-06。设计入口：[ADR-017](../decisions/017-versioned-harness-improvement-loop.md)。
实现状态：取消链缺陷已修复；ADR-021 已交付仓库级候选冻结、受控 native 执行、证据/报告绑定与重跑。
ADR-022 已实现执行级模型选择绑定；完整生产装配快照、在线证据采集和候选发布绑定尚未实现。命令入口见[操作文档](../guides/improvement-loop.md)。

## 1. 改进对象是整个运行框架

[OpenAI 原文](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop)
把 harness 定义为模型周围的完整运行约定，包括指令、工具、路由、输出要求和验证。
它将 trace、人工/模型反馈、评测结果交给分析器，产出开发交接文档，再由开发者或编码 Agent 修改系统。
示例的 Promptfoo 阶段评估已有 trace 输出；验证新候选需要实际执行候选 Agent。

Runner 的顶层候选也必须覆盖整套运行框架。Skill 属于配置的一部分，不能作为唯一版本或评测单位。

| 可改进对象 | 具体例子 | 生效证据 |
|---|---|---|
| Prompt / Profile / Skill | 提示结构、人格、任务说明、技能组合 | Provider 实际收到的 system 与工具定义 |
| 模型与推理配置 | Provider、模型标识、参数、上下文预算 | 请求参数、返回的模型/usage 信息 |
| Tool 与执行策略 | 工具实现、参数校验、设备分发、授权 | 执行端真实参数、回包与拒绝结果 |
| 路由、编排与生命周期 | 子任务树、取消、接续、资源释放 | 跨组件事件、任务终态、在途调用去向 |
| 上下文、记忆与检索 | 压缩、召回、作用域、写入策略 | 下一次实际模型输入与历史来源 |
| 输出及验证 | 可说块、结构化产物、断言、评分规则 | 最终产物内容与版本明确的检查结果 |
| 运行时及装配代码 | Factory、Loop、适配器、依赖版本 | 源码/构建摘要与实际装配快照 |

### 1.1 OpenAI 与 DSH 在整体架构中的位置

OpenAI 的改进循环提供“如何从证据找到问题、提出并验证改动”的参考。DSH 则提供“运行系统由哪些
可替换能力构成、由谁组合与释放”的参考：模型、工具、会话和循环通过配置组合，注册随其所有者卸载而释放。
这是两个可以配合的方向。[DSH 官方架构，固定提交 d347e703908d](https://github.com/deepseek-ai/deepseek-harness/blob/d347e703908d0406b7a7ef80e3a0e594d86b2215/docs/architecture.md)

Runner 据此形成以下目标分工；表中目标尚未全部实现，继续保持 kernel 为基础、web 为唯一 Spring 装配模块。

| 职责 | Runner 现有落点 | 演进目标与当前缺口 |
|---|---|---|
| 能力装配 | agent-web 配置、AgentFactory、Tool/Provider SPI | 将最终模型、提示、工具、策略和适配器组合导出为候选清单；已固定执行及同源子任务的 Provider 选择；尚无统一装配快照 |
| 在线执行 | Gateway→Orchestrator→AgentLoop→ToolCallingLoop | 消费固定候选，携带执行上下文；现有取消与局部工具已接通，身份和根预算待补 |
| 生命周期 | InterruptibleRun、SubagentRuntime、连接 dispatcher | 谁创建谁释放，旧运行清理不影响新运行；ADR-020 已闭合前台取消，通用资源作用域仍需逐项收敛 |
| 事实与证据 | MemoryProvider、trace/span、会话与设备适配 | 历史、诊断与实际执行事实关联到同一运行/候选；存储、证据索引及用户作用域待统一 |
| 离线改进 | 现有 Skill 评测/发布组件、批处理或 CI | 扩展为通用反馈、用例、候选执行和分析交接；Skill 组件作为一个接入场景 |
| 发布与消费确认 | 配置发布服务、代码构建与部署流程 | 各类变更沿自己的发布路径，共同核对候选摘要、评测与实际消费；通用绑定尚未实现 |

借鉴 DSH 的作用域机制时，需要同时明确可见范围与资源所有者；Runner 的取消注册只是本次实现的
一个具体边界，不等于已实现完整动态插件系统。[DSH scope](https://github.com/deepseek-ai/deepseek-harness/blob/d347e703908d0406b7a7ef80e3a0e594d86b2215/docs/subsystems/scope.md)
新扩展继续使用 Tool 和现有 SPI，DSH 的插件组合不映射到 runner 的 legacy Plugin 包。
完整产品架构、Pi/设备边界与分阶段路线见[主方案](runner-minion-system-evolution.md)。

## 2. 闭环产物及其职责

以下描述通用数据职责，不表示仓内存在同名 Java 类。ADR-021 先以开发证据包的 JSON/文件实现其中
候选、评测、证据、报告与交接职责；生产管理服务和存储仍待后续接入。

| 产物 | 必须包含什么 | 不能替代什么 |
|---|---|---|
| 运行框架候选清单 | 代码/构建、配置、工具、模型、装配和依赖的内容摘要 | 不能只用 Skill ID、版本标签或 Git HEAD |
| 运行证据包 | run/case 关联、真实请求、工具结果、输出、错误、usage、候选摘要 | 最终回答不能代替工具实际执行记录 |
| 反馈记录 | 来源、对应证据、期望与实际差异 | 模型评论不能直接成为已确认事实 |
| 评测定义 | 用例内容、断言/评分器、参数、阈值、数据分组及版本 | 通过率不能替代被测内容 |
| 候选报告 | 实际执行的候选摘要、评测摘要、结果与局限 | 旧 trace 评分不能批准新代码 |
| 改进交接包 | 排序后的问题、变更范围、证据引用、验收命令、回退条件 | 交接建议不能替代实现及重新验证 |

保持“采集→反馈→形成用例→执行基线/候选→分析建议→实施→验证→切换→继续采集”的顺序。
分析可以针对提示、工具、编排、记忆或验证器；实施路径随变更类型而变化。

## 3. 怎样锁定整套被测内容

这里的“锁定”是内容绑定和发布时校验，不是在运行时长期持有数据库锁。

1. **候选冻结。** 对候选清单采用确定性序列化并计算 SHA-256；清单引用的每份配置、源码补丁、
   工具定义和构建产物也保存摘要。未提交修改与未跟踪文件必须纳入，不能只记录当前 HEAD。
   验收环境和依赖记录实际解析结果；外部模型版本不能确定时明确记录该可复现性限制。
2. **评测冻结。** 用例、断言/评分器、评分提示、阈值和数据集分别确定内容版本；报告引用这些版本。
   调整候选或评测标准后需要重跑，旧报告保留为历史证据。
3. **执行绑定。** 候选执行器从冻结清单建立运行，导出实际 Provider 请求、工具定义和执行结果，
   报告记录“实际跑了什么”。仅给报告填一个候选 ID 不算完成接线。
4. **发布校验。** stage 核对候选、评测、结果与完整性；activate 使用同一个不可变候选，
   对预期的当前生效版本做条件更新。并发修改草稿或另一次发布不能悄悄替换被批准的内容。
5. **消费确认。** 下一次 native 运行采用该清单中的代码/配置组合，捕获到的请求与报告一致。
   装配失败时保持原生效版本，不能只把管理状态改成 active。

配置快照不冻结运行中权限撤销、设备失联或取消信号；这些动态条件仍须在执行前检查。
回退恢复代码/配置选择，不能撤销已经发生的外部操作。

## 4. 首个系统级改进样本：取消链

问题：前台已经被打断、取消订阅或失败，孙任务仍为 RUNNING，可以继续尝试设备调用。
该问题需要修改运行时和生命周期接线，完全不依赖 Skill 内容。

| 环节 | 本次样本 |
|---|---|
| 已观察失败 | 4 项跨组件断言复现：三种取消/失败路径留下后代运行；隐式接续也未停止旧子任务 |
| 原因 | 前台 CancellationToken 未进入子任务执行上下文；任务注册与取消无联动 |
| 候选变更 | 每次执行绑定独立取消信号；传入 ToolExecutionContext；子任务注册/终态管理可解除回调；失败触发取消 |
| 目标验收 | 旧后代进入 CANCELLED；迟到工具调用被拒绝；同会话新轮工具调用保留正确参数 |
| 独立回归 | 正常完成后独立子任务继续工作；现有权限、设备上下文、轮次、Python 接缝保持通过 |
| 传输证据 | 真实 Spring/Tomcat 驱动 chat→spawn→interrupt，以及断开连接 |
| 最终验证 | 2026-09-06 20:45:46，全量 clean test：2285 项，2265 通过、20 跳过，0 失败/错误，13 模块成功；Python 往返显式启用且通过 |
| 当前进展与局限 | ADR-021 已把受控场景纳入候选/评测摘要绑定，导出真实请求、工具参数及结果并生成交接包；通用在线采集和自动发布校验仍未实现 |

实现与验证入口：[ADR-020](../decisions/020-foreground-subagent-cancellation.md)、
[跨组件场景](../../agent-kernel/src/test/java/com/lightweightai/kernel/orchestrator/ForegroundSubagentCancellationAcceptanceTest.java)、
[真实 WS](../../agent-web/src/test/java/com/lightweightai/web/websocket/MinionVoiceTurnWebSocketTest.java)。
最终测试结果与配套边界统一记录到[实施文档](runner-minion-system-evolution.md#124-2026-09-06-实施进展与续接点)。

## 4.1 第二个系统样本：模型热切换的执行边界

管理端切换全局 DynamicLLMProvider 时，同一轮工具循环会重新读取 delegate。
同步及 HTTP/SSE 两个失败验收都观察到请求序列从预期的 `[v1, v1, v1]` 变成 `[v1, v2, v2]`。

[ADR-022](../decisions/022-execution-model-binding.md) 用可选 Provider 绑定 SPI 和执行作用域修复：
根执行开始时选择 Provider；同一个配置源的子任务继承选择；新的根执行和隐式接续重新绑定。
同步、异步及 reactive 的独立 ToolCallingLoop 入口也遵守这个边界，重试包装保持有效。

| 验收位置 | 实际证据 |
|---|---|
| 真实 Spring native 装配 + MVC 更新 + Provider HTTP/SSE | 旧轮三次出站 model 均为 v1；切换后创建的子任务仍用 v1；并发新轮用 v2 |
| 接续与订阅边界 | 同会话隐式接续用 v2；仅创建 Flux 不绑定；配置构造失败后原 Provider 可继续完成请求 |
| kernel 独立入口 | 同步、异步、reactive 各自跨工具迭代保持模型；下一次执行重新选择；同名/equals 相等但不同源仍独立 |
| 冻结候选执行器 | 独立验收定义引用上述用例，导出同步与流式的 HTTP 请求、工具实参和子任务结果，并绑定候选/评测摘要 |

入口：[验收定义](../../evals/execution-model-binding.json)、
[实际网络请求验收](../../agent-web/src/test/java/com/lightweightai/web/config/ModelBindingAssemblyAcceptanceTest.java)。
这一步把生产执行中的模型选择接上稳定作用域。Profile/Prompt/Skill、Tool 实现、LLMOptions、
发布摘要与观测清单尚未共同冻结；ModelConfigController 的配置还没有持久化或统一元数据原子更新。
不同配置源在首次使用时分别绑定，也不承诺它们属于同一个全局配置版本。

## 5. 后续最小交付顺序

1. **已完成受控开发版。** 仓库候选与评测清单、实际 native 验收、证据文件、内容绑定报告和开发交接包；
   旧源码或证据变化不能沿用结果，可在原工作区变化后 replay 原候选。对应 [ADR-021](../decisions/021-frozen-candidate-evidence-bundle.md)。
2. **继续生产装配与观察端口。** ADR-022 已固定 Provider 选择；把实际解析的 Profile/Prompt/工具/策略/模型参数纳入共同运行快照，
   将受控用例的显式证据导出扩展为可复用采集端口；线上用户轨迹依赖身份、存储作用域与保留规则。
3. **接发布与下一轮实际消费。** 配置和代码发布各走适合的流程，共用候选、评测和实际消费的证据要求；
   当前开发报告不直接批准生产发布。
4. **接分析器。** 自动生成/排序改进建议，再扩展质量评测、交接与调度。Promptfoo、HALO、Codex 可作为外部适配，
   不要求将其依赖加入 Java kernel，也不要求替换 native Agent Loop。

第一步已经使用受控数据独立交付；没有把改进范围限制为 Skill，也没有把受控验收通过当成线上质量提升。
